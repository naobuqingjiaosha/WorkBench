# 文档治理与AI读取规范

文档ID：PM-DOCUMENT-CONTROL。版本：1.1。更新：2026-10-24。状态：当前维护约定。

2026-10-26边界更新：仅共享源码、依赖/构建规则、通用工具、开发文档和配置样例；真实资料、本机配置、测试用例及历史验证产物均保留本机、不上传。旧文中要求随Git携带测试或运行快照的表述由本条替代，具体见[源码与资料边界](../guides/DATA_BOUNDARIES.md)。

## 1. 文档层级和唯一位置

| 信息 | 唯一维护位置 |
|---|---|
| 总入口/AI阅读路线 | README、GPT_CONTEXT、docs/README |
| 业务术语 | CONTEXT |
| 当前功能和业务约束 | PRODUCT_REQUIREMENTS |
| 当前技术结构 | SYSTEM_ARCHITECTURE |
| 当前发布与能力状态摘要 | DEVELOPMENT_PROGRESS |
| 每次任务实际变更、验证与交付状态 | management/CHANGELOG；只记已发生事项，不建立第二份待办队列 |
| 任务负责人、依赖、状态与下一步 | management/PROJECT_PLAN |
| 风险、业务未定项和关键决策 | management/RISKS_AND_DECISIONS |
| 验证方法与未验收项 | management/QUALITY_AND_ACCEPTANCE |
| 使用/开发/运维 | guides下对应手册 |
| 数据/API定位 | reference/DATA_AND_API与source-inventory |
| 原始报告、方案与阶段证据 | docs既有编号报告、collab及archive；不当作当前总状态 |

一条事实只维护一处主记录，其他文档用摘要加链接。当前文档保持短而明确，历史另存；不反复在开头追加整段旧进度。

## 2. 如何裁决冲突

不是简单“代码最高”或“最新文件最高”，要先判断问题类型：

1. **要实现什么**：用户当前明确要求及有效变更优先，当前需求归纳其约束。代码与需求不同是待解释差异，不自动以代码替代需求。
2. **代码现在做什么**：读取当前相关源码与测试，报告只是证据入口；同时标明工作区或发布包。
3. **日常实际上运行什么**：发布指针、RELEASE.json、进程loadedBuild和健康接口交叉核对。数据库查完整迁移集合，不能只看最大版本。
4. **验证过什么**：绑定具体版本/日期的原始日志、场景和产物；不能由“报告说通过”扩大到其他版本。
5. **业务真的发生过什么**：用户确认和适用真实材料；AI建议、生成文书、历史模型输出不构成发生证明。

发现不能裁决的矛盾，记录事实、影响与缺少依据，保留未知。只询问影响当前任务的关键问题。

## 3. 机器索引契约

[knowledge-index.json](../knowledge-index.json)采用UTF-8 JSON，schemaVersion=1。路径相对仓库根且使用正斜杠，不依赖本机盘符。

| 字段 | 含义 |
|---|---|
| baselineDate | 索引体系初始基线日期；当前生成器固定为2026-10-21，不表示本轮生成时间或运行验证日期 |
| readingOrder | AI建议阅读顺序，均为实际文档路径 |
| documents[].id/path/title | 稳定文档标识、路径、标题 |
| documents[].role | entry、current、reference、historical、prototype、collaboration等分类 |
| documents[].status | current-baseline、historical-evidence、reference-check-scope等；不表示功能发布状态 |
| documents[].purpose | 阅读用途与适用边界 |
| documents[].sha256 | 当前文件字节摘要，用于发现编辑后索引未刷新 |
| documents[].localLinks | 文件内本地链接及存在性；本机证据标为local-evidence，不保证可移交 |
| documents[].linksTo | 文档之间的路径关系；程序可按任务加载相关文档 |
| authority | 需求/实现/运行/验证的判定原则；不是指令优先级覆盖机制 |

[source-inventory.json](../reference/source-inventory.json)来自静态文件解析：模块文件、前端页面、API字面量声明与注册调用、SQL创建/变更片段、npm脚本及源码摘要。没有启动服务或导入业务模块；它不是OpenAPI、运行路由证明或实际数据库结构快照。

[current-baseline.json](../reference/current-baseline.json)是有日期的运行核查快照，时效以文件内baselineDate、observedAt及scope为准；当前保存的是2026-10-24发布及两项业务清理后的证据。它包含发布范围、摘要核对、实际迁移集合和验证边界。刷新文档索引不会刷新运行快照，后续要单独重新核查。

## 4. 状态与时间书写

- “需求已明确”“源码已实现”“隔离测试通过”“已发布”“业务已验收”各自写清范围。
- 历史文件标注历史/参考/原型，内含“当前”只代表原日期。
- 标题中的日期表示文件主题日期，不自动表示末次验证。
- 同一天的矛盾优先看事件顺序和证据；不能按报告编号盲目覆盖不相干范围。
- 暂存目录、PID、端口、包、模板数量都可能变化，使用前核实。

## 5. 任务收尾与变更记录规范

### 5.1 保存和Git责任

执行者每次任务结束前将修改写入实际文件并核对保存结果；用户手动进行Git推送。默认不执行 `git add`、`git commit`、`git push`，不代替用户合并或发布。用户单独明确要求本地提交时才在授权范围执行；推送仍由用户负责。仅“已保存”不能写成“已提交/已同步远端”。

### 5.2 五份根文档的维护责任

| 文档 | 每次核对内容 | 无内容变化时 |
|---|---|---|
| GPT_CONTEXT | 最新接续入口、约束、当前任务及下一步入口 | 更新复核信息，保留简明当前结论 |
| CONTEXT | 业务术语及对象边界 | 标注业务术语无变化，不塞入技术方案或聊天过程 |
| PRODUCT_REQUIREMENTS | 用户已确认要求、验收条件、建议与承诺的边界 | 标注业务需求无变化 |
| SYSTEM_ARCHITECTURE | 实际结构、运行依赖与候选边界 | 标注应用架构无变化；建议单独链接 |
| DEVELOPMENT_PROGRESS | 当前发布、实现/验证状态、本轮交付和未完成项 | 更新最新任务摘要及变更记录入口 |

各文档保留文档ID、版本、更新日期和性质；每次使用一条复核信息并链接变更记录，不连续追加对话式段落。日期用Asia/Shanghai。只复核而未改变内容口径时不虚增版本；规则、结构或状态正文变化时递增文档修订版本，应用版本不随之变化。

### 5.3 变更记录必填内容

在[变更记录](CHANGELOG.md)按任务记录，最新在前；标题使用“日期｜GOV编号｜具体变更主题”，不另造任务编号。正文至少包含：

1. **目标与依据**：用户要求、原问题、记录对应的工作区/发布包或原文档。
2. **修改清单**：逐文件或同目的文件组记录路径、操作（新增/修改）、修改前后和原因；自动生成文件单列，未跟踪新文件明确列出。
3. **验证**：实际命令、检查对象、通过/失败/未执行及原因；模拟模型、真实模型、人工检查分开。检查失败应修复并复验，或明确未闭环。
4. **五份文档复核**：每份说明修改或无变化，不把文档检查当成功能验收。
5. **交付状态**：本地保存、Git暂存/提交、远端推送、正式发布、业务验收分别填写；Git基点是任务开始前的已存在提交，不要求文档引用自身提交哈希。
6. **未完成项与接续**：具体限制、缺失证据和下一步；关联PROJECT_PLAN，不复制一套任务队列。

历史报告按原证据范围保留。对旧记录只能明确补录来源和核验范围，不补造当时未记录的测试或操作。一次任务的收尾修正合入该条记录，不为每次工具调用建立条目。

### 5.4 执行顺序与出口

1. 开始时检查Git状态、分支和相关文件；记录既有改动，保留他人工作。有条件时记录变更前摘要以区分本轮增量。
2. 实施、保存文件，运行与改动相称的验证；修复发现的问题。重大文档重整先保留可追溯原文快照。
3. 同步五份根文档，更新CHANGELOG和相关GOV状态；当前入口只保留最新摘要，历史用链接。
4. 执行 `node scripts/docs-maintenance.mjs generate`、`node scripts/docs-maintenance.mjs check`、`git diff --check`，核对新文件存在及索引覆盖。后续又修改文档时重新generate/check。
5. 交付本任务文件清单、实际验证、未完成项和六项状态，给出建议Git提交标题；不执行自动暂存/提交/推送。检查工作区仍有其他改动时明确提示不要整包当作本次变更。

建议提交标题格式为 `类型(范围): 具体变化`，例如 `docs(handoff): 规范本地保存与多设备接续记录`；常用类型feat、fix、docs、refactor、test、chore。标题必须能说明改了什么，避免“更新项目文件”等无法识别范围的描述。此为本仓库约定，不自动授权Git操作。

generate只写docs目录中的总览和两份索引，check不写文件。源码变化后也需generate，以免API/迁移索引漂移。生成器内部的文档分类规则如不覆盖新增现行管理文件，必须同步更新。

## 6. 移交与保密

最小AI移交包为根文档、docs、package.json、锁文件、相关源码与测试；不要只发一份GPT_CONTEXT就假定对方能访问链接。

data与outputs通常被Git忽略，包含本机数据、发布包、备份和验证证据，不自动包含在移交包。若需验证运行或原始结果，按授权另供对应脱敏证据和摘要；拿不到就标未核实。

不得将模型凭证、数据库业务行、真实原件正文或用户个人信息复制进通用知识文档。自动索引只读取允许的代码/文档目录，不扫描data/files、备份正文、node_modules或私人目录。
