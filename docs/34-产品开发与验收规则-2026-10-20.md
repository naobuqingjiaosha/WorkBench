# 工作台产品开发与验收规则

> 2026-10-21现行补充：任务书41取消报送管理，本文SC-01已同步；历史记录中的“报送”不再作为新材料门槛。现行执行摘要见[质量与验收计划](management/QUALITY_AND_ACCEPTANCE.md)，任务队列见[项目计划](management/PROJECT_PLAN.md)。

版本：1.0。制定日期：2026-10-20。

## 一 目的与适用方式

本规则用于工作台后续需求整理、流程与界面设计、开发、测试、发布和维护。目标是让每次改动有明确的用户价值、可验证的完成条件和可追溯的发布状态，减少由用户逐个发现基础问题后反复修补。

本规则作为后续任务的工作基线。存量能力按风险逐步补齐，不因缺少新格式记录而自动作废；历史测试、验收与事故记录保留。规则制定不等于功能已经实现，也不扩大生产修改、删除、资料外发、付费调用和发布授权。

调研依据与原差距见[同类产品调研与差距分析](33-同类产品调研与差距分析-2026-10-20.md)；当前任务只维护[项目计划](management/PROJECT_PLAN.md)。下文的执行细则为本项目制定，不是某一外部标准的认证要求。

## 二 产品目标与职责

### 2.1 产品目标

工作台服务单机使用者的行政周期工作、项目实施、模板文书和资料管理。每条核心链路必须支持“找到事项 → 办理内容 → 核对成果 → 明确完成状态 → 后续可查”。

下一阶段以提高完整任务的可用性为主。新增模块必须说明解决哪一类已确认问题，以及现有功能为什么不能满足。默认复用现有架构，不新增通用流程引擎或低代码平台。

### 2.2 职责

| 责任主体 | 必须承担的工作 | 交付或决策 |
|---|---|---|
| 用户 | 说明真实业务目标，裁决资料无法确定的业务口径，确认正式成果及有外部影响的操作 | 业务选择、关键验收及必要授权 |
| 开发代理 | 调研、整理需求、设计方案、实现、自测、失败复现、回归、文档及发布准备 | 可以直接检查的变更与证据 |
| 复核环节 | 对照验收条件检查实现和证据，记录反例与剩余问题 | 通过、未通过或受阻的明确结论 |

复核是工作环节，不要求增加人员或自动启动额外代理。同一执行者复核时明确标为自检，不称独立审查。用户不承担发现保存失败、重复提交、状态不同步等基础缺陷的主要责任。

## 三 需求进入与范围控制

### 3.1 每项需求的最小记录

一个任务块即可包含以下内容，无需每项都创建单独文档：

```text
编号与名称：
关联业务场景／已有需求：
用户现在要完成的任务：
当前问题与复现依据：
本次范围及明确不包含的内容：
预期结果：
成功条件／失败或缺资料时的处理：
涉及页面、状态、数据、模板和发布范围：
验证方法与所需资料：
优先级、依赖、执行人、当前状态：
证据链接、候选版本、实际发布版本：
```

只有“页面乱”“按钮改一下”“继续优化”时，代理先将其转成具体任务及检查条件。能够通过代码、既有资料和合理假设解决的问题由代理处理；只有改变业务含义、缺少关键事实或超出授权时才请求用户决定。

### 3.2 优先级

| 等级 | 判定 | 执行要求 |
|---|---|---|
| P0 | 数据丢失或损坏、敏感信息越界、错误覆盖正式成果等严重风险 | 优先复现和控制影响；未关闭或经有效方式隔离前，阻止受影响范围发布 |
| P1 | 核心任务不能完成、事实或结果错误、主要流程反复出错、关键状态不一致 | 纳入当前稳定化批次 |
| P2 | 有可行替代路径的体验问题、低频效率问题、非关键表现缺陷 | 主流程稳定后安排 |
| P3 | 尚无明确使用证据的扩展、探索性能力 | 进入候选池，不挤占当前批次 |

“疑似P0”先标为候选，不把静态推断写成已发生事故。普通视觉缺陷不一律升级P1；同一问题若使核心任务无法完成，按实际影响升级。

### 3.3 批次与变更

每批围绕一个主要业务结果组织，允许包含实现该结果必需的数据、页面和测试修改。新发现的问题记录后判断是否阻塞本批；不阻塞的排入后续队列。不得在交付前悄悄扩大需求或合入无关改动。

重复提出的问题关联原任务，保留关闭和重开证据。任务可以取消或延期，但必须留下原因及影响，不使用“已完成”代替取消。

## 四 业务逻辑设计规则

### 4.1 统一对象语义

| 对象 | 统一含义 | 必须区分的边界 |
|---|---|---|
| 导航分类 | 帮助选择工作的展示目录 | 不自动产生新的执行流程 |
| 工作类型 | 定义适用办理方式、规则和模板 | 配置修改不默认重写已有工作快照 |
| 工作 | 一项持续管理的业务对象 | 一项工作可以有多个期次或阶段，不等于某份文件 |
| 期次 | 某工作的一次月、季、年办理范围 | 不混用其他期次数据；完成本期不代表工作永久结束 |
| 阶段 | 项目流程中有业务意义的一段 | 单次简单工作可以没有阶段 |
| 业务记录 | 一次检查、会议等实际登记事实 | 同日同内容也不能仅凭相似度自动合并 |
| 成果与版本 | 文书或其他产物及其修订关系 | 文件存在不等于已定稿，定稿不等于已报送 |
| 外部证明 | 合同、签章、回执等外部发生事项的依据 | AI生成件不能冒充实际完成证明 |
| 归档 | 已明确口径的保管或收起行为 | 档案完整与从列表收起应有可区分的文案，不掩盖业务未完成 |

这些是业务语义，不要求立即增加数据库表。新增或修改字段前，要将语义映射到已有字段，明确兼容方式。

### 4.2 各类工作分别设计

至少维护六条代表性场景：

| 场景 | 办理主线 | 特别边界 |
|---|---|---|
| SC-01 月度检查 | 选期次 → 自动参考历史 → 编辑共享草稿 → 采用或下载待确认文件 | 多次检查独立；草稿不计实际次数，内容/来源改变后核对旧成果 |
| SC-02 工作记录（2026-10-21调整） | 告知一句 → 持久保存 → 查询／总结引用 | 不创建任务或办结流程；原话、发生时间、计划与已做分开，详见方案36第12节 |
| SC-03 在办项目 | 建立项目 → 按适用阶段办理 → 核对材料和成果 → 完成或归档 | 软件、集成和工程按各自适用流程 |
| SC-04 历史项目 | 登记已发生事实 → 补录资料 → 核对档案 → 归档 | 不补造日期，不强迫重演历史阶段 |
| SC-05 季度汇报 | 选择季度及资料范围 → 形成草稿 → 核对来源与内容 → 修改定稿 | 缺失、冲突、跨期、来源变更明确处理；模型不可用有可理解结果 |
| SC-06 部门工时 | 导入同月资料 → 人员项目匹配 → 计算及异常处理 → 对账 → 定稿导出 | 逐人逐日、项目合计与原Excel一致；不自动猜测缺失考勤 |

具体模板和真实外部证明以该类型已确认规则为准；材料准备不管理实际报送。共用入口、组件和证据规则；不强迫六条场景共享全部状态。

### 4.3 状态转换必须可解释

修改完成、定稿、报送、归档等逻辑前，列出：

```text
对象与当前状态 → 触发动作 → 前置条件 → 新状态
实际写入的记录／文件 → 被影响的成果与关联对象
失败后的状态与重试方式 → 撤销或纠正方式
```

工作、期次、文书分别维护自身状态；实际报送仅保留历史，不作为当前材料生成条件；“逾期”和“有缺项”可以是派生标记，不必全都成为新的持久状态。界面提示、待办统计和后端完成校验采用相同业务判断依据，优先复用现有readiness逻辑。

仅在真实业务需要前置关系时阻塞后续操作。可选模板、参考资料以及无关的旧手动步骤，不得形成额外完成障碍。

来源或规则改变时说明受影响范围，保留旧版本，区分“历史保留”和“当前仍有效”。重新核对后才能沿用或生成新的有效成果。

## 五 界面与交互规则

### 5.1 页面职责

首页优先展示当前需要处理的事项。事项至少包含名称、所属工作与期次或阶段、截止时间（如适用）、状态或阻塞原因，以及直达处理位置的动作。多处展示同一事项时复用同一身份和状态，统计必须说明统计的是工作、期次还是操作项，不能混加。

工作详情的主要内容围绕当前任务、输入、成果和缺项展开。配置入口只在需要调整规则时出现；维护操作与日常办理在视觉上区分。

每个任务区域有明确的主要操作，多个独立区域可以各有自己的主要操作。按钮使用具体动词，如“保存检查记录”“生成本期表册”，避免多个含义不同的“确认”。

### 5.2 表单与反馈

1. 已知基础信息自动带入，派生信息由程序计算；不能让用户重复维护文件已经存在这类客观事实。
2. 保留用户有效输入。切换工作、期次或类型时清理不再适用的依赖，旧异步结果不得覆盖新上下文。
3. 每个页面检查初始、加载、空数据、失败、有数据、保存中、成功和存在未保存内容的状态；不适用项说明原因。
4. 错误提示说明哪一步失败、输入是否保留、可以如何修正或重试。不能把读取失败显示成“没有数据”。
5. 有效保存成功后才提示成功；重复点击不能重复创建记录或成果。超时后先核对是否成功，再决定重试。
6. 必填项有清楚标签和校验定位；可用键盘完成关键操作，有可见焦点，状态不只靠颜色表达。
7. 删除、覆盖、批量修改等动作显示具体对象和影响范围；正常查看和可恢复编辑不增加无意义确认。

### 5.3 设计与复用

重要导航或办理流程调整先提供低成本原型或页面结构示例，使用匿名业务样例走查。涉及未确定业务取舍才让用户作选择；一般样式和组件选择由代理完成。

复用现有公共控件和样式变量，逐步统一间距、字号、按钮层级、提示、表格及弹窗。不为了统一外观同时重写所有页面。真正需要新增组件时说明与现有控件的差异。

## 六 开发生命周期与阶段出口

| 阶段 | 必要输入 | 应形成的结果 | 进入下一阶段的条件 |
|---|---|---|---|
| 1 问题登记 | 用户目标、反馈或复现证据 | 需求／缺陷任务块及优先级 | 问题、影响和范围可解释 |
| 2 场景定义 | 需求、现有业务资料 | 主线、关键异常、完成条件 | 不依赖未经确认的关键业务假设 |
| 3 方案设计 | 场景、现有代码及约束 | 页面结构、状态变化、数据和兼容方案 | 输入、输出、失败及历史数据影响明确 |
| 4 实现准备 | 已细化任务 | 开工条件检查、测试样例和隔离目标 | 满足下述开工条件 |
| 5 实现与自检 | 方案和验证计划 | 最小完整变更、相关测试及证据 | 关键成功与失败路径达到预期 |
| 6 任务与产物验收 | 可运行候选和样例 | 端到端办理、实际产物和业务结论 | 满足开发完成标准；待用户项明确 |
| 7 发布准备与发布 | 验收证据、范围及有效授权 | 配套候选包、备份恢复证据、版本和冒烟记录 | 满足发布检查；有权执行的操作才实施 |
| 8 运行观察与反馈 | 已发布版本和实际使用 | 新问题、恢复结果和下一批优先级 | 严重问题关闭；反馈回到统一队列 |
| 9 停用与迁移 | 明确的停用或替换需求 | 数据导出、保留和恢复安排 | 用户确认资料可取回；删除另按授权执行 |

这是按风险裁剪的工作流程，不是要求每个改动写九份报告。文案和样式微调可在一条记录内完成设计与检查；跨模块状态、文件写入和数据迁移须展开影响与失败方案。紧急修复可以缩短文档，但不能省略数据保护、关键验证和真实结果记录。

### 6.1 开工条件

开始实质开发前至少明确：用户任务、当前问题、本次范围、可检查的验收条件、所需资料、涉及的数据边界和验证方式。关键业务口径未知时，先完成不依赖它的调查、样例和方案，不凭空补值。

对现有故障，在可安全复现时先保留失败样例；无法复现的写明条件、静态依据和不确定性。

### 6.2 开发完成标准

同时满足以下适用条件，才标“开发完成”：

- 实现达到本次验收条件，正常路径和关键失败路径均有证据。
- 新旧记录、历史文件与版本关系符合方案；没有已知数据破坏问题。
- 相关自动检查通过；界面改动有浏览器检查，文件改动有实际产物检查。
- 核心任务从入口到结果走通，加载、错误、空态和未保存状态得到检查。
- 遗留问题、验证限制、未发布内容已明确记录。
- 需求、架构或进度中受影响的记录已同步。

“开发完成”不自动等于“业务验收完成”或“已经发布”。业务验收需要真实口径和对应使用者确认的，未获得时仍标待验收；纯内部技术修复可用充分的技术验证作为其任务验收，无需额外制造用户审批。

### 6.3 状态记录

任务采用“待分析 → 可实施 → 实施中 → 待验证 → 开发完成 → 待业务验收／可发布 → 已发布 → 已关闭”；不涉及业务验收或发布的任务跳过不适用步骤并说明。补充状态为受阻、延期、取消和重开。

每条验证记录另保存“通过／未通过／受阻／未执行”，避免一个任务状态掩盖某项检查失败。已发布后关闭的条件是目标范围验收完成、相关发布核对完成、遗留项已明确分流；不要求等待低频业务周期自然结束才能关闭无关修复。

## 七 验证与业务验收

### 7.1 验证按改动风险选择

| 变更类型 | 最少验证内容 |
|---|---|
| 文档、文案或低风险样式 | 内容、链接及必要页面检查；不为此创建镜像实现的测试 |
| 普通业务逻辑 | 相关单元／接口、关键边界、受影响场景回归 |
| 状态、关系或跨模块变更 | 正常及非法转换、历史数据、关联更新、保存后重开、重复提交 |
| 文件写入、删除、迁移、恢复 | 隔离样本下的文件与数据库一致性、失败补偿、重试、共享引用及恢复验证 |
| Word／Excel生成 | 结构解析、字段与数字、实际打开、代表性分页或打印、公式重算及业务对账 |
| AI问答或写作 | 固定样例、来源支持、数字与状态、缺失与冲突、跨期边界、来源变更、失败展示 |
| 发布包 | 影响范围测试、类型检查和构建、候选包启动、对应版本关键场景；基础共用代码广泛变更时运行完整回归 |

使用`package.json`提供的隔离命令。不能因准备测试而先导入会初始化日常数据库的模块，不能覆盖日常前端产物。既有历史通过结果可以用于定位，不可记成新版本通过。

### 7.2 六类场景的验收重点

| 场景 | 成功检查 | 必测反例或边界 | 产物和证据 |
|---|---|---|---|
| SC-01 | 同期两次实际检查独立保存；同一记录用于适用表册；允许不完整草稿生成下载，不要求报送或办结 | 修改检查后旧成果失效提示；缺必备外部证明不能伪装完成；跨期数据不混入 | 操作记录、两次检查及成果归属、实际Word版式 |
| SC-02 | 一句话可记下，重启后仍可按时间和主题找回 | 不新增待办；保存失败保留输入；更正撤回影响后续引用；计划不当已做 | 页面、持久化、检索与引用证据 |
| SC-03 | 正确类型生成适用阶段，资料与成果归属一致 | 缺必备材料有定位提示；可选材料不阻断；不适用有规则依据 | 阶段状态、材料与文件核对 |
| SC-04 | 已结束业务可以直接补录并核对档案 | 未知日期留空；档案未齐不能误显示完整；历史原件保持 | 业务状态与档案状态分别核验 |
| SC-05 | 范围明确，草稿每项重要事实能追溯，修改后可保存正确版本 | 无来源、冲突、计划冒充完成、跨期、来源v1到v2及模型失败 | 原始模型稿、来源、核验结果和人工修订分别保留 |
| SC-06 | 同月全部应填人员逐日及项目合计对账，文件可重算打印 | 姓名或项目不匹配、请假与研发冲突、半天、跨月和缺资料明确处置 | 原始输入副本、计算结果、重算及差异表 |

选样覆盖结构和风险。共用同一模板结构的变体可以按代表样本验收并列明覆盖范围；新增结构、公式、图片、长表或特殊月份另验。不能用少量Word样本宣称全部模板已验收。

AI修改后固定保留独立验收样例。为修复而使用过的失败样例转为回归样例，不再冒充新独立验证。规则整理稿、模型原稿、代理修订稿和用户最终稿分别标记。有限样本不证明任意输入下没有幻觉。

### 7.3 需求与证据对应表

在任务记录或进度中使用下表，不另建重复台账：

| 需求／任务 | 场景 | 验收条件 | 用例或操作 | 实际结果与证据 | 候选版本 | 发布版本 |

| 填实际编号 | SC编号 | 可核对结果 | 命令或步骤 | 通过／未通过／受阻／未执行及链接 | 提交或包标识 | 未发布或实际版本 |

命令日志注明运行日期、环境和代码版本。业务样例匿名化；原始敏感资料不复制到公共文档。截图不替代数据核对，接口成功不替代成果可用，代理走查不替代需要用户判断的业务验收。

### 7.4 易用性与效果

首次代表性任务先建立基线，不编造当前完成率和性能。每次记录任务名称、输入条件、尝试次数、独立完成次数、求助次数、重复填写项、错误路径和处理耗时；AI等待及文件处理耗时单列。

本项目首轮验收目标：

- 六类场景分别给出结论，不用总体平均值掩盖某条关键链路失败。
- 代表性用户任务可在不依赖开发者口头提示的情况下完成；一人一次通过只作为该样例证据。
- 无数据丢失、错误跨期、错误覆盖定稿或把未完成显示成完成。
- 已有且无需重新确认的信息不重复填写；每个阻塞能定位到解决位置。
- 页面、生成和检索性能先实测，再为下一批设明确数据量及机器条件下的阈值。当前不宣称达到任何未测量指标。

用户只参与已通过代理自检的任务体验和业务核对。发现基础故障后回到开发环节修复，不继续要求用户承担全部回归。

## 八 数据 文书与AI保护规则

1. 读写、删除和恢复都明确数据库、文件根和环境身份。开发、演练和日常数据分开。
2. 文件与数据库跨边界操作必须设计失败恢复，不能假设数据库事务会恢复已经删除的磁盘文件。方案可使用受控暂存、补偿或可重试清理，但必须验证断点及结果，不仅调整语句顺序。
3. 删除覆盖全部适用关联，同时保护仍被其他记录引用的文件和只读外部原件；无法清理的对象保留可追踪结果，不能报告全部成功。
4. 完整恢复须包含数据库及相关模板、文件、映射等必要内容。只含数据库的备份明确标注范围。
5. 定稿、实际报送和业务完成由相应证据与明确动作支持。AI不能自动替用户完成正式签发或伪造外部证明。
6. 本地、云端模型及规则回退标识清楚。外发和费用遵循已有授权边界；本地失败不擅自转云端。
7. 关键日志记录对象、动作、结果、版本和错误定位，敏感正文与密钥不写入通用日志。

## 九 发布与维护

### 9.1 发布前检查

每次发布明确：任务范围、候选代码及依赖锁、前端产物、数据迁移、配置变化、验收证据、已知问题、备份、恢复方法及授权依据。

开发工作区、待发布包和正在运行版本分别确认。`git status`干净不代表已发布，数据库迁移号也不代表前后端配套完成。

发布保护沿用现有启动和构建机制。默认日常入口是`启动工作台.cmd`或`npm start`读取发布指针；不得通过绕过该入口来混入开发代码。

### 9.2 恢复与异常

恢复演练使用新隔离目录，核对数据库关系、文件摘要及关键业务场景。数据库迁移不可逆时，说明可恢复的配套版本和恢复后新数据如何处理，不承诺仅退代码就能无损回退。

发布后核对运行版本、健康状态、首页读取、关键工作和文件访问。需要写入的发布验证使用事先批准的办法，不在日常库随意创建测试工作。

发生严重异常时保留证据，先确定影响范围和恢复点，提出最小处置方案；需要生产操作时使用已有授权或请求针对具体方案的授权。修复后将触发场景加入回归，关联原缺陷，不以重新发布代替事故关闭。
