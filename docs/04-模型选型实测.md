# 工作台 · 模型选型实测

> 用途：回答"这五个功能各用哪个模型"。判据按重要性排序：**① 稳定不出错 ② 成本 ③ 速度**。
> 所有数字都是在本机、用你自己的两个 API Key、跑你工作场景里的真任务测出来的，不是看榜单选的。
> 复现方式见文末。

---

## 1. 结论

| 用途 | 选谁 | 一句话理由 |
|---|---|---|
| 文书写作 | DeepSeek `deepseek-flash` | 唯一"该写待补就写待补、绝不编数字"的；5s 一次 |
| 信息抽取 | DeepSeek `deepseek-flash` | 干净文档两轮全对；别的模型会把明摆着的单位名写成"待补" |
| 复杂推理 | DeepSeek `deepseek-flash` | 三家内容质量相当，它最快（17s vs 25s vs 50s） |
| 图像识别 | 阿里 `qwen3-vl-flash` | 真多模态模型（这条流程还没接上代码，先配对） |
| 向量化 | 阿里 `qwen3.7-text-embedding-flash` | 召回与另两个并列满分，批量上限最宽、最快 |

写作用 8192 token 上限（推理模型的"思考"也占额度）。所有用途的试调用都通过。

## 2. 六条候选怎么被淘汰的

任务 A：按「监督检查工作记录表」写检查内容/结果，要求事实原样用、缺的写【待补】、不许编。
3 轮/模型。

| 模型 | JSON 合法 | 字段填全 | 事实用对 | **编造** | 用了【待补】 | 平均耗时 |
|---|---|---|---|---|---|---|
| **deepseek-flash** | 3/3 | 3/3 | 3/3 | **0** | 3/3 | 5.2s |
| deepseek-v4-pro | 3/3 | 3/3 | 3/3 | 0 | 0/3 | 18.5s |
| qwen3.8-max | 3/3 | 3/3 | 3/3 | 0¹ | 0/3 | 29.5s |
| qwen3.8-flash | 3/3 | 3/3 | 3/3 | 0¹ | 0/3 | 31.3s |
| qwen-flash | 3/3 | 2/3 | 3/3 | **2/3** | 0/3 | 2.7s |
| glm-5.3 | 3/3 | 3/3 | 3/3 | 0 | 3/3 | **62.4s** |

¹ 自动检测没报，但**人工读原文发现它在编**：qwen3.8-max 写"已要求相关责任单位及时整改"、qwen3.8-flash 写"经现场核查…已要求立即整改"——资料里只有"发现两处问题"，没有任何"已整改"的事实。qwen-flash 更直接，编出了"**3 个工作日内**提交""**5 个工作日内**补全签收手续"这种期限。

**这一列才是关键**：公文里凭空多出一句"要求 3 个工作日内整改"，是会被追着问的依据。deepseek-flash 和 glm-5.3 会老老实实写 `【待补：整改责任部门、整改期限及复查销号情况】`；glm-5.3 内容同样合格，但一次 62 秒，交互上没法用。

任务 B：从资料抽字段（有标准答案）。2 种文档 × 2 轮。

| 模型 | 短合同（干净） | 会议纪要（含干扰） | 编造 |
|---|---|---|---|
| **deepseek-flash** | **100%（2/2 满分）** | JSON 坏 1/2（见下） | 0 |
| deepseek-v4-pro | 80% | 50% | 0 |
| qwen3.8-max | **100%（2/2）** | 38% | 1 |
| qwen3.8-flash | 80% | 25% | 0 |
| qwen-flash | 80% | 75% | 2 |
| glm-5.3 | **100%（2/2）** | — | 2 |

- 短合同上 **v4-pro / qwen3.8-flash / qwen-flash 都把开头的"山西黄河水利工程咨询有限公司"写成【待补】** —— 明摆着的甲方名称漏了，这种错比慢可怕。
- 会议纪要那一列**不能当准确率看**：文档里有两个日期（会议 9月18日、上月检查 8月20日），"检查时间"到底填哪个本身有歧义，各模型取值不同不算错。它暴露的真问题是**结构化输出的稳定性**：deepseek-flash 两轮里有一轮返回了空对象（`{}`）。

针对这个稳定性疑点又单独压测了一轮（同一份会议纪要 × 5 次）：

| 模型 | JSON 可用 | 字段填全 | 空/坏 |
|---|---|---|---|
| deepseek-flash | **5/5** | 5/5 | 0 |
| qwen3.8-max | 5/5 | 5/5 | 0 |
| glm-5.3 | **0/3** | 0/3 | **3/3** |

glm-5.3 三次全部没给出能用的 JSON（和它 62 秒的响应一起，直接出局）。deepseek-flash 那次空对象是低频抖动，5 次复测没再出现——但不是零，所以**代码里加了自动重试**（见第 4 节）。

任务 C：AI 梳理式批量映射（25 个变量 → 26 个字段，2 轮）。
**六个模型全部 50/50 全对、0 个编造字段名、0 个漏项。** 这个任务对谁都不难，所以它不参与选型，选型看别的任务。

任务 D：缺项分析（长文输出，看会不会编具体数字/人名）。

| 模型 | 完成 | 编造 | 平均字数 | 平均耗时 |
|---|---|---|---|---|
| deepseek-flash | 2/2 | 0 | 605 | 22.6s |
| qwen3.8-flash | — | 0 | 512 | 25.4s |
| qwen3.8-max | 2/2 | 0 | 547 | 32.4s |
| qwen-flash | 2/2 | 0 | 216 | 1.4s |
| glm-5.3 | 2/2 | 0 | 614 | 48.8s |
| deepseek-v4-pro | 2/2 | 0 | 448 | 69.3s |

内容质量三家相当（都能排出"缺检查依据/缺过程佐证/缺整改闭环/缺结论汇总"这类真缺项），差别在耗时和篇幅。qwen-flash 快但只有 216 字，深度不够。

任务 E：向量化召回（16 段语料、四组同主题干扰项、16 个换说法的查询）。

| 模型 | 第一命中 | 前三命中 | MRR | 单次批量上限 | 延迟 |
|---|---|---|---|---|---|
| text-embedding-v3 | 16/16 | 16/16 | 1.000 | **10** | 604ms |
| qwen3.7-text-embedding | 16/16 | 16/16 | 1.000 | 16 | 1035ms |
| **qwen3.7-text-embedding-flash** | 16/16 | 16/16 | 1.000 | **≥24** | **387ms** |

召回质量三家并列满分（语料不够难，分不出高下）→ 那就按**批量上限和速度**选：`text-embedding-v3` 单次只收 10 条，而知识库是按 16 条一批提交的，**每篇文档都会先撞一次 400**。选 flash。

## 3. 实测挖出来的两个真问题

### 3.1 向量化：批量超限会让整篇文档作废

真接口探测结果：

```
text-embedding-v3              10:OK  11:拒  16:拒  24:拒
qwen3.7-text-embedding         10:OK  11:OK  16:OK  24:拒
qwen3.7-text-embedding-flash   10:OK  11:OK  16:OK  24:OK
```

而 `embedDocument()` 是按 16 条一批提交的，原来的失败分支是"记失败 + `break`"——**一篇文档只要超过 10 块，第一批就被拒，然后整篇剩下的全部放弃**，而报出来的错是"Value error, batch size is invalid"，看起来像参数写错，很难联想到"批量太大"。

修复：批量被拒时**自适应劈半重试**（16→8→4→1），成功过的尺寸记住，后续批次直接用，不再逐批撞墙；单条连续失败 3 次才认为是接口整体不可用并停止。用真接口复测 23 块的文档：

| 模型 | 结果 | 耗时 |
|---|---|---|
| text-embedding-v3（上限 10） | 23/23 全部向量化 ✅ | 1.3s |
| qwen3.7-text-embedding-flash（上限 ≥24） | 23/23 ✅ | 0.6s |

自检里加了回归用例：假接口故意只收 10 条，喂一篇 20+ 块的长文档，断言"接口确实拒收过 ≥1 次"且"最终全部向量化成功"——保证这个坑不会再掉进去。

### 3.2 写文书：模型偶尔不按 JSON 返回

实测约十次里有一次会把 JSON 包在解释文字里或干脆回一段话。原来直接把原文丢给用户手工整理；现在**自动重问一次**（把上次输出回给模型并明确"只要 JSON 对象本身"），成功则照常填充并在警告里说明"本次用量含两次调用"。重试的 token 也如实计入用量，不藏。

### 3.3 「配了」不等于「能干」：向量化的绿灯曾经骗人

`aiReadiness()` 最初只检查"档案填没填、服务商启没启用、有没有 Key"，
查不出**这个服务商压根没有 `/embeddings` 接口**。实测把「向量化」指向 DeepSeek 之后：

```
/api/kb/status  →  configured=true，提示"向量化已就绪"
点「试调用」    →  404：服务商「DeepSeek」没有向量化接口
```

一边亮绿灯、一边一篇文档也向量化不了。修复：`embed()` 把每次真实调用的结果按
「服务商:模型」记下来，`aiReadiness('embedding')` 遇到**能力型错误**（404 / 认证失败 / 停用 / 没 Key / 没模型）
就据实报告不可用；临时性错误（限流、超时）不算，避免一次抖动就长期挂红灯。
换个模型或服务商就是新的键，自动重新判断。

现在同样的操作会得到：

```
configured=false
原因：服务商「DeepSeek」没有向量化接口（/embeddings 返回 404）。对话模型不能拿来做向量化……
```

**DeepSeek 无论填哪个模型名都不能做向量化**（`deepseek-flash`、`deepseek-v4-pro`、
连编造的 `deepseek-embedding` 都是 404），它只有对话模型。
同样地，阿里这边的对话模型（`qwen3.8-flash` 等）填进「向量化」也是 404 ——
向量化必须用 `*-text-embedding*` 这类专用模型。

## 3.4 温度 / 最长输出 / 超时 怎么设

### 温度（temperature）

控制发挥程度：0 ≈ 每次尽量一样，1 以上开始跑偏。**这几家的推理模型对温度并不敏感**
（思考过程占输出的大头，实测思考占 89%~96%），所以不必纠结小数位，关键是**别调高**。

| 用途 | 值 | 理由 |
|---|---|---|
| 信息抽取 | 0.1 | 抽取是搬运事实，越死板越好 |
| 图像识别 | 0.1 | 同一张照片的判断要能复现 |
| 文书写作 / 复杂推理 | 0.2 | 留一点行文变化，但不给它发挥成"编造"的空间 |
| 向量化 | 无所谓 | `/embeddings` 不生成文本，这个值不会被用到 |

### 最长输出（max_tokens）

**这是最需要注意的一项**：推理模型的"思考"也从这个额度里扣（见 7.2.1），
一次只回答两个字的请求，思考就能花掉 100~700 token。所以对话用途给的额度要按
"思考 + 正文"算，不能按正文长度算。

| 用途 | 值 | 说明 |
|---|---|---|
| 文书写作 | 8192 | 长模板几十个字段的 JSON + 思考，4096 会半路截断 |
| 信息抽取 | 8192 | 同上；「AI 梳理」那条路径自己还会指定更大的值分批跑 |
| 复杂推理 | 8192 | 缺项分析输出最长 |
| 图像识别 | 4096 | 判断结论很短，够用 |
| 向量化 | 用不到 | 接口不生成文本 |

额度只是**上限**，用不到不花钱 —— 设小了会截断，设大了没有代价。

### 超时（timeout_ms）

单位毫秒，指**单次调用最多等多久**，不是"要等多久"。留 5~10 倍余量即可；
设得过大，真卡住时你会干等而不是早点看到报错。

| 用途 | 值 | 实测耗时 | 余量 |
|---|---|---|---|
| 文书写作 | 120000 | 出一次文书 2.2~7.6s | 16~55× |
| 信息抽取 | 180000 | 单篇 2~13s；批量梳理最慢见过 30s | 6~90× |
| 复杂推理 | 180000 | 缺项分析 21~25s（换慢模型见过 69s） | 7× |
| 图像识别 | 60000 | 判一张照片 0.3~3.7s | 16× |
| 向量化 | 60000 | 每批 ≤16 条，0.5~1.3s | 45× |

注意：向量化的超时管的是**单批**。一篇大文档的总时长 = 批次数 × 单批耗时，
由自适应批量控制，不受这一项影响。

## 4. 想自己复核/改选

- **界面自查**：`系统配置 → 模型接入`，每个用途一行，点「试调用」会报出真实耗时与思考 token 占用。
- **看历史表现**：同页「模型调用记录」有每一次调用的用途、模型、耗时、token、成功与否、错误摘要。
- **换模型**：改完点「保存」即刻生效；换向量化模型后，**已有文档的向量不能混用**，需要重新向量化（知识库页面有提示）。
- **成本怎么看**：报告里记的是 token 数。写作任务单次约 1000–1300 token（含思考），抽取约 500–2400，缺项分析 1500–4600。乘上各家的单价即可。

## 5. 复现方式

评测脚本是一次性的（跑完即删），任务定义和打分口径记录在此以便重建：

- 任务 A：模板「监督检查工作记录表」+ 两条已知事实 + 两处问题，检查 4 个键是否填全、事实是否原样、是否出现凭空期限/日期/金额/人名（去掉 `【待补：…】` 片段后再扫描）。
- 任务 B：一段短合同（5 个可抽字段 + 1 个不存在的字段）与一份会议纪要（含上月数据干扰），比对标准答案，并检查"不存在的字段是否被编内容"。
- 任务 C：25 个模板变量 → 26 个项目信息字段，与人工答案表逐项比对。
- 任务 D：缺项分析长文，检查是否编造具体数字/人名。
- 任务 E：16 段语料 + 16 个改述查询，算 hit@1 / hit@3 / MRR。
