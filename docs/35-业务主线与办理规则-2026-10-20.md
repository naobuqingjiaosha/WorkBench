## 一 业务全景

工作台按实际目标整理为五条业务线：**安全工作、清廉监督、项目实施、部门工时、综合与临时事务**。这是理解业务的视图，不是新增五个数据库分类，也不改变已经确定的“信息化项目、工程项目、行政管理”三个导航目录。

| 业务线 | 要完成的实际工作 | 主要办理方式 | 最终结果 |
|---|---|---|---|
| 安全工作 | 按月整理安全活动、检查与落实情况，形成适用材料 | 月度期次 | 可核对的当月成果及适用证明 |
| 清廉监督 | 谈话、年度计划、月检、自查、三项季度活动及季度汇报 | 按事项、按年、按月或按季 | 各项独立成果；月检含实际报送确认 |
| 项目实施 | 信息化、工程及现有服务项目从准备到交付验收 | 项目阶段；历史项目走补录 | 阶段成果、验收依据及完整档案 |
| 部门工时 | 依据研发、考勤和参与项目情况核算当月工时 | 月度期次内专用计算 | 经对账的部门工时Excel |
| 综合与临时事务 | 年度总结、通用行政文书和临时交办 | 年度期次或单次 | 与事项相符的成果或办结记录 |

“文件库、模板、制度检索、AI助手、回收站、备份”是支持这些业务的共用能力。生成文件是办理中的动作，不能单凭生成成功认定业务完成。

### 如何理解业务层次

```text
业务线：为什么开展这项工作
  └─ 工作类型：这一类工作采用哪些规则
       └─ 具体工作：实际管理的那件事
            ├─ 单次办理：内容与成果
            ├─ 周期办理：年度／季度／月度期次 → 内容或检查记录 → 成果
            └─ 项目办理：适用阶段 → 材料、事项与成果
```

部门工时属于周期办理中的专用计算；月检属于周期办理中的多次记录；历史补录是项目的办理情形。三者不必分别建立一套基础工作系统。

完整术语见[业务术语](../CONTEXT.md)。本文件将已有要求、当前实现和整理建议分开，当前代码存在的限制不能自动成为业务应遵循的规则。

## 三 每条业务线的办理主线

### 3.1 安全工作

**开始条件**：建立安全月度工作，确认首个办理月份、适用模板和真实截止要求。

**办理过程**：选择月份 → 登记本月事实和适用材料 → 生成或导入成果 → 核对内容和文件 → 满足本期要求后完成本期。下个月形成独立期次，不继承上月数字和完成状态。

**输入与输出**：输入为本月安全活动、检查或其他适用事实及附件；输出由已选模板和业务要求确定，不能仅凭“安全月度工作”名称断言每月必须举办某种会议或提交某份报告。

**完成条件**：本期规定的必备成果有效定稿、必备外部材料真实且核对通过。若实际业务要求报送，应核对报送事实；当前通用周期入口没有月检式独立报送确认，不能把“本期完成”直接解释为已经报送。

**反例**：上月已定稿的安全材料不能满足本月要求；附件已上传但内容未经核对，不能自动认定活动完成。

当前专门的逐次检查记录只接入清廉月检。安全检查是否也需要“一月多次记录并分别出表”，属于后续业务扩展判断，本轮不直接共用或复制检查模块。

### 3.2 清廉监督

清廉业务先按固定8项分别办理，再由季度汇报引用适用资料。它们不能因为同一季度或同一天办理，就合并成一个完成状态。

| 固定事项 | 起点及周期 | 办理动作 | 完成应有的结果 |
|---|---|---|---|
| 谈心谈话及台账 | 项目或具体事项触发 | 登记谈话事实 → 核对独立记录 → 更新适用台账 | 记录及台账能对应实际谈话；空白表不作已开展证明 |
| 年度监督检查工作计划 | 选择年度 | 编制计划 → 核对内容 → 定稿并保留版本 | 有效计划成果；编制完成不等于计划获批或全年监督完成 |
| 月度监督检查与报送 | 选择月份 | 逐次检查 → 出表册 → 核对定稿 → 确认实际报送 → 完成本期 | 记录、单次及必备汇总成果、报送事实相符 |
| 季度八大体系自查 | 选择季度 | 填报 → 逐项核对 → 保存成果及适用依据 | 当季有效自查成果；不能由其他季度文件代替 |
| 季度廉政风险研判 | 选择季度及实际活动 | 整理研判事实、纪要及材料 → 核对定稿 | 本项独立纪要和适用材料 |
| 季度廉洁学习 | 选择季度及实际活动 | 整理学习内容、记录及材料 → 核对定稿 | 本项独立学习记录和适用材料 |
| 季度项目研判考评 | 选择季度及实际会议 | 整理会议和考评事实 → 核对定稿 | 本项独立纪要和考评材料 |
| 季度监督工作推进汇报 | 选择季度和参考范围 | 汇集适用来源 → 起草 → 核对事实与缺口 → 修改定稿 | 有来源支持的季度汇报；按实际要求处理报送 |

三项季度活动即使安排在同一天，记录、成果、期次和完成状态也分别保留。

**月检的最小办理单位是一条检查记录。** 同月检查两个项目，或对同一项目检查两次，均各有记录；一条记录可以生成多份适用表册。月度汇总和年度累计按对应范围从记录重建，不把单次检查文书反复手工累加。

```text
本月期次
  ├─ 检查记录甲 → 对应当前修订的单次成果
  ├─ 检查记录乙 → 对应当前修订的单次成果
  ├─ 本期必备汇总成果
  └─ 核对当前记录及成果 → 确认实际报送 → 完成本期
```

修改记录后保留旧稿，但旧修订的定稿不能继续满足新记录；原报送确认与当前成果不一致时必须重新核实。重新打开本期不等于现实中撤销已经发生的报送，后续补报或更正仍须据实记录。

**季度汇报引用其他工作，不代替其他工作的完成。** 其他事项尚未完成，可以在有据情况下写成“已登记的局部进展、尚缺资料”，不能为了起草汇报自动将其办结。没有读取到来源不得解释为现实中没有发生。

当前普通季度模板入口的来源选择限于同领域、同分类、同季度的月度或季度期次；年度计划和无期次谈话不在这个选择器中。业务助手另有证据收集逻辑，两个入口不能视为范围完全一致。后续需要明确年度计划、谈话等如何进入汇报，保留来源时间与身份，不放开为无边界读取所有目录。

补充事项的处理：

- 廉政合同与承诺书按项目或事项收集真实签订材料，空白模板或AI生成稿不能替代已签署文件。
- 清廉临时事项按实际任务建立，成果及是否报送依事项确定。
- “清廉季度工作”与具体季度汇报暂时均保留；不因名称相似删除、合并或迁移历史工作。

### 3.3 项目实施

**开始条件**：明确实际项目、所属类型、适用合同或实施依据、资料目录和已知基本信息。类型由业务特点决定，不能为了覆盖测试场景改变真实项目类型。

| 项目类型 | 当前办理主线 | 核对重点 |
|---|---|---|
| 软件研发 | 需求与计划 → 设计与研发 → 测试与交付 → 验收与归档 | 需求、设计、软件交付和验收相互对应 |
| 系统集成 | 方案与计划 → 采购与供应商交付 → 部署与联调 → 验收与归档 | 到货、供应商交付、部署测试及移交证据 |
| 通用信息化 | 当前12节点，包含开工、设备验收、安装调试、运行、培训、移交等 | 按实际合同判断适用节点，不与软件4阶段重复建立同一项目 |
| 通用工程 | 当前19节点，包含开工申报、方案、报验、日志、分部及竣工验收等 | 承包人、监理、发包人的真实材料及适用性 |
| 现有服务类 | 项目部通知 → 保密协议 → 验收确认 → 结算 | 无设备环节的服务成果、验收及结算依据 |

每个阶段内遵循：确认适用事项 → 提供资料或生成文书 → 核对有效成果和必备证明 → 完成阶段，或依据真实情况注明不适用。列表顺序不等于已经核实的强制前置关系；当前阶段状态函数没有统一强制“前一阶段完成才能开始后一阶段”的逻辑。

项目完成时核对适用阶段、材料、必备成果和未办结事项。登记“供应商交付事项完成”不自动代表合同验收通过，生成验收申请也不等于获得验收结论。

**历史项目走补录支线**：登记已结束事实 → 录入已知日期（未知留空）→ 补录资料 → 核对档案 → 达到条件后正式归档。历史项目可以“业务已结束、档案待整理”，不重走过去的施工、研发或验收动作。

项目月报等周期性成果作为单独周期工作办理并明确参考项目；当前不支持让同一套工作级阶段状态在每个月复用。本轮不新增项目与月报的自动关联关系。

### 3.4 部门工时

**开始条件**：选择所属工作和月份，准备同月研发明细、考勤、部门模板、应填人员范围及人员参与项目依据。

**办理过程**：导入并保留输入 → 核对人员、项目和日期映射 → 按规则计算 → 处理异常并重算 → 逐人逐日及项目汇总对账 → 核对Excel → 定稿 → 完成本期。

研发工时优先计入，普通办公日余额按已确认参与项目分配；请假、调休、半天及人工调整均需适用依据。缺少人员或项目事实时保留异常，不能靠猜测填满表格。

当前期次的完成判断检查**最新一次运行**是否定稿并关联有效Excel。先有定稿、后产生新的未核对计算，不能继续用旧结果认定本期已准备完毕。

**结果**是有来源、有计算规则、可重算且核对过的工时Excel。单纯下载成功、公式存在或总和相等，都不足以证明逐人逐日正确；工时定稿也不代表实际已报送。

### 3.5 综合与临时事务

部门年度总结按年保存独立内容、来源和成果。年度范围、截止日期及是否报送依据实际要求，不直接照搬季度或月度规则。

临时工作采用“登记事项 → 处理内容／附件 → 核对适用结果 → 办结”。没有文书要求的简单事项可以不生成文件；需要正式材料的事项应提前明确必备成果，不能依靠最后一步临时增加条件。

通用“行政管理”当前是文书模式。虽然保留“接收、起草、审核、印发、归档”5个旧阶段定义，新建时只有阶段模式才自动实例化阶段，因此不能声称所有行政管理工作都按这5个阶段执行。

首页快速待办适合提醒或工作内的小事项。需要独立期次、完整成果和档案的业务应建立工作；待办勾选完成不能代替其所属工作的材料核对。

## 四 共用完成规则与状态转换

### 4.1 四类完成事实分别判断

| 事实 | 判断对象 | 不能替代的事情 |
|---|---|---|
| 内容或记录已保存 | 一条记录／本期内容 | 内容真实、活动完成、文书定稿 |
| 成果已定稿 | 某份成果的具体版本 | 实际报送、外部签署、业务验收 |
| 本期／阶段已完成 | 指定期次／阶段 | 整项周期工作结束、其他期次／阶段完成 |
| 工作已结束且档案齐备 | 整项工作与其适用档案 | 删除数据、覆盖历史 |

“逾期、缺材料、来源过期、等待外部反馈”作为办理提示或阻塞原因显示，不把它们全部设计成互斥业务状态。

### 4.2 当前数据状态与办理语义映射

此表描述本轮所查开发源码与迁移。不是新增数据库字段，也不代表已经运行全部转换测试。

| 对象 | 当前数据承载 | 触发及前置条件 | 结果与失败处理 |
|---|---|---|---|
| 具体工作 | `workbench.status`：active／paused／done／archived | 单次／项目完成经过`assertWorkReady`；历史创建可直接登记done | 普通完成缺项时阻断；历史结束事实与档案状态分开 |
| 本期完成 | `work_period.status`：open → done | 用户完成本期；`periodReadiness`检查适用文书、材料、月检或工时 | 通过后记完成时间；失败仍保持办理状态并返回缺项 |
| 本期重新办理 | done → open | 用户重新打开；已收起工作先恢复 | 清除本期完成时间；父工作原为done时恢复active，不删除旧成果 |
| 整个周期工作结束 | `closePeriodSeries` → 工作done | 至少有一期；所有已建期次完成且仍有效；关联待办已结束 | 停止继续同步新期；有欠办期次不能直接结束 |
| 阶段 | pending／doing／blocked／done／skipped | done检查材料与必备成果；skipped要求原因 | 未满足条件不结束；重新办理保留原文件。不是固定单向状态机 |
| 外部材料 | missing／provided／verified／na | 上传后须关联正确文件；verified核对实际文件；na需要依据 | 文件缺失即使曾verified仍不能算满足 |
| 文书定稿 | `artifact.is_final`、版本及核对记录 | 对当前文件与来源执行适用定稿检查 | 文件缺失、内容或来源不满足要求时阻断；新版本不继承旧核对结论 |
| 月检实际报送 | `reported_on`与`report_snapshot` | 当前记录和所需成果已准备好；日期有效且非未来 | 记录实际日期和当前成果签名；记录或定稿变化后重新核实 |
| 工时计算 | `timesheet_run.status`：draft → final | 无阻断异常、规则匹配、输入可读、明确核对、所属月份一致 | 保留运行与Excel；最新运行未定稿时阻断本期完成 |
| 当前“收起／归档” | 工作archived及原状态 | 当前函数对done工作检查完整性，对active／paused未执行同等档案检查 | 可以保留未完成工作并从常用列表收起；不可据此断言正式归档完成 |
| 快速待办 | `quick_todo.status`：open／done | 完成提醒或具体小事项 | 不自行改变对应阶段、成果或整项工作完成事实 |

### 4.3 改变内容后的处理

1. 已完成期次先重新打开，再修改事实；保留原成果及实际发生过的报送历史。
2. 月检记录修改产生新修订；相关单次、汇总和累计成果按其范围重新核对，不能只刷新文件名。
3. 模板或填写规则变化先看本期差异再更新快照，不自动改写旧期次。
4. 工时人工调整形成新运行；新结果重新核对定稿，不能用旧Excel掩盖尚未处理的异常。
5. 跨期汇报使用来源时保留其原本的工作、时间和状态，不将“被引用”写回为“已完成”。

## 五 当前冲突与需要明确的边界

| 编号 | 已核实的现状 | 对业务理解的影响 | 本轮整理结论与后续处理 |
|---|---|---|---|
| BL-01 | “清廉季度工作”与“季度本领域监督工作推进情况汇报”均在用类型列表中 | 新建时不清楚选哪个，可能重复建立同一目标 | 默认保留全部历史；后续明确通用类型是否继续用于新工作，不直接合并 |
| BL-02 | 当前归档函数允许active／paused工作收起，另有`dossierReadiness.canArchive`判断正式档案条件 | 已归档标签可能被理解成全部完成 | 业务术语区分“收起”和“正式归档”；后续统一界面与操作条件 |
| BL-03 | 通用信息化12节点、工程19节点包含具体表单名称；软件／集成按宏观4阶段 | “阶段”有两种粒度，进度百分比容易被误当成相同工作量 | 保留原节点和关系；建议在展示层按实际办理段落分组，分组方案另做设计 |
| BL-04 | 月检必须至少有一条记录及适用定稿；通用周期按配置检查，若无必备模板／材料等要求可能没有成果阻断 | 零检查月不能完成；空配置也可能允许普通期次完成 | 不擅自加入“零检查视为完成”；逐类型明确最低成果和例外口径 |
| BL-05 | 明确的报送日期及成果签名目前只对月检开放；季度汇报规则文字提到报送 | 季度“完成”与“已报送”容易混淆 | 保留实际业务要求；涉及报送的其他类型须另定义记录方式，不能假装已有统一报送状态 |
| BL-06 | 普通季度来源选择不包含年度计划、无期次谈话；助手有另一套收集范围 | 同样说“季度汇总”，不同入口可能读到不同资料 | 后续统一可见参考范围说明与来源预览，不将两个入口的覆盖能力混写 |
| BL-07 | `admin`为document模式但有5个旧阶段定义；谈话和承诺书为process模式但只有材料核对节点 | “行政必定按期次”“有阶段定义就会执行”都不成立 | 以实际办理方式及实例结构判断，历史定义保留 |
| BL-08 | 类型默认截止配置并非全部季末／年末，例如通用季度和部门年度的偏移为0 | 用户可能把系统建议日期当成真实报送期限 | 默认配置明确标为建议；现有期次按其快照核对，不自动批量改期 |
| BL-09 | 旧工作排期字段与独立期次逻辑同时存在 | 同一个“完成本期”可能对应不同数据机制 | 新整理以独立期次为业务标准；旧工作单列兼容范围，不能无审查迁移 |

BL-04中的空要求行为是静态路径分析，不表示已经发现真实工作被误完成。阶段修改后父工作状态、跨期来源变化如何在首页持续提示，仍需要后续专项实测，不能从函数存在直接认定一致性已验收。

## 六 场景检验与验收样例

以下是用于检验业务定义的设计样例，不是已经执行通过的测试结果。匿名“甲、乙”仅为示例对象。

| 业务线或场景 | 正常样例及预期 | 阻塞／边界样例及预期 |
|---|---|---|
| 安全月度 | 本月适用成果与材料齐备后完成本期，其他月份保持独立 | 仅有上月成果，不得代替本月；是否必须报送按明确规则 |
| 月度检查 SC-01 | 同月两次检查分别登记并生成对应表册；必备汇总定稿、真实报送后完成本期 | 修改其中一条检查后，旧成果和报送签名不能继续算当前有效 |
| 单次工作 SC-02 | 一项不要求文书的临时协调，处理并记录结果后完成 | 已明确必备文书的事项缺少成果时不能按“简单事务”跳过 |
| 在办项目 SC-03 | 软件项目按适用4阶段办理；材料、文书和未办事项全部满足后结束 | 只有验收申请没有适用验收证明，不得据此宣布项目验收通过 |
| 历史项目 SC-04 | 业务已结束但部分档案待补，保留“结束＋待整理”；补齐后归档 | 未知实际日期不得由创建时间代填，不要求重演研发或施工 |
| 季度汇报 SC-05 | 选择当季月检及季度活动，按来源写局部进展并核对定稿 | 只有年度计划不证明检查已开展；跨期或未读资料不得混成当季已完成事实 |
| 部门工时 SC-06 | 本月输入匹配，逐日及汇总对账，最新运行定稿后完成本期 | 新运行仍有请假与研发冲突，即使旧运行定稿，也应阻止本期完成 |
| 年度计划与年度总结 | 按年度保留独立内容及成果，计划与总结分别解释 | 计划定稿不等于活动完成，去年总结不能自动完成今年 |
| 同日季度活动 | 风险研判、廉洁学习、项目考评同日但各自保存成果与状态 | 完成其中一个，不自动完成另外两个 |
| 谈话及签署材料 | 按具体事项保存独立谈话记录或真实签署材料 | 空白承诺书、草稿或只有安排日期，不能证明已签署或已开展 |

## 七 对下一步设计的明确输入

下一步的首页和月检原型只需围绕以下结构设计，不必再次从所有功能菜单开始讨论：

1. 首页事项的身份是“哪项工作＋哪个期次或阶段＋待办动作”，明确截止和缺项。
2. 月检详情分为检查记录、对应成果、本期汇总、实际报送和完成核对；参考附件与配置在需要时展开。
3. 项目详情保留阶段办理；历史项目突出补录资料与档案缺口，避免显示要求重走历史的主按钮。
4. 工时从工作及月度期次进入专用计算，结果回到该期，不另建孤立成果入口。
5. “收起、工作结束、档案齐备、实际报送”各自显示真实含义。

优先落实月检主线，因为其具体规则已经较明确。BL-01至BL-09进入后续设计或验证，不将本次整理记作已修复。删除风险GOV-01仍保留原状态，本轮按用户指定先整理业务线。
