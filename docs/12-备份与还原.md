## 1. 自动备份

### 1.1 什么时候跑（读代码）

- 定时器跟着服务启动：`bootstrap.ts` 在启动收尾时调 `startBackupScheduler()`，**不阻断启动**（备份目录不可写只是"今天没备成"，不是"工作台起不来"）。
- **每 5 分钟看一轮**（`TICK_MS = 5 * 60 * 1000`），**启动后 15 秒先看一轮**（`FIRST_TICK_MS`）——所以"到点时机器没开机"也能补上。
- 一轮的判定（`planScheduledBackup`，纯函数）：
  - **还没到 `backup.hour` 点**（本地时间，默认 3 点）→ 什么都不做；
  - **日备**：今天还没有 kind=`daily` 且"不是坏"的备份 → 补一份；
  - **周备**：本周还没有 kind=`weekly` 的备份 → 补一份。**周界**是「最近一次 `weeklyDay` 那天的 `hour` 点」（0=周日，默认 `weeklyDay=1` 即周一），语义是"一周至少一份"，不要求正好周一开机；
  - 日备和 **周备可以由同一轮同时各出一份**。
- 同一天日备最多自动尝试 **3 次**（`MAX_DAILY_ATTEMPTS`）：今天已有的日备**全是坏的**才会重试，避免每 5 分钟刷一份坏文件把盘塞满；到顶后再要备份只能手动点。
- **测试模式不启动**（`WORKBENCH_TEST_MODE=1`），防止回归测试往真实 `data/backups` 里写文件。
- `backup.auto = false` 时那一轮**直接返回**（`runBackupTick` 返回 `skippedReason = '自动备份已关闭'`，什么都不做）；**自动备份关了，界面上的「立即备份」照常可用**。
  定时器本身**照常起**（2026-10-02 修复前是"启动时读到 `auto=false` 就干脆不建定时器"，于是界面上把开关重新打开也不生效，要重启——现在开关每一轮现读，两个方向都立即生效）。
- 定时器每轮**重新读配置**，`workbench.config.json` 与 `app_setting` 都是每轮重读，所以改配置/改环境变量/改界面上的开关**都不用重启**（见 §5.6：界面那四个框现在真的读得回来）。

### 1.2 备份在哪、长什么样（实测）

- 目录：`backup.dir`，**默认 `data/backups`**（相对路径按项目根解析，绝对路径原样用）。界面上会显示这个目录，以及这个值「来自：环境变量 / 界面设置 / workbench.config.json / 默认值」。
- 配置优先级（`loadBackupConfig`）：**环境变量 > 界面存的 `app_setting` > `workbench.config.json` > 内置默认**。
  环境变量名：`WORKBENCH_BACKUP_AUTO` / `_HOUR` / `_DIR` / `_KEEP_DAILY` / `_KEEP_WEEKLY` / `_WEEKLY_DAY`。
  **第二档（界面 `app_setting`）的键名两种写法都认**：带命名空间的 `backup.auto`/`backup.hour`/`backup.dir`/`backup.keepDaily`/`backup.keepWeekly`/`backup.weeklyDay`（设置页写的就是这个，优先）与裸键 `auto`/`hour`/…（旧写法仍兼容）。曾经的"键名对不上"缺陷已修，见 §5.6。
- 默认档（`workbench.config.json` 现值）：`auto: true`、`hour: 3`、`dir: "data/backups"`、`keepDaily: 7`、`keepWeekly: 4`、`weeklyDay: 1`。
- 命名：`workbench-<daily|weekly|manual>-YYYYMMDD-HHmmss.db`，同一秒重名会加 `-2`、`-3`。
- **同名边车**：`<上面那个名字>.json`（`scope: "db"`、kind、时间、大小、备注、`verify` 结论）。**清单就是文件名 + 边车**，不存数据库——否则恢复到旧库时，比它新的备份记录会跟着丢。
- **备份目录禁止落在 `data/files` 里**（`assertDirOk`）：否则会被当成用户资料扫进索引、被 `pack.mjs` 套娃打包、恢复/清理时和用户文件混在一起。违反直接报 `BAD_BACKUP_DIR`（400）。
- 一份备份怎么造出来（`createBackup`，实测现网文件与其边车一致）：
  1. 用 `node:sqlite` 的**在线备份 API** `backup(conn, tmp)` 写到 `<最终名>.partial-<pid>`——是**某一时刻的一致快照**，不是"复制一个正在写的文件"；
  2. `PRAGMA journal_mode = DELETE` 把快照**收成单文件**（在线备份会继承源库的 WAL 模式，旁边会多出 `-wal`/`-shm`；只把 `.db` 拿走可能丢掉压在 WAL 里没落盘的页）；
  3. `verifyDbFile` 校验（见下）；
  4. **原子 `rename`** 发布成最终名——备份目录里永远不会出现"半个文件"被列表看到。**校验不过也照样发布**，只在边车里记成坏。
- 校验内容（`verifyDbFile`）：`PRAGMA quick_check` 必须 `ok` + `PRAGMA foreign_key_check` 必须 0 条 + 能读出**在用的**工作台数量（业务口径：`workbench` 表里 `deleted_at IS NULL` 的行；老库还没这列就不过滤）。每项都跑一遍、结论写进边车。
  - 刻意**不做** `integrity_check`：那是全量深检，日常每轮都跑太慢；要深检请手动跑（见 §5.1）。
- 启动时也会看"恢复日志"（`restore-journal.json`）：上一次恢复被强杀时会 `console.warn` 一行，告诉用户当前库是"换到一半"的状态，以及恢复前那份自动备份叫什么。

### 1.3 保留策略（读代码）

清理（`pruneBackups`）只在**新一轮备份全部校验通过**之后发生，四条规矩：

1. **新备份是坏的 → 整轮不清理任何旧备份**（`newBackupOk=false`）。"新的是坏的还去删旧的"等于把唯一退路删掉换个坏的回来看家。
2. **坏备份与"还没校验过"的备份一律不参与清理**：坏文件本身就是排查线索（磁盘坏了？还是库本来就坏？），只有用户手动删才会消失。
3. **日备按 `keepDaily` 份、周备按 `keepWeekly` 份**（周备优先保留），超出的按时间从最旧的开始删；
   **`manual`（含"恢复前自动备份"）永不被自动清理**——用户自己点的「立即备份」是他明确要留的东西。
4. 安全阀：**任何情况下至少留 1 份可用备份**（`room = 可用备份数 - 1`）——按第 3 条本该被删、因为这条规矩又多留下来的，会记进 `skippedReason`（"清理后就不剩可用备份了，多出来的旧备份已保留"），界面上看得到。

清理时如果发现有备份的边车文件丢了，列表里会标出来（`sidecarMissing`），结论按"未校验"处理，不会被当成可删候选。

## 2. 手动备份与命令行

### 2.1 界面

「系统配置 → 备份」卡片：

- 勾选**每天自动备份**，选**备份时间**（0–23 点的整点），改**保留日/周备份数** → 点「保存备份设置」（走已有的 `PUT /api/settings`，不新增配置写入路径）。
  这四项存进 `app_setting` 的 `backup.auto` / `backup.hour` / `backup.keepDaily` / `backup.keepWeekly`，**下一轮定时判断（≤5 分钟）就按新值走，不用重启**（修复前的"键名对不上"见 §5.6）。
- 右上角「**立即备份**」→ `POST /api/backups {kind:'manual', note:'手动备份（设置页）'}`，成功/失败都会 toast：「已备份：<名>（校验通过，工作台 N 个）」或「备份文件已生成 <名>，但校验没通过：<原因>」；
- 右上角「**校验**」→ `POST /api/backups/verify`（全部重跑一遍；坏的数量 > 0 会以 err 色提示，并明说**文件已保留、没有删除**）；
- 列表每行：文件名、类型、时间、大小、「校验通过 / 坏 + 原因 / 未校验」、「恢复」「删除」按钮；
- 卡片底部会显示**备份目录与数据库路径**；两者在**同一块盘**时会有一行黄字警告（见 §5.2）。

### 2.2 接口（`routes-core.ts`，共 5 个）

| 方法 | 路径 | 入参 | 返回 / 说明 |
| --- | --- | --- | --- |
| GET | `/api/backups` | — | `backupOverview()`：`dir`、`dbFile`、`scope:'db'`、`restoring`、`config{auto,hour,keepDaily,keepWeekly,weeklyDay,dirRaw,origin}`、`items[]`（含 `ok` / `bad` / `sidecarMissing` / `verify`）、`lastRestoreInterrupted`（恢复日志，没有则为 null） |
| POST | `/api/backups` | `{kind?: 'daily'\|'weekly'\|'manual', note?}`，kind 不合法按 `manual` 处理 | **201** + `BackupInfoWithCreated`（含 `verify`，顺带清理时还有 `pruned[]`） |
| POST | `/api/backups/verify` | `{name?}` | 不传 name 校验全部：`{items, total, okCount, bad:[{name, errors}]}`；**坏结论同样写回边车**（留证） |
| POST | `/api/backups/:name/restore` | `{confirm:'恢复'}`（`trim()` 后必须**正好**是这两个字，否则 `NEED_CONFIRM`） | `RestoreReport`（见 §3.4）；成功后会 `reloadBoundRoots()` 重算目录绑定白名单，失败则记进 `warnings` |
| DELETE | `/api/backups/:name` | — | `{deleted}`；**恢复进行中拒绝**（409 `RESTORE_RUNNING`） |

- `:name` 必须是本程序生成的备份名（严格正则），且解析后不许越出备份目录——防目录穿越。
- 接口错误统一走 `BackupFailure → ApiError` 翻译，界面上看到的是人话而不是 500。

### 2.3 命令行（服务没跑也能用，与界面同一条代码路径）

```powershell
node scripts/backup.mjs                   # 立即备份一份（kind=manual）
node scripts/backup.mjs --kind daily      # 指定类型：daily | weekly | manual
node scripts/backup.mjs --list            # 列出备份与校验结论
node scripts/backup.mjs --verify          # 逐份重跑 quick_check + foreign_key_check
node scripts/backup.mjs --json            # stdout 只有一段 JSON（给计划任务/脚本用）
node scripts/backup.mjs --dir D:/备份      # 指定备份目录（默认取 workbench.config.json 的 backup.dir）
node scripts/backup.mjs --db <文件>        # 指定要备份的库（默认 data/runtime/workbench.db）
```

细节（读代码）：

- `--kind` 给了非法值 → 打印提示并 `exit 2`；不给就是 `manual`。
- **`--json` 时 core 层的过程日志被挤到 stderr**，stdout 只剩能 `JSON.parse` 的结果（不然 `| 别的程序` 会先读到「[备份] 日备完成：…」）。
- `--verify` / 新建备份若**校验没过**，进程 `exitCode = 1`（方便计划任务判失败），失败详情照常打印。
- `--dir` 相对路径按**安装根**解析（与 `WORKBENCH_DB`、`backup.dir` 同一口径）。
- 不带 `--db` 时走 `createBackup`（会按保留策略清理）；带 `--db` 时走 `createBackupOfFile`（`skipPrune: true`，**不清理**，适合备份/检查别的库）。
- 服务在跑也**可以**备份：在线备份 API 读的是某一时刻的一致视图，不会被锁文件挡住（这正是它比 `npm run pack -- --with-runtime-state` 强的地方——后者在服务运行时会被锁文件挡住，见 `docs/11` B1-2 背景）。
- 用 Windows 计划任务在服务没开时也能定时备：
  ```powershell
  schtasks /create /tn 工作台备份 /sc daily /st 12:30 /tr "node D:\project\工作台\scripts\backup.mjs --kind daily"
  ```
- 命令行**只备份数据库，不含 `data/files` 里的用户文件，也不删除任何用户文件**。

## 3. 一键恢复

### 3.1 界面路径（实测界面文案）

1. 左侧导航进「**系统配置**」；
2. 找到「**备份（数据库只有本地一份，这里给它上保险）**」卡片，在列表里找到想回到的那一份（**坏备份的「恢复」按钮被禁用**，鼠标悬停提示"这份备份没通过校验，不能用来恢复"）；
3. 点该行的「**恢复**」→ 弹出「从备份恢复（会覆盖当前数据）」；
4. 弹窗里明写："**会先用当前数据做一份备份，再从选定的备份恢复**"、"恢复期间工作台会**暂停接受写入**（几秒钟）"、"`data/files` 里的用户文件不会被删除或修改"，并列出选中的备份名/时间/类型/大小/校验结论；
5. 在「请输入「恢复」两个字确认」里**手输「恢复」**——`trim()` 后不等于这两个字时「确认恢复」按钮**一直禁用**；
6. 点「确认恢复」（`POST /api/backups/:name/restore {confirm:'恢复'}`），完成后卡片上出现「恢复结果」面板：成功/已退回/有问题 + 工作台数量前后对比 + `quick_check` 与 `foreign_key_check` 结论 + 逐步 `steps[]` + `warnings[]`。

### 3.2 恢复前会自动先备份当前库（读代码，`restoreBackup` 第 ② 步）

- 顺序上**紧跟在"校验选中的备份"之后、动库之前**：`createBackup({kind:'manual', note:'恢复前自动备份（即将恢复到 <名>）', skipPrune:true})`。
- 这份备份**做不出来就直接中止**（`PRE_BACKUP_FAILED`，500），**当前库一个字节都没动**；
- 当前库自己那份备份如果校验没过（说明当前库本来就可能有问题）→ 记 `warnings` 但**继续恢复**（用户正是想逃离这个坏库）；
- 它是 `kind=manual`，所以**永不被自动清理**，且能在列表里找到再恢复回来——这就是"恢复错了还有退路"的实体。

### 3.3 恢复期间停写、且全程不就地改库（读代码）

- **停写**：进恢复后置 `maintenance=true`，`routes-core.ts` 的 `onRequest` 钩子对**所有非 GET/HEAD/OPTIONS 的 `/api/` 请求**回 **503**，错误码 `MAINTENANCE`，文案"正在从备份恢复数据库，暂时不接受写入请求。恢复只持续几秒，请稍后重试。"这个钩子挂在根实例上，对**所有**路由文件都生效（工作台/模板/生成/归档/文件/AI…），不需要每个路由自己判。
- 已经在跑的写请求记在 `inFlight` 里，恢复前 `drainWrites` **最多等 3 秒**（`DRAIN_MS`）；3 秒还没结束就记一条 warn 并继续（它们的连接会随关库一起失效）。**这是"停写"真的停写、而不是"希望没人在写"的代价**——见 §5.5。
- **不就地改库**：关库（会把 WAL checkpoint 回主文件）→ 把选中的备份 **`copyFileSync` 成同目录临时文件** `.restore-partial-<pid>` → 清掉目标库残留的 `-wal`/`-shm` → **`rename` 原子替换** → 重开库。任何一步被杀掉，`workbench.db` 要么是旧的、要么是新的，**不会**是半截的。
- **只碰数据库文件与备份目录**：`data/files` 下的用户文件全程只读不动。
- 全程写一份 `restore-journal.json`（`phase: swapping` 等），进程被杀时下次启动能看见并提醒（界面上是一块黄色 notice）。

### 3.4 校验不过会自动退回（读代码）

- 换库后重开库（顺带跑迁移，老备份缺新表/新列会在这里补齐）并再校验一次；
- **新库打不开或校验不过** → 如果"恢复前自动备份"可用，就**再用它做一次同样的原子替换退回去**，`rolledBack: true`，报告里明说"这次恢复没能成功，已自动退回恢复前的数据"；
- 如果"恢复前那份"也不可用 → 记 `warnings`："恢复后的库有问题，而恢复前的自动备份也不可用，无法自动退回，请手工处理备份目录里的文件"（不假装成功）；
- 另外还核对工作台数量：快照里记的数 vs 恢复后读到的数不一致 → `warnings`；恢复前 vs 恢复后不一致 → 记进 `steps`。
- `RestoreReport` 字段：`restored`、`restoredFrom`、`preRestore{name,ok,errors}`、`workbenchCountBefore/After`、`verify`、`rolledBack`、`drained{waitedMs,blockedRequests}`、`steps[]`、`warnings[]`、`finishedAt`。

## 4. 换机器 / 迁移演练（**未实测** —— 本节是按代码与接口写出的操作步骤，本次没有真做）

> `docs/11` B1-2 验收第 ④ 条要求"真做一次还原演练"并把命令与输出记进本文。**本次交的是步骤，不是演练记录**；真正跑过之后请把输出摘要补到 §8。

前提：换机器只需搬两样东西 —— **数据库快照（一个 `.db` 文件）** + **用户文件目录 `data/files`**。备份功能只管前者。

1. **停服务**（旧机器）：正常关掉工作台进程；确认 `data/runtime/` 里的 `server.lock` 不再是活进程持有（不放心就把进程关干净再操作）。
2. **取一份 `.db` 快照**：用**备份目录里的** `workbench-*.db`（例如 `data/backups/workbench-daily-20261002-101849.db`），**不要**直接拷正在跑的 `data/runtime/workbench.db`——后者是 WAL 模式，旁边还压着 `-wal`，直接拷会得到"看着在、内容不全"的库。
   - 备份出来的快照在发布前已被切成**单文件模式**（`PRAGMA journal_mode = DELETE`，代码里 `finalizeSnapshot`），所以按设计**一个 `.db` 文件拿走就能用，不需要 `-wal`/`-shm`**。
     旁证（实测）：`data/backups/workbench-daily-20261002-101849.db` 与 `data/runtime/workbench.db` 大小一致（各 811008 字节），边车记录该快照 `quickCheck: "ok"`、`foreignKeyCheck: 0`、`workbenchCount: 2`。
     ⚠ 但**"把单独的 `.db` 放到另一台机器上打开"这件事本次没有做**（§8 待补）；而且实测那份 `.db` 旁边还带着 `-wal`/`-shm`（成因未验证，见 §5.3），所以搬运时**只拷 `.db` 这一个文件**，别把伴生的 `-wal`/`-shm` 一起拷过去。
   - 嫌不够新就先跑一次 `node scripts/backup.mjs`（或界面「立即备份」）再拿。
3. **放到新机器**：把快照放到新机器的 `data/runtime/workbench.db`；或者放在任意位置并设环境变量 `WORKBENCH_DB=<绝对路径>`（`config.ts`：`DB_FILE = resolve(WORKBENCH_DB || <安装根>/data/runtime/workbench.db)`）。
   - 同时把旧机器的 `data/files` 整个拷到新机器对应位置（或用 `WORKBENCH_DATA_DIR` 指过去）。**备份里没有用户文件**，不拷的话工作台/记录都在、文件全都是"磁盘上找不到"。
4. **启服务**：`node scripts/start.mjs`（或 `启动工作台.cmd`）。启动会自动跑迁移（老库缺新表新列会补齐）。
5. **核对清单**（逐条过，任一条不过就别急着用）：

   | 核对项 | 期望 | 怎么核 |
   | --- | --- | --- |

   没跑过、仅按代码写出的核对命令（**未实测**，PowerShell 5.1 可直接粘）：

## 5. 已知边界（如实写）

### 5.1 `quick_check` 没有页校验和，"校验通过 ≠ 每一位都对"

`verifyDbFile` 做的是 `quick_check` + `foreign_key_check` + 工作台计数。`quick_check` 是 `integrity_check` 的**快速版本**（刻意没上全量深检，见 `backup.ts` 的注释）：它查结构、索引与页的**逻辑**一致性，**不做逐页校验和比对**。所以：

- 「校验通过」= **没发现结构性损坏**，不等于"每个字节都对"；静默的位翻转/磁盘坏道写进去的错值，可能照样过。
- 想要真·深检：手动对那份 `.db` 跑 `PRAGMA integrity_check`（本文没有把它做进自动流程）。
- 也**没有**逐表行数比对：`docs/11` B1-2 设计里写的 `MANIFEST.json` 逐表行数、2GB 总量上限、`/api/health.backupStale` + 首页黄色横幅，**都没有实现**（见 §6）。现在的计数只有"在用工作台几个"这一项。

### 5.2 默认备份目录**与库同盘**，盘坏一起没

默认 `backup.dir = data/backups` 就在项目盘上，而库在 `data/runtime/`，**同一块盘**——硬盘/分区坏了，库和备份一起没。界面上会黄字提示"备份和数据库在同一块盘上"（`sameDrive` 判断按盘符比较，仅 Windows 形态）。

**建议**：把 `workbench.config.json` 的 `backup.dir` 指到**另一块盘**或网盘/同步目录（如 `D:/备份/工作台`）。这样才真正防硬盘故障。注意两点：① 备份目录**不许落在 `data/files` 里**（会被拒绝）；② 备份快照是**单文件**（无 `-wal`/`-shm` 依赖），放同步目录相对安全；但把**正在写的库**（`data/runtime`）放同步盘是另一个已知风险（同步盘拆散 `-wal`/`-shm`，见 `docs/13-跨设备方案评估.md`）。

### 5.3 `data/backups` 里可能残留 `.partial-*` / `-wal` / `-shm`（**成因未验证**）

实测（2026-10-02 11:11 看 `data/backups`）：

```
workbench-daily-20261002-101849.db          811008  10:18:49
workbench-daily-20261002-101849.db.json        400  10:18:49   ← 边车（校验通过）
workbench-daily-20261002-101849.db-shm       32768  10:32:58   ← 比 .db 晚 14 分钟
workbench-daily-20261002-101849.db-wal           0  10:32:58
workbench-daily-20261002-101849.db.partial-10116-shm  32768  10:18:49
workbench-daily-20261002-101849.db.partial-10116-wal      0  10:18:49
（weekly 那一份同样有这 4 个残留）
```

- 代码里在发布后会调 `removeSidecars()` 清 `-wal`/`-shm`，`data/backups` 里**却确实**有这些文件，**为什么还在没有验证过**（可能与"备份文件后来被某条只读连接打开过、只读连接删不掉 `-wal`/`-shm`"有关，但本次没做实验确认）。它们不参与列表（列表只认严格文件名的 `.db`），也不影响校验结论。
  拷贝时**只拷 `.db`**：本次看到的 `-wal` 是 **0 字节**（没有未落盘的事务），`-shm` 只是 SQLite 的共享内存索引、会被重建。但**如果哪天看到非 0 字节的 `-wal`**，说明还有事务没 checkpoint 进主文件，那就得连 `-wal` 一起拷、或者先让库正常关闭再拷。
- `.partial-*` 是中断留下的临时文件：`cleanStalePartials` 会在**每轮备份开始时**删掉 **mtime 超过 2 小时**的这类文件（实测那 4 个的时间戳是 10:18:49，当时才 11:11，不到 2 小时，所以还在——与代码一致）。想要立刻清就手动删，或者跑一次备份后再等一轮。
- `-wal`/`-shm` 这两类**不在自动清理范围内**（`cleanStalePartials` 只认名字里带 `.partial-` 的）。

### 5.4 恢复只恢复数据库

`scope: 'db'`。`data/files` 里的用户文件**不在备份里**，恢复也**不会**动它们。所以"换个旧备份恢复"能让记录回到过去，但**磁盘上的文件还是现在的**——反过来也一样，文件被手工删了，恢复数据库并不能把文件找回来。要连文件一起保，得另外给 `data/files` 做备份（那是 iCloud/网盘的活）。

### 5.5 恢复期间的写请求会被拒，极端情况下 3 秒内没跑完的写不等

`drainWrites` 只等 **3 秒**（`DRAIN_MS`）。超时后照样继续恢复，只打一条 warn——此时那个还在跑的写请求可能落在"已被替换的旧文件句柄"上而**丢失**。正常情况下恢复只持续几秒，且界面/客户端会收到 503 而不会静默失败，但这条边界是真实存在的。

### 5.6 界面上的「保存备份设置」曾经不生效（键名对不上）—— **已修复并实测**

- **原缺陷**：界面（`Settings.tsx` 的 `BackupCard.saveSettings`）保存 `PUT /api/settings` 的 `backup.auto` / `backup.hour` / `backup.keepDaily` / `backup.keepWeekly`，而 `loadBackupConfig()` 的 `pick()` 读的是**裸键** `auto`/`hour`/`dir`/`keepDaily`/`keepWeekly`/`weeklyDay`（`DEFAULT_SETTINGS` 里也没有 `backup.*`）→ 两边对不上，**用户在界面上关掉自动备份其实没关**（界面显示已关闭，定时器照样每天备份）。属于"界面声称能设、实际不生效"。
- **修法（读侧兼容，不动写侧）**：`loadBackupConfig()` 的 app_setting 档现在**两种键名都认**，`backup.*`（界面在写的）优先，裸键作后备（见 `backup.ts` 的 `SETTING_KEYS`）。之所以不把界面改成写裸键：旧库里已经存着 `backup.*` 的行，改键名会把用户以前设的值悄悄作废、悄悄退回 `workbench.config.json` 档。
- **`DEFAULT_SETTINGS`**（`config.ts`）里补上了 `backup.auto` / `backup.hour` / `backup.dir` / `backup.keepDaily` / `backup.keepWeekly` / `backup.weeklyDay` 六项（键名 = 界面写的形状，带类型/名称/说明），但 **`value` 一律留 `null`**：这几项只"登记"，不预置值 —— `applyDefaultSettings()` 每次启动都会把非空默认值种进 `app_setting`，一旦预置，`app_setting` 这一档就会永远压住 `workbench.config.json` 的 `backup` 段，"改配置文件就生效"这条就废了。留空值时 `pick()` 自然落到下一档。（副作用：`PUT /api/settings` 现在能给这几个键带上正确的 `value_type`，`backup.auto` 存成 `boolean`、`hour` 存成 `number`。）
- **顺带修掉的同一类缺陷**：`startBackupScheduler()` 以前"启动时读到 `auto=false` 就不建定时器"，于是**界面上把自动备份重新打开也不生效**（要重启，而保存提示写着"立即按新配置运行"）。现在定时器**无条件起**，开关由每轮的 `runBackupTick` 现读 `cfg.auto`；`auto=false` 时启动日志打印"定时器在跑但不备份"，分钟级生效。
- **实测**（隔离实例：`WORKBENCH_DB`/`WORKBENCH_DATA_DIR`/`WORKBENCH_BACKUP_DIR` 全指向 `.tmp/bkset-*`，走界面同一条 `PUT /api/settings` 写路径）：
  - 全新库 `GET /api/backups` → `origin.auto = origin.hour = workbench.config.json`（`DEFAULT_SETTINGS` 的 NULL 行没有压住配置文件档）；`origin.dir`/`origin.keepDaily` = 环境变量。
  - `PUT /api/settings {"backup.auto":false,"backup.hour":7,"backup.keepDaily":5,"hour":9,"weeklyDay":4}` → 200；随后 `GET /api/backups` 返回 `auto=false`（origin `界面设置`）、`hour=7`（origin `界面设置`，压过同库里的裸键 `hour=9`）、`weeklyDay=4`（裸键仍生效）、`keepDaily=11`（origin `环境变量 WORKBENCH_BACKUP_KEEP_DAILY`，环境变量 > 界面设置 > 配置文件 三档同场验证）。
  - 服务运行中把 `workbench.config.json` 的 `backup.hour` 改 5、`backup.keepWeekly` 改 2 → `hour` 仍是 7/`界面设置`（app_setting 覆盖 config），`keepWeekly` 立刻变 2/`workbench.config.json`（免重启）；改回后 `keepWeekly` 回到 4。
  - 重启实例（`app_setting` 里 `auto=false`）→ 启动日志出现"**定时器在跑但不备份**"；再 `PUT backup.auto=true` 后 `GET` 立即返回 `auto=true`。
  - 优先级链条与本节开头一致：**环境变量 > app_setting（界面设置）> workbench.config.json > 内置默认**。
- **命令行走的是同一条 `loadBackupConfig()`**，所以 `scripts/backup.mjs` 与定时器、接口的取值口径完全一致。

### 5.7 其余

- **`node scripts/backup.mjs --list` 会忽略 `--dir`**（`--list` 分支走 `backupOverview()`，用的是生效配置里的目录；`--verify` 才用 `--dir`）。读代码确认，**没实测**"同时给 `--list --dir` 两个参数"的表现。要列别的目录，用 `--verify --dir` 或临时改配置。
- **命令行用 `--kind daily` 只是给这份备份贴 `daily` 标签**（方便分类/参与日备保留策略），它**不会**替定时器判断"今天是否需要日备"；定时器只认目录里已有的 `daily` 备份的时间与校验结论。
- **命令行不带 `--db` 时会按保留策略清理旧备份**（走 `createBackup`）；带 `--db` 时**不清理**（走 `createBackupOfFile`，`skipPrune: true`）。想"只加一份、什么都不删"就用 `--db` 指到同一个库，但要注意这样可以绕开"至少留 1 份可用"以外的清理，份数会自己涨。
- 恢复**不会自动重启服务**；恢复后 `external_root` 可能和原来不同，接口会调 `reloadBoundRoots()` 重算白名单，失败时只记 `warnings` 提示"重启工作台即可恢复"。
- `data/runtime/backups/prebatch1/` 是**旧设计留下的目录式快照**（`workbench-before-batch1.db` + `baseline.json`），**不被现在的列表/保留策略识别**（列表只读 `backup.dir` 下的 `workbench-*.db`），也没人清理它。看到它不要当成有效备份。

## 6. 与 `docs/11` B1-2 设计的差异（**实现以本文为准**）

`docs/11` 第 159–181 行写的 B1-2 方案与实际实现**不完全一致**，别拿那份当操作手册：

| `docs/11` 设计里写的 | 实际实现 |
| --- | --- |
