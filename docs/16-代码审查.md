## 一、结论与优先级

### 1.1 整体风险判断

这是一款**本机单用户、127.0.0.1 上运行**的工具（所有非 GET 的 `/api/*` 请求都要带 `x-workbench-token`，由 `core/request-guard.ts` 统一校验），因此本次审查中**没有发现可被远程/跨站触发的漏洞**。风险的实际形态集中在三类：

| 形态 | 说明 | 典型条目 |
|---|---|---|
| **A. 真会出错（有明确数据损坏或功能失效路径）** | 触发是日常操作，后果不可逆或需重启才能恢复 | 绑定校验缺口导致平台自己的库/备份被当用户文件删（§2.1.1）；知识库抽取把已入库文档成批物理删（§2.3.1）；同目录绑给第二个工作台后彻底删除旧工作台会删掉别人在用的文件（§2.8.2）；抽取确认后被覆盖的草稿再保存会覆盖抽取结果（§2.6.1） |
| **B. 真实但需要受限前提** | 要 .xlsx 模板、要手工构造的链接/占位符、要外部诱因（句柄占用、磁盘满）才会显现 | 恢复/彻底删除不刷新允许根白名单（§2.8.1）；文书版本链的非原子保存与定稿闸门并发绕过（§2.4.1、§2.4.2）；swapFile 失败后数据库长期关闭（§2.5.1） |
| **C. 边界失效 / 语义不一致 / 误导性文案** | 不损坏数据，只让提示、审计、统计、幂等性与实现不符 | 条款 subNo 不参与匹配、千分位金额漏报与万元/元误报（§2.7）；双链的多条不对称与 N+1（§2.9）；助手动作撤销的字段残留（§2.10）；前端若干文案与状态缺陷（§2.11） |

**大量条目的共同病根只有几个，值得按「一类」而不是「一条」去修：**

1. **同一件事在仓里已有正确实现，只是没被复用。** `core/search-all.ts` 有转义好的 `likePattern()` 与 `live('artifact','a')` 软删守卫，`core/ocr-queue.ts:408` 的 `ocrSummary()` 有正确口径，`routes-preview.ts:109-117` 有把定位错误翻译成 403/410 的示范，`core/ocr.ts:343` 有带 `maxOutputLength` 的解压示范 —— 而引用它们的兄弟代码路径各写各的。**这类问题的修复成本极低（常常每处 1～5 行），应优先批量对齐。**
2. **「允许根白名单」是内存态、由工作台存活状态派生，但没有跟随软删/恢复刷新。** 它同时是写入闸门（`core/paths.ts` 的 `rootOf`）和删除闸门（`assertDeletableFile`），所以一处不同步会同时造成「写不进去」和「删不掉/删错」。这是 §2.8 一整片问题的根源。
3. **「先动磁盘、后写数据库」的写法散落在多处且无补偿。** `store.ts:533`、`trash.ts:687`、`generate.ts:1639`、`backup.ts:992` 都是同一形状：磁盘动作成功、后续落库或换库失败，留下不可回滚的中间态。单进程 + WAL + 同步 SQLite 让触发概率很低，但一旦触发就只能手工收拾。

### 1.2 最该先修的三条

| 排序 | 条目 | 为什么排第一梯队 | 修复量级 |
|---|---|---|---|
| **①** | **绑定校验漏了「绑定根是 DATA_ROOT 的祖先」**（§2.1.1，high） | 这是本次唯一一条**能破坏平台自身数据**的路径：绑定 `D:\project\工作台` 会被挡，但绑定它的子目录 `data` 放行（`sameOrInside(DATA_ROOT, abs)` 对祖先返回 `false`），随后 `runtime/backups/logs` 不在忽略名单里、`registerExistingFile` 不限制扩展名，`.db`/备份文件被当普通用户文件登记；再经回收站「彻底删除」的 `removeArtifactFile` → `unlinkSync` 真删。且另一入口 `DELETE /api/artifacts/:id?withFile=1` 连 `assertDeletableFile` 都没有 | ~2 行校验 + 1 处删除前复核 |
| **②** | **知识库抽取收尾的 stale 清理按「本次计划」物理删库内文档**（§2.3.1，high） | `keep` 只由本次 `decision==='extract'` 的 relPath 组成，`stale` 是该来源下全部 `kb_document` 减去 `keep`，然后 `deleteKbDocument()` **物理删** `kb_chunk_search`/`kb_chunk`/`kb_document`（含已付费的向量）。触发面比原报告更宽：`maxFiles` 截断、遍历被截断、`readdir` 瞬时失败都会让 `keep` 变空 → **该来源全部文档连同向量被删**，且没有测试覆盖 | 十几行（stale 只清本次遍历确实看过、且判定为「不该入库」的项；截断/读失败时中止清理） |
| **③** | **恢复绑定型工作台不刷新允许根白名单**（§2.8.1，high） | 影响面比原报告更大：白名单进回收站时被摘掉、恢复时一行都没刷，于是恢复后「上传/纳管 → 500 路径越界」「预览 → 410 文件已不在磁盘上（但能下载）」「彻底删除 → 文件一个都不删、记录却真删了，只剩一条 console.warn」——**用户从此没有任何入口清理这些孤儿文件**。同源缺陷还有 §2.4，属于同一个「白名单不跟随状态」病根 | 两处各加一次 `reloadBoundRoots()`（回收站恢复处与恢复路由后），共 ~2 行 |

紧随其后的第二梯队（同样建议本轮一起修）：**§2.8.2 回收站工作台不占位导致删错别人的文件**（medium，修法也是几行：占用判定不要过滤 `deleted_at`）、**§2.11.1「从资料自动填写」确认后草稿覆盖抽取结果**（medium，唯一一条「用户被告知已写入、实际会被静默覆盖」的数据丢失）、**§2.1.2 允许根白名单不跟随回收站状态**（medium，与 ③ 同源）。

## 二、已确认问题

读法说明：

### 2.1 路径与文件写入

#### 2.1.1 【high】绑定校验漏了「绑定根是 DATA_ROOT 的祖先」

| 项 | 内容 |
|---|---|
| 问题 | `bindExternalRoot` 的校验只挡住「数据根本身」「位于数据目录内部」「盘根」和 `PLATFORM_ROOT_NAMES`（含 `工作台`，不含 `data`），**没有挡「所选目录是数据目录的祖先」**，于是 `workbench.config.json` 里的 `dataRoot`（`D:/project/工作台/data/files`）被放行绑定 |
| 位置 | `packages/server/src/domain/service.ts:494-497`（校验链）、`:364`（`PLATFORM_ROOT_NAMES`）、`packages/server/src/api/routes-files.ts:427`（导入只跳 `_` 前缀与 `isIgnoredName`）、`packages/server/src/core/ignore.ts:22-31`（忽略名单无 `runtime`/`backups`/`logs`）、`packages/server/src/core/store.ts:256-270`（`registerExistingFile` 无扩展名/大小限制）、`packages/server/src/core/store.ts:533-538`（`DELETE /api/artifacts/:id?withFile=1` 删盘） |
| 后果 | 平台自己的库、备份、日志被「纳管」成普通用户文件（`.db` 也会插行并算 sha256）；再经回收站「彻底删除」（`Trash.tsx:106-112` → `purgeFromTrash('artifact')` → `trash.ts:746` → `unlinkSync`）真删 `backups\*.db` —— 此时工作台仍存活、`data` 仍在白名单，`trash.ts:580-588` 的 `assertDeletableFile` 照样放行。`workbench.db` 因被 SQLite 占用通常报 EBUSY，故实际被删的是备份而非主库 |
| 修复建议 | 在 `service.ts:495` 后补一行反向包含校验：`if (isInsideRoot(abs, resolvePath(DATA_ROOT))) throw new Error(...)`；并在 `store.ts:535` 前补一次与 `trash.ts:580` 等价的允许根复核，堵住 `?withFile=1` 这条无校验的删盘入口 |
| 复核更正 | 原报告的场景③**走错了界面入口**：`Files.tsx:253-266` 的「移到回收站」不带 `withFile`；真正带 `withFile` 的勾选框在 `Trash.tsx:106-112`（回收站内彻底删除）。核心结论不受影响，真删路径成立 |

#### 2.1.2 【medium】允许根白名单不跟随回收站状态

| 项 | 内容 |
|---|---|
| 问题 | 白名单（`reloadBoundRoots`）由 `boundRootEntries()` 派生，后者带 `liveFilter` 即只收 `deleted_at IS NULL` 的工作台。注释与实现不符：代码声称 `restoreFromTrash` 会刷新白名单，实际**软删时刷新、恢复时不刷新** |
| 位置 | `packages/server/src/domain/service.ts:391-396`（派生口径）、`:2103`（注释断言）、`packages/server/src/core/trash.ts:390-436`（恢复分支只清 `deleted_at`）、`packages/server/src/api/routes-files.ts:702-720`（恢复路由只回 message）。全仓 `reloadBoundRoots` 调用点：`service.ts:536/553/2105`、`routes-core.ts:402`、`bootstrap.ts:36`、`trash.ts:722` |
| 后果 | **(a) 彻底删除绑定型工作台删不掉磁盘文件**：软删时白名单即摘根 → `purge` 时 `rootOf` 为 null → 抛「路径不在平台允许的目录内」被吞成 `unlocatable`，库行照删，接口回「共删掉 0 个磁盘文件」。**(b) 恢复后写不进去**：上传/生成走 `routes-files.ts:114-119` → `saveArtifact` → `store.ts:190` `rootKindOf(dirAbs)` → `paths.ts:150-152` 抛「路径越界，拒绝访问」，直到重启（`bootstrap.ts:36`）才自愈 |
| 修复建议 | 在 `trash.ts:436` 前与 `routes-files.ts:711` 后各补一次 `reloadBoundRoots()`（`trash.ts:722` 已有同款动态 import 写法可直接照抄） |
| 复核更正 | 「一个都删不掉」**非绝对**：若同一目录被第二个存活工作台绑走（绑定占用判定 `service.ts:518` 用的是 live 记录，回收站里的不算占用），白名单里仍有该根，`purge` 会**真的删掉另一个工作台正在用的文件** —— 这条独立的错删路径见 §2.8.2 |

#### 2.1.3 【low】全程不做 realpath，绑定根内的 junction/符号链接可绕过允许根校验

| 项 | 内容 |
|---|---|
| 问题 | 工件写/删链路全部是**词法**判断（`relative()`），没有 `realpath`。全仓 `realpathSync` 只出现在绑定（`service.ts:480`）与知识库来源登记（`routes-kb.ts:774`）两处。这是 `paths.ts:94-96` 写明的**刻意选择**（iCloud/OneDrive 占位文件与拔盘场景） |
| 位置 | `packages/server/src/core/paths.ts:94-134`（`isInsideRoot`/`rootOf`）、`store.ts:236-238`、`store.ts:466-474`、`store.ts:535-537`（`unlinkSync`）、`routes-files.ts:419-458`（`import-folder` 用 `readdirSync`/`statSync`，均跟随联接）、`store.ts:606-619`（`pruneEmptyDirs` 会沿连接向上 `rmdir`） |
| 后果 | 绑定根内的目录联接会让库外文件以 `file_rel='照片/a.jpg'` 被登记，删除/写入穿透到联接目标，`pruneEmptyDirs` 也会沿联接向上删空目录。**但链接必须由用户或同步工具放在用户自己绑定、且用户主动执行导入的目录里**，不是可被外部触发的漏洞 |
| 修复建议 | 不改动全局路径语义，只在这三处对 `abs` 做逐段 reparse-point 检查（`lstatSync`，发现即拒绝）：`registerExistingFile`、`saveArtifact`、`removeArtifactFile` |
| 复核更正 | 定级由 medium 下调为 low：机制成立但属「真实但低危的边界失效」，且是刻意不做 `realpath` 的已知取舍 |

#### 2.1.4 【low】`POST /api/settings/test-path` 用请求体里的任意路径建目录并写探针文件

| 项 | 内容 |
|---|---|

### 2.2 SQL 与数据访问

#### 2.2.1 【medium】自动编号 `nextWorkbenchCode` 取字典序最大值再 `Number()`

| 项 | 内容 |
|---|---|
| 问题 | 生成编号时 `SELECT code ... ORDER BY code DESC LIMIT 1` 走的是**字符串序**，再 `Number(row.code.split('-').pop())`。一旦 `workbench.code` 里出现非纯数字后缀（手工指定或历史数据），`Number()` 得 `NaN` 或错值，自动编号会**永久撞** `workbench.code` 的唯一约束 |
| 位置 | `packages/server/src/domain/service.ts:1078-1090`（尤其 `:1081`、`:1087`、`:1088`）、`packages/server/src/db/migrations/001_core.sql:150`（`code TEXT NOT NULL UNIQUE`）、`routes-work.ts:109`（`code` 可由请求任意指定）、`service.ts:1128`（`input.code?.trim() \|\| nextWorkbenchCode(wt)`） |
| 后果 | 复现成立：`2026-P-ABC` 排在 `2026-P-001` 之后 → `NaN` → 发 `001` → 撞约束；`2026-P-9999` 排在 `2026-P-10000` 之后（`'9' > '1'`）→ 发 `10000` → 撞约束。`:1082-1086` 注释**有意**不加 `deleted_at IS NULL`（回收站里的工作台照样占号），所以软删那条污染记录**没用**，用户只能彻底删除它，自动编号才能恢复。加重情节：`:1725` 的可更新字段白名单不含 `code`，编号创建后**无法修改**。失败时 `reply.ts:47-55` 把普通 Error 归为 500 INTERNAL 并原样回传 SQLite 文案，前端 `api.ts:68-71` 直接抛该文案 |
| 修复建议 | 把 `:1087` 的排序改成数值序，例如 `WHERE code GLOB '${year}-${prefix}-[0-9]*'` 或 `ORDER BY CAST(substr(code, ...) AS INTEGER) DESC`；并在 `:1128` 后补一次编号占用预检、命中则回 409（而不是让 SQLite 报错）。备注：`routes-work.ts:65` 定义了 `next-code` 接口但 web 端从不调用，不存在「前端已先取号」的旁路；`:1725` 建议一并放开 `code` 更新，给用户一条自救路径 |
| 复核更正 | 逐条读过**找不到任何上游防护**（全仓无 `codeExists`/编号格式校验；设计文档里的 `^\d{4}-[AP]-\d{3}$` 并未实现），反而发现上述加重情节。后备安全性：`db/index.ts:80-83` 的 `tx()` 用 SAVEPOINT，INSERT 失败不落库；`ensureDir` 在 INSERT 之后（`service.ts:1191`），不会留下半截目录 |

#### 2.2.2 【low】OCR 写回与队列计数都缺软删除守卫

| 项 | 内容 |
|---|---|
| 问题 | 队列统计的汇总查询是**全表**、无 `artifact` 关联、无软删过滤；同一响应的明细却带了 `a.deleted_at IS NULL`。写回侧 `finish()` 只按 `id` 无条件 UPDATE，能把已软删记录的状态翻回 `done` |
| 位置 | `packages/server/src/core/ocr-queue.ts:370`（汇总）、`:372-379`（明细，带软删过滤）、`:408-414`（`ocrSummary()` 的正确口径，注释明确写「回收站里的文件不该出现在队列统计里」）、`:326`/`:343-390`（`runOne`/`finish`）、`packages/server/src/core/store.ts:541-552`（软删只处理 `pending`/`running`，`done` 行原样留）、`startup-repair.ts:58-59`（重启只重置 `running`、只回写状态，不按 `artifact.deleted_at` 对账） |

| 复核更正 | 原报告场景 B 有两处描述不实，已更正：`finish()` 末尾的 `indexArtifact` **不会**把索引种回去（`store.ts:373-378` 的 `liveFilter('artifact')` 会把已删行的 `artifact_search` 行删掉），所以不存在「删了还能搜到」；回收站面板也**不显示** OCR 状态（`trash.ts:238-258` 的 extra 只有 kind/rel/在不在盘上），所以「回收站里看到一条『识别完成』」不成立 |
