# 工作台产品设计方案

> 适用边界：本文保留原日期的业务分析/设计，旧报送与强制办结要求已由[任务书41](41-AI辅助材料生成改造任务书-2026-10-21.md)覆盖。当前要求见[产品需求](../PRODUCT_REQUIREMENTS.md)，当前状态与队列见[项目计划](management/PROJECT_PLAN.md)。原型不代表日常实现。

版本：0.2，日期：2026-10-21。性质：供业务核对的设计基线，对应任务GOV-03。后续实施状态：第12节工作记录已完成源码实现与隔离验证，详见[实施记录38](38-工作记录与助手记忆实施-2026-10-21.md)；其余设计不因此视为已实现，日常版本尚未切换。

本版变更：按用户追加要求，取消SC-02通用单次工作的任务办理设计，改为“一句话工作记录＋持久记忆与检索”。删除的是办理入口及负担，不是历史数据。本文件中的原型仍只演示内存记录；后续实际应用已实现数据库持久化、助手查询与修订引用，当前处于隔离验证完成、尚未日常发布阶段。

## 1 设计目标与依据

用户进入工作台后，应能判断“现在先做什么、这件事到哪里了、还缺什么、办到什么程度才算完成”。开发围绕完整任务交付，基础缺陷由开发者检查，用户主要核对真实业务口径及实际产物。

本方案中的“合规”指符合本项目已确认需求、数据边界和[开发与验收规则](34-产品开发与验收规则-2026-10-20.md)。不声称获得法规、行业标准或单位制度的合规认证；目前没有足够资料确定单位的审批权限、档案保管期限和签章制度，不能凭设计补造这些规定。

依据优先级：用户明确要求 → [产品需求](../PRODUCT_REQUIREMENTS.md) → [业务主线](35-业务主线与办理规则-2026-10-20.md)及[术语](../CONTEXT.md) → 已核实的实现 → 设计建议。同类产品参考沿用[调研报告](33-同类产品调研与差距分析-2026-10-20.md)的来源与检索日期，本轮未进行新的外部调研。

设计交付包含全局业务与交互规范、六类场景、月检详细规则、数据与实现边界、验收矩阵，以及[本地交互原型](prototypes/workbench-v01/index.html)。原型全部使用虚构数据，刷新即重置，不连接业务服务、不调用模型、不生成真实文件。

## 2 范围和需要保留的结构

| 范围 | 设计决定 | 依据或限制 |
|---|---|---|
| 使用者 | Windows本地单机使用者；先做好一人完整办理 | 不增加多人权限、审批引擎或组织管理模块 |
| 业务线 | 安全、清廉监督、项目实施、部门工时、综合与临时事务 | 五条分析主线，不新增五个导航分类 |
| 类型选择 | 保留三个导航分类及现有21类历史标识；通用单次新建入口退出 | 沿用现有独立类型、稳定ID、模板关系和历史快照 |
| 办理结构 | 周期、项目阶段与专项材料办理；零散事项进入工作记录 | 工作记录不生成任务、期次、必备文书或办结要求 |
| 本次详细原型 | 首页 → 工作记录；首页 → 月检本期 → 记录 → 成果核对 → 报送确认 → 完成本期 | 其余场景提供页面及规则设计，不假称已经可用 |
| AI | 位于起草、资料问答等明确操作中 | 不代替事实、计算、用户定稿、报送或签章 |
| 发布 | 本次只交付设计与本地原型 | 实施、正式验收、生产发布分别记录 |

## 3 信息架构与页面职责

保留现有主要入口，不为这一轮设计批量改名。调整的是页面内容优先级和操作位置。

```text
工作台首页：待处理事项 → 继续办理
我的工作台：全部工作／筛选／新建 → 工作详情
  ├─ 历史单次工作：保留历史查看入口，不再作为日常新建办理路径
  ├─ 周期工作：期次列表 → 当前期次
  │   ├─ 一般周期：内容、来源、成果、完成核对
  │   ├─ 月度检查：检查记录、对应成果、汇总、实际报送
  │   └─ 部门工时：输入、匹配、计算、异常、对账、定稿
  └─ 项目：阶段办理；历史项目：资料补录与档案缺口
工作记录：首页说一句 → 自动保存原话 → 时间线／检索／更正／撤回
文件库：按工作／期次／阶段查文件及版本
流程规范、知识库、AI助手、回收站、系统配置：沿用共用入口
```

| 页面 | 第一屏必须回答 | 主操作 | 次级内容 |
|---|---|---|---|
| 首页 | 哪些事项需要处理、为什么、何时到期 | 进入对应办理位置 | 全部工作、搜索、概况 |
| 我的工作台 | 哪项工作、所属类型、业务状态和当前范围 | 继续办理／新建 | 已结束、已收起、历史工作筛选 |
| 工作详情 | 当前工作、当前期次或阶段、缺项及成果 | 最早可执行的下一步 | 工作设置、长期计划、历史版本 |
| 文件库 | 文件所属工作、范围、版本、是否当前有效 | 查看／打开所在工作 | 下载、关联、历史版本 |
| 配置页 | 修改什么规则、影响哪些新工作或新期次 | 保存配置 | 预览差异、旧快照说明 |

### 首页待办规则 D-01

1. 待办身份由“工作＋期次或阶段＋业务动作”确定，不能仅凭标题去重。相同事项在逾期、今日和最近工作中不重复计入待处理总数。
2. 默认顺序：已逾期 → 今日截止 → 其他可办理事项 → 等待外部资料。组内按截止日期、稳定ID排序；无日期显示“未设截止”，不能算作逾期。
3. 每行显示工作名称、范围、缺项、截止日期和明确动作。例如“10月月检 · 乙项目检查表待核对 → 核对成果”。不要仅写“处理”。
4. 首页是待办投影，不维护另一套完成状态。点击进入准确的工作和期次／阶段，并定位缺项；返回后保留筛选与位置。
5. 无待办显示“当前没有待处理事项”及全部工作入口；读取失败显示重试，不能显示“全部完成”。
6. 倒计时与逾期按本机业务时区Asia/Shanghai计算；原型固定2026-10-21作为演示时点，所有示例截止日期不构成真实排期。

### 工作详情共同布局 D-02

顶部固定显示工作名称、类型、当前范围和业务状态。正文顶部只有一个最优先的下一步操作，其后按实际办理顺序组织内容。状态标签、文件版本和缺项保持邻近，用户不需要跨页猜测阻塞原因。

周期工作始终显示当前年月／季度／年度，切换期次时提示未保存内容，不混用记录。参考资料和高级设置默认收起。底部的“完成本期”只处理本期；“结束整个周期工作”放在工作设置中，明确说明后续不再生成期次。高影响操作显示对象与影响，不使用通用“确定操作吗”。

## 4 六类场景设计

| 场景 | 用户路径 | 完成依据 | 必须覆盖的例外 |
|---|---|---|---|
| SC-01 月检 | 本期 → 登记多次检查 → 核对各次及汇总成果 → 实际报送 → 完成本期 | 记录与必备成果有效、报送对应当前成果、其他适用缺项清零 | 零记录、来源变化、漏表、未来报送日、已完成后修改 |
| SC-02 工作记录 | 告知一句 → 保存回执 → 日后查询／总结引用 | 原话持久保存且可按发生时间、主题和关联找回，不设置办结 | 保存失败、时间未知、计划误当已做、重复提交、更正与撤回 |
| SC-03 在办项目 | 选择原类型 → 阶段总览 → 适用阶段 → 核对成果与证明 → 结束／档案整理 | 阶段、必备材料和未办事项满足适用规则 | 有验收申请却没有实际验收证明；阶段不适用需理由 |
| SC-04 历史项目 | 登记历史事实 → 补材料 → 核对档案缺口 | 业务结束与档案齐备分别判断 | 日期未知留空，不用创建日代填；不强制重新研发或施工 |
| SC-05 季度汇报 | 选季度 → 查看来源范围与缺失 → 起草 → 核对来源和正文 → 定稿 | 当前所选范围、可追溯事实与适用成果要求 | 年度计划不能证明活动发生；三类同日活动独立；未读取不冒充已读取 |
| SC-06 工时 | 选月 → 导入 → 人员项目匹配 → 计算 → 异常处理 → 对账 → 定稿导出 | 最新计算通过、输入及规则对应、Excel可用、逐日及汇总对账 | 新计算未通过不能沿用旧定稿完成；缺考勤不能猜补 |

安全月度、年度计划、年度总结沿用一般周期布局；谈话和合同承诺沿用具体事项／材料核对。计划定稿、已签署、已开展是不同事实。其他工作是否必须报送，按第10节待定事项处理，不从月检自动推广。

项目阶段先保持现有4、12或19节点；未来若加视觉分组，只分组展示，不修改阶段ID或映射。各阶段是否强制串行依据类型规则，不凭左到右布局新增前置约束。

季度来源选择须显示“当前可选范围”及被排除的材料。扩大到年度计划、非周期谈话等跨范围参考，需要明确资料性质和过滤规则；不能静默将当前服务的同分类、同季度选择限制当作完整业务覆盖。

## 5 月度检查详细设计 D-03

### 5.1 视图结构

第一屏：工作名称 → 本期 → 本期状态 → 下一步。下方为检查记录与对应成果、本期汇总、实际报送、完成核对。侧栏显示必备项和缺项，宽度不足时置于正文后，不遮住操作。

一条检查是一件独立事实，包含日期、项目、检查事项、检查内容、检查结果。原型使用这五项必填作为演示；实际字段及校验必须与现有接口保持一致，不能仅修改前端。重复相似内容可以提示，不自动合并。

成果按当前类型／期次快照列出必备与可选。对应单次记录的文件放在记录附近；月度汇总独立列出；项目累计、年度累计保留明确范围和可选／必备属性，不拿月度合计冒充年度累计。原型简化为每条检查一份示例成果和一份月度汇总，不代替真实模板清单。

### 5.2 操作与校验

| 动作 | 前置条件 | 成功后 | 失败或变更后 |
|---|---|---|---|
| 保存检查 | 本期可编辑；字段合法；日期在本月；版本未冲突 | 保留独立记录ID和修订号，返回记录行 | 保留输入并指出具体字段；并发修改不覆盖 |
| 起草成果 | 对应记录存在，来源范围确定，模板可用 | 创建草稿版本；显示对应来源及生成方式 | 原记录不丢失，展示失败原因和重试；不冒充定稿 |
| 核对定稿 | 文件可读、必要核查通过、来源仍对应 | 明确标记定稿版本 | 来源变化时阻止沿用旧稿，历史稿仍可查看 |
| 确认实际报送 | 有检查记录；必备成果全部当前有效；日期合法且不在未来 | 记录用户确认及报送所对应的成果集合 | 不自动发送；缺项显示在按钮旁；不能仅凭定稿自动填报送日 |
| 完成本期 | 全部适用完成条件通过，包括当前有效报送 | 本期完成并只读；首页对应待办消失 | 服务端返回全部缺项及跳转位置，保留办理成果 |
| 重新打开 | 本期已完成且该工作允许编辑 | 回到可办理状态，保留历史记录 | 只重新打开不虚构新报送；后续修改按来源变化处理 |
| 修改来源 | 已重新打开或本期原本可编辑 | 受影响成果标记需重新核对，当前报送有效性重新判断 | 未受影响记录的成果不无故作废；旧版本与原报送记录可查 |

“确认实际报送”是用户记录已经发生的事实，不是系统发送按钮。原型的确认弹窗明确为模拟，不会报送。正式系统的事实确认文案为“我已核对本次实际报送日期及对应成果”。

### 5.3 完成条件

本期可完成 = 有适用检查记录 ∧ 各次必备成果当前有效 ∧ 必备汇总当前有效 ∧ 实际报送与当前成果一致 ∧ 其他适用材料／事项要求通过。

原型只演示前四项，不接入正式材料、模板、文件可读性及未办事项检查。实际实现应复用并核对现有`periodReadiness`和`inspectionDocuments`，不能把原型布尔条件复制成生产完成判定。

零检查月份保持未完成并显示“尚无检查记录；零检查月份的办结口径待明确”。不能引导虚构记录，不能提供未经确认的“无需检查直接完成”。

## 6 状态模型与不变量 D-04

| 层级 | 用户看到的状态 | 数据／推导约束 |
|---|---|---|
| 工作 | 办理中、暂停、已结束 | 复用工作状态；暂停不等于完成 |
| 期次 | 办理中、已完成 | 复用open／done；“缺成果”“待报送”作为派生提示 |
| 阶段 | 待办、办理中、受阻、完成、不适用 | 复用pending／doing／blocked／done／skipped；不适用需理由 |
| 成果 | 草稿、已定稿、来源已变化 | 版本、有效性和来源分别判断；过期定稿仍是历史文件 |
| 报送 | 未确认、已确认、需重新确认 | 从日期及成果／来源对应关系判断，不只看日期非空 |
| 档案 | 待整理、齐备 | 由材料缺口推导；与业务是否已结束分开 |
| 列表可见性 | 正常显示、已收起 | 文案明确收起作用，不将既有archived字段直接解释为正式归档 |

不新增一个同时承载所有含义的“总状态”。例如历史项目允许“业务已结束／档案待整理”；本月允许“成果定稿／待实际报送”。

不变量：期次属于唯一工作；阶段属于唯一项目；检查属于唯一月度期次；成果有确定范围及版本；完成操作须在服务端复核；重复提交不重复创建；来源修订后依赖它的有效性须重新计算；历史事实、文件和未知日期不被美化或补造。

现有收起接口对在办工作的行为与正式档案条件不完全相同（BL-02）。设计先区分文案与状态；正式归档功能若实施，需统一服务端条件并补兼容验证，不能只换按钮名字宣称修复。

## 7 数据和实现边界 D-05

| 边界 | 实现要求 | 验证依据 |
|---|---|---|
| 单一状态来源 | 首页及详情消费同一业务就绪结果；缺项含稳定编码、对象、原因、可执行动作与位置 | 同一修订状态在首页、详情、文件库一致 |
| 保存可靠性 | 利用已有修订校验；提交期间防重；失败保留表单；成功后以服务端返回值刷新 | 延迟、重复点击、冲突、断连 |
| 快照兼容 | 类型模板变更只按明确规则影响新建对象；已有期次变更必须显式说明 | 新旧期次并存、旧成果仍可追溯 |
| 文件与数据库 | 修改与删除考虑两者一致性；不得先不可恢复地删文件再赌事务成功 | GOV-01隔离复现、失败注入、恢复核对 |
| AI及资料 | 默认沿用既有本地／外发边界；来源可见；规则整理与模型写作区分 | 无证据、冲突、读取失败、模型失败 |
| 备份恢复 | 数据库及关联文件成套保留并在隔离位置验证恢复 | 文件清单、关联记录及关键成果可打开 |
| 发布 | 区分开发源码、候选包、正式指针和进程加载版本 | 精确清单、验证记录、授权与回退路径 |

在现有React／服务层内落实，先不引入新的状态管理库、工作流引擎或数据库体系。可能需要统一的就绪结果接口，但须先核对现有返回结构再做最小扩展。本方案不预设必须新增表或迁移全部旧数据。

## 8 界面与交互规则 D-06

| 要素 | 规范 |
|---|---|
| 视觉 | 中性色底、白色内容卡、深青色主要动作；用间距和标题体现层级，少用装饰性图表 |
| 信息密度 | 首页先展示待办；详情优先办理内容；不将全量工作、统计、搜索结果、提醒并列争抢第一屏 |
| 字体与布局 | 正文建议14–16px、行高1.6；桌面主要内容最大宽度约1200px；窄屏卡片堆叠，不要求横向滚动完成主任务 |
| 动作 | 页面顶部一个优先动作；行内操作与具体对象相邻；删除、结束整项、收起等放入明确次级位置 |
| 禁用 | 禁用的原因必须可见，不能只变灰；条件满足后及时更新；服务端同样复核 |
| 表单 | 标签常驻；必填与格式明确；错误挨着字段；离开未保存表单需提示；保存期间不重复提交 |
| 可访问性 | 所有操作支持键盘；焦点可见；对话框有标题并约束焦点；状态不只靠颜色区分；关闭后焦点返回来源 |
| 空与错误 | 无数据、加载中、筛选无结果、读取失败分开；失败给重试或可行后续动作，不清空已录内容 |
| 反馈 | 说明“哪条记录已保存”“哪份成果待核对”；成功不掩盖其他缺项；耗时操作显示进度或状态 |
| 文案 | 使用具体业务词；不把接口名、签名、表名和测试术语放进正式办理页面 |

原型顶部的“设计原型／示例数据”及演示场景切换属于核对工具，不进入正式产品界面。原型固定日期及内存数据也不属于生产设计。

## 9 验收矩阵与实施切分

以下为正式实现的验收设计，原型通过不等于这些检查全部通过。

| 编号 | 对应规则／问题 | 检查及预期 | 所需证据 |
|---|---|---|---|
| AC-01 | D-01／GAP-02 | 首页进入指定工作本期；缺项与详情一致；同一待办不重复计数 | 浏览器录屏或截图、接口结果 |
| AC-02 | D-03／SC-01 | 两次检查独立保存、分别形成成果；汇总范围正确；核对报送后完成 | 隔离数据、真实Word逐页核对、操作记录 |
| AC-03 | D-03／BL-04 | 零记录、缺必备稿或未来报送日阻止完成；显示原因 | 反例及服务端拒绝结果 |
| AC-04 | D-04／SC-01 | 修改一条记录使相关成果、汇总、报送失效；其他独立成果保留 | 修改前后版本及界面结果 |
| AC-05 | D-04 | 已完成只读；重新打开后可改；本期完成不结束整个周期 | 状态及后续期次验证 |
| AC-06 | D-05 | 连点、延迟、并发修订、断连不造成重复、覆盖或输入丢失 | 针对性失败注入与浏览器验证 |
| AC-07 | SC-02／SC-03 | 工作记录不产生任务；重启后仍可检索原话及有效修订；项目遵循自身阶段及证明 | 记录持久化、检索与项目隔离实例 |
| AC-08 | SC-04／BL-02 | 历史未知日期保持空；业务结束与档案缺项分开；收起不冒充归档齐备 | 只读核对及隔离验证 |
| AC-09 | SC-05／BL-06 | 来源范围可见；年度计划不冒充活动；同日三活动独立 | 匿名来源、草稿与核查记录 |
| AC-10 | SC-06 | 最新工时运行通过对账方可完成；旧定稿不能掩盖新异常 | Excel实际打开／重算、逐日与汇总对账 |
| AC-11 | D-06 | 桌面／窄屏、键盘、空状态、错误、未保存离开均可用 | 视口截图及交互结果 |
| AC-12 | D-05／GOV-01 | 删除失败无孤立或丢失文件，配套恢复可用，发布清单可核对 | 隔离复现、修复回归、恢复及发布记录 |

实施顺序：①本设计与原型核对 → ②首页和月检一条链路（GOV-04）→ ③其余五场景按风险逐条验收（GOV-05）→ ④版本、恢复与发布核对（GOV-06）。GOV-01风险复核可独立推进，未关闭相关风险前不发布受影响路径。不要同时重写所有页面。

进入月检实现的条件：本方案的对象、页面及完成规则无已知矛盾；实际必备模板／材料按具体期次核对；原型正常及反向路径已自检；未决定事项保持保守边界。用户只需核对真实业务差异，不承担发现基础保存、状态同步和模板损坏问题。

## 10 待明确的业务与制度边界

| 待定项 | 当前设计处理 | 实施触发点 |
|---|---|---|
| 旧通用清廉季度类型是否继续可新建 | 保留入口与历史，不自动迁移 | 改类型选择时 |
| 非月检工作是否要求实际报送 | 不自动新增报送强制条件 | 扩展报送功能时 |

| 实际截止日期与必备成果 | 以已确认通知及对象快照为准；原型仅示例 | 配置每类真实工作时 |
| 单位审批、签章、档案保管与资料分级 | 标为未取得适用制度，不新增法定义务或认证声明 | 用户要求制度／法规合规审查时 |

## 11 原型使用与验证记录

## 12 工作记录与持久记忆 D-07（本版新增）

### 12.1 用户体验

用户自己处理普通零散事项，只需在首页“记一句”或助手对话中明确告知。比如“今天把部门会议材料整理好，发给办公室了”。系统成功保存后回复：“已记下：10月21日，整理并发送部门会议材料。来源为你的告知。”附查看、更正、撤回入口，不要求选择工作类型、创建任务、上传成果或点击完成。

“记一下”不是必须的固定口令。工作台对话中明确表达自己的已发生工作或明确要求记录时，可以直接保存原话；提问、假设、引用他人的消息及助手生成内容不能自动登记为用户已做事项。识别不确定时先保留原话并标注性质待明确；是否需要保存本身不明确时再询问，不悄悄采集所有聊天。

保存原话和模型理解分开：原话可本地直接保存，解释、日期解析、分类和关联在此之后处理。只有存储成功才回复“已记下”；模型不可用也能记原话。新增记录可直接保存的授权仅限轻量记录，不扩展为修改项目字段、完成期次、报送、删除历史等操作。

### 12.2 取消的功能与保留边界

- 取消上版SC-02的通用单次工作新建、任务状态、必备成果、完成及归档流程；不把记录数量变成待办数量，不催用户补材料或办结。
- 实施时核对temporary-task、integrity-temporary及通用admin的一次性创建入口；admin若被用作有效周期工作，不按编码整类删除。不能只根据recurrence=once或无默认周期筛除，否则可能误伤项目和专项事项。
- 谈话、签署材料收集等已有专项事项，以及月检中的单次检查、项目阶段，不因为出现“单次”或没有周期就自动删除。用户此次指向上版通用单次工作；扩大取消专项办理须另明确具体范围。这些事项也允许轻量记录情况，但不由此跳过原有正式要求。
- 旧类型ID、历史工作、文件、版本及关联保留可查，不批量删库、不自动把旧计划转成已做事实。新建入口退出与历史查看分开；仍在办的旧事项是否保留提醒按实际清单核对，不能迁移时悄悄标完成或丢弃。

### 12.3 最小记录内容

| 内容 | 规则 |
|---|---|
| 原话和来源 | 原话必须保留，来源为用户输入及对应消息／录入记录；摘要只是辅助展示 |
| 告知时间 | 系统保存的真实时间，用于追溯，不代替事情发生时间 |
| 发生时间 | 明确日期按原话；今天／昨天按消息当时Asia/Shanghai解析；不说明则未知；“上周”等保留范围及精度，不编造某一天 |
| 内容性质 | 已做、进展、计划、未知分别标识；“准备发”不能变成“已发送”；“提交了申请”不能变成“已获批准” |
| 关联 | 可以没有工作对象；只有唯一且可信匹配才关联，重名或不明确时不猜；关联不修改正式工作状态 |
| 修订与撤回 | 更正保留原版本，正常检索只用当前有效版本；撤回后不再进入检索和新总结，可恢复；彻底删除另走明确操作 |
| 幂等与重复 | 同一提交用请求／消息ID防重；相同文字的不同事件不得自动合并；同一事件跨消息补充须明确关联后再合并展示 |

### 12.4 必须能找回和使用

“我这个月做了什么”按发生时间检索已做情况，并分别列出进展、计划和日期未知记录；不使用录入时间偷换业务月份，也不把记录条数直接当完成事项数。条件查询必须覆盖持久记录全集并分页，不能把提示词里最近几条或top-k记忆当作完整工作清单。

“上次给办公室发了什么”可按内容及关联检索，每条回答带记录编号、发生时间与原话入口。没有检索到就说明“没有找到相关记录”，不推定事情没发生。问答可按相关性取片段，但必须说明范围限制。

月／季／年度总结可纳入这些记录，标明“根据用户告知”，且用户可选择范围；计划不混成成果。系统已有的检查记录与用户口述可能描述同一件事，未经核对不能重复计数。记录也不能代替合同签章、报送回执或验收材料。相关记录更正／撤回后，已有总结保留旧稿但提示来源已变化，新查询和新总结采用有效版本。

### 12.5 现有基础与实施缺口

源码核对：[助手](../packages/server/src/domain/agent.ts)已有remember、relevantMemories和listMemories；[记忆接口](../packages/server/src/api/routes-agent.ts)已有直接保存原话入口；[助手界面](../packages/web/src/pages/Agent.tsx)已有记忆面板和更正相关组件。现有模型写操作先生成待确认动作，手动记忆可直接保存，因此“一句话直接记原话”应建立窄范围入口，不能全局取消写操作确认。

现有due_date是期限，created_at是录入时间，不能拿来充当业务发生时间。相关记忆候选查询存在最近200条及默认少量返回限制，不能支持完整月份盘点；结构化业务证据链对新增工作记录的检索、来源引用、版本变化仍须明确接入。现有删除记忆存在直接删除分支，不满足本设计的撤回保留要求。以上为静态核对，未执行生产记录写入。

实现优先扩展现有记忆机制，补充发生时间／范围、性质、来源标识、当前修订与撤回等必要语义；具体新增字段或表由迁移设计确定，不另造一套只写不读的笔记系统。存储、检索、问答和总结引用须一起交付。

### 12.6 正式验收补充

| 编号 | 场景 | 预期 |
|---|---|---|
| MEM-01 | 明确告知做过的事，保存后重启工作台 | 原话及来源仍可找到；无新任务、文书要求或待确认保存动作 |
| MEM-02 | 保存失败、网络断开、同一提交重试 | 不假称记住；保留输入；只保存一次 |
| MEM-03 | 今天做了、昨天做了、上个月做了、没说日期、准备明天做 | 发生时间与告知时间区分；未来计划不计已做；模糊时间保留精度 |
| MEM-04 | 超过200条后查询指定月份，含同文不同事件 | 不漏早期记录、不因同文自动合并；完整查询和相关片段区分 |
| MEM-05 | 更正或撤回一条已用于总结的记录 | 新查询排除旧有效性；旧总结提示来源变化；可追溯修订 |
| MEM-06 | 一条口述与正式月检描述同一检查 | 不自动重复计数，不绕过月检成果与报送条件 |
| MEM-07 | 旧单次工作与专项事项并存 | 通用新建办理入口退出；历史文件仍可访问，项目与专项流程不误删 |

以上为正式实现的验收条件。后续源码和隔离应用验证已记录于[实施记录38](38-工作记录与助手记忆实施-2026-10-21.md)，包括重启与跨对话查询；日常发布核验尚未执行。这里的HTML原型仍只验证原话输入、手填日期筛选、更正和撤回交互，不能替代真实应用验证。自然语言采用保守规则而非任意理解，正式总结暂输出记录回顾素材。
