### ⚠ 本期最重要的一次事故与教训

### ⚠ 第二个事故：检查器"逼"出了坏代码（`vision-e2e` 红灯的真相）

**现象**：`test:all` 里 `vision-e2e` 失败，报 `TypeError: Provided value cannot be bound to SQLite parameter 1`。

**完整因果链（每一环都实测过）**：

```

**关键认知**：那个数据库绑定错误**从头到尾都是症状**，不是病因。排查中依次**排除**了：参数绑定写法、`liveFilter` 误加在无 `deleted_at` 的表上、插入清单项代码被改坏、测试脚手架不播种、播种抛错被吞——最后用两个**决定性实验**定位：在临时库跑 `seedWorkTypesAndPositions()`（返回 `{workTypes:2, positions:11, materials:46, evidences:19}`，证明播种正常），再顺着"实例化时 `p.evidences` 为空"查回 SQL。

**教训（两条，都关于工具与规则本身）**：

### ⚠ 第三条教训：代理会拿"旧副本"当"真实库"，从而得出错误结论

撤销那路在交付说明里断言「**真实库停在 `009_integrity`、没有 `before_json`、`workbench` 没有 `deleted_at`**」。我直接查真实库，事实完全相反：

```
真实库迁移：001…014, 015_trash（15 条）
agent_action 有 before_json ? true      workbench 有 deleted_at ? true
workbench 2 | template 60 | agent_action 49      quick_check: ok

它是**读了自己早先复制的旧副本**（那次拷贝停在 013 或更早），并据此推出"这一列还没有加上"。两点要记：
1. **凡涉及"真实库现状"的结论，必须用同一时刻的真实文件复核**；代理在验证过程中会复制多份库副本，副本的迁移版本各不相同；
2. **WAL 模式下主库文件的 `mtime` 不会更新**（改动写在 `workbench.db-wal` 里），所以"主文件 mtime 很旧"**不能**用来推断"库没被改过"——这也被那一路误读了。

### 🚨 第四条教训：跨文件的签名改动不能按"单文件任务"派工（整树阻断事故）

**事故**：把 `core/trash.ts` 的 `restoreFromTrash` 半途改成 `async`，但另一个文件 `domain/agent.ts` 里的调用点没有跟上 `await`（注释甚至写着"必须 await"，而所在函数没加 `async`）→ `tsc` 报 **TS1308**，`node packages/server/src/index.ts` 直接 **`ERR_INVALID_TYPESCRIPT_SYNTAX`** → **服务无法启动**。

**后果的严重性**：不只是"某个功能没做完"，而是**所有人的端到端验证都做不了**（另一个代理的 30 项语义实测卡在 29 项），整条流水线停摆。修复过程：4 个类型错误 → 3 → 1 → 0（约 1 分钟，但期间无人能验证）。

**根因（我的派工错误）**：我把 `core/trash.ts` 划给"回收站"那路、把 `domain/agent.ts` 划给"撤销接通"那路。**改一个函数的签名是"跨文件传染"的改动**，它横跨了两条所有权边界——一边改了、另一边没跟上，树就断了。

**规矩（此后照做）**：
1. **改签名 / 改同步异步 / 改数据语义**这类会传染的改动，**要么只派给一个人**（连同所有调用点），**要么先冻结相关文件的所有权**再动；
2. 任何人做这类改动前，先 `grep -rn "<函数名>" packages/server/src` **列出全部调用点**，把它们纳入同一个任务；
3. 派工时**先核对"这个文件还有谁在改"**（本次已因漏了这一步造成过一次撞车风险）。

### ⚠ 第五条教训：检查器有层级盲区，不能互相替代

`check-runtime-load.mjs` 用 `node --check`（**语法级**），查不出 **"非 async 函数里的 `await`"（TS1308，类型级）**——本次整树阻断期间它**一直是绿的**。所以：

- **`check-runtime-load`（strip-only 语法）与 `tsc`（类型）必须都跑**，任何单独一个都会漏；
- 更一般地：**每个检查器都有它看不见的东西**，把"某个脚本绿了"当成"没问题"是本工作反复出现的错误模式（前有"只看 tsc 漏掉运行时加载失败"，今有"只看运行时脚本漏掉类型错误"）。**验收要多种手段交叉，不能只信一个绿灯。**
