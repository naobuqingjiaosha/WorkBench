# 协作信箱（Codex ⇄ 评审代理）

用途：两个执行体在同一个仓库里交接工作，**以文件和实测为准，不以会话自述为准**。

## 目录约定

```
docs/collab/
  README.md                          本说明（协作规则）
  NN-名称-日期.md                    编号任务：一方写"评审 + 补丁建议"，另一方在其下写"回复 + 实现记录"
  _acl-reports/                      本机权限诊断的备份与回滚脚本，不参与协作、可加 .gitignore
  archive/                           已结案的任务移到这里
```

命名沿用 `docs/` 的既有习惯：`NN-中文名称-YYYY-MM-DD.md`。编号在 `docs/collab/` 内独立，不接续 `docs/01–32`。

## 角色

| 角色 | 负责 | 不做 |
|---|---|---|
| **实现方（Codex）** | 改代码、跑测试、写实现记录与实测输出 | 不把"我认为改好了"当作验收凭据 |
| **评审方（本代理）** | 独立只读审计、跨模块一致性、文档与实现对账、给最小补丁 | 不在实现方未回复前改同一批文件，避免冲突 |
| **用户** | 业务口径、授权、发布与数据决策 | — |

## 每封信必须包含

1. **结论**：要解决什么问题，属于 P0/P1/P2。
2. **证据**：`文件:行号`、只读查询结果或命令输出；不允许"应该/大概"。
3. **补丁**：可直接落地的 diff 或完整替换代码，标明为什么顺序/边界不能反。
4. **验收**：可复制的命令 + 期望输出；改完由实现方把真实输出贴回。
5. **待确认**：不属于单方判断的事（业务口径、是否扩大范围）显式列出。

## 纪律（本项目已踩过的坑）

- **报告与代码不一致是常态**：已出现"报告说保留引用编号、代码实际不带""报告说外键完整、实际漏清理"。评审只看代码与实测。
- **测试在隔离库跑**：`npm test` 全部经 `scripts/test-isolated.mjs --unit …`；不要直接改动 `data/runtime/workbench.db` 或 `data/files`。
- **不提交、不重置、不整包发布**：Git 工作区有大量未提交改动，发布另走授权。
- **失败路径要响**：新增能力必须同时给"失败时可见"的证据，不能只贴成功路径。
