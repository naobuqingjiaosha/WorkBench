## 〇、用户已定口径（2026-10-20）

> "如果要彻底删除的话，那就把相关所有的文件一起删了。"

即：**彻底删除 = 删除该成果/工作台名下的全部关联记录与磁盘文件，不留孤儿行**。
不是"任务完成"，也不是"只删这一行"。

## 一、结论

`packages/server/src/core/trash.ts` 的彻底删除事务**漏了两个 NO ACTION 外键**，会直接整笔失败；另有两张无外键的链接表会留下孤儿行。

| # | 阻断/遗留 | 表·列 | 现状 | 触发场景 |
|---|---|---|---|---|
| 1 | **阻断** | `business_ai_run.artifact_id` | 未处理 | 删掉任何"业务助手生成过的成果" |
| 2 | **阻断** | `inspection_record.period_id` | 未处理 | 删掉任何"有检查记录的工作台"（清廉月检必然有） |
| 3 | 孤儿 | `doc_kb_link.artifact_id` | 无外键，未清理 | 删掉被制度引用的文书后，留下指向不存在文书的链接行 |
| 4 | 孤儿 | `compliance_exception.artifact_id / workbench_id` | 无外键，未清理 | 留下无主的"例外放行"留痕 |
| 5 | **顺序错误** | 先删磁盘文件、后开事务（`trash.ts:813-825` 对 `:830`；`:894-898` 对 `:899`） | 事务失败时文件已永久消失 → "记录在、文件没了" |

第 2 条尤其要紧：`inspection_record.period_id INTEGER NOT NULL REFERENCES work_period(id)`（`033_inspection_records.sql:3`，无 ON DELETE），而工作台事务在 `trash.ts:841` 先删 `work_period`。**只要该工作台有检查记录，彻底删除就必失败**。同时 `artifact.inspection_id REFERENCES inspection_record(id)`（`033:11`）决定了顺序必须是"先成果 → 再检查记录 → 后期次"。

`cli/reset.ts:52` 已把 `business_ai_run` 排进清理首位，说明"这类表要清"是已知结论，**只是 trash 漏了**。

## 三、建议补丁

> 只改 `packages/server/src/core/trash.ts` 与 `packages/server/test/trash-fact-review.ts`；不动迁移、不动 `data/`。

### 3.1 新增两个清理助手（放在 `purgeRows` 之前，约 `trash.ts:752`）

```ts
/** 业务助手运行记录（035）引用 artifact 无 ON DELETE；parent_id 自引用须子行先删。 */
function purgeBusinessRunsForArtifacts(where: string, params: (string | number)[]): void {
  if (!get("SELECT 1 FROM sqlite_master WHERE type='table' AND name='business_ai_run'")) return;
  const ids = all<{ id: number }>(
    `SELECT id FROM business_ai_run WHERE artifact_id IN (SELECT id FROM artifact WHERE ${where}) ORDER BY id DESC`,
    params,
  ).map((r) => r.id);
  for (const runId of ids) run('DELETE FROM business_ai_run WHERE id = ?', [runId]);
}

/** 无外键的链接/留痕表：彻底删除要一起清，否则留下指向不存在文书的行。 */
function purgeLooseLinks(where: string, params: (string | number)[]): void {
  for (const table of ['doc_kb_link', 'compliance_exception']) {
    if (!get("SELECT 1 FROM sqlite_master WHERE type='table' AND name=?", [table])) continue;
    const cols = all<{ name: string }>(`SELECT name FROM pragma_table_info(?)`, [table]).map((c) => c.name);
    if (cols.includes('artifact_id')) {
      run(`DELETE FROM ${table} WHERE artifact_id IN (SELECT id FROM artifact WHERE ${where})`, params);
    }
    if (table === 'compliance_exception' && cols.includes('workbench_id')) {
      run(`DELETE FROM ${table} WHERE workbench_id IN (SELECT id FROM workbench WHERE ${where})`, params);
    }
  }
}
```

### 3.3 工作台事务重排（`trash.ts:830-855`）

现有顺序"先删期次、后删成果"与两条外键方向相反。**必须**改成下面这个顺序：

```
1  DELETE artifact_search WHERE wb_id
2  DELETE quick_todo / timesheet_run WHERE workbench_id
3  DELETE workflow_event / period_material WHERE period_id IN (该工作台的期次)
4  UPDATE agent_memory SET period_id=NULL WHERE period_id IN (…)
5  purgeRows('artifact', 'workbench_id = ?')        ← 先成果（连带 fact_review、business_ai_run、级联子表）
6  DELETE inspection_record WHERE period_id IN (…)  ← 成果没了才能删检查记录
7  DELETE work_period WHERE workbench_id            ← 检查记录没了才能删期次
8  DELETE work_period_rule WHERE workbench_id
9  DELETE checklist_item / purgeRows('position_instance')
10 DELETE compliance_exception WHERE workbench_id   ← 无外键，显式清
11 DELETE generation_log / archive_proposal / agent_memory WHERE workbench_id
12 purgeRows('workbench', 'id = ?')
```

原 `:839` 的 `UPDATE artifact SET work_period_id=NULL` 在新第 5 步面前已无必要（成果整批删除）；保留也不影响，但不能挪到第 5 步之后。

### 3.4 删磁盘文件移到事务提交之后

工作台分支（原 `:813-825`）与单文件分支（原 `:894-898`）都把 `removeArtifactFile` / `recyclePlatformDirs` 移到 `tx(...)` 之后：

- 事务失败时文件必须还在，否则"回滚只回库、文件已经没了"；
- `recyclePlatformDirs` 只回收空目录，必须在文件真的删掉之后调用。

`unlocatable` / `skipped` 的告警位置不变（仍能看到哪些文件没删成）。

## 五、待确认（默认值已给，用户可推翻）

1. **助手问答记录**：随成果一起删（用户 2026-10-20 已定"一起删"）。
2. **聊天历史（`agent_message` / `agent_session`）**：**默认不删**。它们不按工作台归属（`agent_session` 只有 id/title/时间），无法界定范围；删了会连带丢失其他对话。`business_ai_run.message_id` 因此不会阻断（消息行保留）。
3. **共享输入副本**（被其他工时运行引用的源 XLSX）：**保持现有规则**（仍被引用则跳过并回报），不因"一起删"而误删别的记录在用的文件。
4. **`--snapshot` 分支**：写死 `artifact #265 / workbench #98`，真实库中这批测试数据已被用户清空，该分支现在**静默通过而不再证明任何事**；建议改为自造数据或删除。
5. **`inspection_record` 与期次绑定的语义**：检查记录属于期次，随期次一起删没有歧义；但如果产品上要求"检查记录应长期保留供年度台账回溯"，则删工作台会一并清掉台账来源——请用户确认这是期望行为。
