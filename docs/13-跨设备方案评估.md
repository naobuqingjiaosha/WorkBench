## §1 一句话现状

**文件可以跟着用户走，状态不能跟着用户走。**

| 事实 | 依据（已核实） |
|---|---|
| 文件可以放在同步盘/工作台外部目录：绑定后文件直接落在用户自己的目录里 | `workbench.external_root` + `artifact.root_kind='external'`，`packages/server/src/db/migrations/010_folder_binding.sql:17-19` |
| 绝对路径不落库，由「所属根 + `file_rel`」现算 → 换机器/换盘符后**路径本身不会失效** | `010_folder_binding.sql:9-12` |
| **数据库固定在本地**磁：`dataRoot` 只管文件，不管库 | `packages/server/src/core/config.ts:31-38` |
| 服务是单进程本地服务：单实例锁 + 只监听回环 + 会话 token | `packages/server/src/index.ts:39`、`core/server-lock.ts:43`、`core/request-guard.ts:6-11` |
| 已有自动备份（一致性快照 + 保留策略）与一键恢复 | `core/backup.ts:576`（快照）、`core/backup.ts:696`（保留）、`core/backup.ts:902`（恢复） |

**分叉的三条真实场景**（用真实字段名）：

1. **A 机登记、B 机看不见**：台式机上绑 `D:\…\2.安全` 并登记 17 张照片 → `artifact` 里 17 行、`root_kind='external'`、`file_rel` 相对 `external_root`。笔记本装上工作台、绑同一个 iCloud 文件夹 → **那 17 行记录在笔记本的库里根本不存在**，界面显示 0 张。用户的 17 个文件好端端地在文件夹里，系统说「没有这件资料」。
2. **B 机重复纳管、两边互相覆盖**：笔记本上重新扫描纳管同一批文件 → 笔记本库里 17 行、**新的 artifact id**；两台机器的 `artifact.id`、`workbench.external_root`、`position_instance.folder_rel` 从此各说各话，任何一边做的登记在另一边都是脏数据。
3. **库文件被同步拆散**：A 机正在写（WAL 模式），`workbench.db`、`workbench.db-wal`、`workbench.db-shm` 三个文件在上传队列里各有各的进度 → B 机拿到的是「某个瞬间的库 + 另一个瞬间的 WAL」，或「新库 + 旧 WAL」。

## §2 对比表

**风险等级**：低 = 不会造成不可逆数据损失；中 = 会丢一段时间的登记成果但原文件还在；高 = 可能损坏数据库或丢失记录；极高 = 可能同时损坏库并把无认证的服务暴露到网络。

| # | 方案 | 需要改什么 | 风险等级 | 推荐与否 |
|---|---|---|---|---|
| 1 | **保持现状（单机）** | 什么都不改 | **低** | ✅ 推荐（基线） |
| 2 | **库也放同步盘**（iCloud/OneDrive/坚果云） | 改配置即可（`WORKBENCH_DB` 指向同步盘），但**要安全就必须改代码**：sync 检测、跨机锁、启动拒绝 | **高** | ❌ 不推荐 |
| 3 | **库放移动硬盘 / 局域网共享** | 改配置（`WORKBENCH_DB` / `WORKBENCH_RUNTIME_DIR`） | **高**（SMB 同 2，另加性能与锁问题） | ❌ 不推荐 |
| 4 | **手动迁移**（库 + `data/` 整体拷到另一台） | 不改代码；只做操作 | **低**（前提：停服务 + 校验） | ✅ 推荐（换机时用） |
| 5 | **服务跑在常开机上，另一台局域网访问** | **必须改代码**：放开 `host` 监听、扩展会话 token 到跨机认证、加登录与权限 | **极高** | ❌ 当前不做 |
| 6 | **折中：主力机 + 备份快照同步出去** | 不改代码；改 `backup.dir` 指向另一块盘或同步目录 | **低** | ✅✅ **首选推荐** |
| 7 | 两台机器各跑一份，互不干扰 | 不改代码；纪律上要求「一台负责一个工作台」 | 低 | ⚠️ 可作为过渡（分裂状态） |
| 8 | 真云端多租户 | 重做 | — | ❌ 明确不做（`docs/11` §9） |

## §3 逐条评估

### 3.1 保持现状（单机）—— 方案的基线

**怎么做**：什么都不改。文件可以（也建议）放在 iCloud 等同步目录里，通过绑定落盘；库留在本地 `data/runtime/workbench.db`。

**换台电脑会发生什么（已核实的行为）**：另一台机器的库里没有 `workbench` / `artifact` / `position_instance` 记录，所以工作台列表是空的；而用户的文件**在**（iCloud 会同步文件夹本身）。也就是说，**丢的不是文件，是「这是什么、属于哪个阶段、完成到哪一步」**。

**代价**：换机器 = 重新建工作台、重新绑目录、重新纳管（且纳管会新建一套 id）。没有别的代价。

**风险**：低。唯一风险是误解——用户以为「文件在 iCloud，所以系统在 iCloud」。

**不适用**：用户需要两台机器**日常交替使用同一批状态**。这种情况现状直接不成立。

---

### 3.2 把数据库也放进同步盘 —— **必须把风险讲透**

> ⚠️ **独立警告：两台机器同时打开同一个同步盘上的库 = 库可能损坏，且损坏后没有任何自动机制能判断「哪一份是对的」。在补上多实例检测之前，不要打开这个用法。**

**怎么做（两条路，风险都不低）**：
- 配置路：`WORKBENCH_DB` 指向同步盘（`core/config.ts:38` 已支持），**不改一行代码就能跑起来** —— 这正是它危险的地方：能跑通不代表安全。
- 安全路（要改代码）：启动时检测库所在卷是不是已知同步目录、检测同库是否被第二个实例打开、检测到就**拒绝启动**或强制本地运行目录（`docs/11` B4-15 第 4 条）。

**五条风险，逐条给依据**：

| 风险 | 为什么 | 依据 |
|---|---|---|
| **WAL 在同步盘上不被支持** | SQLite 官方明确：WAL 需要各进程共享一小块内存（wal-index），**所有进程必须在同一台机器上；WAL 不能跨网络文件系统工作** | SQLite 官方 [Write-Ahead Logging §1](https://sqlite.org/wal.html)（未验证：本文不做实测，只引用官方结论） |
| **`-wal`/`-shm` 与库文件被拆散** | 官方原话：WAL 文件是数据库持久状态的一部分，拷走库时要连 WAL 一起带走；**库与 WAL 一旦分离，先前已提交的事务可能丢失，库可能损坏**；删除 WAL 的唯一安全方式是打开再关闭连接 | SQLite 官方 [WAL §4](https://sqlite.org/wal.html)（未验证） |
| **网络/同步盘的文件锁不可信** | 官方原话：有些文件系统的锁实现有 bug，**网络文件系统尤其如此，NFS 尤甚**；锁不可靠时两个进程同时访问就可能损坏库 | SQLite 官方 [How To Corrupt §2.1](https://sqlite.org/howtocorrupt.html)（未验证） |
| **只拷 `.db` 不拷 journal/WAL 是官方点名的损坏方式** | 官方列出的必损操作包含「拷贝数据库文件而未同时拷贝它的 journal」 | SQLite 官方 [How To Corrupt §1.4](https://sqlite.org/howtocorrupt.html)（未验证） |
| **两台机器同时写** | 本平台自己的单实例锁**只防同机双开**：锁文件里是本机 `process.pid`，用 `process.kill(pid,0)` 判断存活 —— 在另一台机器上读到的 pid 与本机无关 | `core/server-lock.ts:23`（锁路径 = `dirname(DB_FILE)/server.lock`）、`core/server-lock.ts:33`（`process.kill(pid,0)`）、`core/server-lock.ts:43`（只拒绝同机的活进程）。**跨机无保护（已核实）** |

**一个本地观察到的、同方向的证据（已核实，但成因未验证）**：本机 `data/backups/` 里现在实际有 12 个文件，其中含 4 个 `-shm`/`-wal` 与 4 个 `.partial-*-shm/-wal` 残留：

```
workbench-daily-20261002-101849.db       811008
workbench-daily-20261002-101849.db-shm    32768   ← 残留
workbench-daily-20261002-101849.db-wal        0   ← 残留（0 字节）
workbench-daily-20261002-101849.db.partial-10116-shm  32768  ← 残留
workbench-weekly-…（同样四个）
```

代码里 `removeSidecars()`（`core/backup.ts:287`）在 `finalizeSnapshot()` 之后是**要删**这些边车的，快照也被切成了单文件模式（`core/backup.ts:305-319`）。**残留的成因我没有实验验证**（推测是本机连接持有句柄导致删除失败；`core/backup.ts:311` 只吞掉了收尾失败）。它证明的是**一句更保守的话**：`-wal`/`-shm` 与主库文件的「在一起」并不是天然稳定的，连本地都会留下伴生文件；一旦这套文件被同步盘按文件粒度搬运，风险只会放大。**需实测**才能确认成因与是否影响可恢复性。

**不适用**：任何「两台机器都可能同时开着工作台」的用法；以及库放在 OneDrive/坚果云这类**按文件同步**（不是块存储）的目录。

### 3.3 库放移动硬盘 / 局域网共享

**怎么做**：`WORKBENCH_DB` 指向 `E:\…\workbench.db`（移动硬盘）或 `\\NAS\share\workbench.db`（SMB）。

**代价与风险**：
- **网络共享（SMB）同 3.2 全部风险**，且更确定：SQLite 官方把「锁实现有 bug 的网络文件系统」列为首要损坏来源（[How To Corrupt §2.1](https://sqlite.org/howtocorrupt.html)，未验证）。
- **性能**：WAL 的 checkpoint（把 WAL 内容搬回主库）本身就是大量随机 seek，代码里 `PRAGMA synchronous = NORMAL`（`db/index.ts:27`）意味着 checkpoint 是主要 fsync 点（[WAL §2.3](https://sqlite.org/wal.html)，未验证）。走网络文件系统时这块会明显变慢 —— 具体倍数**需实测**。
- **`busy_timeout = 8000`（`db/index.ts:26`）**：网络盘上锁获取本来就慢、还可能假成功，8 秒的超时只是缓解报错，不解决锁不可信。
- **移动硬盘特有的风险**：盘符会变（`E:` / `F:`），锁文件里记的 pid 与本机无关（同上），拔盘瞬间正在写 → 未 checkpoint 的内容只在 `-wal` 里。

**不推荐**：移动硬盘仅可作为**备份目录**（见 3.6），不适合作为运行时库所在。

### 3.4 手动迁移（库 + 数据目录整体拷到另一台）

**这是当前能力下唯一「换机也能继续用」的正路，且不需要改代码。**

**怎么做（具体步骤）**

**第 0 步 · 确认没有绑外部的状态**：如果某工作台绑过外部目录（`workbench.external_root` 非空），该目录**不在迁移包里**（它本来就在用户自己的文件夹里，通常已由 iCloud 同步）。迁移后新机器上这个绝对路径必须仍然存在；**路径变了就要重新绑定**（`docs/10` §7.4：绑定目录消失会明确报错）。

**第 1 步 · 停服务**：
- 关闭工作台窗口/进程；确认 `data/runtime/server.lock` 不再被活进程持有（锁里若还有 pid 且那个进程活着，`acquireServerLock()` 会拒绝启动，`core/server-lock.ts:43`）。
- **必须停服务**：不停服务等于在 WAL 还开着的时候搬库。

**第 2 步 · 迁移前先产出一份「可验证的凭据」**（复用已有备份能力，不手拷）：
- 界面「设置 → 备份 → 立即备份」，或 `POST /api/backup/run`；随后 `GET /api/backup/:id/verify`。
- 合格判据：边车 `.db.json` 里 `verify.ok = true`、`quickCheck = "ok"`、`foreignKeyCheck = 0`、`workbenchCount` 与界面一致（本机现成样例：`data/backups/workbench-daily-20261002-101849.db.json` 记 `workbenchCount: 2`）。
- **记下基线数字**：工作台数、模板数、`artifact` 行数。

**第 3 步 · 拷贝**（三样都要，缺一不可）：

| 拷贝对象 | 说明 |
|---|---|
| `data/backups/` 里刚校验通过的那一份 `workbench-*.db` + `.db.json` | **首选凭据**：它是 SQLite 在线备份 API 产出的单文件快照，已被切成 DELETE 模式（`core/backup.ts:305`），不含必须一起搬走的 WAL |
| 整个 `data/` 目录 | 含 `data/files`（未绑定工作台的文件）、`data/runtime`（库、日志）、`data/backups` |
| `workbench.config.json` | 注意里面的 `dataRoot` 是**绝对路径**（现为 `D:/project/工作台/data/files`，`workbench.config.json:4`）；新机器路径不同就要改 |

**第 4 步 · 校验（迁移后必做）**：
- 在**新机器**上启动服务 → 它会对库跑迁移与 `bootstrap`（`core/bootstrap.ts:17-26`）。
- `GET /api/health` 返回 `dbFile` 与 `dataRoot`（`api/routes-core.ts:63-71`）—— 确认新机器读到的是**新路径**，不是你插着的旧盘。
- 对拷过去的快照跑一次校验（`GET /api/backup/:id/verify`，或直接打开库跑 `PRAGMA quick_check` + `PRAGMA foreign_key_check`），逐表行数与第 2 步基线比对。
- 逐项核对：工作台数量、随机 3 个工作台的阶段/清单/文件数、1 个已绑定工作台的 `file_exists`。
- **指纹比对的正确姿势**：比 `.db` 的 sha256 只对**同一时刻的静默副本**成立；WAL 模式下主库文件的 `mtime` 不随写入更新（`docs/14` 第三条教训），**不要用「主文件 mtime 很旧」推断「库没被改过」**。

**第 5 步 · 旧机器**：确认新机器一切正常前**不要删**旧机器上的任何东西；迁移不是搬运，是复制。

**检查清单（可逐条打勾）**

| # | 检查项 | 判据 |
|---|---|---|
| 1 | 已停服务 | `server.lock` 无活进程 |
| 2 | 已产出一份通过校验的快照 | `verify.ok = true` |
| 3 | 已记录基线 | 工作台数 / 模板数 / `artifact` 行数 |
| 4 | 已拷备份快照 + `data/` + `workbench.config.json` | 三样齐全 |
| 5 | 新机器 `dataRoot` 已按新路径修正 | `workbench.config.json` 与实际目录一致 |
| 6 | 新机器启动成功、`/api/health` 路径正确 | 不是旧盘 |
| 7 | 逐表行数与基线一致 | 差值 = 0 |
| 8 | 绑外部的绝对路径在新机器上仍存在 | 不存在则重新绑定 |
| 9 | 旧机器数据保留 | 至少留到新机器确认可用 |

### 3.5 服务跑在一台常开的机器上，另一台通过局域网访问

**需要改什么（都不是小改）**：

| 改动点 | 现状 | 要变成 |
|---|---|---|
| 监听地址 | `SERVER_HOST` 默认 `127.0.0.1`（`core/config.ts:43`、`workbench.config.json:6`），`app.listen({host: SERVER_HOST})`（`index.ts:259`） | 放开到 `0.0.0.0`，并处理多网卡/防火墙 |
| 来源校验 | **只允许本机来源**：host / origin 主机名必须是 `localhost`/`127.0.0.1`/`[::1]`，端口必须是 8787 或 5273，且拒绝 `sec-fetch-site: cross-site`（`core/request-guard.ts:6,8`） | 换成真正的跨机认证 |
| 会话 token | 每次启动 `randomBytes(32).toString('hex')`（`request-guard.ts:5`），由 `/api/session`（`request-guard.ts:14`）**无认证地发给本机页面**，前端拿它放进 `x-workbench-token` 头（`packages/web/src/api.ts:15-16`）；只对非 GET/HEAD/OPTIONS 的 `/api/*` 校验（`request-guard.ts:9-12`） | 真正登录 + 每用户凭据 + 授权 |
| 传输 | HTTP 明文 | HTTPS 或隧道 |
| 敏感配置 | 库里存 `ai_provider.api_key`；`scope='secret'` 只在**响应**里打码（`api/routes-core.ts:85-89`），**库里是明文** | 静态加密与密钥管理 |

**安全影响（必须写清）**：
- **一旦对外监听，就等价于把一个没有登录权限的平台暴露到网络上。** 现在的 token 机制是为「同机浏览器」设计的：它防的是**别机网页/跨站请求**（靠来源校验），而不是「知道地址的任何人都能连」。**它不具备跨机认证能力**——token 本身就由无认证的 `/api/session` 发放，任何能访问该端口的人都能先拿 token 再调写接口。
- 还都是**只读接口不校验 token**（`request-guard.ts:9`）：`GET /api/system/info` 会返回 `dataRoot`、`dbFile`、`dirs`、`node`、`platform` 和全部 `app_setting`（`routes-core.ts:73-83`）—— 路径、配置、结构直接对局域网公开。
- 库里的 `ai_provider.api_key` 一旦被读走，是**真金白银**的损失。
- 结论：**在补上真正的登录与权限之前，不做这件事。** `docs/11` §9 的口径一致：「出现多人同时用同一个库，先做局域网共享 + 库锁」。

### 3.6 折中方案（**首选推荐**）：主力机 + 备份快照同步出去 + 换机器时恢复

**怎么做**：
1. 日常只有**一台主力机**跑工作台，库在本地盘（现状）。
2. 把 `workbench.config.json` 的 `backup.dir` 指到**另一块物理盘**或**同步目录**：

```json
{ "backup": { "auto": true, "hour": 3, "dir": "D:/备份/工作台", "keepDaily": 7, "keepWeekly": 4, "weeklyDay": 1 } }
```

说明（已核实）：`dir` 支持绝对路径，相对路径按项目根解析（`core/backup.ts:148-150`）；**只能改这一个目录**，且**不许落在 `data/files` 里面**（`core/backup.ts:171-178` 会直接拒绝）。
3. 快照本身已经是「一个文件拿走就能用」：在线备份 API 产出 + 切成 DELETE 模式 + `quick_check`/`foreign_key_check` 校验 + 同名 `.db.json` 边车记录结论（`core/backup.ts:614-647`）。
4. 换机器时：在目标机器上装好工作台 → 把同步过来的快照交给它 → **用「一键恢复」**（`core/backup.ts:902`），而不是手工覆盖文件。恢复流程自己会：先校验备份 → 先给当前库做一份 `pre-restore` → 停写 → 关库 → 原子替换 → 重开校验 → 不行就退回（`core/backup.ts:886-901` 的七步）。

**代价**：不是实时同步；快照按天（+周）粒度，最坏丢一天。两台机器**不能同时开着**同一个库（本方案根本不做同一时刻双开）。

**为什么它是当前最稳的**：① 不改一行代码；② 走的是产品自己**已经验证过**的路径（快照 + 恢复有校验、有回退、有留证）；③ 不存在「两个进程同时写同一个库」这个唯一的不可逆风险；④ 冲突不是被自动解决，而是**根本不会被制造出来**。

**不适用**：需要「两台机器当场切换、继续同一份未提交的操作」；或者不能容忍一天粒度的回退。

## §4 推荐与不推荐（结论）

| 结论 | 内容 |
|---|---|
| ✅✅ **首选** | **方案 6**：主力机 + 备份快照同步到另一块盘/网盘 + 换机器时恢复。日常零风险，换机路径有校验有回退。 |
| ✅ **配合** | **方案 1**（平时保持单机）+ **方案 4**（真换机且要连带 `data/files` 与绑定时，按 §3.4 清单手工迁移）|
| ⚠️ **可过渡** | 方案 7：两台机器各管各自的工作台（状态天然不冲突），但用户必须清楚「A 机看不到 B 机的工作台」。 |
| ❌ **不推荐** | 方案 2（库进同步盘）、方案 3（库放移动硬盘/局域网共享）：官方文档级的损坏风险，且本平台的跨机保护为零（`server-lock.ts` 只防同机）。 |
| ❌ **当前不做** | 方案 5（局域网共享服务）：**没有登录与权限就不是安全的产品**，现状 token 只是同机浏览器的防伪，不是认证。 |
| ❌ **明确不做** | 方案 8（云多租户），同 `docs/11` §9。 |

**触发条件**：如果用户明确要「两台机器日常切换同一份状态」，才去评估方案 5；且**必须先补完 §5 的清单**，不允许「先把 `host` 改了先用着」。

## §5 如果将来真要做多设备，需要补哪些能力（**不是当前范围**）

> 这一节是「将来要花多少钱」的清单，不是排期。`docs/11` §9 已把「云多租户」列为不做；本节只覆盖**局域网/多设备**这条线。

| # | 要补的能力 | 为什么必须 | 现状缺口（已核实） |
|---|---|---|---|
| 1 | **真正的登录与权限** | 一旦跨机，来源校验就失效；token 由无认证接口发放，等于没有认证 | `request-guard.ts:6-14` 只有「本机来源 + 一次性 token」，无用户概念 |
| 2 | **跨机库锁 / 单写者** | 现在只有同机进程锁 | `server-lock.ts:33` 用本机 pid 判活，跨机无效 |
| 3 | **库所在位置检测** | 检测到库在同步盘就拒绝启动或强制本地运行目录 | 无任何检测 |
| 4 | **多实例检测** | 同一库被两个进程打开时必须能发现并拒绝 | 无 |
| 5 | **冲突解决 / 重建索引入口** | 文件与库不一致时（B 机看到文件但无记录）：扫描目录 → 差异报告 → **人确认后**补登记 | `docs/11` B4-15 第 4 条列的「重建索引」入口**不存在** |
| 6 | **HTTPS / 传输加密** | 局域网也是网络，明文传 `api_key` 与全部业务数据 | 无 |
| 7 | **敏感配置的静态保护** | `ai_provider.api_key` 在库里是明文，只在响应里打码 | `routes-core.ts:85-89` 是展示层打码，不是存储加密 |
| 8 | **同步/导出的版本与格式约定** | 两台机器版本不同时，快照要能判断「能不能恢复」 | 有迁移兜底（`bootstrap.ts:21` 恢复时会跑迁移），但没有版本门槛提示 |
| 9 | **WAL 处理策略的显式化** | 「能不能放同步盘」应由程序判定，不能靠用户读文档 | 无 |

**这九条里，1、2、3、4、6 是「不做完就不该开放多设备」的硬前置。**

## §8 诚实声明

1. **本文没有做任何同步盘实测。** 所有「同步盘会怎样」的判断来自 SQLite 官方文档与代码读法，不是实验。
2. **本文没有动任何代码、配置或数据。** 只新增本文件一个 Markdown。
3. **没有验证的第一风险**：用户看完选了方案 2 或 5 并直接改配置跑起来 —— 方案 2 能「跑通」，正因为能跑通才危险。所以 §3.2 开头是独立警告框。
4. **剩余风险里最可能先出事的一条**：备份目录仍与库同盘（`backup.dir = data/backups`），且**备份不含 `data/files` 里的用户文件**（`workbench.config.json:3` 已写明）—— 也就是说，若用户文件不在任何同步盘里，本方案的「备份」只保护状态，不保护文件。
