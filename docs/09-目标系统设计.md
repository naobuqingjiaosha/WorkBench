# 工作台 · 目标系统设计（应该达到的水平）

> 这份文档回答一个问题：**要把现在这个能跑的工作台，做到它应该有的水平，它应该长什么样、按什么顺序做。**
>
> 读者设定：未来的我自己 + 一个接手的技术同事。所以每一条都写清"为什么需要、怎么做、怎么算做完、依赖什么"，
> 并且**明确写出被否决的方案和否决理由** —— 否则接手的人会把已经踩过的坑再踩一遍。
>
> 写作时间：2026-09-30 之后。文中"现状"一节的所有数字都是**在真实库和真实磁盘文件上跑出来的**，
> 不是引用文档（见第 1 节的核实方法；我没能核实的部分在第 7.2 节逐条列出）。

---

## 0. 这份文档怎么读

- **第 1 节**是现状基线。后面所有设计都以这一节的数字为准；数字变了要回来改这一节。
- **第 2 节**是设计原则（"宪法"）。原则不是口号，每条都配一个"违反它会出什么事"的实例。
- **第 3 节**是能力地图：每个域"现在到哪、应该到哪、差值是什么"。
- **第 4 节**是分域详细设计（含 4.10 的质量与验收体系），可以单独抽出来当施工图用。
- **第 5 节是路线图**，也是这份文档最该被反复看的部分。
- **第 6 节**写"明确不做的事"。
- **第 7 节**是我核实了什么、没核实什么（诚实性声明，先看 7.2 再引用本文任何数字）。
- **第 8 节**是一页速查，可以打印贴墙。
- 与 **`docs/08-现状系统设计.md`（As-Is）** 的分工：08 回答"现在是什么样"（含它的 S1–S11 风险编号），本文回答"应该是什么样、按什么顺序做"；第 5.7 节给出 S 编号 → 阶段任务的对应关系。

### 1.1 核实方法

在项目根目录上用只读方式取数，不依赖任何文档描述：

| 取数对象 | 方法 |
|---|---|

## 2. 目标定位与设计原则

### 2.1 这个系统到底是什么

一句话：**它是这位办事员的"文书车间 + 材料档案室 + 制度口径检查员"，不是一个更聪明的聊天框。**

- 输入是**零散的、口头的、不完整的**交代（"这个月的检查做了，两处问题，材料已经从甲方那拿到了"）。
- 输出必须是**能直接交出去的成品**：排版正确的 Word/Excel、页码对得上的证明文件、能过审计的影像和台账。
- 中间所有"我记一下""我算一下""我查一下制度怎么写的""我把照片贴进去""我按上个月那份改改"——这些**重复劳动由系统接管**，人只做两件事：**判断**和**确认**。

用户的原话定了标准，我把它翻译成可验收的指标：

| 用户说的 | 翻译成系统指标 |
|---|---|
| "帮我搭建完善的系统，而不是帮我完善项目" | 新工作类型的接入成本必须低到**用户自己能在界面上配完**（加字段、加模板、加影像规则、加口径校验），不需要改代码、不需要叫我 |
| "我没空仔细操作或设置，直接交代给大模型" | 一句话交代 → 系统自己找出该做哪几件事、缺什么、下什么文书、用哪些照片 → **列成清单等确认**；不是"你必须先学会六个页面的操作" |
| "填表、写文书、整材料、留证据、对口径" | 这五件事各自的"人只做判断"状态：填表=已核对；写文书=已读改；整材料=已清点；留证据=已看样；对口径=已确认例外 |

### 2.2 十一条设计原则（每条都配一个已经发生的反例）

**P1. 确定性归确定性，模型归模型。**
凡是能用死规则算出来的值（今天是几号、合同金额的大写、编号的下一号、清单完成度、变量取哪个档案字段），**一律不许经过模型**。模型只负责"把已知事实组织成通顺的公文语言"和"从非结构化资料里认字段"。
> 反例：`domain/archive.ts` 的解析链（系统变量 → 别名 → 原生字段 → 未命中）就是这条原则的正面样板，132 个别名、零模型调用、结果可复现。要守住它，不要为了"更智能"把别名匹配换成模型判断。

**P2. 一切写入可追溯、可撤销。**
写操作必须能回答三个问题：谁改的（人/助手/规则）、改成什么（前值→后值）、怎么撤销（恢复入口在哪）。
> 反例：`DELETE /api/workbenches/:id` 一次 HTTP 调用就把库记录和整个磁盘目录一起清掉，撤销入口不存在（D6）。

**P3. 宁可说"不知道"，也不编造。**
不确定的一律写 `【待补：缺什么】`，并且**在界面上把它当成一件事**（计数、置顶、拦"定稿"），而不是当成文档里的一段文字。
> 反例：模型写"要求 3 个工作日内整改"，资料里没有这个期限（`docs/04` 实测：qwen-flash 2/3 编造）。这类句子会被追着问依据。

**P4. 同一输入必得同一结果。**
同一模板 + 同一档案 + 同一天，跑两次必须产出**字节级一致**的文件（除非显式换了模型或改了风格设置）。
> 反例：`temperature` 没有按"可复现"分层；EXIF 时间、`_今天` 这类变量在不同时刻取值不同却没有在文档里留"取值时刻"的痕迹。

**P5. 用户能自己扩展，不用改代码。**
字段、别名、模板、影像规则、口径校验规则、提示词，全部是**数据**而不是代码。加一条制度口径检查不该需要我发一次修复包。
> 反例：`prompt_template` 表存在但代码不读，提示词硬编码在 `domain/generate.ts:190-230`；`docs/01` 第 494 行自认"要在模板里写别的占位符写法，得先改 `core/template.ts`"。

**P6. 失败要响，不能静默。**
任何"我以为成功了但实际没生效"的路径都是缺陷，优先级等同数据损坏。
> 反例：归档一个不存在的工作台曾经返回 `200 {archived:true}`（`docs/06` 已修）；坏模板出文书返回 `200` + 打不开的文件（D1，**未修**）。

**P7. 程序坏了，数据不能坏。**
所有资料是磁盘上普通文件夹里的普通 Office 文件；数据库可以重建，文件不能重造。**备份必须自动化，且必须验证过能还原** —— 手动命令等于没有备份。
> 反例：`.repair-delivery/修复前备份-20260930-105059/` 证明了"出事时才回滚"这条路走通过，但它是人肉流程。

**P8. 一行数据只有一个真源。**
同一件事有三个字段表达，就一定会分歧，就需要靠"每次启动修一遍"来维持。
> 反例：`status` / `archived_at` / `archive_status`（D5），已经产生过"取消归档后工作台消失"的死循环 bug，现在靠 `startup-repair.ts` 打补丁。

**P9. 自动化的上限由数据质量决定，先把数据做对，再谈智能。**
覆盖率 36% 的时候，换更强的模型只能让那 64% 的手工项写得更漂亮一点，接管不了它们。
> 推论：提升映射覆盖率的优先级**高于**换模型、高于调提示词。

**P10. 每一个"看起来还行"的结果都要有机器能判的判据。**
"文书质量好不好"不能只靠人读。可判的代理指标：数字/日期是否全部来自事实集（幻觉检测）、`【待补】` 是否用在该用的地方、格式是否合法、口径校验是否通过。
> 反例：验收报告结论是"272 项全绿 + 链路打通"，但同一份报告第 263 行写着生成件打不开 —— 因为**没有一条断言检查过产物的可读性**。

**P11. 界面上出现的能力，必须在真实链路里被调用过。**
`wired: true` 这个字段（`ai/providers.ts:47`）是对的方向，要推广到所有能力：EXIF、初检、规则库，都要有"最近一次真实使用时间"，长期为空就在界面上标出来。
> 反例：`artifact.version`、`evidence_rule.sample_artifact_id`、`checklist_item.done_by`、`prompt_template` 都是"建了没用"的列/表。

## 3. 目标能力地图

每一域写三行：**解决用户的哪个具体麻烦 → 现在到哪 → 应该到哪**。"差值"就是后面要干的活。

### 3.1 模板与文书生成

- **麻烦**：每次出文书都要手工改带编号的表格（工程量清单、设备清单、人员名单），每次都要开 Word 手动插照片、调大小、加图注，改完还常常忘改"共 X 页""附照片 X 张"。
- **现在**：`{变量}` 和 `{变量|默认值}` 可用、docx 走 XML 级替换保排版（这是核心资产，别动它）；xlsx 走 ExcelJS 保公式样式；坏模板**静默出坏文件**（D1）；`{#循环}`/`{@图片}` 不渲染（D2）；预览是"下载到本地再打开"。
- **应该到**：模板**健康状态是一等公民**（坏模板进不了出文书流程，且能一键定位坏在哪一段）；表格行数随数据自动增减且**并入原表的合并单元格规则**；照片按容器尺寸嵌入、自动带拍摄时间/说明、自动旋转；**浏览器内能看清成品长什么样**（不必离开页面）。
- **差值**：健康检查 + 拦截（P0）、渲染器字节级校验与回滚（P0）、循环+图片（P3）、HTML 预览（P4）。

### 3.2 档案与变量体系

- **麻烦**：同一个"项目名称"在 36 份模板里各填一遍；换个单位接的项目又要重新填几十个字段。
- **现在**：字段/别名/解析链/提议-确认机制都在，设计是对的；但别名只有 132 条、**无一条是用户手工确认的**（全是 seed 82 + AI 50），引用加权覆盖率 36.1%，且有 539 个未映射变量名。同一个模板（保密协议、成立项目部通知）在库里重复 3 份，变量各扫一份。
- **应该到**：覆盖率进入**看板可观测**；长尾变量按"语义归并 + 编号枚举转循环"两条路走完；用户能点开任何一条未映射项，看到**它来自哪份模板的哪一处**，然后一键建字段/建别名；模板去重（同一份逻辑模板只留一份，多工作类型共享）。
- **差值**：覆盖率看板 + 来源可解释（P1）、AI 批量梳理 + 一键采纳（P1）、模板去重与共享（P1）、长尾两类处理法（P1/P3）。

### 3.3 影像与取证

- **麻烦**：检查完回来写记录，想不起来当时拍了什么、照片拍得够不够（没拍到铭牌、没拍全景）；审计要看"什么时候拍的、在哪拍的"，照片文件名是一串 IMG_xxxx。
- **现在**：影像清单卡片、张数校验、EXIF 提取（已存库）、按清单核销、单张/单条初检（视觉模型）都在；但 `evidence_rule` 是 0 条，**规则库没建**；EXIF 存了不用；核销纯手工。
- **应该到**：**拍之前就知道该拍什么**（要点 + 合格示例图 + 最少张数），**拍完立刻知道行不行**（批量初检 + 补拍清单），**核销有依据**（模型初检 `ok` 且张数够 → 预勾选待确认；`issue` → 阻止核销并说明原因），**归档自动规范**（时间/地点/要点进文件名与元数据）。
- **差值**：规则库 + 引导（P2）、批量初检（P2）、初检→核销闭环（P2）、EXIF 参与校验与嵌入（P2/P3）。

### 3.4 知识库与制度依据

- **麻烦**：写文书要"照制度的口径"，但制度在哪、第几条、金额大写小写要一致、日期不能早于开工日 —— 这些现在全靠脑子记，记漏了就是被退回。
- **现在**：切块（500 字重叠 60）→ 向量化 → FTS+语义混合检索 → 提问标出处，链路完整且已验证（55 项自检）；但**语料为 0**，且切块是"按语义边界切"，**不知道"第几条第几款"**；引用只能给到"某文件某段"。
- **应该到**：制度按**国家/行业/单位/项目**四层组织；文档先按"条/款/项"切分再按字数兜底，**引用能精确到条款**；出文书时不仅检索依据，还**跑确定性口径校验**（金额大小写一致、日期序列合法、编号格式、人数与清单匹配），不通过就拦下并要求填"例外说明"。
- **差值**：分层与条款级切块（P3）、口径校验规则引擎（P3）、第一批语料导入与确认（P3）。

### 3.5 AI 助手与代理执行

- **麻烦**：用户不想学操作流程，想直接说"把这个月的检查做了"。
- **现在**：19 个工具、写操作先提议后确认、`risk=destructive` 单列、记忆参与对话与出文书、附图先由视觉模型转述；工具调用最多 6 轮。差距：**没有"生成文书"这类工具**（助手能记账、能核销、能改字段，但**不能替你出一份文书**），也没有多步任务的编排与进度汇报。
- **应该到**：助手能做"月度检查"这类**多步任务**：列出步骤 → 逐条执行 → 每步产出提议 → 汇总成一张确认单；能发起出文书（仍走"提议→确认→生成→归档"）；任务有状态、可中断、可续做、可回滚；长期记忆按"工作台/工作类型/全局"三层组织并被检索使用。
- **差值**：任务编排（P3）、生成类工具（P3）、记忆分层与索引（P3）、回滚（P3）。

### 3.6 检索与归档

- **麻烦**：找"上次那份验收资料在哪"，以及"我到底还缺什么"。
- **现在**：FTS 全文（中文逐字空格化）+ 语义混合检索 + 目录纳管 + 幽灵索引行清理；`artifact_search` 与 `artifact_fts` 由触发器同步。缺口：**artifact 数为 0**（真实资料一件没进来）；生成文书没有版本历史。
- **应该到**：真实资料进得来（`_待归档` → 纳管 → 归档到项目目录）；同一份文书的多次生成有**版本链**（v1 草稿、v2 补齐、v3 定稿），能对比差异、能回退；归档状态**一个字段表达**。
- **差值**：文书版本历史（P1）、工作台归档三列合一（P2）、首批真实资料纳管（随用户日常使用自然发生，不做专项）。

### 3.7 任务与周期

- **麻烦**：月度检查这种按月重复的活，"这个月做了没有""上个月欠的那期补了没有"。
- **现在**：`recurrence/recur_day/recur_month/last_done_period/schedule_due_date` 都在，`computeSchedule()` 会算下一期与欠办期，`completeWorkbench()` 完成的是"本期"；`/api/workbenches/due` 有待办列表。实测工作台 #39 是 `monthly / recur_day=20`，到期日 2026-09-20，**`last_done_period` 为空**（一期都没完成过）。
- **应该到**：到期前提醒（不是靠用户想起来打开系统）；"本期"能**自动生成一份空的检查包**（用哪张表、要拍什么、要备什么材料）；完成后归档物自动落到本期目录（`2026-09/`），下期不串。
- **差值**：周期包的预生成（P3）、到期提醒（P3）、分期归档目录（P2，随版本历史一起做）。

### 3.8 质量与验收

- **麻烦**：（这是给维护者的）"自检全绿但用户拿到打不开的文件"不能再发生。
- **现在**：7 套 272 项、跑在隔离库（`scripts/test-isolated.mjs` 起独立 DB + 独立文件目录 + 独立端口 + 随机 token），这一点做得对；但**全部用假模型**、**没有用真实在用模板做黄金样本**、**没有产物可读性断言**、**没有真实模型质量门**。
- **应该到**：五层（单元 / 接口回归 / 端到端 / 黄金样本质量 / 性能）+ **真实模板库抽样自检** + **产物合法性硬断言** + 真实模型评测跑分与门禁；模型档案带"已验证"标记，没跑过评测的模型不许设为写作/抽取用途。
- **差值**：黄金样本套件（P2）、真实模型评测与门禁（P2）、模板库健康自检（P0）。

### 3.9 多用户 / 协作

- **判断**：**不做**（见第 6 节）。但有一个例外必须做：**"这个值是谁填的、什么时候填的"**要留痕 —— 因为一旦助手开始替人写值，事后追责的对象是"人还是模型"必须有答案。这不需要权限体系，只需要审计字段。

### 3.10 数据安全与备份

- **麻烦**：硬盘坏了、误删了、Word 保存时崩了。
- **现在**：数据与程序分离（`data/files` 可放同步盘）；`npm run pack -- --with-runtime-state` 能出**服务停止时**的一致性备份并自校验；`.repair-delivery/` 里有 2026-09-30 的修复前快照。缺口：**没有自动备份**、**没有回收站**、**删除无防护**、**密钥明文**、**没有还原演练**。
- **应该到**：每天自动快照 + 保留策略 + 还原演练过的 `RESTORE.md`；回收站（工作台/文件/模板/生成文书统一入口）；删除必须二次确认 + 影响预览；密钥可改走环境变量并给出说明。
- **差值**：自动快照与保留（P0）、回收站（P0）、删除防护（P0）、密钥（P4）。

### 3.11 可维护性与扩展点

- **麻烦**：（给接手的人）改一处会不会悄悄弄坏别处？用户能不能自己加东西？
- **现在**：`docs/01` 是"宪法"但已经与实现有偏差（它写"删工作台是真删，不可恢复"，与我们要做的回收站冲突，需要同步修订）；死导出、死表、死列、重复实现一堆（`docs/06` 第 62-73 行列了 17 个死导出 + 3 个死对象）；**测试只覆盖 60/132 个接口（45%）**，`routes-archive.ts` 20 个接口零覆盖。
- **应该到**：文档与实现一致（有一条自检能发现偏差）；扩展点集中且被文档化（字段、别名、模板、影像规则、口径规则、提示词六处）；`routes-archive.ts` 有回归覆盖；死代码清完。
- **差值**：口径规则的数据化扩展点（P3）、archive 路由回归（P2）、文档同步（P2）、死代码清理（P2）。

## 4. 分域详细设计

每域的结构固定：**要解决的问题 → 设计 → 验收标准 → 前置依赖 →（有取舍时）被否决的方案**。

### 4.1 模板健康检查与"坏模板不许出文书"

#### 4.1.1 要解决的问题

现在对 6 个坏模板（id 65/73/76/77/84/96）调出文书接口，链路返回成功，用户下载到一个 Word 打不开的文件。用户不知道是模板坏了还是系统坏了，而且**下一次还会再遇到**（模板 96 就在项目类工作台的 S01 阶段上，是"成立项目部"这条最高频的线上）。

#### 4.1.2 设计

**① 新增一张表 `template_health`（迁移 `010_template_health.sql`）**

```
id, template_id (FK, UNIQUE), checked_at,
status           -- ok | broken | warning | unknown
severity         -- ok=0, warning=1, broken=2（数值化，便于比较）
format           -- docx | xlsx | text | other
parts_total      -- OOXML 部件数
parts_bad        -- 解析失败的部件数
bad_parts        -- JSON: [{part, error, offset}]
missing_parts    -- JSON: 必需部件缺失
placeholder_errors -- JSON: [{kind, where, detail}]  kind ∈ advanced_not_supported | unclosed | empty_name | too_long
var_count        -- 扫描到的变量数
render_probe_ok  -- 试渲染是否成功（用全空值的 dry-run）
render_probe_ms
render_probe_error
bytes, sha1      -- 检查时的文件指纹，用于判断"文件换过了但要重检"
note             -- 人写的处置说明（如"已从旧备份重传"）
```

**② 新增 `core/template-health.ts`，导出 `checkTemplate(absPath): HealthReport`**

检查项，按"能不能拦住事故"排序：

| 检查 | 判据 | 判 broken 的条件 |
|---|---|---|
| ZIP 完整性 | `new PizZip(buf)` 不抛 | 抛了 |
| 必需部件 | `[Content_Types].xml`、`_rels/.rels`、`word/document.xml` 存在 | 任一缺失 |
| **XML 良构性** | 对 `word/document.xml, header{1..3}, footer{1..3}, [Content_Types].xml, word/styles.xml, _rels/.rels, word/_rels/document.xml.rels` 逐个 `ET.fromstring()` 等价校验 | **任一部件 ParseError**（这一条就是拦住 D1 的那一条） |
| 替换可行性 | 对每个 `<w:p>` 段落跑一遍现有的"合并 `<w:t>`"逻辑，统计**跨 run 的占位符**数量 | 不作为 broken，记为 warning 并给出定位（跨 run 已由 `replaceInXml` 处理，但数量多说明模板是别的工具生成的，值得提示） |
| 占位符语法 | `scanPlaceholders()` 结果里出现 `#`/`/`/`@` 前缀 | 若渲染器尚未实现（P0/P1/P2 阶段）→ **broken**，消息："模板里用了 `{#循环}`，当前版本还不支持渲染，出文书会原样保留占位符。要么先改成固定行，要么等 X 版本。"；实现后 → 降为 warning |
| 变量清单 | 扫描到的变量数为 0 | warning（可能是扫描规则不适配，不拦） |
| 试渲染 | 用"所有变量取空值 + keepUnfilled"跑 `renderTemplate()`，再用上面同一套 XML 校验器验产物 | 产物不合法 → broken |
| 大小/超时 | 部件总大小、单部件 > 8MB | warning（渲染慢、模型也可能读不下） |

**关键实现决定：用什么做 XML 校验。**

- **不引入第三方 XML 解析库**（`fast-xml-parser`、`libxmljs` 都要加依赖，后者还是原生模块，和本项目"零原生编译"的技术底线冲突）。
- **不用正则做良构性判断**。我第一版用 `<w:p` 计数试过，48 个在用模板里报出 18 个"不平衡"——全是误报（`<w:pPr` 被 `<w:p` 匹配到了）。误报比不报更糟：用户会学会无视告警。
- **做法：给 `core/template.ts` 加一个结构感知的校验器** `validateXmlStructure(xml)`，用一个**极小的栈式扫描器**：
  1. 词法层：跳过 `<!-- -->`、`<![CDATA[]]>`、`<?...?>`、`<!DOCTYPE...>`；只认 `<\S+` 起始的标签，用 `[\w:.-]+` 严格取标签名（因此 `<w:pPr` 取到的是 `w:pPr`，不会和 `w:p` 混淆）。
  2. 语法层：`<a/>` 自闭合直接跳过；`<a>` 入栈；`</a>` 必须与栈顶同名，否则报**带偏移量的 `mismatched tag`**；到文件末尾栈必须为空。
  3. 属性层：属性值里的引号要正确处理，`>` 出现在属性值内不算标签结束。
  - 验收这个校验器的正确性用**双向对拍**：拿 60 个模板（48 在用 + 12 归档）跑，结果必须与 Python `ElementTree` 的判定**逐个一致**（6 broken / 54 ok）。这条对拍写进自检。
- **被否决的方案**：把校验委托给 `python`。机器上确实有 Python 3.14，但它不是本项目的运行时依赖，用户重装机器就可能没有；健康检查是**每次上传、每次出文书前都要跑**的热路径，跨进程调用不可接受。可以在**一次性数据盘点脚本**里用 Python，不进产品代码。

**③ 出文书前拦截（三道）**

1. `GET /api/generate/readiness?templateId=` 返回 `{ renderable, healthy, reasons[], fixHint }`。前端在"生成"按钮旁显示状态；`healthy=false` 时按钮禁用并给出修法。
2. `POST /api/generate/preview` 与 `POST /api/generate/save` 在渲染前查 `template_health`：`status='broken'` 且指纹一致 → 直接 `412 TEMPLATE_BROKEN`，消息里带**坏在哪一段**（`word/document.xml 第 2 行第 2037 列：标签不匹配`）和**怎么修**（"用 Word 打开这份模板，另存为 .docx 再重传；或者把这个阶段换绑到模板 #85"）。
3. `renderTemplate()` 本身**不再无条件 `ok:true`**：渲染后跑 `validateXmlStructure()`，不合法就返回 `{ok:false, code:'RENDER_CORRUPT'}`，并且**不写盘**。这是最后一道闸 —— 即使健康表过期了、新传了坏模板还没检查，也不会产出坏文件。
4. 渲染返回结构补齐（顺带解决"静默漏填"）：`{ok, bytes, replacedCount, missing[], leftoverAdvanced[], warnings[]}`；`X-Missing-Vars` 响应头继续保留，新增 `X-Render-Health`。

**④ 隔离与重传流程**

- 坏模板不删除、不隐藏（用户需要看到它、需要知道它有 3 个副本），而是**在模板库列表里打红标 + 置顶 + 提供三个动作**：`重新检查` / `上传修复件（覆盖本模板文件，保留 id 与变量映射）` / `换绑到别的模板`。
- 新增 `POST /api/templates/:id/replace-file`：上传新文件 → 写健康记录 → **保留原 `template.id`、`code`、变量说明 `.vars.json`**（只补新增变量、保留人工写过的 `label/hint/type`）→ 旧文件移进回收站。这条接口是"修模板"的主路径，没有它用户只能"删了重传"，而重传会换 id，**所有 `material_check`、`workbench.template_ids`、阶段绑定都会断**。
- 新增 `POST /api/templates/health/scan`（批量重检，支持 `?only=stale|all`）与 `GET /api/templates/health`（看板数据）。
- **归档模板**的文件缺失（12 条 `【自检】…` 记录，文件已在 `_归档模板/` 或已被清理）算 `warning` 不算 `broken` —— 归档件不参与出文书。

**⑤ 界面**

模板库列表增加一列"健康"：`正常 / 有提示 / 打不开（点这里看原因）`；顶部一条横幅："**6 个在用模板的文件结构损坏，用它们出文书会得到打不开的文件** → 查看/修复"。横幅必须能在修完之后消失（这决定了用户会不会真的去修）。

#### 4.1.3 验收标准

1. 对全部 60 个模板跑 `POST /api/templates/health/scan`，结果与 Python `ElementTree` 判定**逐条一致**：48 个在用里恰好 6 个 `broken`（65/73/76/77/84/96），12 个归档为 `warning`（文件缺失），其余 `ok`。
2. 对 id 65、73 调 `POST /api/generate/preview` → **HTTP 412**，`error.code = TEMPLATE_BROKEN`，消息包含部件名 + 行 + 列 + 修法；**磁盘上不得新增任何文件**。
3. 直接调 `renderTemplate(坏模板)` → `ok:false`，`bytes` 为空。
4. 上传一个手工构造的坏 docx（把 `document.xml` 里一个 `</w:p>` 改成 `</w:body>`）→ 上传接口 201 返回但 `health.status='broken'`，且列表红标可见。
5. 用 `POST /api/templates/96/replace-file` 上传修好的文件 → `template.id` 仍为 96、`.vars.json` 里人工写过的 `label` 保留、旧的坏文件出现在回收站、健康状态变 `ok`、**工作台 #25 的 S01 阶段绑定不丢**。
6. 对 48 个在用模板跑一次全量"渲染试跑"（`skipAi=true` 空值渲染），产物 **48/48 通过 `validateXmlStructure`**（修复 6 个之后）。
7. 这个校验器本身的正确性断言进 `npm run test:unit`：6 个已知坏模板必判 broken、42 个已知好模板必判 ok、人为构造的 5 种 malformed（未闭合、错配、属性内 `>`、注释里的假标签、CDATA）各自得到预期结论。

### 4.2 模板引擎补齐：`{#循环}` 与 `{@图片}`

#### 4.2.1 要解决的问题

两类真实模板现在就卡在这两个语法上：

- **工程量清单 / 设备清单 / 人员名单类**：表格行数不定。典型是 `10-原材料产品报验单`（60 个变量）、`05-设备产品验收表`（68）、`07-设备到货开箱验收清单`（42）、`11-设备移交清单`（44）—— 这些模板的变量名里出现了 `设备1名称`…`设备13名称`、`设备1数量`、`设备1单位`、`乙方人员一姓名`、`乙方人员一身份证号`…**这是把"一行的列"手工展开成了 N 组标量变量**。后果有三：模板变量数虚高（推低了覆盖率）、清单多一行就得改模板、模型要填几十个高度相似的键（出错率随键数上升）。
- **要贴照片的文书**：检查记录表、验收报告、隐蔽工程记录，都要"文字 + 现场照片"。现在只能出附件说明，用户拿到文书还得手工贴图、调大小、加图注。

#### 4.2.2 设计：语法与语义（先定死，再实现）

**语法沿用现有约定**（`core/placeholders.ts` 已经能扫到，兼容已有扫描器与 `.vars.json`）：

| 写法 | 含义 |
|---|---|
| `{#列表名}` … `{/列表名}` | 循环块。块内可以再出现 `{#子列表}`…`{/子列表}`（嵌套） |
| `{列表名.字段}` 或块内直接写 `{字段}` | 行内变量。**两种都支持**：带前缀的（`{设备.名称}`）用于嵌套时消歧，不带的（`{名称}`）用于单层循环（模板写起来最省事） |
| `{@照片}` / `{@照片|宽:8cm}` | 图片占位。可选参数：`宽/高`（带单位 cm/mm/px/%）、`说明` |
| `{@照片.拍摄时间}` | 图片的派生文本（EXIF 时间），用于图注 |
| `{#列表}` 空列表时 | 整块（含所在表格行）删除；若写了 `{#列表|空:无设备}` 则输出该兜底文本 |

**数据形态**（写给模型和写给用户的都是这个）：

```json
{
  "项目名称": "数据中心机房建设项目",
  "设备明细": [
    { "名称": "精密空调", "数量": "2", "单位": "台", "备注": "含安装" },
    { "名称": "UPS 电源", "数量": "4", "单位": "台", "备注": "" }
  ],
  "现场照片": [
    { "artifact_id": 812, "说明": "设备到货开箱前外包装" },
    { "artifact_id": 813, "说明": "铭牌与序列号特写" }
  ]
}
```

**为什么用"列表名 + 对象数组"而不是"用变量名前缀猜列表"**：前者是显式契约，模型和人都不会猜错；后者（把 `设备1名称`、`设备2名称`… 自动聚成列表）虽然能免去改模板，但 N 的判断不可靠（第 14 行是空的怎么办？编号跳号怎么办？），而且**它掩盖了模板本身的设计问题**，让"改模板"这件一次性的活永远拖下去。折中做法放在 P1：**给用户一个"把编号变量合并成循环"的一键助手**，由用户确认后自动改写模板（见 4.3.3）。

#### 4.2.3 设计：docx 表格行复制（怎么写才不破坏排版）

这是整个引擎最容易出事的地方，所以把算法写死在这里。

**第一步：把循环块映射到"重复单元"**

块的开标记 `{#列表}` 和闭标记 `{/列表}` 在 XML 里可能落在不同层级。做法：

1. 先按现有逻辑得到每个 `<w:p>` 段落的纯文本。
2. 扫描 `<w:tr>` 序列，找出**第一个包含 `{#列表}` 的单元格所在的行 R_start**，和**包含 `{/列表}` 的行 R_end**。
3. 三种情况：
   - `R_start == R_end`（开闭标记在同一行内，常见写法：一个单元格放 `{#设备明细}`，表头行的下一行放 `{名称}{数量}…{/设备明细}`）→ **重复单元就是这一行**。
   - `R_start < R_end` → **重复单元是 R_start…R_end 之间的整段行**（支持"一个循环项占两行"的双行卡片式表格）。
   - 行内找不到标记、但段落里找到了（非表格里的循环，如"一、……二、……"的分段列表）→ **重复单元是包含该段的 `<w:p>` 段落组**，按段落复制（走第二条实现路径，见下面"非表格循环"）。
4. 一个表里多个循环：按"最先出现的开标记"配对"最近的可闭合标记"（用栈配对），依次处理，**每次处理完从 XML 里移除已处理块**，避免嵌套错位。

**第二步：计算重复次数**

`n = 数组长度`（`{#列表}` 的 `列表` 必须与数据键同名）。`n = 0` 时按"空列表"处理。

**第三步：复制行**

对 `R_start…R_end` 的每一行 `tr`：

1. 取该行 XML，替换其中的**行内变量**（`{字段}` / `{列表名.字段}` → 数组第 i 项的对应值）与**图片占位**（见 4.2.4）。
2. **合并单元格处理（必须做对，否则表格会错位）**：
   - `<w:gridSpan w:val="N"/>` 是水平合并：**原样复制**，因为它在源行里是什么样、复制出来就是什么样，不影响列数。
   - `<w:vMerge/>`（无 `w:val` = continue，垂直合并的延续）是垂直合并：**延续行必须跟在起始行下面**。复制时，如果重复单元里包含 `vMerge` 的**起始**行（`<w:vMerge w:val="restart"/>`），那么每一份复制都要带上它；如果包含的是**延续**行，那么每份复制也带上 —— 前提是重复单元的第一行就是起始行。**判定规则**：若重复单元的首行含 `vMerge w:val="restart"`，则正常复制；若首行是 `vMerge` continue，则把首行**降级为普通单元格**（去掉 `vMerge`）并警告 —— 因为"表头垂直跨越到数据行"这种结构里，重复数据行不该继续延续合并。
   - 复制出的行必须重新生成 `w:tr` 里的 `rsid` 属性（Word 用 `w:rsidR/w:rsidTr` 标记修订会话，重复值不致命但会让"修订"视图怪异）→ 直接**删除复制行的 `w:rsid*` 属性**。
3. **边框与外框**：表格的外框通常在 `<w:tblBorders>` 上（不在行里），复制行不影响它。要处理的是行的**首行上边框 / 末行下边框**（有些模板把外框写在 `tcBorders` 里）：
   - 原始重复单元的首行若定义了 `tcBorders.top`，复制时**只有第一份保留**，其余份的 top 置为 `nil` 或继承表级边框；
   - 末行若定义了 `tcBorders.bottom`，**只有最后一份保留**；
   - 这条规则做成可配置（模板变量 `{#列表|边框:保留}`），因为有些模板确实希望每一行都有上边框（分栏效果）。
4. 把复制结果 `n` 份拼起来，**替换掉原来那一段行**（第一份留在原位，其余插入其后）。

**第四步：非表格循环（段落组）**

有些循环不在表格里（如"检查发现的问题"逐条列出）。做法：以包含 `{#列表}` 的 `<w:p>` 为起点、`{/列表}` 所在 `<w:p>` 为终点，把这段 `<w:p>` 序列作为重复单元，按同样方式复制与替换。段落级没有合并单元格问题，但要处理 `w:numPr`（自动编号）：**复制后必须保留每份的编号属性**，让 Word 自己编号（不要手工写"1. 2. 3."，否则用户改顺序后编号就错了）。

**第五步：渲染后的自检**

渲染完必须验：
- 循环标记 `{#…}`、`{/列表}` 在产物里**剩余 0 个**（剩一个就是配对失败，返回 `RENDER_UNBALANCED_LOOP` 并**不写盘**）。
- 表格行数增量 == 预期增量（可断言：`产物行数 - 原行数 == (n-1) * 重复单元行数`）。
- 产物仍通过 `validateXmlStructure`。

#### 4.2.4 设计：`{@图片}` 嵌入 docx

**第一步：定位插入点**

占位符 `{@照片}` 一定在某个 `<w:p>` 的 `<w:t>` 里（`replaceInXml` 已经能把它拼出来）。做法：

1. 渲染到该段落时，**不把占位符替换成文本**，而是在该段落的 `<w:pPr>` 之后插入一个 `<w:r><w:drawing>…</w:drawing></w:r>`，并把原来的占位符文本清空。
2. **保留段落原有样式**（居中、行距、缩进都在 `w:pPr` 里，不动它）；`{@照片}` 所在段落若同时有说明文字（`{@照片} {照片说明}`），说明照常替换为文本。
3. 一个段落里多个 `{@照片}` 且用 `|并排:2` 参数时，插入一个 2 列的**浮动表格**（`<w:tbl>` 无边框）承载 —— 这是"两张照片并排"最常见的排版需求。**默认不并排**（一图一段），因为自动并排会改变页面结构，用户没要求就不做。

**第二步：图片尺寸与方向**

1. **尺寸解析优先级**：占位符参数 `宽:8cm` > 档案/模板设置 `证据图片默认宽` > 容器宽度。
   - "容器宽度" = 所在单元格 `w:tcW`（减左右边距）或页面可用宽度（`w:pgSz - w:pgMar`）。这些都从 XML 里读，**不做猜测**。
   - 高宽比从图片本身读（本机可用 `exifr` 已解析的 `宽度/高度`，见 `routes-files.ts:29`；没有就按 96 DPI 从像素算）。
   - 单位换算：`cm → EMU = cm × 360000`；`px → EMU = px × 9525`。**上限保护**：嵌入后宽度不得超过容器宽度，超过就等比缩到容器宽。
2. **方向（EXIF Orientation）**：`artifact.exif` 里已抽了 `Orientation`，但现有代码只存原值没纠正。嵌入前：对 `Orientation ∈ {5,6,7,8}` 做 `<a:xfrm rot="5400000|16200000">` 旋转（6/8 是 90°/270°，需要交换宽高）。**这是"手机竖拍照片插进 Word 是躺着的"的直接原因**，不处理会被用户一眼看出来。
3. **压缩**：单图 > 4MB 时按"最长边 1600px、JPEG 质量 82"重编码后再嵌（避免一份 40 页的检查记录变成 200MB）。缩图用**已有依赖**能做的事：Node 无内置图像编码器，所以这一步用 `exifr` 之外**不新增原生依赖**的路径 —— 方案是"若图 > 4MB 且系统检测不到可用的缩放器，则原样嵌入并在界面提示'图片较大，文件体积 XX MB'"。**被否决的方案**：引入 `sharp`（原生模块，与"零原生编译"底线冲突）或 `jimp`（纯 JS 但要再引一个 40MB 级依赖）。**接受体积代价，换取零安装风险**；真需要压缩时由用户先压好（界面给出指引）。
4. **关系与内容类型注册（最容易漏的一步）**：每张嵌入图片要做四件事，缺一件 Word 就打不开：
   - 把图片字节写进 `word/media/imageN.ext`（编号取现有最大值 +1，避免覆盖模板自带的图）；
   - 在 `word/_rels/document.xml.rels` 加一条 `<Relationship Id="rIdN" Type=".../image" Target="media/imageN.ext"/>`（Id 必须全局唯一，避开模板已有的 rId）；
   - 在 `[Content_Types].xml` 里确保有该扩展名的 `<Default Extension="jpeg" ContentType="image/jpeg"/>`（**这一步经常被漏，漏了 Word 报"内容有问题"**）；
   - 在 `<w:drawing>` 里写 `<a:blip r:embed="rIdN"/>`，并把该 `<w:drawing>` 需要的 `xmlns:a`、`xmlns:r`、`xmlns:wp` 命名空间**确认在根元素上已声明**（文档级，通常已有；没有就在根上加）。
5. **图注**：`{@照片}` 后面若紧跟 `{@照片.拍摄时间}` 或 `{照片说明}`，则生成"图 N：说明（2026年9月16日 09:24 摄）"。图 N 由渲染器自动编号（按出现顺序），**这是人能一眼核对"共几张"的依据**。
6. 只允许嵌 `.jpg/.jpeg/.png`（Word 兼容性最好）。`.webp/.bmp/.tif` → 明确报错并给出转换提示（不要静默跳过）。
7. 图片缺失（`artifact_id` 查不到、文件不在盘上）→ **不静默留占位符**，而是在该位置插入一个红色文本 `【缺图：artifact #812 文件不存在】` 并计入 `warnings`；`strict` 模式下（配置项）直接拒绝生成。

#### 4.2.5 设计：AI 怎么产出循环数据

现在 `generateVariables` 要求模型输出 `Record<string, string>`，`specLines()` 也按"一行一个变量"描述。要扩展两处：

1. `.vars.json` 的变量项增加 `kind: 'text' | 'list' | 'image'` 与 `itemFields: string[]`（列表的列名）。扫描器扫到 `{#x}…{/x}` 时自动产出 `kind=list`、`itemFields=[块内出现的不带前缀的行内变量名]`。
2. `specLines()` 对 `kind=list` 输出：

   ```
   5. 设备明细 [列表]（可 0..N 项）列：名称、数量、单位、备注
      依据：本次指定参考资料《到货清单.pdf》与本项目已归档资料
   ```
   `kind=image` 输出：
   ```
   9. 现场照片 [图片]（引用本项目已上传的影像证据，最多 6 张）
   ```
3. 输出 JSON 允许这两类值是**数组**；解析后做类型校验：`list` 项必须是对象数组、`image` 项必须是 `{artifact_id}` 数组且 **artifact_id 必须属于当前工作台**（防止模型编一个 id）。

**重要边界（写进提示词和代码检查）**：`artifact_id` 只能由系统从"本项目已有影像证据"里挑，**绝不允许模型自己生成数字**。做法：提示词里给出候选清单（`#812 设备开箱前外包装（2026-09-16 09:24 摄，初检 ok）`），模型只允许从这份清单里选；代码侧再校验一次（不在候选集里的一律丢弃并计 warning）。

#### 4.2.6 设计：预览

分三层，按投入从小到大排，**P3 只做前两层，第三层放 P4**：

**第一层：结构化预览（P3，必做）**

`POST /api/generate/preview` 的 JSON 返回里带 `plan`：

```
{
  "segments": [
    { "kind": "text", "text": "关于成立数据中心机房建设项目项目部的通知" },
    { "kind": "table", "rows": [
        ["序号","设备名称","数量","单位"],
        ["1","精密空调","2","台"],
        ["2","UPS 电源","4","台"] ] },
    { "kind": "image", "artifactId": 812, "caption": "图 1：设备开箱前外包装（2026-09-16 09:24 摄）" }
  ],
  "replaced": 41, "missing": ["监理工程师"], "leftoverAdvanced": []
}
```

界面上把它渲染成 HTML 表格 + 缩略图。**它验证的是"数据对不对"**：行数、顺序、每格的值都是真的（因为它就是渲染器实际用到的结构，不是另写一套解析）。它诚实的地方是：**不还原字体字号分页**，界面要写明"这是内容预览，排版以 Word 打开为准"。

**第二层：产物合法性 + 系统打开（P3，必做）**

- 预览接口返回时同时跑 `validateXmlStructure` + "循环标记残留检查"，把结果显示成一条绿色/红色横幅：`✓ 产物结构合法，可正常打开` / `✗ 产物结构异常，已阻止保存`。
- "在本机打开预览"按钮：把预览文件写进 `data/runtime/preview/<uuid>.docx`，服务端调 Windows `start` 打开（`child_process.spawn('cmd', ['/c','start','','<path>'])`，**不阻塞、不解析返回值**），前端提示"已用系统默认程序打开预览文件（临时文件，不会归档）"。
  - **这是零依赖拿到"所见即所得"的务实做法**：用户机器上本来就有 Word（不然他没法用这些模板）。
  - 若系统没装 Office（`start` 返回错误），降级提示"本机未关联 Word，请下载后查看"。
- **被否决的方案**：把 LibreOffice 打进包里做服务端 PDF 转换。理由是安装体积（~300MB）和"另装一个 Office 会有字体/分页差异"的风险；而用户的最终交付物是 docx，用真 Word 看才是最准的。

**第三层：HTML 近似排版（P4，可选）**

从 `document.xml` + `styles.xml` 还原段落/字体/对齐/表格边框，在浏览器内出近似页面。**明说它是近似**：分页、浮动对象、域代码（页码/目录）不还原。
- 必要性判断：只有在"用户经常不在装有 Word 的机器上看预览"时才值得做。当前是单机单用户、机器上有 Word → **P4 再评估**。
- **被否决的方案**：前端引 `docx-preview` 之类的库。它会引入一套独立的解析实现，与后端渲染器的行为产生第二真源；一旦两边不一致（而它们一定会在合并单元格、编号这些地方不一致），用户就不知道该信哪个。要做也**只在前端渲染后端产出的结构（第一层的 `plan`）**，不重新解析 docx。

#### 4.2.7 验收标准

**循环**
1. 构造一个 3 行的表格模板，`{#明细}` 在数据行、列是 `{名称}{数量}{单位}`：数组 0 项 → 数据行消失、表头留存、无残留占位符；1 项 → 一行；5 项 → 五行。
2. **合并单元格用例**：模板表格首列是跨两行的垂直合并（`vMerge restart` + continue），重复单元是这两行；渲染 3 项 → 产物里 6 行的合并关系正确（`gridSpan`/`vMerge` 数量与预期一致），且在 Word 里打开不错位（人工验收一次，之后作为黄金样本固定）。
3. 嵌套用例：外层 3 项、内层各 2 项 → 内层共 6 行，落在正确的外层行下。
4. 空列表 + `{空:无}` → 输出"无"。
5. 配对失败用例（只有 `{#x}` 没有 `{/x}`）→ `ok:false`、`RENDER_UNBALANCED_LOOP`、**不写盘**。
6. 用真实模板 `10-原材料产品报验单` 的改造版（把 `设备1名称…设备13名称` 改成 `{#设备明细}` + `{名称}`）出一次文书，产物 48 项自检里"行数增量 == 数据项数"断言通过。

**图片**
7. 单图嵌入：占位符段落居中样式保留；`word/media/` 下多一个文件；`document.xml.rels` 多一条关系；`[Content_Types].xml` 有对应 `Default`；**python-docx 用严格模式能打开并读到一个 inline shape**。
8. `Orientation=6` 的竖拍照片 → 产物里图片方向正确（宽高已交换），在 Word 里不是躺着的。
9. 尺寸：`{@照片|宽:8cm}` → 产物 `extent cx` 落在 `8cm × 360000 = 2880000` EMU（允许 ±1% 误差）；不给参数且单元格宽度 6cm → 宽度 ≤ 6cm。
10. 图注自动编号：3 张照片 → 产物里出现"图 1/图 2/图 3"，顺序与数据顺序一致。
11. 缺图：传一个不存在的 artifact_id → 产物含 `【缺图：artifact #999】`、`warnings` 有该条、**接口仍返回 200**（不因为一张照片废掉整份文书）；`strict` 模式返回 412。
12. 超过 4MB 的图：不报错、嵌入成功、界面提示体积。
13. 老模板回归：所有**不含** `{#`/`{@` 的模板渲染结果与改造前**字节级一致**（用改造前的 48 份产物做基线，逐字节比对）。

**预览**
14. `POST /api/generate/preview` 返回 `plan.segments`，其中表格行的值与请求里的数组一一对应。
15. 坏产物路径：人为让渲染器产出一个不合法 XML → 预览返回 `ok:false` + 结构异常横幅，磁盘无文件。
16. 单份 40 个变量的模板，从"填完变量"到"看到预览"≤ 2 次点击、页面不跳转。

#### 4.2.8 前置依赖

- 强依赖 **4.1**（渲染后校验器、健康检查），因为循环/图片的实现必须建立在"能判断产物合不合法"的基础上。
- 依赖 **4.3** 的变量模型扩展（`kind: list/image`）—— 两件事要一起改 `.vars.json` 结构与 `specLines()`，分开做会改两遍。

### 4.3 映射覆盖率：从 36% 到 80%+

#### 4.3.1 要解决的问题

引用加权覆盖率 36.1% 是自动化率的天花板。645 处引用（1089 - 393）落在"档案带不出来"的区间里，它们只能靠模型写或人填。而在 `.vars.json` 里，这 64% 表现为 539 个未映射变量名 —— 其中一大块是**结构性冗余**（编号枚举），另一块是**真的没建字段**（甲方法定代表人、监理机构、合同金额大写…）。

#### 4.3.2 设计：覆盖率看板（先量出来，再谈优化）

新增 `GET /api/archive/coverage`：

```
{
  "overall": {
    "distinct": { "total": 632, "mapped": 93, "rate": 14.7 },
    "weighted": { "total": 1089, "mapped": 393, "rate": 36.1 }
  },
  "target": { "weighted": 80, "deadline": null },
  "byTemplate": [ { "templateId": 61, "name": "技术开发（委托）合同范本",
                    "vars": 137, "mapped": 19, "rate": 13.9,
                    "unmappedTop": ["甲方法定代表人","乙方委托代理人","合同金额大写"] } ],
  "unmapped": [
    { "var": "甲方法定代表人", "refs": 6,
      "usedBy": [ { "templateId": 58, "name": "货物类合同模板" },
                  { "templateId": 61, "name": "技术开发（委托）合同范本" } ],
      "guess": { "field_key": "party_a_legal_rep", "label": "甲方法定代表人",
                 "reason": "与已有字段 party_a_name「甲方名称」同前缀、共现 6 次" },
      "kind": "scalar" },
    { "var": "设备7名称", "refs": 3, "usedBy": [...],
      "cluster": "device-enum",
      "suggestion": "与 设备1名称…设备13名称 同族，建议合并为循环 {#设备明细}",
      "kind": "enum" }
  ]
}
```

**"这条线索来自哪份模板"必须是可解释的**：界面上点任一未映射变量，右侧列出它在哪几份模板里出现（模板名 + 出现次数），点模板名直接跳到模板的变量清单页，并把该变量高亮。这一条决定用户愿不愿意动手 —— 只给一个数字（"还有 539 项没映射"）没有人会去处理。

看板上给出**两个数**（不同名覆盖 / 引用加权覆盖）并显式解释差别，避免用 14.7% 或 36.1% 中的某一个去误导判断。

#### 4.3.3 设计：把 36% 提到 80% 的三条路

**路线 A：AI 批量梳理 + 一键采纳（覆盖长尾的"真字段"部分）**

现有 `POST /api/archive/analyze` 已能"读一批模板的变量 → 提议字段与别名"，并且**已有提议-确认机制**（`archive_proposal`，当前 93 accepted / 1 pending）。要补的是"能一口气跑完、能看懂、能批量确认"：

1. **扩展输入**：支持不传 `templateIds` → 默认**全部在用模板**，按变量频次降序分批（每批 ~40 个变量）。
2. **降本**：只把"未映射且频次 ≥ 2"的变量送去分析（频次 1 的变量收益低、噪声高）；已在别名表里的不重复提（现在就有这个跳过逻辑，保留）。
3. **提示词升级**（关键，现在的提示词只要求"提字段和别名"）：
   - 明确给出**已有字段清单**（`field_key=label`），要求"能归到已有字段的一律归过去，不要新建重复字段"；
   - 要求给出 `reason`（为什么这么归），并**引用模板里的相邻文字**作为上下文（例如 `合同金额大写` 出现在"人民币（大写）"后面）；
   - 明确要求**识别编号枚举族**：如果一组变量形如 `<同一前缀><中文数字/阿拉伯数字><同一后缀>`（≥3 个成员），不要逐个建字段，而是输出 `{kind:"enum_family", prefix, members, suggestion:"改为循环"}`。
   - 要求 `confidence`：`high`（同名/近义直接对应，如"甲方法定代表人"→ 新字段，或"承包单位简称"→ 已有 `party_b_short`）/ `medium` / `low`（要人判断）。
4. **界面上按 confidence 分组**：`high` 一组默认全选（"待确认 42 条，预计把引用覆盖率从 36% 提到 61%"）→ 一键采纳；`medium/low` 逐条看。**批准前先显示"采纳后覆盖率会变成多少"**，这是让用户愿意点的唯一动力。
5. **同名合并**：`acceptProposal` 现在遇到已存在的 `field_key` 只复用不改名（这是对的，保住 `field_key` 契约）。补一条：如果提议的 `label` 与已有字段**同义**（编辑距离 ≤ 1 或命中 `labelAliases`），把提议降级为"给已有字段加别名"，而不是建新字段。系统必备字段的 `labelAliases` 已经在 `SEED_FIELDS` 里维护了（如 `party_a_name` 的 6 个别名），要把这份同义词表**提升为可编辑的数据**（放 `app_setting` 或新表），因为用户单位里还会有别的叫法。

**路线 B：编号枚举 → 循环（既提覆盖率，又降模板复杂度）**

`设备1名称…设备13名称`（39 个变量名）、`乙方人员一姓名…乙方人员五身份证号`（10 个）、`设备1数量/设备1单位…`（26 个）—— 光是这三族就吃掉约 75 个变量名。它们**不该有别名**，该被循环替代。

做法（P1 做"发现"，P3 做"改造"）：

1. **发现**：在覆盖率看板里按 `prefix + 数字/中文数字 + suffix` 聚类，标为 `enum`，不参与"覆盖率分母"（否则优化目标会被这批假的未映射项污染）。看板同时给出"扣掉编号枚举后的加权覆盖率"。
2. **改造助手**：用户点"帮我合并成循环" → 系统生成改造后的模板文件（在 `_模板库` 下另存一份 `_v循环`），并把改动**逐处列出来**（第几行第几个表格）→ 用户用 Word 打开对比确认 → 点"采用"才替换（走 4.1 的 `replace-file`，保 id）。
3. 改造后模板的变量数从 60 降到 ~15（`10-原材料产品报验单` 这类），覆盖率自然上升，且模型出错率下降。

**路线 C：把"档案没有但资料里有"的值抽出来（让已有值被复用）**

`POST /api/archive/extract/artifact` 已能从一份资料抽字段值并走确认流程。缺的是**主动找**：系统知道"这个工作台缺 `监理机构`"，而 `_原始资料` 里有一份《监理合同》，就应该主动提议"从《监理合同》里抽"。做法：

1. 覆盖率看板增加一栏"**档案空缺但已有资料里可能有的字段**"：对每个工作台，取"该类型模板高频引用、档案里为空"的字段 top 10，与该工作台已归档文件的抽取文本做词面匹配（不调模型，纯 BM25 式词频），命中就提议抽取。
2. 抽出来的值仍走 `archive_proposal` 的确认流程，**不自动写**。

#### 4.3.4 设计：跨模板复用与去重

实测同一份「02-保密协议」在库里 3 份（`template.name` 重复）、「01-成立项目部的通知」3 份（且**坏的是同一个源**）。这不是数据洁癖问题，它有直接后果：**同一份模板的变量被算 3 次，别名要维护 3 遍，修模板要修 3 处**（D1 里 3 个坏副本就是同一份文件）。

设计：
1. `template` 增加 `content_sha1`（文件内容指纹）；上传时计算，与库中在用模板比对，命中则**默认提示"这份模板和 #85 内容完全相同（保密协议），要共用一份吗？"**，用户可选"共用"（只建一条 `template` 记录，多个工作类型通过 `work_type_id` 之外的方式引用）或"另存"（写明区别）。
2. 由于 `work_type_id` 现在是一对一绑定，"共用"需要一张 `template_work_type` 关联表（多对多）。**迁移成本**：现有 48 条 `template.work_type_id` 全部迁进关联表，`listTemplates(workTypeId)` 改走关联表；界面上的"模板绑定到工作类型"变成多选。改动面约 6 个文件（`service.ts` 的 `listTemplates`、`routes-template.ts` 的列表/更新、`Workbench.tsx` 的模板选择、迁移脚本），**值得做**，因为它同时解决"修模板要修 3 处"和"覆盖率分母被重复计算"。
3. `template_health` 挂在 `template.id` 上，共用后天然只检查一次。

#### 4.3.5 验收标准

1. `GET /api/archive/coverage` 返回的数字与第 1.2 节一致（632 / 93 / 14.7% 与 1089 / 393 / 36.1%）；用一个独立脚本（读 `.vars.json` + 查别名表）复核，两者必须一致。
2. 点某个未映射变量 → 返回的 `usedBy` 里模板名与出现次数正确（用 `甲方法定代表人` 验证：6 次，来自货物类合同模板与技术开发合同范本等）。
3. 跑一次全量 `POST /api/archive/analyze`（全部在用模板）：`high` 置信度提议 ≥ 120 条，且其中**至少 100 条采纳后不产生新的 `field_key` 冲突**；采纳后加权覆盖率 ≥ 55%（P1 阶段目标）。
4. `enum` 聚类正确：`设备1名称…设备13名称` 归为一族、`乙方人员一姓名…乙方人员五身份证号` 归为一族；扣掉 enum 后的加权覆盖率作为看板第二指标显示。
5. 模板去重：上传一份与 #85 内容相同的保密协议 → 接口返回 `duplicateOf: 85` 提示；选"共用"后 `GET /api/templates?workTypeId=` 在两个工作类型下都能看到同一条记录，且 `template` 表只有一条。
6. 改造助手：对 `10-原材料产品报验单` 生成循环版 → 变量数从 60 降到 ≤ 20、渲染出的表格行数与原模板在"13 行数据"时一致（人工比对一次）。

#### 4.3.6 前置依赖

- 路线 B（改造助手）依赖 **4.2**（循环渲染必须先用起来）。
- 路线 C 依赖 **4.9**（知识库/资料抽取）的部分能力，但可独立先做词面匹配版。
- 路线 A 不依赖任何其他改动，**可以在 P1 立刻做**。

### 4.4 AI 填变量的质量保障

#### 4.4.1 要解决的问题

三个还没答案的问题：
1. **真实模型到底行不行？** 现有 272 项自检全部跑假模型（`scripts/test-isolated.mjs` 起独立服务 + 假服务商）。`docs/04` 的手工评测（6 个模型 × 5 个任务）说明这套判据是有效的，但那是**一次性脚本，跑完即删**，不能回归。
2. **模型会不会编数？** 已知：`qwen-flash` 会编出"3 个工作日内提交"这种期限；`deepseek-flash` 与 `glm-5.3` 会老实写 `【待补】`。这个差别必须在**换模型时自动拦住**，而不是靠人记得。
3. **哪些字段永远不许模型写？** 现在只要模型在 JSON 里给了值、且不在 `known` 里，就会被写进文书（`domain/generate.ts:336-353`）。日期、金额、编号就这么进了正式文件。

#### 4.4.2 设计：变量来源分级（先立规矩，再谈评测）

给每个变量一个**来源等级**，渲染前强制校验：

| 等级 | 含义 | 允许的来源 | 典型变量 |
|---|---|---|---|
| `auto` | 系统/档案能确定性带出 | 系统变量、档案字段、工作台原生字段 | `项目名称`、`合同编号`、`年份`、`经办人` |
| `ai` | 模型可以写，但必须基于给定事实 | 模型（且值不得包含新数字/日期） | `检查情况`、`结论意见`、`整改要求`、`备注` |
| `manual` | 只能人填或从资料抽取后**由人确认** | 人工输入 / 抽取提议被采纳 | `验收结论`、`签字日期` |
| `readonly` | **模型禁写**，只能来自 `auto` 或人工 | 系统变量、档案、人工 | 一切 `type ∈ {date, money, number, percent}` 的字段、一切 `field_key` 命中"金额/编号/日期/法定代表人/身份证/账号/电话"的字段、清单里的**数字类列**（数量、单价、合计） |

实现：
1. `.vars.json` 的变量项加 `sourceLevel`；扫描时按名字与 `type` 给**默认值**（`date/money/number/percent` → `readonly`；其余 → `ai`），写成默认值让用户能在界面上改（这就是 P5"用户自己扩展"的落点）。
2. `generateVariables()` 末尾新增 `enforceSourceLevels(variables, resolved, specs)`：
   - 对 `readonly` 且没有任何 `auto` 来源（`resolved[].from ∈ {system, archive, native}`）、也不在人工 `known` 里的变量 → **清空并标 `【待补：请填写<label>】`**，同时计入 `warnings`：`"合同金额（小写）属于只读字段，模型未参与填写，请从档案或手工填入"`。
   - 对 `ai` 等级 → 跑下面的幻觉检测，命中就把该值改成 `【待补：资料中没有<label>，请补充】` 并把命中理由放进 `rationale`。
3. `readonly` 清空这件事**必须在界面上可见**：出文书页面按"自动带出 / 需你确认 / 需你填写"三栏显示每个变量，`需你填写` 栏给出"去填档案"的直达链接（现在 `sources` 已经区分了 `system/archive/native/mapped-empty/unmapped`，界面要用满这个信息，别只显示两个数字）。

#### 4.4.3 设计：幻觉检测（数字/日期/单位必须来自事实集）

这是**纯确定性代码**，不调模型：

```
factSet = 从提示词实际用到的所有文本里抽取的"事实原子"
        = 档案值 + 工作台原生字段 + 参考资料文本 + 照片识别文本 + 备忘
        + 用户本次 instruction 里出现的数字与日期
        + 系统变量（_今天/_年份/_本月/_工作台编号）

extractAtoms(text):
  · 阿拉伯数字及其带单位/千分位写法：\d[\d,，.]*\s*(万|亿|元|万元|%|‰|个|台|套|平方米|m2|m³|天|日|个月|年|次|人|份|页|张|kW|kWh|kg|吨|米|m|mm|cm)?  → 归一化（去千分位、去空格、全角转半角）
  · 中文数字 + 单位：一二三…十百千万 + (元|日|天|月|年|个|台|次|人|份)
  · 日期：2026年9月16日 / 2026-09-16 / 9月16日 / 二〇二六年九月十六日 → 归一化为 YYYY-MM-DD（缺年份的按当前年补）
  · 编号：≥4 位的连续数字串（含字母数字混合如 XM2026-001）

check(value, factSet):
  对 value 里抽出的每个原子：
    排除掉 value 中已存在的 【待补：…】 片段（这是被允许的"承认不知道"）
    若原子不在 factSet 里 → 记为一次 hallucination {atom, context: 该原子前后 12 字}
  返回 hit 列表
```

**已知误报与处理**（必须先想清楚，否则用户会关掉这个功能）：
- 合法的"顺序号/编号生成"（如"一、二、三"的层次编号、`图 1`）→ 把这类**结构性数字**放进白名单：单个中文数字后紧跟 `、` 且位于段首的；`图 N`/`表 N`/`第 N 条` 形式；`（一）（二）` 形式。
- 单位换算产生的数字（"1,250,000 元" 与 "125 万元"）→ 事实集里同时存在两种写法时都放行；只存在一种时，**换算关系正确也算通过**（对金额做一次元/万元的等值判断）。
- 模型复述指令中的示例值 → 指令文本本身进事实集，所以不会误报。

**这件事的价值不只是"防编造"**：它同时给出一份可交付的**质量指标**——`hallucinationRate = 命中数 / 生成次数`，可以按月看、可以按模型比、可以卡门禁（见 4.4.5）。

#### 4.4.4 设计：黄金样本回归（把 `docs/04` 的一次性评测变成常驻资产）

新增 `packages/server/test/golden/`：

```
golden/
  cases/
    A-月度检查记录表.json      # { templateFile, facts, instruction, expect: {...} }
    B-短合同抽取.json
    C-变量映射梳理.json
    D-缺项分析.json
    E-向量召回.json
  templates/                  # 用的是真实在用模板的副本（保密协议、监督检查工作记录表…）
  answers/                    # 标准答案（人工写过、review 过的）
  run.ts                      # 跑分器
  baseline.json               # 上次成绩（随代码提交）
```

`cases/A-月度检查记录表.json` 长这样（这是把 `docs/04` 任务 A 的判据固化下来）：

```json
{
  "id": "A-monthly-check",
  "templateFile": "templates/月度安全检查记录表.docx",
  "facts": { "检查月份": "2026年9月", "受检单位": "第三项目部",
             "检查依据": "《清廉工程建设管理办法》第12条",
             "发现问题": "1) 材料堆放区未设置标识牌；2) 劳务实名制台账缺 8 月记录" },
  "instruction": "按上面两条问题写检查情况与整改要求，资料里没有的不要写",
  "expect": {
    "requiredKeys": ["检查月份","受检单位","检查依据","检查情况","整改要求"],
    "mustContain": ["材料堆放区","标识牌","劳务实名制","8 月"],
    "mustNotContainAtoms": ["3个工作日","5个工作日","立即整改","已整改"],
    "minTodos": 1
  }
}
```

`run.ts` 对每个 case 输出：

| 指标 | 算法 | 门禁 |
|---|---|---|
| `jsonValid` | `parseJsonLoose` 成功（含自动重试后成功） | 100% |
| `keysExact` | 输出键集合 ⊇ `requiredKeys` | 100% |
| `factsExact` | `mustContain` 里的每个串都出现在值里 | ≥ 95% |
| **`noFabrication`** | `mustNotContainAtoms` 一个都不出现 **且** 幻觉检测 0 命中 | **100%（硬门禁）** |
| `todosUsed` | 资料不足的键里 `【待补` 出现次数 ≥ `minTodos` | ≥ 90% |
| `latencyP95` | 耗时 P95 | ≤ 60s |
| `costPerDoc` | 该次调用 token × 单价 | 记录、不卡 |

**必须用真实模型跑**（否则这个套件的意义等于零），所以：
- 它**不进 `npm test`**（不花钱、不联网），而是 `npm run test:model`，并且**默认只跑 1 个 provider**（配置文件里指定的"候选写作模型"）。
- 每次跑完把成绩写进 `baseline.json`（含时间、provider、model、各指标），**成绩变差会在输出里高亮**。
- 用固定 `temperature=0.2` + 固定 `seed`（若服务商支持）+ 固定提示词，保证可复现；模型本身有随机性，所以每个 case **跑 3 次取最差**（宁可悲观）。

#### 4.4.5 设计：模型门禁（"没跑过评测的模型不许设为写作用途"）

1. `ai_profile` 增加 `verified_at`、`verify_score`（JSON：各指标值）、`verified_model`。
2. `PUT /api/ai/profiles/:purpose` 在 `purpose ∈ {writing, extract}` 且 `model` 变化时：**若新模型没有 `verified_at` 记录 → 返回 409 `MODEL_NOT_VERIFIED`**，消息给两条路：`立即跑评测（约 3 分钟，消耗约 X token）` / `我知道风险，仍然启用（记入 note，界面显示"未验证"黄标）`。
3. `aiReadiness('writing')` 把"未验证"作为**提示**而不是错误（不能因为没跑评测就不让用），但界面上模型档案那一行必须显示 `已验证（noFabrication 100%，P95 5.2s，2026-09-30）` 或 `未验证`。
4. 门禁的判据写死：`noFabrication = 100%` 且 `keysExact = 100%`。**达不到就不建议设为写作模型**（可以设，但黄标常驻）。

#### 4.4.6 验收标准

1. `npm run test:model` 能跑完、输出 5 个 case 的指标表，并把结果写进 `baseline.json`；在 DeepSeek `deepseek-flash` 上 `noFabrication` 必须为 100%（与 `docs/04` 的结论一致，若不一致说明判据或提示词变了，要查）。
2. 拿 `docs/04` 里被淘汰的模型（`qwen-flash`）跑同一个 case → `noFabrication` **必须失败**（若它这次没编，说明判据不够狠，要加 case，而不是放宽判据）。这条断言的作用是**证明检测器真的能抓到编造**。
3. 幻觉检测单测：给 8 组"事实集 + 生成值"，其中 3 组有编造（凭空期限、凭空金额、凭空的整改状态）、2 组是安全的换算（125 万 vs 1,250,000）、2 组是结构性数字（`一、`、`图 2`）、1 组是复述指令示例 → 检测结果与预期逐条一致。
4. `readonly` 强制：构造一个含 `{合同金额小写}`（`type=money`）的模板，档案里**不填**金额 → 生成结果的 `合同金额小写` **必须是 `【待补：…】`**，且模型即使返回了 `"1250000"` 也被丢弃、`warnings` 里有说明。
5. 换模型门禁：把 writing 的 model 从 `deepseek-flash` 改成任意未验证模型名 → **HTTP 409**；带 `?force=true` 或确认参数后成功，且档案里记 `verified_at=null`、界面显示黄标。

#### 4.4.7 前置依赖

- 幻觉检测依赖**变量来源分级**（要先知道哪些字段禁写）。
- 黄金样本用例依赖 **4.2** 的 `kind: list/image`（否则月度检查表里的清单类数据测不了）。
- 门禁依赖 `ai_profile` 的表结构变更（迁移）。

### 4.5 影像取证闭环

#### 4.5.1 要解决的问题

用户的原话里"拍现场照片留证"是五件事之一。现在系统能收照片、能校验张数、能让模型单张看，但**拍照的人在现场不知道该拍什么**（`evidence_rule` = 0 条，`position_template` 只有项目类阶段，行政管理类连阶段都没有），**拍完不知道该不该重拍**（初检要一张张点），**拍得好不好和"这条清单算不算完成"没关系**（核销纯手工）。

#### 4.5.2 设计：规则库（把"该拍什么"变成数据）

**表结构**（`evidence_rule` 已有 `position_template_id`、`title`、`min_count`、`max_count`、`shooting_points`、`angles`、`required`、`sample_artifact_id`、`hint`）—— 只补两个维度：

```
+ scope         -- 'position'（阶段） | 'checklist'（检查项，如清廉工程的某条） | 'generic'
+ tags          -- JSON: ["安全","材料","廉洁"]，用于按主题复用
+ standard_ref  -- 依据（如《清廉工程建设管理办法》第12条）
+ archived_at   -- 已有
```
`sample_artifact_id` 从"死列"变成一等公民：**每个规则可以挂 1 张合格示例图**（存 `artifact.id`，指向 `_规范库/示例/` 下的图）。

**第一批要建的规则（不是"以后慢慢加"，是 P2 就要落地的具体清单）**：
- **清廉工程月度检查**（服务对象最真实的那件事，工作台 #39 就是它）：把"检查什么"拆成 8–12 条检查项，每条给 `shooting_points` + `angles` + `min_count` + 一张示例图。示例图从用户手上的历史检查资料里找（`_原始资料` 里放进去，或让用户拍一张合格的）。
- **项目类阶段**（复用现有 40 条 `position_template`）：现在 `evidence_rule` 是空的，但 `seed.ts` 里**已经写了**项目类的影像清单（开箱前外包装、设备铭牌与序列号、验收会现场…），要做的只是**把它们种进 `evidence_rule` 并补上要点与示例图** —— 这是"已有数据没被用起来"的典型。
- 落地方式：`POST /api/rules/evidence/import-defaults`（幂等种入，不覆盖用户改过的）＋ 界面上的"规则库"页（现在只有 `POST /api/evidences` 和 `DELETE /api/rules/:kind/:id`，没有列表与编辑页）。

#### 4.5.3 设计：拍摄引导（拍之前就知道该拍什么）

1. **清单项详情页**显示"要拍什么"：`title` + `shooting_points` + `angles` + `min_count` + **示例图缩略图**（点开看大图）。
2. **上传时前置校验**（目前只校验"是不是图片"）：
   - 文件太小于 300×300 像素 → 提示"这张太小，看不清铭牌，建议重拍"（尺寸从 EXIF 读，`routes-files.ts` 已经在抽 `宽度/高度`）；
   - `captured_at` 早于工作台 `start_date` → **提示但不拦**："这张的拍摄时间是 2026-03-02，早于开工日期 2026-05-10，作为本阶段证据可能被质疑"（这是审计真会问的问题）；
   - `captured_at` 为空（有些图没有 EXIF）→ 提示"这张没有拍摄时间，建议用手机原图重传"，并要求人工填 `doc_date`。
3. **拍摄引导的可移动性**：用户在现场大概率用手机拍照再传回电脑。系统不做移动端（见第 6 节），但要把"要拍什么"做成**可带走的东西**：清单页提供"打印/导出拍摄要点卡片"（一张 A4，列出本次要拍的项目、张数、要点、注意事项）。这是零成本的务实替代。

#### 4.5.4 设计：批量初检与人核销的关系

**批量初检**（`POST /api/vision/review-batch`，新增）：
- 入参：`{ workbenchId, positionCode?, checklistItemIds? }`；默认**该工作台所有"有照片但没初检过（或照片 sha256 变了）"的清单项**。
- 逐条调 `reviewChecklistItem()`（已存在，会带上拍摄要点），串行 + 每条限流；返回逐条结果 + 总体摘要。
- 结果写入 `evidence_review`（已存在）并**汇总成一张表**：`✓ 合格 12 条 / ⚠ 需补拍 3 条（列出要补什么）/ ? 看不清 2 条`。
- 界面上一键"按初检结果预勾选"：`ok` 的预勾选、`issue` 的**保持未勾选并置顶**、`unclear` 的标黄要求人看。

**与人核销的关系（这是设计要点，不能含糊）**：

| 初检结论 | 清单项状态 | 人的动作 |
|---|---|---|
| `ok` 且张数 ≥ `min_count` | 预勾选（`done_count` 由系统写，`done_by` 写 `vision:model`） | **确认或取消**（一次点击） |
| `issue` | **不许勾选**，清单项置顶并显示"要补拍：<具体问题>" | 补拍，或写"接受理由"后强勾（会记 `note`） |
| `unclear` | 标黄、不自动勾选 | 人看一眼再定 |
| 没有视觉模型 / 调用失败 | 完全回退到现状（纯人工核销），并在页面顶部说明原因 | 照旧手工 |

**铁律**：模型**永远不能**直接把清单标成完成。它只能写"预勾选建议"，落库动作仍然由人触发（和 AI 助手"写操作先提议"一致，`core/vision.ts` 开头的注释就是这个立场，要守住）。

#### 4.5.5 设计：从初检到文书内容的贯通

现状已经有一条：出文书时照片先由视觉模型转述，转述文本进写作提示词（`evidenceContextFor`）。要补三件：
1. **只送合格/已确认的照片**（现在把勾选为参考的照片全送，包括 `issue` 的）→ 送之前过滤，`issue` 的照片送"问题点"而不是"结论"，让文书能写"现场发现…"（而不是把有问题说成没问题）。
2. **照片元数据进文书**：图注带拍摄时间（`artifact.captured_at`，EXIF 已抽）、地点（若 EXIF 有 GPS，转成"经度/纬度"文字或地址提示 —— **本机不做逆地理编码**，那是需要联网的服务）、设备型号。审计问"这照片什么时候拍的"时，文书里直接有答案。
3. **照片清单表**：文书末尾自动生成"附件：现场照片 X 张"并逐张列出（序号、说明、拍摄时间），数量与实际嵌入的图片数**由同一份数据算出**，不会出现"写了 6 张实际贴了 5 张"。

#### 4.5.6 验收标准

1. `evidence_rule` 从 0 条到 ≥ 20 条（清廉工程 ≥ 8 条、项目类复用 seed ≥ 12 条），每条都有 `shooting_points`，≥ 8 条有 `sample_artifact_id`。
2. 清单项详情页能看到要点与示例图；导出拍摄要点卡片为一份 docx（用模板生成的，顺带验证循环能力）。
3. `POST /api/vision/review-batch` 对 5 条清单项 × 共 12 张照片跑完：返回逐条结论、总耗时 < 60s（假视觉模型下 < 3s）、结果全部落 `evidence_review`。
4. **初检→核销闭环的可靠性断言**（关键，防止"模型说行就行"）：
   - `issue` 的清单项调 `PUT /api/checklist/:id {status:'done'}` 时，**接口仍允许**（不能剥夺人的权力），但**响应里必须带 `warnings` 说明模型认为不合格**，且库里 `note` 自动追加该警告（留痕）；
   - 用假视觉模型返回 `ok` → 界面"预勾选"按钮可用；返回 `issue` → 按钮禁用且显示补拍说明。
5. EXIF 校验：上传一张 EXIF 时间早于 `start_date` 的照片 → 返回 `warnings` 含该提示，但**入库成功**（不拦）。
6. 出文书时勾选 3 张照片（2 张 ok、1 张 issue）→ 产物里图片 3 张（如果是图片变量模板）或提示词里 3 段描述，且 `issue` 那张的描述是"问题"语气；"附件：现场照片 3 张"与实际数量一致。

#### 4.5.7 前置依赖

- 图片嵌入（4.2）是"照片进文书"的前提，但本域的**规则库、引导、批量初检、核销闭环**都不依赖它，可以并行。
- 规则库的示例图需要一个放图的地方：`_规范库/示例/`（目录规范里新增一个子目录，要同步 `docs/01`）。

### 4.6 知识库落地：分层、条款级引用、口径校验

#### 4.6.1 要解决的问题

三个层次的问题，代价从小到大：

1. **没有语料**（`kb_document` = 0，`_规范库` 空）→ 检索链路再好在空库上也等于零。
2. **引用不够用**：现在能回答"出自《XX管理办法》第 3 段"，但公文里要写的是"依据《XX管理办法》第十二条"，**给不出条号**，用户还得自己翻回去对。
3. **口径校验完全没有**：合同金额大写小写要一致、日期不能早于开工日、编号格式要对、人数要与清单匹配 —— 这些是"制度口径"里**唯一能被机器判定**的部分，现在一条都没做。而它们恰恰是最容易被退回的地方。

#### 4.6.2 设计：知识库分层

`kb_document` 补三列（迁移）：

```
+ tier        -- 'national'（国家）| 'industry'（行业）| 'org'（单位）| 'project'（项目）
+ doc_no      -- 发文字号（如「晋清廉办〔2026〕3号」）
+ effective_date, expire_date, supersedes_id
```

**为什么要分层**：检索时**层级决定优先级**。同一个问题如果国家规定和单位细则都命中，公文里应写单位细则（更具体）+ 国家依据（更权威）。所以 `searchKnowledge()` 的排序从"纯相似度"改成"**分层加权**"：`score × tierWeight`（project 1.15 / org 1.10 / industry 1.05 / national 1.0），并在返回里标出层级。**同一主题多个层级都有命中时，提示用户"该主题存在 3 个层级的依据，建议同时引用"**（这是真实公文写作的习惯）。

#### 4.6.3 设计：条款级引用（切块策略改造）

现在 `chunkText()` 按"段落 → 句子"切 500 字。对制度类文档要改成**先按条款切**：

1. **结构识别**（确定性，不用模型）：在文本里识别
   - `第[一二三四五六七八九十百零〇\d]+条` / `第…款` / `（一）（二）` / `1.1` / `１．` 等编号形态；
   - 识别到"条"级边界时，**以条为单位切块**（一条超过 1200 字时，按款再切，并在 `heading` 里保留条号）；
   - 完全识别不到条号（如一份通知）→ 回落到现有的段落/句子切块。
2. 每块带 `heading = "第十二条 适用范围"`，`kb_chunk` 增加 `clause_no`、`clause_path`（如 `第三章/第十二条/第二款`）。
3. **问答与生成的引用格式**：模型返回的引用改成 `《清廉工程建设管理办法》第十二条`；界面上的 `citations` 直接显示条号 + 原文片段（点开看整条）。
4. **验收方式**：拿一份真实制度文件（用户提供的 PDF/Word），切块后**人工抽查 10 条**：条号对不对、有没有把两条切进一块。

**被否决的方案**：用模型给文档自动加条号。原因是模型会重新编号（把"第十二条"流畅地写成"第十一条"），而制度文号是**错一个数字就被退回**的东西。**结构识别必须是纯规则的**，识别不到就老实回落到段落切块，并在块上标"无条号"。

#### 4.6.4 设计：口径校验规则引擎（本域最重要的一块）

**核心决定：口径校验全部是确定性规则，绝不交给模型判断。** 模型可以**解释**规则为什么不过，但不能决定过不过。

**规则的数据结构**（新表 `compliance_rule`，P3）：

```
id, code, name,
scope_work_type_ids  -- JSON，适用哪些工作类型（空=全部）
scope_template_ids   -- JSON，适用哪些模板（空=全部）
severity             -- 'block'（拦下，不许保存）| 'warn'（提示）| 'info'
kind                 -- 'builtin' | 'custom'
checker              -- builtin 规则用内置函数名；custom 用表达式
params               -- JSON，规则参数（如 tolerance、正则）
message              -- 人话说明（"合同金额大写与档案里的金额不一致"）
fix_hint             -- 怎么改
enabled, sort_order, origin, created_at, updated_at
```

**第一批内置规则（P3 落地，按"真实会被退回"排序）**：

| code | 检查 | 判据 | severity |
|---|---|---|---|
| `amount_cn_case` | 合同金额大写与小写一致 | 档案 `contract_amount`（数字）经 `amountToChinese()` 转换后，与文书里 `合同金额大写` 变量的值**归一化比对**（去"人民币"、去空格、全/半角统一） | **block** |
| `date_order` | 日期序列合法 | `sign_date ≤ start_date ≤ plan_end_date`；文书的落款日期 ≥ `sign_date`；任一违反 | **block** |
| `date_before_start` | 文书日期不早于开工日 | 生成日/填表日 < `start_date` | warn |
| `party_consistency` | 甲乙方名称在同一份文书内一致 | 同一份文书的"甲方"出现多次时必须同一字符串（含简称映射，用 `labelAliases`） | **block** |
| `number_format` | 编号格式符合规范 | 项目编号 `^\d{4}-[AP]-\d{3}$`（与 `next-code` 的生成规则同源）；合同编号若档案里有 `doc_no` 规则则按其校验 | warn |
| `unit_whitelist` | 单位量纲合法 | 数量类变量的单位 ∈ 白名单（台/套/个/米/平方米/…）；出现"个/台"混用同一列表 | info |
| `phone_format` | 电话格式 | 11 位手机号、固话带区号 | warn |
| `credit_code` | 统一社会信用代码 | 18 位 + 校验位算法（GB 32100-2015，纯算法可实现） | **block** |
| `person_count_match` | 人员数量与清单匹配 | 模板写了"共 N 人"，实际列出的姓名条数 = N | **block** |
| `amount_sum` | 明细合计等于总额 | 循环列表的"金额"列求和 = 合同金额（允许 ±0.01 舍入） | **block** |
| `attachment_count` | 附件数量与实际一致 | "附件：X 张/Y 份"与实际嵌入的图片/附件数一致（由渲染器回填实际数量，见 4.5.5） | warn |
| `check_items_complete` | 廉洁检查项齐全 | 月度检查表里的检查项条数 = 规则库该主题的条数（漏项就是漏检） | **block** |

**实现位置**：新增 `core/compliance.ts`，导出
```
runCompliance(ctx: { templateId, workTypeId?, workbenchId?, values, loopData, resolvedVars }): RuleResult[]
RuleResult = { code, name, severity, passed, message, fixHint, evidence: {actual, expected, where} }
```
在 `POST /api/generate/save` 与 `POST /api/generate/preview` 里调用：
- `block` 规则不通过 → **412 `COMPLIANCE_BLOCKED`**，响应体列出每条违规的"实际值/期望值/在哪一项"；
- 允许人工**例外放行**：`POST /api/generate/save { allowRuleViolations: ["amount_cn_case"], exceptionNote: "甲方要求按合同原件写法" }` → 放行但把例外写进 `generation_log.variables` 旁的审计字段（新列 `compliance_exceptions`），**并且产物里不体现**（不污染公文），但界面上该文书显示"有 1 项口径例外"标签。
- `warn` → 照常保存，界面上黄色提示 + 列出。

**用户自定义规则（P3 加分项，P5 原则的落点）**：`kind='custom'` 用**受限表达式**而不是 `eval`：
```
{"kind":"custom","checker":"expr",
 "expr":"{合同金额小写} == {明细合计}",
 "message":"明细合计与合同金额不一致"}
```
求值器只支持：变量引用、`== != > < >= <=`、`+ - * /`、`&&` `||`、`in [...]`、`matches("正则")`、`sum(列表.字段)`、`count(列表)`。**绝不 `eval`**（本地单用户也绝不允许，因为规则可能由 AI 提议生成）。

#### 4.6.5 设计：把制度送进知识库（语料从 0 到有用）

1. **入口**：`_规范库/` 手工拷贝 + `POST /api/kb/import-all`（已有：扫目录 + 补登记 + 抽取文字）；界面加"分层"选择（录入时选国家/行业/单位/项目，或从文件名/发文字号自动猜）。
2. **元数据补全**：导入后对每份文档跑一次 `extract` 用途，抽 `doc_no / 发布单位 / 发布日期 / 施行日期 / 层级`，**以提议形式给人确认**（不自动写）。这一步的提示词可以做得非常窄（只抽 5 个字段），出错率低。
3. **第一批要进的语料（具体的，不是"有空再传"）**：清廉工程相关的上级文件与本单位实施细则（这是用户月月要用的）、工程类的验收规范/质量标准、本单位合同管理办法与合同模板配套的制度。**先 3–5 份、每份确认过条号**，把链路验通，再放量。

#### 4.6.6 验收标准

1. 分层：导入 4 份不同层级文档，同一问题检索 → 返回里标出层级，且单位细则排在国家级之前（同等相关度时）。
2. 条款切块：对一份含"第一条…第二十条"的制度，切块后**抽查 10 条，条号 10/10 正确**；对一份没有条号的会议纪要，回落到段落切块且不报错。
3. 引用格式：问答返回的 `citations` 含 `clause_no`；前端显示"《XX办法》第十二条"并可点开整条原文。
4. 口径校验（每条规则至少一个正例一个反例）：

   | 规则 | 反例输入 | 期望 |
   |---|---|---|
   | `amount_cn_case` | 档案 1250000.00，文书里写"壹佰贰拾万元整" | 412 block，消息指出实际/期望 |
   | `date_order` | 开工 2026-09-01，签订 2026-09-10 | 412 block |
   | `credit_code` | 18 位但校验位错 | 412 block |
   | `amount_sum` | 明细 3 项合计 1249000 ≠ 合同 1250000 | 412 block |
   | `check_items_complete` | 月度检查表少填 2 项 | 412 block |
   | `date_before_start` | 填表日 2026-08-01，开工 2026-09-01 | 200 + warn |
   | `phone_format` | "1234" | 200 + warn |

5. 例外放行：带 `allowRuleViolations` 保存 → 200，且 `generation_log.compliance_exceptions` 记录了规则码与说明；界面上该文书有"口径例外"标签。
6. 自定义规则：建一条 `{expr:"{数量} matches(\"^[0-9]+$\")", message:"数量必须是数字"}`，用字母值触发 → 412；表达式里出现 `eval`/函数调用白名单外的标识符 → **建规则时就被拒绝**（不是运行时）。
7. 语料导入：`_规范库` 放 3 份真实制度 → 导入后 `kb_document=3`、分块数合理、`/api/kb/ask` 能答出带条号的引用。

#### 4.6.7 前置依赖

- 口径校验依赖**档案字段的类型信息**（`archive_field.type` 已有）与 `contract_amount` 等原生列（已在 `workbench` 上）。
- `attachment_count` 依赖 4.2/4.5 的实际嵌入数量回填。
- 语料导入不依赖任何改动（现在就能做），**应该尽早开始**，因为"制度进库"是纯人工活，早一天开始早一天有用。

### 4.7 AI 助手的边界与能力扩展

#### 4.7.1 要解决的问题

用户明说了："我可能有一个事情没空仔细操作或者设置，我直接交代给大模型，他帮我记住或者直接修改了。"
现在的助手能：查数据、改字段、加别名、改设置、记备忘、核销清单、看照片、删工作台（需确认）。
**不能**：出一份文书、把"这个月的检查"从一件事拆成十几步并盯着做完、回滚自己做过的事。

#### 4.7.2 设计：哪些操作允许直接做、哪些必须确认、如何回滚

把现有的两档（读 / 写）细化成三档，并明确回滚方式：

| 档 | 判据 | 例子 | 回滚 |
|---|---|---|---|
| **直接执行** | 只读，或写入只影响"助手自己的"记录 | 查工作台/模板/待办/设置、检索知识库、列记忆、看照片（`review_photos` 会写 `evidence_review`，但那是"意见"不是"事实"，可接受） | 不需要 |
| **必须先确认**（现有机制） | 改的是**用户可见的业务数据或配置** | 改档案值、改工作台字段、加别名/字段、改系统设置、改模型接入、核销清单、给文件写说明、记备忘 | `agent_action.result` 里记 `before` 值 → 撤销时反向写回（**新增**，现在只记 `result` 没记 `before`） |
| **危险 + 二次确认**（现有机制 + 加重） | 删除、批量覆盖、涉及已定稿文书 | 删工作台、批量采纳提议、覆盖已有别名（`force`）、把 `verified` 模型换掉 | 删除走**回收站**（4.11）；批量操作按 `batch_id` 整体撤销（**新增**） |

具体改动：

1. **`agent_action` 增加 `before`（JSON）与 `batch_id`**，让"撤销"成为可能：`POST /api/agent/actions/:id/revert` —— 只允许撤销 `status='applied'` 且 `before` 非空的动作，撤销本身也生成一条 `agent_action`（留痕，可再撤销）。
2. **危险动作的确认信息要"说清后果"**：`delete_workbench` 现在的 `summarize()` 要升级为带上"将删除：3 个阶段、47 条清单勾选、12 个文件、共 86MB"，并把数字**从库里实时算**（不是模型编的）。人在点确认前必须看到这些数字。
3. **`update_setting` / `update_ai_profile` 的确认要有 diff**：显示"AI 助手模型：deepseek-flash → glm-5.3"，而不是"修改了一个设置"。
4. **写入前先"再查一遍"**：`set_archive_value` 执行时若发现目标值与 `agent_action` 生成时读到的旧值不同（有人在界面上先改了），**拒绝执行并提示"该字段已被改动（旧值 X，现值 Y），请确认后重试"**。这是防"模型基于过期信息写入"的必要一道。

#### 4.7.3 设计：多步任务编排（"帮我把这个月的检查做了"）

**不做自主 agent 循环**（让模型自己无限轮次地规划 — 太贵、不可预测、出错难追）。做**模板化的任务单 + 人确认的推进**：

1. **任务单的形态**：一个"月度检查任务"= 一串有序步骤，每步是"**要产出的东西** + **判据**"：

   ```
   步骤 1  生成本月检查通知        （模板：03-开工申请…换成"月度检查通知"；判据：文书已归档）
   步骤 2  备齐制度依据            （判据：知识库里能检索到 ≥1 条清廉工程制度条款，且已列进任务的依据清单）
   步骤 3  现场拍照并核销          （判据：全部影像清单项 status=done 或 na）
   步骤 4  填写检查记录表          （模板：监督检查工作记录表；判据：文书已归档且口径校验通过、无 block）
   步骤 5  汇总本期材料并归档      （判据：本期目录下 3 类文件齐全：通知/记录表/照片）
   步骤 6  完成本期                （判据：调 completeWorkbench，写 last_done_period）
   ```

2. **任务单从哪来**：由**工作类型的"周期包"模板**定义（新表 `task_recipe` / `task_recipe_step`），用户可在界面上编辑 —— 又一次落在 P5（数据而非代码）。第一份周期包就是"清廉工程月度检查"。
3. **助手的角色**：用户说"把这个月的检查做了" → 助手（1）识别是哪个工作台（用 `findWorkbench`，歧义就拒绝并要求指定，这个已有）；（2）读该工作台的 `recurrence` 与当前期；（3）**生成一份任务单实例**（新表 `task_run` / `task_run_step`），把它作为**一条可操作的清单返回**，而不是自己去执行；（4）用户点"开始"，助手**逐步执行只读动作**（查模板、查知识库、列照片、算缺口），把每一步的"需要你做什么"变成**待确认动作**；（5）每完成一步更新状态，最后汇总。
4. **状态与续做**：`task_run.status ∈ {planned, running, blocked, done, abandoned}`；每一步 `{status, evidence, action_id}`。因为落在库里，**可以关掉浏览器明天接着做**（这是"按月重复的行政工作"的真实需要 —— 一件事不会一次做完）。
5. **汇报格式**（用户要能一眼看懂）：任务单页面固定三段：
   - `已完成`：做了什么（带时间）
   - `等你确认`：N 条待确认动作（可逐条或全选）
   - `卡住了`：为什么（缺数据/缺模型/口径不过），以及**下一步该做什么**
6. **助手新增工具**（`domain/agent.ts`）：
   - `start_task({ workbench, recipe })` → 生成任务单实例（写操作，需确认）
   - `get_task({ taskRunId })` → 读任务单状态
   - `step_done({ taskRunId, stepNo, evidence })` → 标记步骤完成（写，需确认）
   - `generate_document({ workbench, templateId|checklistItemId, instruction })` → **生成文书草稿并返回给用户确认**（不直接归档；沿用 `generateVariables` + `previewDocument`，把变量与预览一起返回）
   - `list_photos_to_review({ workbench })` / `review_photos`（已有）
   - `propose_archive_filing({ workbench, artifactIds })` → 提议把 `_待归档` 里的文件归到哪个阶段目录（写，需确认）

   `generate_document` 是这里最重要的一条：**助手能出文书，但出的永远是"草稿"**，归档动作必须人来点。

#### 4.7.4 设计：长期记忆的组织

现状 `agent_memory` 只有 `text, tags, workbench_id, due_date, source, status, created_at`，检索是"与消息做词面/gram 匹配"（`relevantMemories`）。问题：记忆越多，词面匹配越不准。

改为**三层 + 显式来源**：
```
+ scope      -- 'global'（单位口径、习惯，如"我们单位文书落款写'XX公司'不写全称"）
             | 'work_type'（工程类通用，如"隐蔽工程验收必须有监理签字"）
             | 'workbench'（本项目专属，如"甲方换成了 XX 公司"）
+ key        -- 可为空；有 key 的记忆是"事实型"（同一 key 的新记忆顶掉旧的）
             |   无 key 是"提醒型"（累积）
+ source_msg_id, source_action_id  -- 这条记忆是从哪句话/哪个动作来的（可追溯）
+ superseded_by  -- 被哪条新记忆取代
```

- **注入规则**：对话时注入 `global + 对应 work_type + 当前 workbench` 的记忆，按 `scope` 加权（workbench > work_type > global），**事实型只取最新一条**。
- **出文书时**（`domain/generate.ts` 已在做）注入 `workbench + work_type` 的事实型记忆，并保持"与备忘冲突以备忘为准"的现有规则。
- **冲突检测**：写入一条与已有记忆同 `key` 但值不同的记忆时，**必须显示冲突**（"之前记的是 A，这次是 B，改吗？"）而不是静默新增。这是防止"记了等于没记"的关键（用户原话是"以后涉及到就直接给我正确的答案"，那系统就不能同时记住两个答案）。

#### 4.7.5 验收标准

1. 撤销：助手提议改档案值 → 确认执行 → 调 `POST /api/agent/actions/:id/revert` → 值回到改前；再撤销一次 → 回到改后（两级撤销可用）；撤销动作本身在 `agent_action` 里可见。
2. 过期写入防护：生成待确认动作 A（把 `party_a_name` 改成 X）→ 在界面上手工改成 Y → 确认 A → **被拒绝**并提示"已被改动（旧值 A 的旧值，现值 Y）"。
3. 危险动作摘要含实时数字：`delete_workbench` 的待确认卡片显示"3 个阶段 / 47 条清单 / 12 个文件 / 86MB"，数字与库和磁盘一致（用一个已知工作台核对）。
4. 任务单：对工作台 #39 起一个"月度检查"任务单 → 6 个步骤、每步有判据；关掉服务重启 → 任务单还在（`status` 与各步状态保留）；步骤 3 因"没有照片"置 `blocked` 并给出"去拍照"的入口。
5. `generate_document`：助手被要求"出这个月的检查记录表" → 返回草稿变量 + 预览链接 + **待确认的归档动作**，且**在用户确认前磁盘上没有新文件**。
6. 记忆冲突：先记"甲方是 A 公司"，再记"甲方是 B 公司"（同 `key='party_a_name'`）→ 第二次写入前返回冲突提示；用户确认后旧记忆 `superseded_by` 指向新记忆，检索只返回 B。
7. 记忆分层：一条 `global` 记忆（"落款写'数科公司'"）在**另一个工作台**的对话里也能被注入（同一 `work_type` 内验证一次、`workbench` 隔离验证一次：A 工作台的记忆不出现在 B 工作台）。

#### 4.7.6 前置依赖

- 撤销依赖 `agent_action.before`（迁移）。
- `generate_document` 依赖 4.2（否则清单类文书出不来）与 4.4（来源分级，防止助手出的草稿乱填数字）。
- 任务单依赖 4.5（步骤 3 的照片核销）与 4.6（步骤 2 的制度依据、步骤 4 的口径校验）。

### 4.8 数据安全与可恢复

#### 4.8.1 要解决的问题

四个具体场景，每一个都可能真发生：

1. **硬盘坏 / 误删目录** → 现在只有手动 `npm run pack -- --with-runtime-state`，用户不会定期跑（而且要先停服务）。
2. **删错工作台** → `deleteWorkbench` 直接 `rmSync` 目录（D6），不可恢复。用户的原话里"我可能没空仔细操作"——**越是这样的人，越容易点错**。
3. **Word 保存时崩了 / 改坏了想回退** → 生成文书没有版本概念，`artifact.version` 是空的死列（D8）。
4. **同步盘冲突** → `workbench.config.json` 明说数据目录可以放 OneDrive/坚果云；但 SQLite 的 `-wal`/`-shm` 与 `.db` 在同步盘上**可能被同步成不一致的组合**。这条现在的处理是"用户自己小心"。

#### 4.8.2 设计：自动快照（P0）

`npm run pack -- --with-runtime-state` 的机制是对的（`node:sqlite` 的 `backup()` 做在线一致性快照 + `quick_check` + `foreign_key_check` + tar 校验），**问题只是它需要手动、且要停服务**。改造：

1. 新增 `core/backup.ts`：
   ```
   createSnapshot(kind: 'auto'|'manual'|'pre-restore'): SnapshotResult
   ```
   - 用 `backup(db, tmpFile)` 做**在线**快照（WAL 模式下这是唯一正确的做法；**被否决的方案**：直接 `copyFileSync(workbench.db)` —— 在 WAL 模式下会丢掉未 checkpoint 的事务）。
   - 快照落 `data/runtime/backups/YYYYMMDD-HHmmss-<kind>/workbench.db`。
   - 三个校验必须全过才算成功：`PRAGMA quick_check` = ok、`PRAGMA foreign_key_check` 空、表行数与源库一致（逐表 `COUNT(*)` 比对）。
   - 写 `MANIFEST.json`：时间、kind、库大小、各表行数、`data/files` 的文件数/总字节、模板 48 份的 sha1（**这就是 4.1 的 `template_health` 之外的独立凭证**）。
2. **触发时机**（三个都要，缺一个都会漏）：
   - 启动时（`bootstrap` 末尾，异步、不阻塞监听）：一天最多一次；
   - 每次"危险操作"前：`deleteWorkbench`、`templates/:id/permanent`、批量采纳提议、`reset` → 先建一个 `pre-restore` 快照；
   - 界面上一个"立即备份"按钮（原来那个 `pack` 命令的可视化版）。
3. **保留策略**：自动快照保留最近 7 日 + 每月 1 号保留 6 个月；**总量上限 2GB**，超了删最旧的自动快照（手动快照永不自动删）。
4. **失败要吵**：快照失败 → `/api/health` 返回 `backupStale: true` + 界面上一条黄色横幅（"最后一次成功备份是 3 天前"）。静默失败的备份等于没有备份（P6）。
5. **还原文档 `docs/10-备份与还原.md`**：写清"快照怎么还原"（停服务 → 换库文件 → 起服务 → 验证 `db:init` 输出）、"文件目录怎么还原"（`data/files` 直接拷回）、**以及备份里不含什么**（`ai_provider.api_key` 在库里，会在快照里 —— 这条必须明说，因为快照可能被拷到 U 盘）。
6. **同步盘风险**：`ensureBaseDirs()` 时若检测到 `DATA_ROOT` 路径里含 `OneDrive`/`坚果云`/`Dropbox` 等字样 → 界面提示"数据库放在同步盘上，`-wal` 文件可能在同步中被拆散，建议把 `data/runtime` 移出同步目录（`workbench.config.json` 里把 `dataRoot` 指到非同步盘，或把 `RUNTIME_ROOT` 单独指出去）"。**并给出一个真正可行的方案**：允许 `WORKBENCH_RUNTIME_DIR` 环境变量把 runtime 目录（库、日志、快照）与 `data/files` 分开配置 —— 文件放同步盘、库放本地盘。

#### 4.8.3 设计：回收站与删除防护（P0）

**统一回收站**（一张表 + 一个目录）：

```
deleted_item:
  id, kind ('workbench'|'artifact'|'template'|'generated'), ref_id,
  trash_rel      -- _回收站/<kind>/<uuid>/... 下的实际路径
  meta           -- JSON：删之前的完整记录快照（workbench 行、template 行、artifact 行）
  dir_meta       -- JSON：被移走的目录树清单（相对路径+大小+sha1）
  size_bytes, deleted_by ('user'|'agent:<actionId>'|'rule:<code>'),
  deleted_at, restore_deadline, restored_at, purged_at
```

- **删除 = 移动，不 = 删除**：`deleteWorkbench` 改成把整目录 `rename` 到 `_回收站/workbench/<uuid>/`（同盘 rename 是原子的、快的、可回滚），库记录**不删**而是打 `deleted_at` 标记（或者复制一份到 `meta` 再删 —— 选择**打标记**，因为外键级联会让"恢复"变成重建地狱）。所有"列表"查询排除 `deleted_at IS NOT NULL`。
  - **迁移成本要诚实说**：`workbench`、`artifact`、`template` 三张表各加一列 + 所有列表查询加一个条件（`service.ts` 的 `listWorkbenches`、`listTemplates`、`store.ts` 的 `listArtifacts`/`searchArtifacts`、`checklist` 的计数、`kb` 的文档列表）。**共约 12 处查询**。这不是"加个按钮"，是这一阶段最需要细心的一项。
- **保留与清空**：默认保留 30 天；回收站页面显示总占用；"彻底删除"二次确认（手打"彻底删除"四字，沿用界面上已有的确认模式）+ 删除前自动建 `pre-restore` 快照。
- **删除防护（三个都必须做）**：
  1. **服务端要求确认参数**：`DELETE /api/workbenches/:id` 必须带 `?confirm=<workbench.code>`（输入的编号与记录一致才执行）；不带 → 400 并返回"将要删除什么"的清单。**这条是防脚本/AI 误删的关键**（现在 AI 助手有 `delete_workbench` 工具，它只能提议；但服务端再要一次确认，双保险）。
  2. **影响预览接口**：`GET /api/workbenches/:id/deletion-impact` 返回 `{positions, checklistItems, artifacts, bytes, generatedDocs, photographs}` —— 界面上的确认框必须显示这些实时数字。
  3. **AI 助手侧**：`delete_workbench` 只允许在**用户在该轮对话里明确说了"删除"**时提议（提示词已经在做）；执行时再校验 `confirm`。
- **恢复**：`POST /api/trash/:id/restore` → 目录 `rename` 回原位（若原位已被占用则恢复到 `<原名>_恢复_<时间戳>`）→ 还原库记录标记 → 记 `restored_at`。目录树清单用于校验"文件一个不少"（比对 sha1 列表，缺文件就明确报告缺哪些，**不假装恢复成功** —— 这条与 `docs/07` 里"缺失文件不会被报告为恢复成功"的既有立场一致）。

#### 4.8.4 设计：生成文书的版本历史（P1）

**问题**：现在同一份文书改三遍，磁盘上是 `XXX_v1.docx`、`XXX_v2.docx`、`XXX_v3.docx`（或带时间戳），三个都是"文档"，没有"这是同一份的三个版本"的概念；`artifact.version` 列空着不用。

**设计（不做内容级 diff，只做版本链）**：

1. `artifact` 增加 `version_group`（同一份文书的版本链 id）、`revision`（第几版）、`supersedes_id`、`is_final`。
2. `saveGeneratedDocument()` 的行为改变（**这是关键决定**）：
   - 若同一 `workbench + template + checklist_item` 已有 `is_final=0` 的生成件 → **默认不新建文件**，而是新建版本：老版本文件保留在 `.versions/` 子目录下（`_生成文书/.versions/<group>/v1.docx`），新版本占据正式文件名。
   - 界面上"生成"对话框默认给三个选项：**新建**（另一份不同用途）/ **更新这一版**（推荐，默认）/ **另存为定稿**（把当前版本 `is_final=1`，之后不允许再覆盖）。
   - `generation_log` 增加 `version_group`、`revision`、`prev_artifact_id`，让"这份文书是怎么一步步变成现在这样的"可查（每次的变量取值都在 `generation_log.variables` 里，已经存了）。
3. **版本对比**：提供 `GET /api/artifacts/:id/versions` 返回版本链；对比只做**变量级差异**（`generation_log.variables` 逐键 diff，输出"合同金额：1250000 → 1300000"），**不做 docx 正文 diff**。
   - **被否决的方案**：文本级 diff 两份 docx。原因是 docx 的差异大量来自 XML 结构（重新保存会让 Word 重排 rsid、样式），文本 diff 会淹没真正的改动；而用户真正想知道的"哪个字段改了"在 `generation_log` 里本来就有。
4. **回滚**：`POST /api/artifacts/:id/rollback-to/:revision` → 把该版本的文件复制回来成为新的一版（`revision+1`），并记 `generation_log`。**永不删除中间版本**（磁盘便宜，追溯贵）。

#### 4.8.5 设计：密钥（P4）

- 现状：`ai_provider.api_key` 明文列（本地单机）。
- 目标：**不是加密**（本地密钥加密的密钥也在本地，收益接近零），而是：
  1. 界面/接口**永不明文返回**（`maskProvider` 已经在做，但 `GET /api/settings/:key` 没做掩码 —— `docs/06` B12 已记，要顺手修）；
  2. 支持 `api_key_env` 从环境变量取（已实现），并在文档里给出"把 Key 放环境变量、库里留空"的做法；
  3. 备份上明说"完整备份包含 Key，别乱拷"（`BACKUP-NOTICE.txt` 已经在做，要保留并强化）；
  4. **明确不做**：不进系统凭据管理器、不做主密码。理由是单机单用户、要防的是"备份文件外流"而不是"本机被攻破"；主密码会引入"忘了密码=数据全废"的风险，与 P7 冲突。

#### 4.8.6 验收标准

1. 自动快照：清空 `backups/` → 启动服务 → 3 秒内（异步）出现一份 `auto` 快照；同一天再启动不重复建（防抖）。
2. 快照有效性：`MANIFEST.json` 里的逐表行数与源库一致；把快照的 `.db` 单独打开跑 `PRAGMA integrity_check` = ok、`foreign_key_check` 为空。
3. 危险操作前快照：删一个工作台 → `backups/` 里出现 `pre-restore` 快照，且该快照里那个工作台**还在**。
4. **还原演练（必须真做一次并记录在 `docs/10`）**：把某份快照的库与文件目录还原到 `WORKBENCH_DATA_DIR` 指向的临时目录，起服务，`db:init` 输出与还原前一致（工作台数、模板数、别名数、文件数逐项相等）。
5. 回收站：删工作台 #39 → 列表里消失、`_回收站/workbench/<uuid>/` 下有完整目录树、`GET /api/trash` 能看到；`restore` → 工作台回来、进度/清单/文件数与删除前一致（逐项断言）；删满 30 天 → 只在"彻底删除"时清理，不自动清（**自动清理会让"我以为还在"变成事故**）。
6. 删除防护：不带 `confirm` 的 `DELETE` → 400 + 影响清单；带错 `confirm` → 400；带对 → 200 且建了快照。用 AI 助手提议删除 → 执行时同样要求 confirm（脚本模拟）。
7. 版本历史：同一文书连出 3 次 → 磁盘上只有 1 个正式文件 + `.versions/` 下 2 个，`GET /api/artifacts/:id/versions` 返回 3 版，变量 diff 显示每次改了哪个字段；回滚到 v1 → 新版本 v4 内容与 v1 逐字节一致。
8. 同步盘提示：把 `dataRoot` 指向一个路径含 `OneDrive` 的目录 → 启动后 `/api/health` 带该提示，界面横幅可见；设 `WORKBENCH_RUNTIME_DIR` 后库不再落在同步目录下（`DB_FILE` 路径断言）。
9. 密钥掩码：`GET /api/settings/ai.*` 与 `GET /api/settings/:key` 都不返回明文 key。

#### 4.8.7 前置依赖

- 回收站与自动快照互为基础：**先做快照（P0 前半）再做回收站（P0 后半）**，因为回收站的"彻底删除"要依赖快照。
- 版本历史依赖 4.2（新一轮生成会用到循环/图片，版本链要在结构定型后再设计落盘位置，避免改两遍）。

### 4.9 数据模型与规范清理（为上面所有改动铺路）

这不是一个"功能域"，但它是前面所有域的地基，单独列出来以免被漏掉。

#### 4.9.1 归档状态三列合一（P2）

**现状**：`workbench.archived_at` + `status`（含 `'archived'`）+ `archive_status`（归档前状态）三列共同表达一件事，靠 `service.ts:542-610` 的注释维护不变量（`archiveWorkbench`/`unarchiveWorkbench` 在 565/601）+ `startup-repair.ts:18-36` 每次启动修脏行（D5）。

**目标**：**一列表达归档**。
- 新增 `archived_at`（已有，保留）作为**唯一**归档判据；
- `status` 的取值集合**去掉 `'archived'`**（改成 `active|paused|done`）；
- 删除 `archive_status`（迁移里 `ALTER TABLE ... DROP COLUMN`，SQLite 3.35+ 支持；`node:sqlite` 的版本足够）；
- 取消归档时还原成什么？**不再需要记"归档前状态"** —— 因为 `status` 在归档期间**保持不变**（归档只是加一个时间戳）。这正是"一列表达一件事"带来的简化：`unarchiveWorkbench` 变成 `UPDATE workbench SET archived_at=NULL`，那一大段不变量注释和启动修复逻辑一起删掉。
- **迁移步骤**（不能一步到位，因为旧数据里 `status='archived'`）：
  1. 迁移脚本先做数据修复：`archived_at IS NOT NULL` 的行，`status` 从 `archive_status`（或按 `actual_end_date` 回退）还原成合法值；`archived_at IS NULL AND status='archived'` 的行按同一规则修（这就是 `startup-repair.ts` 现在在干的事，把它搬进迁移，只跑一次）。
  2. 代码里所有 `status='archived'` 的判断改为 `archived_at IS NOT NULL`（约 8 处：`listWorkbenches` 的过滤、`Workbench.tsx` 的状态下拉、`archiveWorkbench`、`unarchiveWorkbench`、`completeWorkbench` 的守卫、`agent.ts` 的 `list_workbenches`）。
  3. 删除 `archive_status` 列与 `startup-repair.ts` 里对应的两段。
- **验收**：`archiveWorkbench` + `unarchiveWorkbench` 往返 100 次后（脚本），`status` 恒等于操作前的值；`grep archive_status` 在全仓（含文档）零命中；`service.ts` 里那段不变量注释与 `startup-repair.ts` 的对应逻辑一起删掉（不留"历史说明"）。

#### 4.9.2 阶段/清单模板的增量同步（P2）

**现状**：`instantiatePositions()` **只增不改**（`service.ts:703` 那句 `if (!existing)`）——改了工作类型的材料清单/影像清单，**已建的工作台不会更新**。用户的真实需要恰恰相反："我现在想加一项检查内容，以后每次都要有。"

**设计**：新增 `POST /api/workbenches/:id/sync-rules`，把模板侧的增删改同步到实例侧：
- **新增**：模板里有、实例里没有（按 `source_id` 匹配）→ 加进清单，`status='todo'`；
- **改标题/要点**：更新 `title`/`detail`，但**如果实例项已经被勾选（`status='done'`）或有人写过 `note`** → 只更新 `detail`（要点），保留状态与备注，并记一条"规则已更新"提示；
- **删除**：模板里删了、实例里还有 → **不自动删**（可能已经有人勾了、有照片挂在上面）；改为标记 `orphan=1` 并在界面上显示"这条规则已从规范中移除，是否保留？"，由人决定；
- 前端在"清单"页给一个"规范已更新（+2 项 / ~1 项）→ 同步"的按钮，**sync 前后显示 diff**，由人确认。
- **验收**：给某工作类型加 2 条材料 + 1 条影像规则 → 对已有工作台点同步 → 清单 +3、原有勾选状态与 `done_count` 不变；删 1 条规则 → 实例里该条标 `orphan` 而不是消失。

#### 4.9.3 文档与实现对齐（P2）

### 4.10 质量与验收体系（详细）

**这一节是"路线图的验收标准"的展开，放在第 4 节里因为它本身就是一个域（它有自己的数据、接口、界面和验收标准）。路线图每一阶段的"出口条件"都引用这一节。**

#### 4.10.1 五层自检

| 层 | 命令 | 跑在什么上 | 覆盖什么 | 现在 | 目标 |
|---|---|---|---|---|---|
| L1 单元 | `npm test` | 纯函数，不碰库 | 占位符渲染、排期计算、JSON 容错、**XML 结构校验器**、**幻觉检测器**、**金额大写转换**、**合规规则**、chunk 切分 | 68+28 项 | ≥ 140 项（新增的确定性模块必须全部有单测） |
| L2 接口回归 | `npm test`（regression） | 独立库，假模型 | 132 个接口的契约、状态码、错误语义、参数校验 | 28 项 / 60 个接口有覆盖（45%） | **全部 132 个接口至少 1 项**，`routes-archive.ts` 20 个接口补齐（`docs/06` D1） |
| L3 端到端 | `npm run test:e2e/kb/agent/vision/ocr` | 独立库 + 独立目录 + 独立端口 + 随机 token（`scripts/test-isolated.mjs`，这个机制是对的，保持） | 完整业务链路 | 5 套 172 项 | 增加：**模板健康→出文书拦截**链路、**回收站→恢复**链路、**版本历史→回滚**链路、**口径校验→例外放行**链路 |
| L4 黄金样本（真实模型） | `npm run test:model`（新增，默认不进 `test:all`） | 真实 provider | 文书质量：JSON 合法率、键名、事实用对、**幻觉率**、`【待补】`使用率、耗时、token | **不存在** | 5 个 case、每 case 3 次、出指标表 + `baseline.json` |
| **L5 真实模板库自检**（新增，最重要） | `npm run test:templates` | **用户真实库的只读副本** | 对全部在用模板：健康检查 + 空值渲染 + 产物 XML 合法性；对抽样模板：填充真实档案值出文书并验产物 | **不存在** | 48/48 模板健康、48/48 空值渲染产物合法 |

**L5 是防止"自检全绿但文件打不开"的核心机制**。它的设计要点：
- **只读**：在库和文件的**副本**上跑（`mkdtemp` + 复制 `.db` 与 `_模板库`），绝不改用户的库（这一点 `docs/06` 的做法值得沿用："数据层审计在库副本上做写语义验证，真实库 mtime 未变"）。
- **断言必须是"字节级可读"**：不是"接口返回 200"，而是"产物的 `word/document.xml` 能被严格解析器解析 + 表/段落数与源模板的差值符合预期"。
- **回归基线**：把每次跑的产物 sha1 与"预期的确定性产物"比对 —— **同一模板 + 同一组变量 + 同一日期，渲染两次 sha1 必须一致**（这是 P4"同一输入必得同一结果"的可执行形式；docx zip 的时间戳会让 sha1 不稳定，所以要么固定 zip mtime，要么比对"解压后各部件文本的 sha1 组合"）。

#### 4.10.2 什么算"可以交付"

一条硬清单，**任意一条不满足就不发版**（这份清单本身进 `docs/07`，每次交付时逐条打勾）：

1. `npm run typecheck` 零错误。
2. `npm test` 全绿（L1+L2）。
3. `npm run test:all` 全绿（L3）。
4. `npm run test:templates` 在**用户真实库的副本**上全绿（L5）：在用模板健康率 100%、空值渲染产物合法率 100%、确定性比对一致。
5. 迁移在**旧库副本**上跑通，且跑完 `PRAGMA integrity_check` 与 `foreign_key_check` 都通过（"原数据副本升级验证"这件事 `docs/07` 已经做过，要变成常规动作）。
6. 新增/修改的接口在 L2 里有覆盖，**没有"零覆盖的新接口"**。
7. 涉及的界面在**真实服务**上看过一次（截图或人工描述记进交付说明）。
8. `docs/01`（宪法）与实际一致，第 4.9.3 节的文档漂移自检通过。
9. 备份能建、能校验、**本次改动没有让还原路径失效**（改了表结构的版本必须重跑一次还原演练）。

#### 4.10.3 必须人工验收的部分（不能自动化）

诚实列出，避免用自动化指标假装覆盖了它们：

| 项 | 为什么不能自动 | 人工怎么做 |
|---|---|---|
| **公文的语言质量** | "读起来像不像人写的公文"没有可判据 | 每月抽 3 份真实生成的文书通读，记录"要改哪几句" |
| **排版分页** | 分页依赖 Word 的排版引擎 | 打开产物看有没有跨页断行、表格被拆、图片压标题 |
| **口径是否符合本单位习惯** | 制度里没写、但大家都知道怎么写 | 出 1–2 份给同事看，收集"我们这儿不这么写" |
| **照片能不能作为证据** | 视觉模型会给 `ok`，但审计认不认是人的判断 | 每次检查后自查一遍补拍清单 |
| **模型换了之后的表现** | 自动指标能拦"编数"，拦不住"写得太空" | 换模型后手工读 3 份产物再决定是否长期用 |

#### 4.10.4 "自检全绿但用户拿到打不开的文件" 为什么会发生、怎么杜绝

**事故复盘（这是本设计里最重要的一段经验）**：
- 7 套 272 项自检**全部通过**；
- 验收报告还专门跑了"出文书链路"，4/4 阶段 `draft ok:true` + `preview` 200；
- 报告的"总判定"里写着"有效 OOXML"——**但同一份报告 4.5 节的表格里明明写着 S01 的生成件是 `malformed`、python-docx 打不开**；
- 于是结论是"链路打通"，而用户实际拿到的是坏文件。

**根因有三条，每条对应一个机制**：

| 根因 | 机制 |
|---|---|
| 断言的是**接口返回码**，不是**产物可用性**。`ok:true` + 200 被当成成功。 | **产物级断言进 L3/L5**：任何"生成文件"的测试都必须验证产物能被严格解析器打开。写成可复用的 `assertDocxReadable(bytes)`，所有生成类测试必须调用它。 |
| 自检用的是**合成模板**（`make-samples` 造的简单 docx），真实模板库里的 6 个坏文件从来没进过测试。 | **L5 真实模板库自检**：拿用户真实在用的模板跑。合成模板永远发现不了真实数据的脏。 |
| 已知的缺陷被记成"数据问题"（报告里写"归因：源模板自身损坏"）而不是**变成代码里的拦截**。 | **缺陷必须落成测试或守卫**：任何一条"发现的问题"要么有测试用例，要么有运行时守卫，二者必居其一；只写在报告里不算处理。这条要写进 `docs/07` 的交付要求。 |

## 5. 实施路线图

### 5.1 排序原则（先说清凭什么这个顺序）

1. **先堵"会让用户拿到错误结果或丢数据"的口子。** 坏模板出坏文件（D1）和删除无防护/无备份（D6、D8）属于这一类：它们的共同点是**用户会把错的当成对的**（文件打不开、数据没了却以为只是隐藏了）。这类问题的代价不是"功能少一个"，而是"信任崩一次"。
2. **再把确定性做扎实。** 覆盖率、口径校验、影像规则、模板健康，都是"确定性"的活：做完之后每次都能省下同样的时间。**它们不依赖模型，也就不会被模型换版本搞坏。**
3. **然后提升自动化率。** 循环/图片（模板能力）、模型质量门禁、任务编排 —— 这些让"人只做判断和确认"从口号变成现实。
4. **最后才是锦上添花。** 所见即所得的排版预览、多用户、性能优化。
5. **横切原则**：每个阶段结束都必须**可交付**（第 4.10.2 节的清单全过），不许出现"半截功能上线"。

**为什么"模板健康检查"排第一而不是"循环变量"？** 循环变量是"能力缺口"（少一个功能，用户知道自己在手工补行）；坏模板是"**错误结果**"（用户以为成功了）。前者损失时间，后者损失信任。而且健康检查只有约 3 人日，收益/成本比是全表最高的。

## 6. 明确不做的事（以及为什么）

"克制"也是设计决策，写下来是为了让接手的人知道**这些不是遗漏，是想过之后的选择**。

| 不做 | 理由 | 什么条件下会重新考虑 |
|---|---|---|
| **不做云端 / 多租户** | 数据是行政单位的内部资料（合同金额、人员身份证号、现场照片）。上云会引入"谁运维、谁备份、谁负责"的问题，而对一个单用户工具没有任何收益。系统的全部价值来自"文件就在你机器的文件夹里"。 | 如果出现"多人同时用同一个库"的真实需求，先做**局域网共享 + 文件锁**，也不上云。 |
| **不做移动端 App / 小程序** | 现场拍照用的是手机相机（原生体验最好），系统要解决的是"拍什么"和"拍完怎么进系统"，而这两件事可以用**要点卡片导出 + 上传 + 初检**解决。做一个移动端要重新解决登录、上传、离线、权限，投入巨大而收益是"少插一次数据线"。 | 如果用户开始**每天都在外勤**且需要当场出文书，再评估"手机浏览器上传页"（不是 App）。 |
| **不引入向量数据库（Milvus/Qdrant/faiss）** | 现在 `kb_chunk` = 0，上限估算是一万块左右；一万块 × 1024 维的全量余弦打分是几十毫秒（`core/kb.ts` 已经算过这笔账），SQLite BLOB + 内存矩阵完全够。引入向量库要额外进程、额外运维、额外备份对象，**而它带来的唯一好处是"超过万级片段时的延迟"**。 | 片段数稳定 > 2 万且检索延迟 > 500ms。届时优先换 HNSW（一个纯 JS/单文件的索引），也不引独立服务。 |
| **不做复杂权限体系（角色/审批流/组织架构）** | 单用户单机，权限的唯一作用是"防自己"——而防自己靠的是**二次确认 + 回收站 + 快照**（都已做），不是角色。角色体系会让每一次操作都多一个"我是谁的什么角色"，直接违背"人只做判断和确认"。 | 若真出现第二个使用者，做**最简的双角色**（可编辑 / 只读），不做审批流。 |
| **不做登录 / 密码** | 服务只监听 `127.0.0.1`（`docs/01` 第 492 行的约定）。加登录只防"能物理接触这台机器的人"，而那种情况下他可以直接拷 `data/files`。真正的边界是"服务不暴露到局域网"这条约定，以及会话 token 挡跨站写请求（已有）。 | 一旦要开放到局域网，**先做**"必须登录 + HTTPS"，再开放端口。 |
| **不做模型本地化部署（内置大模型）** | 用户机器是办公电脑，跑不动可用的中文写作模型；`Ollama` 这条路径已经留着，需要时用户自己配。 | 用户机器升级到有独立显卡且明确要求"数据绝对不出本机"时，把 `ollama` 服务商配起来即可（代码已支持）。 |
| **不做自动改写模板（未经确认）** | 循环改造助手**一定会生成候选模板**，但**绝不自动替换**。模板是用户的资产，改错一次就会连锁影响所有历史绑定。 | 永不自动。这是底线。 |
| **不做 docx 正文的内容级 diff** | 见 4.8.4：docx 的差异大量来自 XML 结构噪声，文本 diff 会淹没真改动；而"哪个字段改了"在 `generation_log.variables` 里本来就有。 | 如果用户真的需要"逐字对比两稿"，做**纯文本导出的对比**（把两份 docx 抽成纯文本再 diff），不做 XML 级。 |
| **不做"模型自主执行多步任务"（自主 agent 循环）** | 让模型自己规划并连续执行，成本不可控、错误不可追、失败不可解释。替代方案是**模板化任务单 + 人确认推进**（4.7.3），它同样能把"这个月的检查"拆成步骤，但每一步都有判据、都能中断、都能追。 | 不做。宁可"多一点确认"，也不要"错了一串"。 |
| **不做"AI 自动润色已定稿文书"** | 已定稿的文书是有对外效力的文件。自动改它意味着"用户手里的纸质版和系统里的电子版可能不一致"。 | 可以对**草稿**做润色，且必须走"提议→确认"。 |
| **不引入 PDF 生成 / 电子签章** | 这套系统的交付物是 Word/Excel（单位的实际工作流是打印、签字、盖章、扫描归档）。生成 PDF 会引入字体与排版依赖（体积、跨机差异），而收益是"少按一次另存为 PDF"。 | 用户明确要求"批量出 PDF"时，优先用**已装的 Word/WPS 命令行转**，不引新依赖。 |
| **不做多语言 / 国际化** | 使用者与交付物都是中文公文。 | 不做。 |
