# 运行、备份、恢复与发布手册

文档ID：GUIDE-OPERATIONS。版本：1.1。更新：2026-10-24。适用：本机日常实例。涉及日常切换、恢复或重要数据修改时，按具体任务的有效授权执行。

## 1. 运行组成

| 对象 | 当前约定 |
|---|---|
| 日常启动 | 根目录启动工作台.cmd或npm start |
| 发布选择 | data/runtime/current-release.json |
| 发布清单 | 指针所选目录下RELEASE.json |
| 后端入口 | 所选包packages/server/src/index.ts |
| 前端 | 根packages/web/dist，与该包配套 |
| 数据库/文件 | data/runtime/workbench.db、data/files，配置覆盖时先核实 |
| 日志与锁 | data/runtime/logs、data/runtime/server.lock及启动器日志 |
| 外部原件 | 绑定/参考目录，单独保护，不默认为内部备份的一部分 |

当前包见[进度](../../DEVELOPMENT_PROGRESS.md)和[只读快照](../reference/current-baseline.json)，不要把本文路径当永远不变的运行事实。

## 2. 日常启动与只读检查

已有服务可用时直接打开页面。需要正常启动时运行：

```powershell
npm start
```

快捷方式使用既有后台逻辑；启动器记录日志。启动可能执行迁移和初始化，不是纯只读操作。端口占用先确认是不是现有工作台，不盲目另起相同数据库实例。

只读查看：

```powershell
Get-Content -LiteralPath data/runtime/current-release.json
Invoke-RestMethod -Uri http://127.0.0.1:8787/api/health
```

核对status、webBuilt、dbFile、dataRoot、loadedBuild与发布清单。不要在日志或对外文档中贴出凭证或不必要业务信息。只有健康200还不能证明包、前端、数据均正确。

## 3. 配置优先级

core/config.ts中环境变量优先于适用的根配置，最后使用缺省值。关键环境包括WORKBENCH_DB、WORKBENCH_DATA_DIR、WORKBENCH_RUNTIME_DIR、WORKBENCH_WEB_DIST、PORT、HOST；隔离还需备份、OCR等完整设置。

启动器为日常发布包传入原数据和前端绝对路径，不能依赖包内默认新库。模型配置与凭证不从文档复制，使用应用已有设置及相应授权。默认本机监听，当前不是公网多用户服务。

## 4. 备份范围

| 类型 | 保护范围 | 限制 |
|---|---|---|
| 自动数据库备份 | SQLite数据库 | 不等于模板、业务文件和前端完整备份 |
| scripts/snapshot.mjs配套快照 | DB与内部文件、摘要、完整性 | 离线配套；外部绑定原件不包含；目标为新目录 |
| 发布前备份 | DB、内部文件、旧前端、旧指针/配置和清单 | 每次核对实际内容，不能仅凭目录名认定完整 |
| 外部原件备份 | 按其原有存储/备份安排 | 不因工作台有索引就视为已备份 |

已有快照可执行只读验证：

```text
node scripts/snapshot.mjs verify --snapshot <已有快照目录>
```

配套备份和恢复的准确参数：

```text
node scripts/snapshot.mjs create --db <数据库文件> --files <内部文件根> --out <尚不存在的新目录>
node scripts/snapshot.mjs restore --snapshot <快照目录> --to <尚不存在的新恢复目录>
```

尖括号是需替换的参数，不可原样复制。create要求源环境静止且获得相应锁；先按操作范围处理正在运行的实例。restore只还原到新目录，不覆盖在线库。工具实际校验数据库、文件集合及摘要，结果失败时不能宣称备份可恢复。

## 5. 限定范围发布

1. 重新读取指针、清单、运行身份及Git差异，确定本次基础。
2. 从合适已发布基线构造本次范围包；列明包含/排除的文件、迁移与依赖，不整包复制脏工作区。
3. 在该包或准确对应副本完成类型检查、受影响测试、配套前端构建及业务/产物验证；绑定实际候选摘要。
4. 对日常副本演练迁移，核对旧表原列与文件，明确预期数据变化和不能回退的部分。
5. 准备可验证备份、切换步骤、失败恢复与新增数据保护，按已有有效授权处理日常切换。
6. 停止经过身份核实的工作台，保存最终一致备份；切换配套前端和指针，通过原入口启动。
7. 核对加载身份、实际迁移集合、首页/本批入口及数据摘要，记录实际结果和未验收项。
8. 同步RELEASE、进度、计划和证据路径；避免向真实库写匿名测试数据。

没有通用“一键把工作区发布”的脚本承诺；各次范围包以可审查清单为准。发布后保持后端、前端、依赖锁和迁移相容。

## 6. 回退与数据恢复

功能回退和数据恢复不同：回退优先恢复已核实兼容的旧指针与前端；数据恢复会影响发布后新增业务，必须先保护当前状态，不能在线覆盖。

本台式机reliability-20261024-r1的功能回退目标是data/releases/pre-reliability-20261024-base，后端/依赖锁及其packages/web/dist已核对与切换前进程完全一致。需要回退时，先核实并停止当前工作台、保留当前前端及新数据，将根packages/web/dist与指针一起切至该回退组合，再通过原入口启动并复核加载摘要。本轮没有新增迁移，回退保留原数据库及发布后的新业务；不要把发布前数据库直接覆盖回去。

发布前完整备份在data/backups/before-reliability-20261024-r1：snapshot保存一致数据库和内部文件集合，frontend保存旧前端，配置与previous-runtime.json保存旧运行依据；snapshot已verify并restore到其restore-check新目录。外部绑定原件仍不在配套快照范围。原指针不存在的状态已记入发布报告，不假定此前有笔记本正式包可用。

报告43说明039是新增表/可空列，可在回退功能时保留以保护新草稿。报告44中040仅新增5张表，已在日常副本验证原039包迁移器可保留040。功能回退需要匹配旧指针与旧前端，保留040和新增业务记录；不得删除表、降级迁移记录或覆盖新成果。逐包重新核查兼容，不把此结论扩大到未来版本。

恢复演练先在新目录核对数据库完整性、外键、文件摘要、模板/成果关系与可访问性，再决定正式处置。外部路径迁移单独处理；旧快照不承诺无损热回退。

## 7. 故障处理

| 现象 | 先收集/检查 | 后续动作 |
|---|---|---|
| 端口占用 | 健康接口、进程身份、日志 | 已有服务可用则复用；不能随意杀未知进程 |
| 服务退出 | 时间、启动日志、健康事件、锁和失败阶段 | 分析根因；不能仅靠无限重启掩盖 |
| 发布指针无效 | 路径范围、入口和RELEASE存在性 | 修正已批准范围；不要退回工作区源码冒充正式 |
| 迁移失败 | 具体文件、事务结果、当前迁移集合 | 保留原数据与日志，在副本复现；不手工跳过迁移 |
| 资源/页面版本不符 | loadedBuild、磁盘包与dist摘要 | 使用配套产物，不能运行中默认覆盖dist |
| 来源/修订冲突409 | 工作/期次/草稿、revision及当前来源 | 保留输入，重新核对，不移除保护 |
| 文件缺失410 | 登记关系、绑定根及文件 | 先查备份与外部原件；不造空文件冒充修复 |
| 删除失败 | 对象范围、错误、文件占用、外键 | 进入GOV-01隔离复核；不直接清库清文件 |
