# 运行、备份、恢复与发布手册

文档ID：GUIDE-OPERATIONS。版本：1.3。更新：2026-11-10。适用：当前源码默认启动与显式历史恢复。重要数据恢复及真实设备处置按具体任务授权执行。

## 1. 运行组成

| 对象 | 当前约定 |
|---|---|
| 日常启动 | 根目录启动工作台.cmd或npm start，自动准备当前源码 |
| 源码副本 | 检出目录.local/source-builds/<内容与运行环境摘要>，含源码、node_modules、web与SOURCE_BUILD.json |
| 成功版本记录 | 当前环境runtime/source-current.json，只有新实例身份及健康匹配后才更新 |
| 数据库/文件 | 当前环境解析的dbFile与dataRoot；新安装源码外daily，旧安装原路径兼容 |
| 日志与锁 | runtime/logs、数据库旁server.lock；runtime/source-update.lock仅串行化准备与更新 |
| 历史发布包 | current-release.json与RELEASE保留，仅显式--release入口使用 |
| 外部原件 | 原绑定/参考目录，不包含在源码副本或自动数据库备份中 |

实际环境必须读取当前路径和健康身份；历史报告的data路径只适用于当时旧布局。

## 2. 日常启动与只读检查

在原仓库pull成功后双击即可，完整步骤见[安装指南](INSTALLATION.md)。启动器不会自动执行git pull，不覆盖本地修改；按磁盘代码构建。构建失败保留旧服务；更新已运行版本需先保存全部页面输入并明确确认。旧服务无安全停止接口时要求先停止或重启电脑，不强杀。再次双击当前版本复用实例；--auto保留参数兼容但不再绕开冲突另起端口。

已有库需要迁移时先列出并确认，备份及副本演练通过后才启动，全部待执行SQL用同一事务；未知较新结构拒绝降级。升级前备份放在当前backupRoot/before-source-update-*，仅含SQLite与说明，不自动清理备份或历史缓存。初始化与升级均为写操作，不能用启动探测真实库。

只读查看健康：

```powershell
Invoke-RestMethod -Uri http://127.0.0.1:8787/api/health
```

核对status、webBuilt、dbFile、dataRoot、runtimeProfile、loadedBuild.sourceBuildId和实际SOURCE_BUILD。源码摘要含运行环境，不等于Git SHA。仅健康200不能证明真实业务已经验收。日志和对外文档不要贴凭证或不必要的业务信息。

## 3. 配置优先级

原runtime-layout规则保持：显式资源环境变量优先，再是当前本机配置，最后默认路径。启动器传WORKBENCH_LAYOUT_ROOT为原检出根，避免缓存副本改变旧配置的相对路径；WORKBENCH_WEB_DIST指向该副本的配套web，其他资源保持。原检出根和实际副本都属于平台保护路径，不能作为可删除的工作目录绑定。

配置错误、目录重叠或链接越界明确停止；新安装可指定WORKBENCH_HOME，旧布局不自动迁移。默认本机监听，不是公网多用户服务。

## 4. 备份范围

| 类型 | 保护范围 | 限制 |
|---|---|---|
| 自动数据库备份 | SQLite数据库 | 不等于模板、业务文件和前端完整备份 |
| scripts/snapshot.mjs配套快照 | DB与内部文件、摘要、完整性 | 离线配套；外部绑定原件不包含；目标为新目录 |
| 发布前备份 | DB、内部文件、旧前端、旧指针/配置和清单 | 每次核对实际内容，不能仅凭目录名认定完整 |
| 外部原件备份 | 按其原有存储/备份安排 | 不因工作台有索引就视为已备份 |

已有快照可执行只读验证：

```text
node scripts/snapshot.mjs verify --snapshot <已有快照目录>
```

配套备份和恢复的准确参数：

```text
node scripts/snapshot.mjs create --db <数据库文件> --files <内部文件根> --out <尚不存在的新目录>
node scripts/snapshot.mjs restore --snapshot <快照目录> --to <尚不存在的新恢复目录>
```

尖括号是需替换的参数，不可原样复制。create要求源环境静止且获得相应锁；先按操作范围处理正在运行的实例。restore只还原到新目录，不覆盖在线库。工具实际校验数据库、文件集合及摘要，结果失败时不能宣称备份可恢复。

## 5. 源码更新与特殊发布

普通用户按安装指南pull后双击，不再手工构造发布包或改指针。源码提交推送本身不会改变已运行进程或其他电脑数据库；用户在目标机器启动并确认后才实际升级。准备需要Node24/npm11及磁盘空间；可核对的已有依赖或完整npm缓存支持离线接续，仅缺项时需依赖源。按当前锁核对已有安装，再使用原缓存离线安装，最后才尝试联网获取缺项；失败不自动运行旧源码。

特殊范围发布或恢复旧包仍须核对包、依赖、迁移、前端和数据兼容，先在副本验证并保护新增业务。历史current-release指针只用于显式--release；不能仅改指针就认为默认入口会切换。正式资料迁移与外部路径搬迁仍是独立操作。

## 6. 回退与数据恢复

功能回退与恢复数据不同。`node scripts/start.mjs --last-good --background --start-only --open`明确使用本目录上次成功副本；仍在停旧服务前检查源码/界面、安装记录/依赖图/模块与esbuild可用性，再核对环境身份和数据库迁移集合，较新未知结构拒绝。没有成功记录就不猜测缓存目录。新版本健康后记录会更新，因此--last-good表示最近一次成功，不是任意历史版本选择器。

`node scripts/start.mjs --release --background --start-only --open`仅供已核实的旧包恢复，先停止现有服务；拒绝没有指针、不完整包、未知较新数据库或缺失迁移。不会替用户改指针、降级schema或覆盖数据。不支持安全接管的旧后台服务由用户停止或重启电脑。

准备阶段失败不会停止旧版本；停止后备份、演练或启动失败可能留下已停止实例或已升级数据库，必须先检查日志、锁、迁移及健康，不能盲目重试或把旧备份盖回去。source-update.lock异常残留只在确认原进程已结束后人工处理，未知归属不自动清理。

历史before-reliability-20261024-r1、before-inspection-drafts-20261021-r1等备份及旧报告只说明当时验证；是否存在、配套性及能否恢复须重新核对。旧039/040兼容结论不能推广到当前迁移，当前恢复入口采用更保守的未知迁移拒绝。数据库备份不含全部文件，正式恢复先在新目录检查数据库完整性、外键、文件摘要与模板/成果关系；不覆盖在线库，不删除表或改迁移记录来强行回退。

## 7. 故障处理

| 现象 | 先收集/检查 | 后续动作 |
|---|---|---|
| 端口占用 | 健康接口、进程身份、日志 | 已有服务可用则复用；不能随意杀未知进程 |
| 服务退出 | 时间、启动日志、健康事件、锁和失败阶段 | 分析根因；不能仅靠无限重启掩盖 |
| 历史恢复指针无效 | --release使用的路径、入口和RELEASE | 仅修正已确认的恢复范围；默认源码入口不受旧指针控制 |
| 迁移失败 | 具体文件、事务结果、当前迁移集合 | 保留原数据与日志，在副本复现；不手工跳过迁移 |
| 资源/页面版本不符 | loadedBuild、磁盘包与dist摘要 | 使用配套产物，不能运行中默认覆盖dist |
| 来源/修订冲突409 | 工作/期次/草稿、revision及当前来源 | 保留输入，重新核对，不移除保护 |
| 文件缺失410 | 登记关系、绑定根及文件 | 先查备份与外部原件；不造空文件冒充修复 |
| 删除失败 | 对象范围、错误、文件占用、外键 | 进入GOV-01隔离复核；不直接清库清文件 |
