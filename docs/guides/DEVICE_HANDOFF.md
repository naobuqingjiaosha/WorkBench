## 3. 旧电脑需要带走什么

建议保留旧机器作为恢复来源，在所有写入停止后，将以下内容复制到可信介质或自己控制的加密存储，逐项清点。不要直接上传含业务数据和凭证的目录到代码仓库。

| 内容 | 位置/核对方式 | 用途 |
|---|---|---|
| 开发工作区和历史 | 根目录所有源码、脚本、配置、五份文档、AGENTS、docs、package及锁文件、启动cmd、`.git`；包含未跟踪候选 | 保存尚未提交的开发与版本历史 |
| 正式运行身份 | `data/runtime/current-release.json`、指针选择的完整 `data/releases/<版本>`、该包RELEASE和锁文件、配套 `packages/web/dist` | 继续运行已发布版本 |
| 成对数据快照 | 实际DB与实际内部文件根；默认 `data/runtime/workbench.db` + `data/files` | 模板、记录、配置、成果和文件关系保持一致 |
| 恢复依据 | 最近有效发布备份、删除前备份、必要 `outputs` 验证报告 | 支持排查和恢复；无需搬全部重复临时产物 |
| 外部资料 | 实际绑定目录、参考原件、桌面模板源、设计图/交互说明等尚在使用的仓库外资料 | 数据库索引不包含这些原件 |
| 环境与工具 | Node/npm/Git版本、Office与字体、所需OCR语言包、本地模型服务、浏览器测试工具 | 新机按需安装或重建 |
| 私有配置 | `workbench.config.json`、必要环境变量或私有配置文件，单独安全保存 | 核对路径和服务；不把密钥值写进交接文档 |

`node_modules`、包管理缓存和运行日志通常无需搬迁，按锁文件重建依赖。旧 `server.lock`、PID和活动日志不是新机运行身份，不作为恢复内容。`.tmp`不要整批当正式数据搬走；其中若有尚未纳入源码的唯一文件，应先逐项保留。UI空预览的 `.empty-preview` 语义需要重新核对，避免意外灌入样例。

数据库和内部文件必须是同一静止时点。正式迁移前，核实并停止对应工作台服务和相关文件编辑，再用现有离线快照工具；不要从运行中的目录只复制一个 `.db`，也不要手工丢弃WAL文件。以下是届时执行的示例，本次未执行：

```powershell
# 在旧电脑项目根目录运行；先停止已核实身份的工作台服务。
$handoffSnapshot = Join-Path (Get-Location).Path ('data\backups\device-handoff-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
node scripts/snapshot.mjs create --db data/runtime/workbench.db --files data/files --out $handoffSnapshot
node scripts/snapshot.mjs verify --snapshot $handoffSnapshot
```

若配置覆盖了数据位置，改用实际路径。目标必须是尚不存在的目录；命令失败就停止后续搬迁。此快照只包含数据库和内部文件，不含发布包、根前端、Git或外部原件。SQLite内部可能保存模型密钥，应按私有资料保护整个快照。

复制完成后，对照源与目标核验文件集合、大小及SHA-256；仅有压缩包能打开不算验收。接续记录至少包含Git基点、未提交/未跟踪清单、发布名、快照日期与验证结果、外部旧/新路径对应表。此记录保存在迁移资料中，避免在通用文档列出业务正文或凭证。

## 4. 新电脑环境与恢复顺序

1. 优先使用Windows并保留原路径 `D:\project\工作台` 及外部资料路径，以减少绝对路径失效。路径必须改变时，先建立旧/新路径清单，核对配置、数据库中已有绑定/工时来源/工具路径；没有通用自动重定位承诺，不全库字符串替换。
2. 安装Git和满足根package要求的Node.js（≥24）；本次旧机实测Node v24.21.0、npm 11.19.0，可作为复现参考，不表示必须升级到这些版本以上。在新机核对版本，在项目根按锁文件运行 `npm ci`；不要复制旧node_modules代替安装。若正式包锁文件与工作区不同，先为正式运行准备与发布清单一致的依赖环境，不能用工作区锁覆盖它。
3. 恢复开发工作区及Git历史，检查未提交/未跟踪清单。新机安装Codex或使用既有开发工具后打开该目录，按末节接续提示读取仓库文档。个人技能/全局记忆若仍需要，单独清点；本项目的关键接续信息已经保存在仓库。
4. 将已验证的数据快照恢复到尚不存在的新目录，先检查，不覆盖已有数据。`snapshot.mjs restore --snapshot <快照目录> --to <新目录>` 生成 `runtime/workbench.db`、`files` 和 `restore-environment.json`；它不会自动恢复发布指针，也不会自动加载JSON中的环境变量。再按目标部署布局安放数据，核对配置及绝对路径。
5. 复制所选发布包、指针和配套根dist，确认三个文件/目录都齐全；不要先从开发源码运行 `npm run build` 覆盖dist。确认数据库与文件目录均为新机副本，才使用 `npm start`。启动可能执行迁移，首次启动前必须保留原始快照。
6. Office桌面软件和所用字体用于Word分页、Excel重算及打印验收；只做源码检查时不必先完成全部办公环境。若使用本地模型或OCR，另检查服务端点、模型文件和 `data/runtime/tessdata`；测试本身不会证明这些能力可用。
7. UI验收脚本使用Playwright和Edge；Playwright不在项目package依赖中，当前脚本默认引用本机工具运行时路径。新机按实际安装设置 `WORKBENCH_PLAYWRIGHT_PACKAGE` 为其package.json绝对路径，并确认Edge可用。不要把旧用户目录当可移植配置。

## 5. 新机通过哪些检查才算接续成功

先进行静态与隔离检查，避免在未确认发布身份前启动正式数据：

```powershell
node --version
npm --version
git status --short
node scripts/docs-maintenance.mjs check
npm run typecheck
npm test
```

新机检查代码可能暴露未发布候选的独立问题，应记录实际结果，不能用旧机通过记录替代。前端编译使用[开发指南](DEVELOPMENT.md)的专属outDir；业务测试使用现有隔离入口，不直接运行初始化模块。开发代理默认18889并核对独立开发数据库身份；换机仍应检查实际路径。

完成上一节的正式布局检查后启动日常服务，再核对 `/api/health` 的数据库路径、文件根、webBuilt和loadedBuild，与搬迁的发布清单比对。检查模板、业务行数、成果及文件摘要与迁移快照一致，确认外部绑定可访问；当时“工作0、模板77”的历史记录不是未来固定验收值。必要时在副本验证一次文档生成/打开、Office重算/打印与隔离UI流程。

验收后再确定新电脑为主用环境；旧机备份继续保留。当前没有两台机器自动合并SQLite和文件的实现，不要让两台机器同时修改各自副本后直接互相覆盖，也不要把运行中的数据库放进双向同步流程。

## 7. 长期多设备开发建议（待采用）

建议以Git同步源码和文档，指定一台Windows主机保管正式工作台、真实数据、模板原件及Office验收环境；其他电脑使用自己的代码副本和隔离测试数据。这样普通代码开发不依赖主机在线，也不需要反复复制正式库。正式发布仍以主机的current-release.json及其包为准，Git的main分支不自动代表当前正式版。

| 内容 | 多设备约定建议 |
|---|---|
| 源码、测试、五份文档、AGENTS、CHANGELOG | 执行者本地保存并提供修改清单，用户审查后手动提交/推送；先核实仓库可见性与内容 |
| 未完成开发 | 保存到明确的codex/任务分支，检查点写明未完成和未通过项；不混入正式发布 |
| 数据库、业务文件、模型密钥、外部原件 | 留在指定主机；副机仅使用获准副本或匿名样例，离线备份单独管理 |
| 发布及Office真实验收 | 在指定主机按限定范围验证、备份、发布；副机测试不替代这些步骤 |
| 对话与个人设置 | 各设备本地运行Codex，新聊天读取仓库文档接续；不依赖聊天跨机转移，各机配置按需设置 |

同一任务的日常切换流程：

1. 旧设备上的Codex完成或停止修改，将文件保存本地、执行必要验证、更新五份根文档和CHANGELOG。GPT_CONTEXT保留任务/GOV、分支、基点和接续入口，详细变更及验证只维护在CHANGELOG。提交哈希使用已经存在的基点，不要求文件包含自身提交哈希。
2. 用户审查本次文件清单，手动把对应源码和接续文档提交并推送，确认成功后再切换。Codex默认不执行git add/commit/push；未完成检查点明确标注，不视为测试通过或发布。当前混合改动先按来源和范围整理，不能直接全部加入main。
3. 新设备先检查自身未提交工作，再拉取对应任务分支；无本地分歧时使用快进更新，有分歧先审查，不能强推或覆盖。依赖锁变化时重装对应依赖，按AGENTS和GPT_CONTEXT接续，在隔离数据上验证。
4. 同一任务同一分支尽量只由一台设备持续写入；若确实同时做不同任务，各用独立分支/工作目录，之后审查合并。worktree隔离源码不自动隔离数据库、端口、文件路径或Office环境。

用户在2026-10-24明确“Codex远程这一条无法实现”。此前远程控制/跨主机聊天交接建议撤回，不再安排配对或远程入口，不推测不可用原因。常规切换只要求两台机器能够在交接时访问Git远端；原电脑完成推送后可关机。新设备开本地聊天读取五份文档，交接信息需包含当前分支、检查点、未完成项和下一步。正式数据主机仅在真实业务验收和发布时需要使用。

Codex会在工作前读取适用的AGENTS.md，适合保存各机共享规则；五份根文档继续由该入口指引读取。不要把整个个人.codex目录当作双向同步工程目录。[官方项目指令说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md) 需要并行任务时可评估worktree；其Git检出和忽略文件规则也不构成正式数据备份。[官方worktree说明](https://learn.chatgpt.com/docs/environments/git-worktrees)

建议落地顺序：先整理当前未提交候选、形成可追溯的Git接续点，再准备第二台机器的匿名隔离环境并完成一次往返接续。补齐pack迁移工具有助于备份和整机迁移，不是每次切换开发的前置步骤。本轮仅记录远程不可行约束并修订文档，未执行Git写入或数据操作。
