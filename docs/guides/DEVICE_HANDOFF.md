# 换机开发与接续清单

文档ID：GUIDE-DEVICE-HANDOFF。版本：1.2。更新：2026-10-26。关联：GOV-11。性质：源码接续与完整运行迁移的操作规范。

源码接续与完整运行迁移分开处理。Git只共享源码、通用工具、开发文档和配置样例；测试用例、夹具、私有配置、业务数据及历史验证产物不随源码上传。具体范围见[资料边界](DATA_BOUNDARIES.md)。各设备的实际状态以现场核查为准，汇总见[开发进度](../../DEVELOPMENT_PROGRESS.md)，过程见[工作日志](../management/WORK_LOG.md)。

## 1. 文档与任务接续

五份根文档应能独立表达当前有效信息：

| 文件 | 维护内容 |
|---|---|
| GPT_CONTEXT.md | 项目约束与接续阅读入口 |
| CONTEXT.md | 业务术语及对象边界 |
| PRODUCT_REQUIREMENTS.md | 当前需求、约束与验收条件 |
| SYSTEM_ARCHITECTURE.md | 实际结构、依赖、启动与数据关系 |
| DEVELOPMENT_PROGRESS.md | 当前源码能力、环境、验证边界、发布与未完成项 |

每次任务逐一复核，完整整合受影响章节并删除过时结论；无变化不在正文追加复核段落。工作目标、实际修改、验证、五份文档复核与交付状态只记入[工作日志](../management/WORK_LOG.md)，规则见[文档治理](../management/DOCUMENT_CONTROL.md)。已有历史保留在[CHANGELOG](../management/CHANGELOG.md)。下一步只维护[项目计划](../management/PROJECT_PLAN.md)的GOV队列。

执行者保存文件并提供修改清单及建议提交说明；用户手动提交、推送。默认不执行git add/commit/push或发布。保存、提交、远端同步、发布和业务验收分别记录。文档维护后运行docs-maintenance generate/check及git diff --check。

## 2. 源码接续

1. 旧设备检查分支、HEAD、未提交与未跟踪文件，确认所需修改已实际保存；核对共享边界，不能将私有文件混入Git。
2. 用户审查对应修改，手动提交并推送。仅配置了远端或执行push不证明未提交文件也已上传；以提交清单与远端结果为准。
3. 新设备先保护已有修改，再clone或更新目标分支。有分歧先审查，不强推或覆盖。核对分支、HEAD、远端差异和五份根文档。
4. 按根package.json安装支持的Node.js（≥24）及Git，按锁文件执行npm ci；依赖锁变化后重新核对环境。不能用旧机器node_modules代替新机安装验证。
5. 开发使用源码外独立环境及默认18889端口。前端代理必须核对development及数据库身份，不能借用正式数据库补齐开发或测试条件。
6. 测试资源只有在用户另行授权时私下接续。未提供用例时明确记录缺项，不运行缺失入口后宣称测试通过。

默认pack按共享白名单打包源码、根文档、通用工具和配置样例，不读取真实配置，不包含Git历史、正式数据和完整运行现场。它可用于源码交付，不能代替完整运行迁移。

## 3. 完整运行迁移需另行清点

完整迁移须有对应授权，保留原机器和原始备份。新安装使用源码外环境根；旧data目录只属于兼容布局。先解析实际路径，不将以下旧路径示例视为固定位置。

| 内容 | 必须核对的范围 |
|---|---|
| 正式运行身份 | 当前环境runtime/current-release.json、所选完整发布包、RELEASE、依赖锁及配套前端 |
| 成对数据 | 实际SQLite数据库与内部文件根，同一静止时点的快照及验证结果 |
| 配置与外部资料 | 私有配置、必要环境变量、绑定目录与原件；模型密钥单独保护，不写入通用文档 |
| 开发现场 | 所需源码、Git历史、尚未提交文件；本机测试与夹具按授权另行接续 |
| 验证与恢复依据 | 可访问的备份、适用报告、设计图及交互说明；缺失时明确记录 |
| 环境工具 | Node/npm/Git、Office与字体、OCR资源、本地模型、所需浏览器工具 |

确认服务身份并停止相关写入后，使用离线快照工具；不要从在线库只复制一个.db，也不要手工丢弃WAL文件。命令参数替换为已核实的实际路径，目标须为尚不存在的新目录：

```text
node scripts/snapshot.mjs create --db <实际数据库> --files <实际内部文件根> --out <新快照目录>
node scripts/snapshot.mjs verify --snapshot <快照目录>
node scripts/snapshot.mjs restore --snapshot <快照目录> --to <新恢复目录>
```

快照只包含数据库与内部文件，不包含发布包、前端、Git历史或外部原件。SQLite可能保存模型密钥，应按私有资料保护整个快照。复制后核对集合、大小与摘要，不能只检查压缩包可打开。不要把node_modules、缓存、旧PID或server.lock当作新机运行身份。

## 4. 新设备恢复与验收

1. 建立旧、新路径对应表；检查配置及数据库中的绑定、工时来源和工具路径。不全库字符串替换，没有通用自动重定位承诺。
2. 将已验证快照恢复到新目录。restore-environment.json不自动恢复发布指针，也不自动加载环境变量；按目标布局核对数据与配置。
3. 恢复指定发布包、指针、配套前端和依赖。指针缺失时启动器可能选择工作区源码，不能用npm start探测搬来的真实库；首次启动前保留原始快照。
4. 先做源码与隔离检查，再按授权使用npm start启动日常服务。核对健康接口中的数据库、文件根、webBuilt和loadedBuild，与实际发布清单一致。
5. 对照迁移快照检查业务行数、模板、成果与文件摘要，确认外部绑定可访问。历史设备的表数、模板数和文件数不能作为未来固定验收值。
6. 按业务范围验证文档生成、Word分页、Excel重算与打印。Office、字体、本地模型和OCR需要独立核验，代码测试不能证明这些环境可用。

静态检查可运行：

```powershell
node --version
npm --version
git status --short
node scripts/docs-maintenance.mjs check
npm run typecheck
```

仅在测试资源已备齐时通过根package指定的隔离入口执行npm test。前端构建使用[开发指南](DEVELOPMENT.md)的独立outDir，避免覆盖日常前端。浏览器验证工具按实际安装配置；若使用既有Playwright脚本，按脚本要求设置WORKBENCH_PLAYWRIGHT_PACKAGE，不沿用旧用户目录。

没有证据的检查记为未验证。验收后再确定新设备为主用环境，原机备份继续保留。

## 5. 多设备协作边界

常规开发建议用Git同步源码和文档，正式数据留在明确指定的主机；副机使用独立开发环境。正式主机选择与实际迁移需另行明确，不由文档假定已完成。

同一任务同一分支尽量只在一台设备持续写入；切换时先保存、验证、完整更新当前文档、填写工作日志，由用户提交推送。新设备核对自身修改及远端基点后接续。有并行工作需求时采用独立分支/工作目录，但代码隔离不自动隔离数据库、端口或Office环境。

当前没有两台机器自动合并SQLite和文件的实现。不要让两个日常副本各自写入后相互覆盖，也不要双向同步在线数据库。普通源码接续不要求正式主机始终在线，正式发布与业务验收才需要相应环境。

接续流程不依赖Codex远程控制或跨主机聊天交接。每台设备打开本地项目，读取仓库约定和当前文档即可理解工作；个人技能、记忆与设置另行管理，不同步整个个人.codex目录来替代项目交付。

## 6. 给接续执行者的提示

> 先读AGENTS.md、GPT_CONTEXT.md、docs/README.md及五份根文档，再检查Git和实际环境。区分源码候选、正式发布与业务数据，保留已有修改，不初始化或重置正式库，不把缺失资料当空业务。依据PROJECT_PLAN说明当前状态和缺项，只执行用户指定范围。完成后将受影响文档整合为完整有效的当前说明，每次工作的经过只记录在WORK_LOG.md，并生成、检查索引。
