### 2.2 为什么是这个顺序

1. **先防丢数据，因为它是唯一"不可逆"的一档。** 其余三档做错了只是"不好用"，A 档做错是"东西没了"。而 A 档现在全缺：`deleteWorkbench()` 一次 HTTP 调用就 `rmSync` 目录 + 删库行（`docs/09` D6）；备份只有手动 `npm run pack` 且要求先停服务；`agent_action` 没有 `before` 列，所以"改前是什么"根本没落库（`docs/09` §1.3）。
2. **A 档内部是"底座 → 依赖它的人"**：B1-2 的 `pre-restore` 快照是 B1-1「彻底删除」的前置（`docs/09` §4.8.7 明确"先做快照再做回收站"）；B1-1 的 `deleted_at` 口径是 B1-4 版本链的落盘前提（删掉的旧版本不能还挂在版本列表里）。
3. **B2-5 覆盖率排自动化率第一，因为成本最低、信息量最大**：它先"把数看清楚"，再谈 AI 梳理（`docs/09` P1-1 → P1-2）。没有看板，后面所有优化都是盲打 —— 改完不知道从 36% 变成多少。
4. **B2-6 循环/图片排第二，因为它一次救三件事**：清单类模板行数不定、照片进正文、以及"编号枚举变量（`设备1名称`…`设备13名称`）虚高分母"这个压着覆盖率数字的真问题（`docs/09` §4.2.1）。它必须在 B3-9 口径校验之前做，因为"报审附件名与清单一致"这类规则要读循环出来的数组。
5. **C 档排第三，因为它的前置是"语料 + 人工确认"，不是代码**：`docs/09` §4.6.5 已写明"语料导入从现在就开始做（纯人工，不占开发窗口）"；B3-8 的代码只值约 2 人日，剩下 4–6 人日是**跑一遍、给人看、按他改**。
6. **D 档排最后，因为它全是"锦上添花 + 兜底"**：B4-12 依赖 B2-6 的产物先是对的（预览一个错文件等于把错误放大）；B4-13 没有 B3-8 的制度语料就只搜得到工作台和文件名；B4-15 是纯文档，随时可插队，放最后只因它需要用户有空读。
7. **一条贯穿逻辑**：A 档提高**下限**（不出事故），B 档提高**上限**（省人工），C 档提高**正确性依据**，D 档提高**顺手程度**。下限没兜住就谈上限，一旦出事就是"省下来的时间一次性还回去"。

## §4 第一档：防丢数据

### B1-1 回收站与撤销（软删除 + 改前快照）

**要解决什么问题**

- 用户点"删除工作台"，确认框只有一句"不可恢复"。助手侧实测**提议删除 `清廉工程月度检查` 8 次、用户 8 次全部拒绝**，摘要里一个数字都没有（`docs/09` §7.1 第 10–11 条）。
- 助手改了字段想改回来：`agent_action` 只有 `result`（改成什么），**没有 `before`（改前是什么）**，撤回在数据层不可能实现。
- 删一个阶段或字段后，挂在其下的清单项、生成记录跟着受影响，事后无法判断"当时是什么样"。

**怎么做（数据模型 / 接口 / 界面）**

迁移 `015_trash.sql`（**名称已按批次一实际落地物固定，见 `docs/14-进度快照.md`**）：

```sql
-- ① 统一软删列（5 张表列名一致，便于一个查询器通吃）
--    checklist_item 不加列：它的存活跟随 position_instance（父行软删时同事务递归软删子行）
ALTER TABLE workbench         ADD COLUMN deleted_at TEXT, ADD COLUMN deleted_by TEXT, ADD COLUMN delete_reason TEXT;
ALTER TABLE artifact          ADD COLUMN deleted_at TEXT, ADD COLUMN deleted_by TEXT, ADD COLUMN delete_reason TEXT;
ALTER TABLE position_instance ADD COLUMN deleted_at TEXT, ADD COLUMN deleted_by TEXT, ADD COLUMN delete_reason TEXT;
ALTER TABLE archive_field     ADD COLUMN deleted_at TEXT, ADD COLUMN deleted_by TEXT, ADD COLUMN delete_reason TEXT;
ALTER TABLE archive_alias     ADD COLUMN deleted_at TEXT, ADD COLUMN deleted_by TEXT, ADD COLUMN delete_reason TEXT;
CREATE INDEX IF NOT EXISTS idx_workbench_alive ON workbench(deleted_at);
CREATE INDEX IF NOT EXISTS idx_artifact_alive  ON artifact(deleted_at);

-- ② 回收站主表（一行 = 一次删除动作）
CREATE TABLE deleted_item (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  kind TEXT NOT NULL,            -- workbench | artifact | position | checklist | field | alias
  ref_id INTEGER NOT NULL,       -- 原表主键
  workbench_id INTEGER,          -- 便于按工作台过滤
  title TEXT NOT NULL,           -- 给人看的名字
  meta TEXT,                     -- JSON：删之前的行快照（逐列）
  dir_meta TEXT,                 -- JSON：被移走的文件清单 [{rel,size,sha256}]
  trash_rel TEXT,                -- _回收站/<kind>/<uuid>/...
  size_bytes INTEGER NOT NULL DEFAULT 0,
  item_count INTEGER NOT NULL DEFAULT 0,   -- 连带影响的子项数
  deleted_by TEXT NOT NULL,      -- user | agent:<actionId> | rule:<code>
  deleted_at TEXT NOT NULL, restored_at TEXT,
  purge_after TEXT,              -- deleted_at+30 天，**仅供界面显示，不自动清理**
  purged_at TEXT
);

-- ③ 撤销能力的地基：改前快照
ALTER TABLE agent_action ADD COLUMN before TEXT;       -- JSON：执行前被改记录的关键列
ALTER TABLE agent_action ADD COLUMN batch_id TEXT;     -- 一次对话里的一批动作，便于整体撤销
ALTER TABLE agent_action ADD COLUMN reverted_at TEXT;
ALTER TABLE agent_action ADD COLUMN revert_of INTEGER; -- 撤销动作指向被撤销的动作
```

- **删除 = 打标记 + 移动文件**：`deleteWorkbench()` 的 `rmSync` 改成库行打 `deleted_at`、磁盘目录 `rename` 到 `_回收站/workbench/<uuid>/`（同盘 rename 原子、快、可回滚）。
- **绝不碰用户文件的边界**（同 `docs/10` §7.1）：绑定型工作台只移走「平台登记过的 artifact 文件」+「平台自己的 `_` 子目录」，用户原有文件一个不动，`rename` 前逐条列出。
- 所有列表查询加 `deleted_at IS NULL`。**读点必须一次改齐**：`docs/09` §4.8.3 估"约 12 处"，而批次一的**实测读点是 152 处**（`FROM workbench|artifact|position_instance|archive_field|archive_alias` 的出现次数，见 `docs/14-进度快照.md` §四；分布：`service.ts` 32、`archive.ts` 19、`agent.ts` 17、`routes-files.ts` 7、`routes-work.ts` 6）。
  **这条是本项最大的坑，也是唯一可对账的数字**：`grep` 到的守卫数（`deleted_at IS NULL`）远低于读点数，就是**没做完**。软删除最典型的翻车不是删不掉，而是**删了还能被搜到、还能被 AI 当依据引用、还能出现在统计里** —— 那种情况下"删除"只是骗过了列表页。

接口：

```
GET    /api/trash?kind=&workbenchId=        回收站列表（含 size_bytes 合计）
POST   /api/trash/:id/restore               恢复；原位被占 → <原名>_恢复_<yyyyMMddHHmm>
DELETE /api/trash/:id?confirm=彻底删除      先建 pre-restore 快照，再真删（手打四字确认）
GET    /api/workbenches/:id/deletion-impact 影响预览 {positions,checklistItems,artifacts,bytes,generatedDocs,photographs}
DELETE /api/workbenches/:id?confirm=<code>  不带 confirm → 400 + 影响清单
POST   /api/agent/actions/:id/revert        撤销一条已 applied 的助手动作（读 before 写回）
POST   /api/agent/actions/:id/revert-batch  按 batch_id 整体撤销
```

界面：① 左侧导航新增「回收站」，列 `名称|类型|大小|删除人|删除时间|剩余保留天数`，行操作 `恢复/彻底删除`；② 删除对话框把"不可恢复"换成**实时数字**（"将删除 4 个阶段 / 23 条清单 / 17 个文件 / 46.2 MB"），确认输入与后端 `confirm` 同源；③ 助手动作卡片加「撤销」，悬停显示 `before → after`。

**验收标准**：① 建工作台（4 阶段/23 清单/3 文件）→ 删除 → 列表消失、回收站 1 条且 `item_count` 与影响预览一致，其余列表接口（工作台/阶段/清单/文件/搜索）逐个断言不出现；② 恢复 → 阶段数、清单数、`done_count` 合计、`artifact` 行数**逐项等于删除前**，文件 sha256 一致；③ 原位被占 → 恢复到 `<原名>_恢复_<时间戳>` 并明确报告；④ 不带 `confirm` → 400 且响应含影响清单，带错 → 400，带对 → 200 且 `backups/` 多一份 `pre-restore`，该快照里那个工作台**还在**；⑤ 改字段后 `before` 有 JSON，`revert` 回到改前值并新增 `revert_of`，对同一动作 revert 两次第二次 409；⑥ **穷举自检**（`docs/09` §7.3 第 3 条要求）：遍历所有列表接口造一条已软删数据，断言都不返回 —— 漏改一处这条就红。

**风险**：① 漏改一处列表查询 → 靠上条穷举自检 + "目标文件清单写进本文逐个对照"；② 外键 `ON DELETE CASCADE` 不再触发 → 软删父行时**同事务递归软删子行**，并断言"父行软删后子行 `deleted_at` 全非空"；③ 误碰用户文件 → 沿用 `docs/10` §7 安全阀，删除前逐条打印将移动的路径，隔离目录演练；④ 回收站被同步盘同步导致膨胀 → 回收站放 `RUNTIME_ROOT/trash`（本地盘），不放绑定根。

**工作量**：4–5 人日（迁移+存储层 1.5、接口 1、12 处查询 1、界面+穷举自检 1）。

> **基线口径更新**：`docs/09` 的核实快照（2026-10-01）记"迁移 9 个、`ai_call_log` 627"，批次一实测为"迁移 001–014、`ai_call_log` 628"（`docs/14-进度快照.md`）。本文引用 `docs/09` 数字时以它的"当时口径"为准，对账时以最新实测为准。

### B1-2 自动备份与一键恢复

**要解决什么问题**

- 唯一备份是手动 `npm run pack -- --with-runtime-state`，且 `docs/09` §1.3 已核实：**服务在跑时会被锁文件挡住**。要求"先关服务"的备份命令，用户不会定期跑。
- `workbench.config.json` 允许数据目录放 OneDrive/坚果云；WAL 模式下直接 `copyFileSync(workbench.db)` 会得到**丢了未 checkpoint 事务**的库。
- 没做过还原演练 = 不知道备份能不能用。`docs/09` P7 已写死："备份必须自动化，且必须验证过能还原"。

**怎么做**

- 新增 `core/backup.ts`，复用 `scripts/pack.mjs` 已验证的机制：`node:sqlite` 的 **`backup(db, tmpFile)` 在线快照** + `PRAGMA quick_check` + `PRAGMA foreign_key_check` + 逐表 `COUNT(*)` 与源库比对，三者全过才算成功。
- 落盘 `RUNTIME_ROOT/backups/YYYYMMDD-HHmmss-<kind>/`：`workbench.db` + `MANIFEST.json`（时间、kind、库大小、逐表行数、`data/files` 文件数与总字节、启用模板 sha1）+ `BACKUP-NOTICE.txt`（**明说快照含 `ai_provider.api_key`，别乱拷**，`docs/09` §4.8.2 第 5 条）。
- **触发时机三个都要**：启动时（异步、不阻塞监听、一天最多一次防抖）；危险操作前（删工作台/彻底删除/批量采纳提议/`reset`）建 `pre-restore`；界面「立即备份」。
- **保留策略**：按天 7 份 + 按周 4 份（周一那份），总量上限 2GB，超了删最旧 `auto`；`pre-restore` 与 `manual` **永不自动删**。
- **失败要吵**：快照失败 → `/api/health` 返回 `backupStale: true` + 最后成功时间；首页黄色横幅"最后一次成功备份是 N 天前"。

接口与界面：`POST /api/backup/run`（`{kind:'manual'}`）、`GET /api/backup/list`、`GET /api/backup/:id/verify`（重跑 quick_check + 行数比对，只读）、`POST /api/backup/:id/restore`（`{confirm:'恢复'}`）。界面在设置页加「备份」卡片（上次成功时间、占用、列表、立即备份、还原）；**还原两步**：第一步显示"将从 <时间> 的快照恢复，当前库会被替换，替换前的库自动另存为 `pre-restore`"，第二步手打"恢复"。流程写进 `docs/12-备份与还原.md`。

**验收标准**：① 清空 `backups/` → 启动 → 3 秒内出 `auto` 快照，同一天再启动两次**不重复建**；② `MANIFEST.json` 逐表行数与源库一致，快照 `.db` 单独打开 `integrity_check`=ok、`foreign_key_check` 空；③ 删一个工作台 → 出现 `pre-restore` 且该快照里那个工作台**还在**；④ **还原演练（必须真做一次）**：还原到 `WORKBENCH_DATA_DIR` 指向的临时目录，起服务，`db:init` 输出与还原前逐项相等（工作台/阶段/别名/文件数），演练命令与输出摘要记进 `docs/12`；⑤ 造 10 份 `auto` → 清理后剩 7 份，`manual`/`pre-restore` 一份不删；⑥ 把 `backups/` 设为只读 → 手动备份返回失败、`/api/health` 带 `backupStale`、横幅可见。

**风险**：① 逐表行数比对慢 → 只比行数>0 的表，比对 30 秒超时则标 `partial` 并在界面显示"未完成全表校验"，不假装成功；② 磁盘占用失控 → 2GB 上限 + 显示占用，`pre-restore` 超 20 份只提示不自动删；③ 还原覆盖成更旧的版本 → 两步确认 + **还原前自动建一份 `pre-restore`**（还原本身也可回退）；④ 同步盘拆散 `-wal`/`-shm` → 按 `docs/09` §4.8.2 第 6 条检测 `OneDrive`/`坚果云`/`Dropbox` 并提示，支持 `WORKBENCH_RUNTIME_DIR` 把库与大文件目录分开。

**工作量**：3–4 人日（快照模块 1.5、接口 0.5、界面 0.5、保留策略+演练与文档 1）。

**要解决什么问题**

ALTER TABLE agent_action ADD COLUMN actor TEXT NOT NULL DEFAULT 'user';  -- user | agent | selftest

### B1-4 生成文书版本管理与「最终版」标记

**要解决什么问题**

- 真遇到过的事：**"生成文书返回成功但文件打不开"**（`docs/09` D1，模板 id 65/73/76/77/84/96）；同时"同一份文书改 3 遍"在磁盘上是 `XXX_v1/v2/v3.docx` 三个并列的独立文档，**没有"这是同一份的三个版本"这个概念**。
- 用户判断"哪份是最终版"靠文件名猜；`artifact.version` 列**存在但无任何写入路径**（`docs/09` D8 已核实）。

**怎么做**

迁移 `017_doc_version.sql`：

```sql
ALTER TABLE artifact ADD COLUMN version_group TEXT;      -- 版本链 id（uuid）
ALTER TABLE artifact ADD COLUMN revision INTEGER NOT NULL DEFAULT 1;
ALTER TABLE artifact ADD COLUMN supersedes_id INTEGER;   -- 上一版 artifact.id
ALTER TABLE artifact ADD COLUMN is_final INTEGER NOT NULL DEFAULT 0;
ALTER TABLE artifact ADD COLUMN final_at TEXT;
CREATE INDEX IF NOT EXISTS idx_artifact_version_group ON artifact(version_group, revision);
ALTER TABLE generation_log ADD COLUMN version_group TEXT;
ALTER TABLE generation_log ADD COLUMN revision INTEGER;
ALTER TABLE generation_log ADD COLUMN prev_artifact_id INTEGER;
```

- `saveGeneratedDocument()` 行为改变（**关键决定**，`docs/09` §4.8.4 已定）：同一 `workbench + template + checklist_item` 已有 `is_final=0` 的生成件时，**默认不新建并列文件** —— 老文件移到 `_生成文书/.versions/<group>/v<N>.docx`，新版本占正式文件名。组的键固定为这个三元组，判定不出来就**新建组**（宁可多一条链也不错串）。
- 生成对话框给三选项：**新建**（另一份不同用途）/ **更新这一版**（推荐默认）/ **另存为定稿**（置 `is_final=1`）。已是定稿的文书，生成入口拦下并提示"请先取消定稿或另存为新版本"。

接口与界面：`GET /api/artifacts/:id/versions`（revision/时间/生成人/is_final）、`POST /api/artifacts/:id/mark-final`（`{final}`）、`POST /api/artifacts/:id/rollback-to/:revision`（复制回来成为 revision+1，**永不删中间版本**）、`GET /api/artifacts/:id/diff?from=&to=`（仅变量级）。界面在文书详情加「版本」标签：`v3（当前）· 定稿` / `v2` / `v1`，两版对比显示"`合同金额`：1250000 → 1300000"，定稿带锁图标，版本项给**真实绝对路径** + 「在资源管理器中打开」。**不做 docx 正文 diff**（`docs/09` §6 的否决理由：差异大量来自 XML 结构噪声，而"哪个字段改了"在 `generation_log.variables` 里本来就有）。

**验收标准**：① 连出 3 次 → 磁盘正式文件**只有 1 个**、`.versions/<group>/` 下 2 个，版本链接口返回 3 版且 `revision` 递增、`supersedes_id` 成链；② 第三次改 `合同金额` → `/diff?from=1&to=3` 只返回该键；③ 定稿后再点生成被拦且错误明确（不静默覆盖）；④ 回滚到 v1 → 新版本 v4 与 v1 **逐字节一致**（sha256 相等），v1/v2/v3 仍在；⑤ 软删正式文件 → 版本链该条消失、`.versions/` 历史版本不随之消失（口径写进本文并断言）；⑥ 旧数据零影响：迁移前生成件全为 `version_group IS NULL`、`revision=1`，界面显示"v1（未分链）"不报错。

**风险**：① 老文件移进 `.versions/` 后用户"找不到上一版" → 版本列表给真实绝对路径 + 打开目录（沿用 `docs/10` §10.5 的立场）；② 落盘逻辑与 B2-6 打架 → B1-4 先落地式（`.versions/` 位置与命名），B2-6 只改渲染内容不改落点，两者口径开工前各写一句到本文；③ 组归属判错 → 固定三元组键 + 判定不出就新建组。

**工作量**：3–4 人日。

## §5 第二档：自动化率

### B2-5 变量映射覆盖率（三口径 + 看板 + AI 批量梳理）

**要解决什么问题**

- 真数字（`docs/09` §1.2 已核实）：**1089 处引用、632 个不同变量名、132 条别名（手工确认 0 条）**，引用加权覆盖率 **36.1%**。含义直白：**每 100 个待填位置只有 36 个能确定性带出**。
- 现在没人能回答"到底哪些变量没覆盖、来自哪份模板的哪一处"，AI 梳理只能盲跑。
- 长尾里有一批**看着是变量、其实是列表被手工展开**的键（`设备1名称`…`设备13名称`、`乙方人员一姓名`…），它们**虚高分母**，必须单独计数，否则覆盖率数字被永久压住。

**怎么做**

- 服务端抽 `domain/coverage.ts`，`computeCoverage()` 返回**三个口径**：`byReference`（引用加权，1089 处命中多少，主口径）、`byName`（不同变量名，632 里命中多少，副口径）、`exclEnum`（**扣掉编号枚举与循环/图片变量后**的引用加权 —— 必须同时报，否则 B 批出口的 55% 无法与过去比较）。**口径文字写进响应体**（`docs/09` §4.3.2 硬要求：没有口径说明的百分比，三个月后一定会被当成两种东西引用）。
- 每个未映射项带 `usedBy: [{templateId, templateName, hitCount, locator}]`，`locator` 形如"表格 2 第 4 行第 2 列"（复用模板健康检查的 XML 定位能力）。
- **AI 梳理分批**（不按变量逐条调模型，632 次又慢又贵）：按模板分批 → 每批 20–40 个未映射变量 → 提示词带"已有字段与别名清单（截断到相关域）"→ 输出 `{varName, action:'alias'|'field', targetFieldKey?, label, confidence, reason}`。**能本地确定性判定的不经过模型**（`docs/09` P1）。
- **编号枚举不逐条建字段**：识别 `^(.+?)(\d+|[一二三四五六七八九十]+)(.+)$` 族 → 标 `family`，只出"建议改造为 `{#循环}`"，交给 B2-6/B2-7 的模板改造流程，**不产生 N 条别名**。

接口与界面：`GET /api/archive/coverage`（三口径 + `calibers` 文字 + totals）、`GET /api/archive/coverage/by-template`、`GET /api/archive/coverage/unmapped?templateId=&family=&page=`、`POST /api/archive/analyze`（`{scope,batchSize}`）、`GET /api/archive/proposals?confidence=`、`POST /api/archive/proposals/accept`（`{ids}` 或 `{minConfidence:'high'}`）。界面独立「覆盖率」页：顶部三个大数字 + 一句口径说明；按模板列表可点进去看未映射清单；每条给「来自哪份模板哪一处」「AI 建议」「一键建别名/建字段/忽略」；中/高置信度分组，"采纳后覆盖率变成 XX%"实时预告。

**验收标准**：① 三个数字与独立脚本（读 `.vars.json` 与 `archive_alias` 求交）算出的**完全一致**（同一口径误差 0），响应含口径文字；② `by-template` 各模板命中数与手算一致（抽 3 份核对）；③ 未映射项点得开：任选 1 项，`usedBy` 的模板与"表格/行/列"定位在 Word 里能对上（人工核对 1 次）；④ AI 梳理一轮产生提议数 ≥ 未映射数 60%，**采纳 120 条 high 提议时新建 `field_key` ≤ 20 个**（`docs/09` P1-3 口径），采纳后看板数字刷新；⑤ `设备1名称…设备13名称` 13 个键归为 1 个 `family`，**不产生 13 条别名**；⑥ 梳理可重跑且幂等（按 `varName+targetFieldKey` 去重）。

**风险**：① 口径歧义 → 响应体与界面都带口径文字，同时报三口径；② 字段爆炸 → 采纳前本地同义合并 + `new field_key ≤ 20` 硬门禁，**AI 提议永不自动采纳**；③ 模型成本 → 分批 + 先本地匹配 + 只对未映射项调用，每轮调用数进 B1-3 审计。

**工作量**：5–7 人日（`coverage.ts` + 3 个接口 2、看板 2、AI 分批与采纳 2–3）。

### B2-6 docx 模板引擎支持 `{#循环}` 与 `{@图片}`

**要解决什么问题**

- 行数不定的清单/台账：`10-原材料产品报验单`（60 变量）、`05-设备产品验收表`（68）、`07-设备到货开箱验收清单`（42）、`11-设备移交清单`（44）—— 模板把"一行的列"手工展开成 `设备1名称…设备13名称`，**清单多一行就得改模板**，模型要填几十个高度相似的键。
- 现场照片进不了正文：检查记录表、验收报告、隐蔽工程记录都要"文字 + 现场照片"，现在只能出附件说明，用户拿到文书还得手工贴图、调大小、加图注。
- 现状已核实：`core/placeholders.ts:64` 对 `#` `/` `@` 三种前缀**直接 `return raw`**，`core/template.ts` 渲染路径完全不认识它们（`docs/09` D2）。

**怎么做**

- **算法不在这里重复**：`docs/09` §4.2.2–§4.2.6 已把语法语义、表格行复制与合并单元格规则（`gridSpan` 原样、`vMerge` 首行判定、`tcBorders` 只留首末、删 `w:rsid*`）、`{@图片}` 的四件必做注册（media 文件/`document.xml.rels`/`[Content_Types].xml`/`blip`）、尺寸与 EXIF 方向、预览三层**写死**。本文只落排期与边界：**本项只做 docx**（xlsx 循环走 ExcelJS 的另一条实现路径，不在本项内）。
- **前置硬条件**：`docs/09` P0-1/P0-2（`validateXmlStructure` + 渲染后校验 + 坏模板不出坏文件）**必须先就位**；没有校验器就做循环 = 在坏文件生产线上加产能。
- 变量模型同步扩展：`.vars.json` 每项加 `kind: 'text'|'list'|'image'` 与 `itemFields: string[]`；扫描器识别 `{#x}…{/x}` 自动产出 `kind=list`。
- AI 侧（`specLines()` 与 JSON 解析）允许数组值；`image` 项的 `artifact_id` **只允许从"本项目已有影像证据"候选集选**，代码侧二次校验，不在候选集一律丢弃并计 warning（防模型编 id，`docs/09` §4.2.5）。
- 分两批提交：**先循环（P3-1）后图片（P3-2）**，每批都跑老模板字节级回归。

**验收标准**（出口必过 6 条，全量 16 条见 `docs/09` §4.2.7）：① 3 行表格模板数组 0 项 → 数据行消失、表头留存、**无残留占位符**；1 项 → 1 行；5 项 → 5 行；② 合并单元格用例（`vMerge`）渲染 3 项 → 产物 6 行合并关系正确，且**人工在 Word 里开过一次**并固化为黄金样本；③ 配对失败（只有 `{#x}` 无 `{/x}`）→ `ok:false` + `RENDER_UNBALANCED_LOOP` + **磁盘无新文件**；④ 单图嵌入 → `word/media/` 多 1 个文件、rels 多 1 条关系、`[Content_Types].xml` 有对应 `Default`，严格解析器（python-docx）能读到 1 个 inline shape；⑤ `Orientation=6` 竖拍照片 → 产物宽高已交换，Word 里不躺着；⑥ **老模板回归**：所有不含 `{#`/`{@` 的模板渲染结果与改造前**字节级一致**（48 份产物做基线逐字节比对）。

**风险**：① 表格行复制破坏排版 → 规则已在 `docs/09` §4.2.3 写死，每条规则配 1 个单测；② 图片注册漏一步导致 Word 报"内容有问题" → 四件事合成一个函数，缺任一件**抛错不写盘**；③ 大图让文书体积失控（40 页 → 200MB）→ **不新增原生依赖**（`sharp`/`jimp` 均否决），超 4MB 原样嵌入 + 界面提示体积；④ 模型编造 `artifact_id` → 候选集 + 二次校验 + `strict` 模式 412；⑤ 循环与图片一起上难定位 → 分两批，每批跑老模板字节级回归。

**工作量**：8–11 人日（循环 5–6、图片 4–5，含单测与回归基线）。

## §6 第三档：知识库依据

### B3-8 内容抽取与向量化

**要解决什么问题**

- 框架已就位：`kb_source` 表（`012_kb_source.sql`）、来源登记接口（`GET/POST/DELETE /api/kb/sources`、`POST /api/kb/sources/:id/scan`）、界面卡片都在，但**只统计 `file_count`/`total_bytes`，一个字节内容都没读**（`docs/10` 决定 7："先搭框架"）。

- 可直接复用：`core/extract.ts`（docx/pptx/pdf/xlsx 抽文本）、`core/ocr.ts` 与 `core/ocr-queue.ts`（扫描件 OCR + 排队）、`core/kb.ts`（切块 500 字重叠 60 + 向量化 + FTS/语义混合检索）。识别结果长什么样用户**已经看过**：`docs/制度识别预览.md`。

**待用户确认的三个口径（不确认不开工）**

| # | 口径 | 选项 | 影响 |
|---|---|---|---|
| 1 | **去重口径** | ① 仅 `sha256` 相同 ② `sha256` + 归一化文本（去空白/换行/页眉页脚）③ 不算重复，同名文件各存一份 | 决定 `kb_document` 里有多少重复制度，影响"同一份制度在检索里出现 3 次" |
| 2 | **法规与参考制度是否入库** | ① 只本单位制度 ② 本单位 + 行业规范 ③ 全部（含国家法规） | 决定 `kb_source` 是否按"国家/行业/单位/项目"四层组织（`docs/09` §3.4）与检索默认过滤层 |
| 3 | **上会/历史版本是否抽取** | ① 只现行版 ② 现行 + 历史（历史标 `superseded`，检索默认不返回）③ 都抽不区分 | 直接决定 B3-10 双链会不会把旧版当依据 |

**怎么做**

- 抽取流程 `POST /api/kb/sources/:id/extract`（异步 + 进度）：① 遍历源目录（`readdir`+`stat`，**跳过 `.`/`_` 开头目录**，沿用 `docs/10` §12.5）；② **按需下载** —— iCloud 占位文件只在"要读内容"时触发下载，**不批量预下载**（`docs/10` §6：扫描阶段只读元数据）；③ 按扩展名分流：`.docx/.xlsx/.pptx/.pdf` → `extractAny()`，图片/扫描 PDF → `ocr-queue` 排队（进度 + 超时，单项失败不阻塞整批）；④ 按口径 1 去重 → 写 `kb_document`（`source_id`/`rel_path`/`sha256`/`doc_kind`/`layer`/`version_status`）；⑤ 切块 → 向量化 → 写 `kb_chunk`（**沿用 `core/kb.ts` 现有切分与 embedding 链路，不换实现**）。
- **抽取前先出预览**：`POST /api/kb/sources/:id/preview` 返回前 20 份文件的"识别摘要 + 切块数 + 疑似重复项 + 无法识别清单"，界面确认后再真跑 —— 这正是 `docs/制度识别预览.md` 做过的事，把它变成**按需生成的接口**。
- **绝不写入来源目录**（`docs/10` §11 铁律）：中间产物写 `RUNTIME_ROOT/kb-tmp`。

**验收标准**：① 对**临时目录里的制度副本**（不是用户 iCloud 原目录）跑抽取 → `kb_document`/`kb_chunk` 行数 >0，且抽取前后源目录**快照对比完全一致**（递归文件清单 + mtime + 大小）；② 同一份制度两份（内容相同、文件名不同）→ `kb_document` 只 1 条，第 2 份记"已跳过（与 #N 相同）"；③ 无法识别的文件（加密 docx/损坏 pdf）进 `failures` 并给原因，整批不失败；④ 抽完 `GET /api/kb/search` 能命中新制度并给出文件名与段落，`POST /api/kb/ask` 能带出处回答；⑤ 三个口径各留一份对比记录（同一批文件的 `kb_document` 计数），写进本文附录供拍板时看数字；⑥ 进度可见：`GET /api/kb/status` 返回 `{total,done,failed,current}`，界面有进度条与已用时间。

**风险**：① **触发 iCloud 批量下载**（几百 MB 甚至 GB）→ 只对确认目录跑、preview 只读元数据、下载有并发上限与超时，界面**先显示"将读取 N 个文件 / 约 XX MB"再确认**；② OCR 拖慢整批 → 走独立队列 + 可"先跳过 OCR 只抽文字层"，分开报进度；③ 向量化成本 → 分批 + 断点续跑（`kb_document.embedded_at` 为空就重试），失败不整体重跑；④ 语料质量差（页眉页脚/扫描噪声）→ preview 阶段就把切块样例给人看，差的文件可标 `disabled` 排除。

**工作量**：6–8 人日（代码约 2、跑批与口径对比 2、按用户反馈调 2–4）。

### B3-9 条款级引用 + 出文书前口径校验

**要解决什么问题**

- 真被退回来的事：**合同金额大小写不一致**、**日期早于开工日**、**报审附件名与清单不一致**、**"共 X 页"与实际页数不符**（`docs/09` §4.6.4 那 12 条草案就是从这类公文惯例拟的）。现在这些全靠人眼，常在盖章交出去之后才发现。
- 引用只能给到"某文件某段"：切块按语义边界，**不知道"第几条第几款"**（`docs/09` §3.4）。

**怎么做**

- **条款切分**：`core/kb.ts` 的切块前加一层"按条/款/项"识别（`第[一二三四五六七八九十百零\d]+条`、`（一）`/`1.`、`第N款`），识别成功先按条款边界切，失败回退字数切块；`kb_chunk` 加 `clause_no`/`clause_path`（如 `3.2.1`）。检索结果与 `POST /api/kb/ask` 的出处精确到条款。
- **口径校验规则引擎**（`docs/09` §4.6.6 已设计，本文不重复）：`compliance_rule` 表（`code`/`severity: block|warn`/`expr`/`message`/`scope`/`enabled`）+ `core/compliance.ts` 求值；**不引第三方表达式引擎**，用只允许 `字段名 运算符 常量` 与少量函数的受限求值器（`docs/09` P5：规则是数据）。
- 12 条内置规则**先做草案给人改**（`docs/09` §7.2 第 14 条明确："必须由用户逐条确认或改写后才算数"）：

| 规则码 | 检查 | 级别 |
|---|---|---|
| `AMOUNT_CASE` | 合同金额大小写一致（含换算校验） | block |
| `DATE_ORDER` | 日期序列合法：签订 ≤ 开工 ≤ 竣工 ≤ 今天 | block |
| `DATE_NOT_BEFORE_START` | 报审/验收日期不早于开工日 | block |
| `ATTACHMENT_MATCH` | 报审附件名与清单一致、数量相符 | block |
| `HEAD_COUNT` | 人数/份数合计与明细相符 | block |
| `REQUIRED_FIELD` | `readonly` 字段（金额/日期/编号）不得为空、不得为 `【待补】` | block |
| `PAGE_COUNT` | "共 X 页"与已知页数一致（**B2-6 之后才可算**） | warn |
| `NUMBER_FORMAT` | 编号格式符合单位规则（如 `HT-YYYY-NNN`） | warn |
| `NAME_CONSISTENCY` | 同一主体全篇用同一名字（不混用简称全称） | warn |
| `UNIT_CONSISTENCY` | 单位与数量配套（有数量必有单位） | warn |
| `PERIOD_MATCH` | 期次与文书日期同属一期 | warn |
| `SIGN_DATE_PRESENT` | 落款日期已填 | warn |

- **检查点**：`POST /api/generate/preview` 与 `/save` 渲染后都跑规则；`block` 不通过 → 拒绝保存并列出"不通过项 + 怎么改"；`warn` → 允许保存但必须填**例外说明**（`compliance_exception`：`rule_code`/`artifact_id`/`reason`/`actor`/`created_at`），留痕供 B1-3 审计页查看。

**验收标准**：① 条号抽查 **10/10** —— 从用户确认纳入的制度里随机抽 10 条引用，条号与原文一致（人工核对，结果记入本文附录）；② 12 条规则各有**正例 + 反例**单测：正例放行、反例被拦且提示指出"哪个字段、错在哪、期望什么"；③ 端到端：故意把金额小写改得与大写不符 → 被 `AMOUNT_CASE` 拦下（block）且磁盘无新文件，改一致后通过；④ 例外放行：对 `PAGE_COUNT` 的 warn 填例外说明 → 保存成功，`compliance_exception` 1 条，审计页能看到"谁在何时以何理由放行了哪条规则"；⑤ 规则数据化：界面上改一条规则阈值（不改代码）立刻生效；⑥ 无假阳性：不含相关字段的文书不报错（求值遇空值 → 跳过并计入"未求值"）。

**风险**：① 假阳性让人不敢用 → 默认只开 6 条 block（金额大小写/日期序列/报审日期/附件一致/人数合计/必填非空），其余 warn，每条可单独关；② 条款切分误判表格里恰好出现的"第X条" → 只对"行首 + 前后段落边界"生效，失败回退字数切块并记日志；③ 求值器写错导致规则静默失效 → 12 条全有正反例单测，"求值为空"与"求值为假"分开计数；④ 页数规则依赖 Word 实际分页 → **不做真实分页计算**，模板没给页数变量就跳过（不假装能算）。

**工作量**：2–3 人日（条款切分 + 引用 + 6 条 block 规则先落地）；若把 12 条规则引擎与界面算全，另加 4–6 人日，按用户逐条确认后追加。

### B3-10 文书↔制度双链

**要解决什么问题**

- 正向：这份文书引用了哪几条制度？被问"依据是什么"时只能靠记忆。施工方案写"依据《XX管理办法》"**没写第几条**，也没入库。
- 反向：**制度改了以后哪些文书受影响？** 例如《安全检查管理办法》第 5 条改了检查频次，按旧版出的检查记录表与检查计划都需复核。现在没有机制能回答，只能等审计发现。
- 没有双链，"制度依据"就只是检索出来看一眼的建议，不进文书、不进档案、不可追溯。

**怎么做**

迁移 `019_doc_kb_link.sql`：

```sql
CREATE TABLE doc_kb_link (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  artifact_id INTEGER REFERENCES artifact(id) ON DELETE CASCADE,
  kb_document_id INTEGER NOT NULL REFERENCES kb_document(id) ON DELETE CASCADE,
  kb_chunk_id INTEGER REFERENCES kb_chunk(id) ON DELETE SET NULL,
  clause_path TEXT,                 -- '3.2.1'
  link_kind TEXT NOT NULL,          -- explicit（模板里写了条号）| suggested（检索命中）| manual（人加的）
  confidence REAL, quote TEXT,      -- quote：原文片段，制度改了以后能对比
  doc_sha256 TEXT,                  -- 引用时那份制度的 sha256：变了就说明制度改过
  created_at TEXT NOT NULL,
  deleted_at TEXT, deleted_by TEXT, delete_reason TEXT
);
CREATE INDEX IF NOT EXISTS idx_dkl_artifact ON doc_kb_link(artifact_id);
CREATE INDEX IF NOT EXISTS idx_dkl_kbdoc ON doc_kb_link(kb_document_id);

CREATE TABLE kb_change_impact (        -- 影响面缓存，避免每次现算
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  kb_document_id INTEGER NOT NULL,
  old_sha256 TEXT NOT NULL, new_sha256 TEXT NOT NULL,
  changed_clauses TEXT,      -- JSON：变了的条款号
  affected_artifacts TEXT,   -- JSON：[{artifactId,title,workbenchCode,clausePath}]
  computed_at TEXT NOT NULL
);
```

- **正向建链三来源**：① **显式** —— 正文出现 `《制度名》第X条` 组合写法，扫描后自动建 `explicit` 链（**不需要模型**）；② **建议** —— 出文书时检索命中的制度建 `suggested` 链，**要人点确认才升为 `manual`**；③ **人工** —— 用户在文书页手动加。默认视图只显示 `explicit` + `manual`，`suggested` 折叠且标"未确认"（**不冒充实锤依据**）。
- **反向影响面**：制度重新抽取后比对 `doc_sha256` 与条款号集合 → 变了的条款 → 反查引用过这些条款的文书 → 写 `kb_change_impact` + 首页提示"3 份文书引用的条款已变更，需复核"。
- **不做自动改文书**：只报告，复核结论由人给（不适用/已更新/待处理）。自动改已定稿文书违背 `docs/09` §6 底线。
- 接口：`GET/POST /api/artifacts/:id/citations`、`DELETE /api/citations/:id`（软删）、`GET /api/kb/documents/:id/usages`、`GET /api/kb/documents/:id/impact`、`GET /api/kb/impact/pending`。界面：文书详情加「制度依据」卡片（制度 + 条款号 + 原文片段 + 来源徽标，可手加/取消）；知识库文档详情加「被引用」标签；首页加"待复核影响"提示。

**验收标准**：① 正文写 `《XX管理办法》第5条` → 生成后引用接口返回该条，`link_kind=explicit`、`quote` 与原文一致、`doc_sha256` 非空；② 出文书检索命中 3 条 → 3 条 `suggested` 显示"待确认"，确认 1 条变 `manual`，未确认的以虚线和"未确认"标注；③ `usages` 反查返回引用它的全部文书（含工作台编号与标题）；④ 把被引用制度改一字重新抽取 → `impact` 返回 `changed_clauses` 与 `affected_artifacts`，`/api/kb/impact/pending` 计数正确，首页提示可见；⑤ 软删一条文书 → 引用不再出现在反查里（与 B1-1 口径贯通）；⑥ 制度内容没变（sha256 相同）→ `impact` 为空，`pending` 不增加。

**风险**：① `suggested` 噪声 → 默认折叠 + 单份文书建议链上限 10 条；② 条款号误判 → 只认 `《…》第N条` 组合写法，单独出现的"第N条"只记低置信度建议；③ 影响面计算量大 → 结果落缓存表，只在"重新抽取且 sha256 变化"时算；④ 用户觉得"要复核的越来越多" → 复核三态 + "整批标为不适用"，结论回写 `doc_kb_link` 让下次不再报。

**工作量**：4–6 人日。

### B4-11 崩溃自愈 / 看门狗 + `/api/health` 暴露"上次未捕获异常"

**要解决什么问题**

- `packages/server/src/index.ts:58` 已有 `uncaughtException`/`unhandledRejection` 钩子，但**只写日志，不影响任何界面**。用户看到的是"服务悄悄不响应了"或"某个功能一直转圈"，而系统看起来一切正常 —— 正是 `docs/09` P6"失败要响，不能静默"的典型违反。
- 单机单用户、没有运维；出问题时唯一依靠是用户自己发现。**首页红灯**比任何日志都管用。

**怎么做**

- 迁移 `020_app_health_event.sql`：**已落地**，表 `app_health_event(id, at, kind, message, stack_head)` + `idx_app_health_event_at` / `idx_app_health_event_kind_at`。`kind ∈ uncaughtException|unhandledRejection|ocrFailure|selfCheckFailed`（`core/health.ts` 的 `HealthEvent` 口径）。**列按 health.ts 的实际 INSERT 来定、不加它不插的列**：草稿里的 `count`/`seen_at` 若建成 NOT NULL 且无默认值，会让 `INSERT (at,kind,message[,stack_head])` 每条都失败，连续 5 次后 health.ts 永久降级为"仅内存"（重启即清零）——这个坑已避开；将来要合并计数再补 `ADD COLUMN count INTEGER NOT NULL DEFAULT 0`。
- OCR 失败也要进事件列表：`core/ocr-queue.ts` 在任务被判 `failed` 的每个分支各记一条 `ocrFailure`（① `runOne` 抛出、由 `processQueue` 的 catch 交给 `failItem` 的异常，含识别超时；② 文件已不在磁盘上；③ `ocrFile` 返回 `ok:false`；写在 `finish()` **之前**，所以连"failed 写不进库"也留得下痕迹），message 形如 `OCR 失败：<可读原因>｜文件：<文件名>（artifact #<id>）`；`done`/`skipped`（PDF、无文字、已取消）**不记**，避免噪声。
- `index.ts` 钩子改成：写 `app_health_event` + `console.error` + **不退出进程**；但连续 N 次同一异常说明状态已不可信 → 明确写"建议重启"标记（**数据库损坏/迁移失败这类仍要停下并 `exit(1)` + 可读错误**）。
- 看门狗三件事：① **心跳** —— 每 30 秒写内存时间戳，`GET /api/health` 即可反映"进程是否活着"；② **DB 锁自愈** —— 捕获 `SQLITE_BUSY` 重试 3 次（指数退避），仍失败记 `db_locked`；③ **启动自检** —— `PRAGMA quick_check` + `foreign_key_check`（`docs/09` §4.10 已有约定）+ `data/files` 可读性 + 备份是否过期，结果进 `/api/health`。
- `/api/health` 扩展（**向后兼容，只加字段**）：`lastUncaughtAt`、`lastUncaughtMessage`、`uncaughtSinceBoot`、`dbOk`、`backupStale`、`lastBackupAt`、`pendingImpact`、`heartbeatAt`、`uptimeSec`。
- 界面：首页顶部状态条 —— 绿（正常）/ 黄（备份过期、有待复核影响、有 warn 事件）/ 红（有未捕获异常、`dbOk=false`）；点开看事件列表并「标记已读」。**红灯时不藏内容但置顶提示**（用户可能正急着用）。

**验收标准**：① 人为触发一次 `uncaughtException`（测试路由抛错）→ `/api/health` 带 `lastUncaughtAt` 与 `uncaughtSinceBoot=1`，首页红灯，标记已读后红灯消失；② 服务重启 → `lastUncaughtAt` 仍能读到上一次（来自表，不是内存），`uncaughtSinceBoot` 归零（区分"本次启动以来"与"历史上"）；③ `db_locked` 自愈：两个连接争抢写锁 → 日志有重试记录且最终成功，人为让重试全失败 → 出现 `db_locked` 事件；④ 把 `backups/` 最新时间改成 3 天前 → 首页黄灯 + 文案"最后一次成功备份是 3 天前"；⑤ 正常跑 `npm run test:all`（隔离实例）**不产生**任何健康事件。

**风险**：① 事件表被刷爆（循环错误每秒一条）→ 同一 `kind+message` 5 分钟内合并计数（记第一次 + `count`）；② 吞掉异常导致状态已坏 → 只对可安全继续的路径（HTTP 处理、任务失败）吞；③ 看门狗本身有 bug → 定时器内全部 `try/catch`，心跳不写磁盘。

**工作量**：1.5–2 人日。

### B4-12 真·预览（页面内预览文书，不再下载文件）

**要解决什么问题**

- 现状已核实：`GenerateModal.tsx` 的 `doPreview` 调 `postBlob` 后 `api.saveBlob(...)` —— **用户必须离开浏览器打开文件**（`docs/09` §7.1 第 18 条）。
- 这条路径还在放大错误：坏模板产出的坏文件"下载得到、打不开"（`docs/09` D1），而预览这一步**没有任何可读性判断**。
- 用户只是想知道"长什么样、数字对不对"，不该每次开 Word、每次在磁盘留一个 `_预览.docx`。

**怎么做**

- **三层里做两层 + 第三层的一种做法**（`docs/09` §4.2.6 已论证）：① **结构化预览（必做）** —— `POST /api/generate/preview` 的 JSON 带 `plan.segments`（`text`/`table`/`image`），界面渲染成 HTML 表格 + 缩略图；界面必须写明"这是内容预览，字体分页以 Word 为准"。② **产物合法性横幅（必做）** —— 预览时同跑 `validateXmlStructure` + 循环标记残留检查，绿色 `✓ 产物结构合法，可正常打开` / 红色 `✗ 产物结构异常，已阻止保存`；**没有这条横幅，预览就只是好看**。③ **HTML 近似排版只做一种** —— **只把后端产出的 `plan` 渲染成 HTML**，**不做前端重新解析 docx**（理由同 `docs/09` §4.2.6：会生成第二真源，两边在合并单元格/编号上一定会不一致）。
- **`plan` 必须由渲染器实际使用的数据结构产出**（不是另写一套解析），从而与真实 docx 天然一致。
- 兼容路径：保留「用系统打开」（写 `RUNTIME_ROOT/preview/<uuid>.docx` → `cmd /c start`，不阻塞不解析返回值）—— 机器上有 Word 时这是最准的预览，也是 HTML 近似的兜底。预览文件是临时文件：启动时清理 24 小时前的，**永不进 `artifact`**、永不落进用户目录。

**验收标准**：① 单份 40 变量模板：从"填完变量"到"看到内容预览"**≤ 2 次点击、页面不跳转**，表格行数与请求数组一一对应；② 预览**不产生下载** —— 浏览器下载目录无新文件、`artifact` 不新增行、用户目录快照不变；③ 坏产物：人为让渲染器产出不合法 XML → 预览 `ok:false` + 红色横幅，磁盘无文件、接口不保存；④ `plan.segments` 的 `image` 段在页面内显示缩略图 + 图注（"图 1：…（2026-09-16 09:24 摄）"），顺序与数据一致；⑤ 「用系统打开」本机成功一次；去掉 Word 关联 → 降级提示"本机未关联 Word，请下载后查看"，**不报 500**；⑥ 循环/图片模板预览里表格 5 行 → 实际 docx 也是 5 行（同一份 `plan` 驱动）。

**风险**：① 用户把"内容预览"当"排版预览" → 界面固定提示 + 旁边放「用系统打开」；② `plan` 与真实 docx 不一致（第二真源）→ 验收第 6 条断言两者行数一致；③ 预览临时文件堆积 → 启动清理 + 24 小时过期 + 显示占用；④ 大文书卡顿 → 表格行 > 500 折叠显示 + 提供导出。

**工作量**：3–4 人日。

### B4-13 全局搜索（一个框搜工作台 / 文件 / 制度 / 文书）

**要解决什么问题**

- 真需求原话是"找'上次那份验收资料在哪'"（`docs/09` §3.6）。现在入口分立：工作台列表有筛选、文件有 `artifact_search`（FTS）、制度有 `/api/kb/search`、文书只能进工作台翻。**用户得先想清楚"那东西属于哪一类"**，而这恰恰是他不知道的。
- 它也是让 B3-8 抽出来的语料真正被用起来的地方。

**怎么做**

**验收标准**：① 输入一个同时出现在四类的词（如"检查"）→ 四组都有结果，`total` 与各自模块列表数交叉验证一致；② 标题命中排在内容命中之前（造一个标题含词的 + 一份正文含词的，断言顺序）；③ `types=workbench,artifact` 只返回这两组，非法 `types` → 400 且提示合法值；④ 性能：隔离库造 2000 份 artifact → 输入到出结果 ≤ 500ms（人工计时，记进验收记录）；⑤ 中文两字/三字/单字都能出结果，`segCJK` 逐字空格化口径与现有 `buildMatch` 一致；⑥ 只搜未软删记录（复用 B1-1 的穷举自检）。

**风险**：① 混合排序看着"更智能"实际更难找 → **不做混合排序**（有意取舍）；② 单字查询拉全库 → 单字限 20 条/组 + 提示"输入更多字更准"，且不查 `kb_chunk`；③ 语义检索慢 → 全局搜索**默认只做 FTS**，语义只在点"深度搜索（含制度内容）"时跑且有 3 秒超时。

**工作量**：2–3 人日。

### B4-14 今日待办聚合（一屏）

**要解决什么问题**

- 用户场景原话是"我没空仔细操作或设置"。现在信息打散在四处：`/api/workbenches/due` 的欠办周期、每个工作台里的缺照片、缺材料、助手待确认动作。**要回答"我今天该干什么"得点开四个页面逐个看。**
- 更实际的麻烦：欠办的周期工作（工作台 #39 `schedule_due_date=2026-09-20` 且 `last_done_period` 为空 —— 一期都没完成过）、缺的影像证据、缺的材料、待确认动作，**四类事性质完全不同**（"该做了" vs "上次没拍够"），混在一起会让人不知从哪下手。

**怎么做**

- 新增 `GET /api/today?date=`，返回**四组 + 一个总数**，每组项带 `why`（"为什么它在这里"）：

| 组 | 数据来源 | 排序 | 每项动作 |
|---|---|---|---|
| 欠办的周期工作 | 复用 `computeSchedule()` 的 `nextDue`/`overdueDays` | 逾期天数降序 | 「开始本期」/「本期不做（记原因）」 |
| 缺的照片 | `checklist_item`（`kind='evidence'` 且 `done_count < min_count`）+ 阶段/工作台 | 缺得最多的在前 | 「去上传」/「这期不需要（标 na）」 |
| 缺的材料 | `checklist_item`（`kind='material'` 且 `status != 'done'` 且未标 na） | 到期日近的在前 | 「登记已备齐」/「暂缺（写备注）」 |
| 待确认的助手动作 | `agent_action`（`status='pending'`） | 创建时间升序 | 「确认」/「驳回」/危险动作显示影响数字 |

- **口径显式**：`why` 形如"欠办 11 天（应 2026-09-20）"、"照片 2/5 张"、"清单第 7 项未备齐"，一屏能看出**凭什么是待办**；**"缺"的判定写死在接口里**（`required=1 且 status != done 且未标 na`），界面不改口径。
- **不做自动做事**：这一屏**只列和跳转**，所有动作都要人点（`docs/09` §6 已否决"模型自主执行多步任务"）。
- 界面：首页就是这一屏（不再是统计数字墙），四组不同颜色标签，每项右侧一个主按钮，底部"以上都不急"折叠（避免一屏 40 条）。

**验收标准**：① 造场景（#39 欠办 11 天 + 某阶段缺 3 张照片 + 某材料未备齐 + 1 条待确认动作）→ 四组各出现对应项，`total` 等于四组之和；② 每项 `why` 与实际数据一致（人工核对 4 项，逐项断言）；③ 补齐 3 张照片后该项**从首页消失**（刷新后）；④「本期不做（记原因）」→ 该项不再出现且原因可在 B1-3 审计里查到；⑤ 四组都空时显示"今天没有待办"而非空白页；⑥ 20 个工作台 + 200 条清单的隔离库上 `/api/today` ≤ 300ms。

**风险**：① 待办越积越多没人看 → 每组默认最多 5 条 + "还有 N 条"、折叠、支持"本期不做"降噪；② 口径含混 → 每项带 `why`，判定写死在接口；③ 与 `/api/workbenches/due` 重复 → `today` **直接复用** `computeSchedule()`，不另写一套排期（`docs/09` P8：一行数据只有一个真源）。

**工作量**：2–3 人日。

### B4-15 跨设备方案评估（只出方案，不改代码）

**要解决什么问题**

- 真实约束：`workbench.config.json` 明说数据目录可以放 OneDrive/坚果云，愿望是"文件跟着 iCloud 走、换台机器也能用"。
- 系统的真相是：**文件在文件夹里，状态在数据库里**（`artifact.file_rel` + `workbench.external_root` + `position_instance.folder_rel`，绝对路径不落库、全靠现算 —— `docs/10` §2）。于是：① A 机器登记的文件，B 机器库里**没有那条记录** → 文件明明在，系统说"没有这件资料"；② 反过来 B 机器纳管的文件 A 机器不知道 → 两边状态分叉，接着互相覆盖；③ `-wal`/`-shm` 与 `.db` 在同步盘上**可能被同步成不一致的组合**（`docs/09` §4.8.2 第 4 条）。
- 所以"跨设备"不是打开开关，是**必须在用户拍板前讲清代价的决定**。本项**只交一份评估文档，不改任何代码**。

**怎么做**

产出 `docs/13-跨设备方案评估.md`（落在平台自己的 `docs/` 下，**不落在任何 iCloud 目录**），内容五块：

1. **问题陈述**：三条分叉场景各配一个具体例子（"在台式机上登记了 17 张照片，笔记本打开同一个 iCloud 文件夹，系统显示 0 张，用户以为照片丢了"）。
2. **候选路径对比表**：

   | 路径 | 怎么运作 | 好处 | 代价与风险 | 改代码量 |
   |---|---|---|---|---|
   | **① 保持现状（推荐）** | 库与程序留本机；`data/files` 可放同步盘 | 零风险、零改动；状态永远单一真源 | 换机器用不了（只能拷整个 `data/`） | 0 |
   | ② 库也放同步盘 | 整个 `data/` 放 iCloud/OneDrive | 换机器能接着用 | `-wal`/`-shm` 拆分风险；两台机器同时开 = 库冲突/损坏 | 中（需加"库在同步盘 + 多实例检测"告警） |
   | ③ 库本地 + 文件同步 | `WORKBENCH_RUNTIME_DIR` 指本地盘，`data/files` 走同步盘 | 避开 WAL 风险 | **状态分叉依旧**（B 机看到文件但没记录）；需"重新纳管扫描"入口 | 小（但解决不了核心问题） |
   | ④ 单向导出/导入包 | 一台 `pack`，另一台 `restore` | 明确、可验证、无静默冲突 | 不是实时同步，要人记得做；两台机器历史各自分叉，合并无自动办法 | 小（复用已有 `pack`） |
   | ⑤ 局域网共享库 | 一台当主机，其它机器连它的 HTTP（`docs/09` §6 提过） | 单一真源、实时 | 需登录 + HTTPS（`docs/09` 明确"开放到局域网前必须先做"）；不解决"人在外面" | 大 |
   | ⑥ 真云端多租户 | 上云 | 任意设备 | **明确不做**（`docs/09` §6） | — |

3. **推荐路径与条件**：**① + ④** 作为过渡；若用户明确要"两台机器日常切换"，才评估 ②（且必须先有三道防护）。

## §8 验证纪律（本项目既有约定，逐条照做）

> 以下不是建议，是既成约定：`docs/10` §11（用户 2026-10-01 明确要求）与 §12.6 已把边界写死。本文把它们**逐条落到每一项的验收动作上**。

### 8.1 三条铁律

1. **绝不写入、移动、删除用户 iCloud 工作目录里的任何文件。** 所有端到端验证一律用**本地临时目录**做"绑定根"（如 `D:\project\工作台\.tmp\bind-test\`），验证完删除；与制度/知识库相关的验证（B3-8）用**临时目录里的只读副本**，不用真实 `工作\3.制度`；**不做**"绑真实的 `2.安全` 然后上传一张照片"这种测试，也**不做**任何 iCloud 同步实验（含 B4-15）。
2. **只改平台自身**（代码、平台自己的数据库与 `data/`）；用户的 iCloud 目录在首次真实绑定前保持零改动。
3. **对真实目录的第一次只读操作（列子目录、统计文件数）前也要先说一声**；第一次真实写入必须**他明确同意后**才发生，并且要能一眼看出写入了什么。

### 8.2 每一批（不止每一项）必须跑完的最小验证

| 步骤 | 命令 / 动作 | 通过判据 |
|---|---|---|
| 类型检查 | `npm run typecheck` | 零错误（server 与 web 都过） |
| 单元测试 | `npm run test:unit` | 全绿；本批新增的确定性模块必须有断言，不许恒真式断言 |
| 接口回归 | `npm run test:regression` | 全绿；本批每个新接口至少 1 项契约断言（状态码 + 关键字段） |
| 端到端 | `npm run test:e2e`（涉及助手/影像/知识库时加 `test:agent`/`test:vision`/`test:kb`） | 全绿，跑在 `scripts/test-isolated.mjs` 起的**独立库 + 独立目录 + 独立端口 + 随机 token** 上 |
| 手工验收 | 各项"验收标准"逐条走一遍 | 每条都有可观察结果，记进验收记录 |

**隔离验证的机器纪律**：① 用 `scripts/test-isolated.mjs` 既有机制，**不在真实 `data/` 上跑破坏性用例**；② 迁移类改动（B1-1、B1-3、B1-4、B2-7、B3-10）**必须先在库副本上跑一遍迁移**，比对迁移前后行数与关键查询结果，再上真库；③ 涉及外部目录的用例**前后各做一次快照对比**（递归文件清单 + mtime + 大小），不一致即失败（`scripts/check-folder-names.mjs` 已有这个做法，照它抄）。

### 8.3 如实报告与"做完"的定义

- **未验证的部分要明说**，不用"应该没问题"顶替（`docs/09` §7.2 列了 14 条"没核实"的就是范本）。每项交付回答三句话：① 我实测了什么（命令 + 结果）；② 我**没有**实测什么（原因）；③ 剩余风险里最可能先出事的是哪一条。自动化率数字（B2-5）与依赖真实模型的结论**必须标口径与样本量**；假模型跑出来的"通过"要写明是假模型。
- 一项只有同时满足四条才算做完：① **可观测**（有接口或界面能看到状态，不藏在日志里）；② **可复现**（验收步骤写下来别人照着能跑出同样结论）；③ **不回归**（以改动前行为做基线，逐条断言"不该变的没变"，B2-6 的"老模板字节级一致"是最好的样板）；④ **失败会响**（自己的失败路径有人看得见：横幅/红灯/明确错误码，不静默）。

## §9 明确不做（与 `docs/09` §6 同口径，本文再确认）

| 不做 | 理由（一句话） | 什么条件下重新考虑 |
|---|---|---|
| 云多租户 / 上云 | 数据是内部资料；系统的全部价值来自"文件就在你机器的文件夹里" | 出现"多人同时用同一个库"，**先做局域网共享 + 库锁**，也不上云 |
| 移动端 App / 小程序 | 现场拍照用手机相机最好；要解决的是"拍什么"和"拍完怎么进系统"，用要点卡片 + 上传 + 初检解决 | 用户开始**每天在外勤**且要当场出文书 |
| 向量数据库（Milvus/Qdrant/faiss） | `kb_chunk` 还没上万，一万块内 SQLite BLOB + 内存打分是几十毫秒；多一个进程就多一个备份对象 | **片段数稳定 > 2 万且检索延迟 > 500ms**，届时优先换 HNSW（单文件纯 JS），不引独立服务 |
| 复杂权限体系（角色/审批流/组织架构） | 单机单用户，防自己靠的是**二次确认 + 回收站 + 快照**，不是角色 | 真出现第二个使用者，做**最简双角色**（可编辑/只读） |
| docx 正文内容级 diff | 差异大量来自 XML 结构噪声，会淹没真改动；"哪个字段改了"在 `generation_log.variables` 里本来就有 | 用户真要"逐字对比两稿"，做纯文本导出后 diff |
| 自动改写模板 / 自动改已定稿文书 | 模板与定稿文书是用户资产，改错一次连锁影响所有历史绑定 | **永不自动**；只生成候选，由人确认后替换 |
| 引入原生图像依赖（`sharp`/`jimp`）压缩图片 | 与"零原生编译"底线冲突 | 用户明确接受安装体积与跨机编译风险 |
