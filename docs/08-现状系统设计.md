## 1. 一句话定位与使用场景

**一套跑在单台 Windows 电脑上的本地文书工作台**：一个人用，浏览器访问 `http://127.0.0.1:8787`，把"按月重复的行政检查"和"分阶段推进的工程项目"这两类工作，落成可勾选的清单、可留存的照片、可检索的文书。

| 维度 | 现状 |
|---|---|
| 用户数 | **1**（没有登录、没有账号、没有权限模型） |
| 网络暴露面 | 仅 `127.0.0.1:8787`（`workbench.config.json` 的 `port/host`，默认值在 `core/config.ts:42-43`） |
| 服务形态 | 单个 Node 进程，同时提供 API、静态 SPA、`/files/*` 受限文件流（`index.ts:57-121`） |
| 数据形态 | 一个 SQLite 文件 + 一个普通文件夹树；程序坏了数据不丢 |
| 面向的业务 | 中国行政/工程单位的公文与过程资料：行政管理（按月/季/年重复）、工程项目（分阶段出文书、留材料、拍照片） |
| 当前真实工作量 | 工作台 **2** 个、在用模板 **48** 份、已归集文件 **0** 个 |

两处**与业务形态直接相关、但容易误解**的设计：

- 工作类型分两种模式（`work_type.mode`，见 `005_schedule.sql:13`）：
  - `document` **文书驱动**（行政管理）：**没有阶段序列**，按频率重复，编号 `YYYY-A-NNN`；
  - `process` **流程驱动**（项目类）：按阶段实例化 `position_instance`，带材料清单和影像清单，编号 `YYYY-P-NNN`。
- 库里 `work_type` 只有 4 行：`admin`(1, document)、`eng`(3, process, 19 阶段)、`info`(4, process, 12 阶段)、`svc`(5, process, 4 阶段)。预置的 `project`（"项目实施"，P01–P06）已被用户删除，并记入 `app_setting['work_types.deleted'] = ["project"]` 的黑名单（`core/config.ts:131-152`），否则每次启动都会被种回来。
- **行政管理的 5 个阶段种子（A01–A05）在库里存在，但永远不会被实例化** —— `createWorkbench` 对 `mode='document'` 直接跳过 `instantiatePositions`（`domain/service.ts:378`）。这是 `docs/06` 的 ❓4，至今未处理。

### 3.3 三组"同一件事多个字段"的历史包袱（必须知道）

1. **归档状态有三列**：`workbench.archived_at`（列表过滤依据）、`workbench.status='archived'`（显示用）、`workbench.archive_status`（归档前的状态，用于取消归档还原）。
   - 不变量在 `domain/service.ts:565-610`：归档时只在 status ∈ {active,paused,done} 时记 `archive_status`，**绝不把 `'archived'` 存成"归档前状态"**；取消归档优先用 `archive_status`，按 `actual_end_date` 兜底，并清空 `archive_status`。
   - `core/startup-repair.ts:18-36` 每次启动再统一修一遍存量脏行（`archived_at IS NULL AND status='archived'`）。
   - 这是历史包袱：三列表达一件事，靠不变量 + 自愈维持一致，而不是靠表结构。
2. **档案值与原生列重叠 3 个键**：`contract_no` / `contract_amount` / `start_date` 同时存在于 `workbench` 原生列和 `profile` JSON 桶。
   - 现状的单一真源是**原生列**：`readArchiveValues` 会把这三列的值覆盖进档案 map（`domain/archive.ts:483-484`），`writeArchiveValues` 把这三个键的写入重定向到原生列（`archive.ts:511-515`），`buildNativeContext` 也优先取原生列（`service.ts:1173`）。
3. **"清单项是否完成"有多份判据**：详情页、进度重算（`core/checklist.ts:11`）、缺口分析（`domain/generate.ts:485-486`）各写一遍。`docs/06` B8 未修。

1. **命名规范已经改了，老目录没迁移。** `workbenchFolderName` 现在产出 `{hash16}-{code}-{name}`，但库里现存两个工作台的 `folder_path` 是 `工作台/2026-P-001-项目精细化管理系统`（无哈希前缀），磁盘上也是这么建的。也就是说：**这份哈希前缀只对新工作台生效，两个真实工作台都是旧命名**。`docs/01` 第 3 节写的 `{编号}-{名称}` 只描述了旧行为。
2. **`_索引` 目录是空承诺。** `docs/01` 和 `docs/02` 都说它装"全文索引导出（可读的旁路文本，方便 grep）"，但全仓只有 `core/config.ts` 提到 `DIRS.index`（创建目录），**没有任何写入代码**。全文索引实际只存在 SQLite 的 `artifact_search` + `artifact_fts` 里。

### 4.3 模板文件与 `.vars.json`

- 模板文件放 `_模板库/{相对路径}`，变量说明是同目录下的 `*.vars.json`（`template.vars_rel`）。
- 实测命名不是"同名 `.vars.json`"：`.vars.json` 用的是**编码名**（`eng-01.vars.json`、`hetong-01.vars.json`、`ql-01.vars.json`、`xingzheng-01.vars.json`…），与 `template.name`（中文名）不对应，靠 `vars_rel` 列挂接。`docs/01 §5.3` 的"每个模板旁边有一个同名 `.vars.json`"与现状不符。
- 实测 **48 个在用模板全部有 `vars_rel`，且 48 个文件全部在位**（0 缺失）。
- 实测 **48 个在用模板清一色是 `.docx`**：`select file_format,count(*) ... group by file_format` 只有一行 `docx=48`。也就是说：**xlsx 分支、文本分支在当前真实数据里没有任何在用样本**。

### 5.3 回退规则（`ai/providers.ts:157-168`）

```
FALLBACK_TO_WRITING = ['extract', 'reasoning', 'agent']
```
- 这三个用途**档案没配或没指定服务商时**，会借用 `writing` 的服务商与模型，档案名显示为 `xxx（回退）`。
- `vision` 与 `embedding` **不回退**：它们有硬性能力要求（看图必须多模态、向量化必须走 `/embeddings`），宁可明确报"还没指定服务商"，也不拿一个干不了这活的模型去撞墙（代码注释里记了实测：拿 DeepSeek 向量化是 404，拿它看图是 content 类型报错）。
- 删除服务商时会把指向它的档案**连模型名一起清掉**（`providers.ts:123-131`），避免解析回退后拿一个对方没有的模型名去撞。

### 5.4 "配了"不等于"能用"：`aiReadiness(purpose)`

`ai/gateway.ts:322-349` 复用真正的解析逻辑，返回 `{ready, reason, code, provider, model}`。检查顺序：用途档案存在 → 指定了服务商 → 服务商存在 → 服务商启用 → Key 存在（本机地址免 Key）→ 模型名非空。
`embedding` 多一层：记住**最近一次真实向量化的结果**（按 provider/base_url/model/updated_at 签名），遇到 `NOT_FOUND/AUTH/DISABLED/NO_KEY/NO_MODEL` 这类能力性错误就明确说"这个组合干不了向量化"。

「试调用」（`POST /api/ai/profiles/:purpose/test`）分三种量身定做：

| 用途 | 探针 |
|---|---|
| `embedding` | 真发一条 `/embeddings`，回报维度 |
| `agent` | 发一个**必须调工具**的请求，直接看模型会不会 `tool_calls`；不会则给警告"助手可能只会聊天" |
| 其余 | 1024 max_tokens 的普通对话探针（不是 200 —— 推理模型的"思考"也吃 `max_tokens`，200 会被吃光，导致接口通了却报"被截断"） |

### 5.5 什么时候**不**调模型（确定性边界）

这一节是这套系统的核心设计取向：**能用死规则的地方一律不用模型**。

| 环节 | 是否调模型 | 依据 |
|---|---|---|
| 模板变量取值（`resolveVariable`） | **不调** | `domain/archive.ts:559-638`，纯函数，同一输入必得同一结果 |
| 系统变量（`_今天`/`_本月`/`_年份`/`_工作台编号`/`_工作台名称`/`_当前阶段`…） | **不调** | `service.ts:1149-1189` 的 `buildNativeContext` 直接算 |
| 变量别名映射（`archive_alias` 查表） | **不调** | SQL 查询，先查工作类型专有、再查全局 |
| 文档切块、向量编解码、余弦相似度 | **不调** | `core/kb.ts`（只在前两步完成之后才调 embedding 出向量） |
| 模板正文扫描、占位符替换、漏填检测 | **不调** | `core/placeholders.ts` + `core/template.ts` |
| 排期计算（下期到期日、逾期天数） | **不调** | `domain/schedule.ts`，六个导出全是纯函数 |
| 采集/核销影像张数 | **不调** | `core/checklist.ts` 的 `evidenceCount` 实算磁盘文件数 |
| 权限/会话/来源校验 | **不调** | `core/request-guard.ts` |
| 是否需要检索知识库 | **不调** | `knowledge.shouldSearchKnowledge`：特别要求 ≥8 字、或参考资料 ≥30 字、或模板里有 `longtext` 项，才去检索，省一次 embedding 调用 |
| 模板检索 | **不调向量** | 模板正文几乎全是固定套话，向量化既贵又没用；改用"名称/说明/可填项"关键词匹配（`knowledge.ts:134-199`），命中不了就给"本类工作可用的表"候选（`optional: true`） |
| 出文书填变量 | **调 `writing`** | 但 `skipAi:true` 走纯确定性路径（只用已知值 + 档案 + 系统变量），界面上是"先渲染一份、手工填" |
| 档案字段/别名梳理 | **调 `extract`**，但只产出 `archive_proposal` | 人点采纳才落库 |
| 验收前缺项分析 | **调 `reasoning`** | |
| 照片初检 | **调 `vision`** | 结论只是意见 |
| 知识库语义检索/问答 | **调 `embedding` / `writing`** | |

### 6.4 归档与检索

| 对象 | 归档 | 取消归档 | 彻底删除 |
|---|---|---|---|
| 工作台 | `POST /api/workbenches/:id/archive`（写 `archived_at` + `status='archived'`，记 `archive_status`） | 同接口 `?undo=1` | `DELETE`（库记录 + 磁盘文件夹一起删，见 §9-S6） |
| 模板 | `DELETE /api/templates/:id` → 把 `.docx` 与 `.vars.json` **复制到 `_归档模板/{id}/` 并更新 `file_rel/vars_rel`**，再置 `archived_at` | `POST /:id/unarchive`（**文件缺失时返回 410**） | `DELETE /:id/permanent`（已被 `generation_log` 用过则拒绝，提示"先归档"） |

检索有三条路：

1. **文件全文检索**：`GET /api/search` → FTS5 + bm25(10.0, 3.0)，中文按"逐字空格化 + 短语匹配"（`core/search.ts`、`002_fts.sql`）。
2. **知识库混合检索**：`GET /api/kb/search?mode=` → 全文与语义按 **0.6 语义 / 0.4 全文** 加权融合（`kb.ts:509-586`）。全文分按**名次指数衰减** `exp(-i/2.2)` 归一（不能用"除以最大值归一"，否则全文第一名恒等于 1、语义分再高也翻不了身）。
3. **知识库提问**：`POST /api/kb/ask` → 取 topK 片段（默认 6，阈值 0.15）拼上下文，要求模型"每条结论标注来源编号 [资料N]"，返回 `answer` + `citations[]`（文档名、标题、第几段、分数）。

### 6.5 知识库两个模块（分开摆、一起查）

| 模块 | 里面是什么 | 检索方式 | 代码 |
|---|---|---|---|
| **模板库** | Word/Excel 模板（要填的表） | 名称 / 说明 / 可填项关键词匹配；命中分数 1 / 0.95 / 0.7 / 0.6；命中不了给"本类工作可用"候选（`optional: true`） | `core/knowledge.ts:134-199` |
| **公司制度** | 制度、规范、标准、上级通知（办事照的口径） | 语义检索（向量，`minScore=0.15`） | `knowledge.ts:228-244` → `core/kb.ts` |

- `searchKnowledge()` **一次检索两边都查**（`Promise.all`），每条结果标 `sourceLabel`（模板库 / 公司制度），拼成提示词里的「可依据的制度与模板」段落；制度定口径，模板定格式。界面上「知识库 → ⚖ 查依据」看到的就是模型看到的那份依据。
- 向量按**"服务商 + 地址 + 模型 + 维度"签名**隔离：`embeddingSignature()`（`gateway.ts:305`）写进 `kb_chunk.embedding_model`；检索时只比较签名一致且维度相同的向量，全都不匹配就明确回"已有向量的服务商、模型或维度与当前配置不一致，请重新向量化"（`kb.ts:462-463`）。
- 批量自适应：默认 16 块/批，被接口拒收就劈半重试（16→8→4→1），成功过的尺寸记住复用（`kb.ts:275-359`）。实测 `ai_call_log` 里有 14 条 `batch size is invalid, should not be larger than 10` 的历史记录，正对应这条机制的由来。
- 文件进库路径：`POST /api/kb/upload`（保留上传目录结构、挡 `..`、最多 5 层、sha256 去重）→ `POST /api/kb/import-all`（顺手把手工拷进 `_规范库` 的文件补登记成 artifact）。
- **现状提醒**：`kb_document` 0、`kb_chunk` 0 —— 制度这一侧**一篇文档都没有**。语义检索/提问在真实库里没有任何可检索内容，模板一侧有 48 份模板可查。

> **关于"自动带出规则（算金额、算日期）"**：代码里**没有**独立的规则库/公式引擎/计算器。实际机制是：制度文本被检索出来、作为提示词里的"依据"交给模型，由模型按制度口径写内容（包括按制度给的算法自行推算金额或日期），**系统不复核、不校验**。请按这个理解使用，不要当成确定性计算。

| 机制 | 实现 |
|---|---|
| token 生成 | 每次启动 `randomBytes(32).toString('hex')`；可用环境变量 `WORKBENCH_SESSION_TOKEN` 覆盖（自检就是这么做的） |
| 下发 | `GET /api/session`，响应头 `Cache-Control: no-store` |
| 强制范围 | **所有非 GET/HEAD/OPTIONS 的 `/api/*` 请求**必须带 `x-workbench-token`；用 `timingSafeEqual` 定长比较，失败返回 403 `{code:'BAD_SESSION'}` |
| 前端恢复 | `web/src/api.ts:35-43`：遇到 403 且 code 为 `BAD_SESSION` → 丢弃缓存 token → 重新取一次 `/api/session` → 原样重试**一次** |
| 不覆盖 | `GET` 类接口无需 token（读接口在"仅本机来源"的前提下开放） |

### 7.2 只允许本机来源

`onRequest` 钩子（`request-guard.ts:8`）同时校验三件事，任一不满足即 403 `UNTRUSTED_ORIGIN`：

1. `Host` 必须是 `localhost` / `127.0.0.1` / `[::1]`，且端口是本机端口（或 dev 的 `5273`）；
2. 带了 `Origin` 时，`Origin` 也必须通过同一判定；
3. `Sec-Fetch-Site` 不能是 `cross-site`。

另有 `nosniff` 响应头；`/files/*` 只提供**数据库里登记过的** artifact 或模板（未登记 → 404，`index.ts:114-121`），并附 `Content-Security-Policy: sandbox; default-src 'none'`。

### 7.3 单实例锁（`core/server-lock.ts`）

`data/runtime/server.lock` 写自身 PID（`flag:'wx'` 原子创建）；启动时若锁存在，读 PID 并 `process.kill(pid, 0)` 探活，存活则拒绝启动（"同一数据库已有服务运行"），已死则删除锁继续；进程退出时按 PID 比对删除。
**注意**：锁只认 `DB_FILE` 所在目录，所以"同一数据库"才是互斥单位；换 `WORKBENCH_DB` 就能并行起第二个进程（自检正是这样做的）。

### S1【高·数据缺陷】48 个在用 docx 里 6 个源文件损坏，接口不报错

| 模板 id | 文件名 | XML 错误（实测） |

| 84 | `01-成立项目部的通知_v2.docx` | 同上（同一处，位置 2092） |
| 96 | `01-成立项目部的通知_v3.docx` | 同上（同一处，位置 2092） |

| 77 | `13-工序施工质量报验单.docx` | `</w:body>` 对上了 `<w:tc>`（位置 156493） |

- 我用的判定方式：解压 `word/document.xml`，做标签栈配对检查（不是完整的 XML 解析器，但足以发现这类不闭合/错配）。
- **影响**：`POST /api/generate/preview` 对损坏模板返回 **200**，并把损坏字节**原样吐出**；用户会拿到"生成成功但 Word 打不开"的文件，**系统没有任何预警**。修法（渲染后做一次 XML 合法性检查并拒绝或告警）目前不存在。

### S2【高·能力未验证】写作模型的"停用"说法已不成立，但真实产出质量从未验证

- 库里 `deepseek.enabled = 1` 且有 Key（35 字符）；6 个用途中 4 个（writing / extract / reasoning / agent）都指向它。
- **实测接口自述**（2026-09-30 11:40，`GET /api/ai/status`，只读）：`{"configured":true,"provider":"DeepSeek","model":"deepseek-flash","embedding":{"ready":true,...},"hint":"模型已就绪"}`；`GET /api/ai/providers` 里 DeepSeek 是 `enabled=1, has_key=true, key_hint=已配置`。
- 而 `ai_call_log` 里有 24 条 `DISABLED`（"服务商「DeepSeek」已被停用"），集中在 2026-09-18 ~ 09-21，最后一条是 `2026-09-21T02:43:36Z`；09-30 的验收报告也把写作模型记为停用，并据此用 `skipAi:true` 绕过模型完成验收。
- **结论**：`enabled` 这一位现在指向"启用"，所以"AI 填变量当前不可用"这个判断**不成立**（或至少已经过期）。真正没被验证的是两件事：
  1. **那个 Key 现在是否有效** —— 本轮不允许调用外部接口，无法验证；
  2. **真实模型的产出质量** —— 从来没有验证过。`docs/07` 明确写"未验证真实外部模型的效果、计费和返回格式"；`ai_call_log` 里 206 条真实调用中 `writing` 只有 44 条且 18 条成功，其余是配置错误与截断，**没有一次是完整走完"出文书 → 落盘"的真实业务**（`generation_log` 0 行可证）。

### S3【高·功能缺口】docx 不支持 `{#循环}` 与 `{@图片}`

- 扫描器**认**这两种写法（`PLACEHOLDER_RE` 支持 `[@#/]` 前缀，`scanPlaceholders` 会把它们列进变量清单）；
- 渲染器**不处理**：`renderText` 遇到 `#` / `/` / `@` 前缀直接原样返回（`core/placeholders.ts:64`），docx 替换里 `rendered===m[0]` 就跳过（`core/template.ts:257`）。
- **影响**：模板里写了这两种标记，生成的文件里会**留下一串 `{#…}` / `{@…}` 原文**，而漏填检测也把它们排除在外（`missingVariables` 里 `if (hit.prefix) continue;`），所以**连"有东西没填"的提示都不会有**。设备清单类模板只能手工补行，照片只能靠附件说明。

### S4【中·历史包袱】归档状态由三列共同表达

`archived_at`（过滤依据）/ `status='archived'`（显示）/ `archive_status`（归档前状态）。已加不变量（`service.ts:565-610`）与启动自愈（`startup-repair.ts:18-36`），行为正确，但**表结构层面同一件事有三个字段**，任何直接写 `status` 的路径都可能再制造脏行。实测当前 2 个工作台的 `archive_status` 均为空、`archived_at` 均为空 —— 没有现存脏数据。

### S5【中·效率】变量映射覆盖率低

- 48 份在用模板共 **1089 处**变量引用（各模板去重后之和）；**632 个不同变量名**。
- 别名表 **132 条**，能命中 **386 处 = 35.4%**；按"不同变量名"算，只有 **93 / 632 = 14.7%** 有别名。
- 未映射的高频变量集中在合同类与人员类：`甲方法定代表人×6`、`乙方法定代表人×5`、`报审附件名称×4`、`分部工程名称×4`、`甲方委托代理人×4`、`合同金额大写×4`、`乙方人员一/二/三/四/五姓名/身份证号各×3`、`设备1..5名称各×3` 等。
- 后果：其余变量只能手工填或让模型写；模型写就有编造风险（提示词里已用「【待补：…】」约束，但那是模型自律，不是系统保证）。

### S6【中·破坏性操作】工作台删除没有前置防护、没有快照，且 AI 助手持有该入口

- `deleteWorkbench`（`domain/service.ts:642-673`）：库记录 + 阶段 + 勾选 + 文件记录 + 索引行 + **磁盘整个文件夹**一起删，**不可恢复**。
- 已有的守卫只有三处：拒绝删数据根目录、拒绝删被其它工作台共用的目录、拒绝删"附件不在本工作台目录内"的工作台。
- **没有**的：不要求"必须先归档"、不留快照、不进回收站、不可撤销。
- 界面上有防护：删除对话框列出"将要删除的内容"清单（阶段数、文件数、目录路径），且**只要已有文件或阶段，就必须手打「删除」二字才能点确认**（`pages/Workbench.tsx:1408,1440-1441`）。
- 但 **AI 助手持有 `delete_workbench` 工具**（`domain/agent.ts:724-749`）。它的保护是：动作标 `risk='destructive'`、"全部执行"默认跳过破坏性动作（`routes-agent.ts:94`）、必须逐条点确认。实测 `agent_action` 里 8 条 `delete_workbench` 全部是 `discarded`（自检产物）——**这条闸门只被自检验证过**。

### S9【中·安全边界】单机单用户，无登录/无多用户/无回收站，密钥在本地库中明文

## 10. 能力边界：现在做不到什么

明确列出来，避免把"设计里想过"当成"现在能用"。

**格式与文档**
1. **做不到**把照片嵌进 Word（`{@图片}` 原样保留）；**做不到**表格行自动增减（`{#循环}` 原样保留）。两者都会在成品里留下原文。
2. **做不到**渲染 `.doc` / `.xls` 旧二进制格式，也**不校验**模板 XML 是否合法（6 个损坏 docx 会一路 200 到底）。
3. **做不到**保证"变量之外的排版完全不变"：长文本替换后会改变分页（`docs/01` 与 README 都写了这条限制）。
4. **做不到**自动识别扫描版 PDF 的内部文字（WASM 引擎读不了 PDF），必须先转成图片。
5. **做不到**按"意思相近"找**文件**：文件库（`/api/search`）只有 FTS5 关键词检索；语义检索只存在于知识库的**制度**一侧，而且必须先导入 `_规范库` 并完成向量化（当前 0 篇）。

**AI 相关**
6. **做不到**在没有配置对应用途模型的情况下使用该用途：`vision` 与 `embedding` **不回退**到写作模型（故意的）；`extract/reasoning/agent` 会回退到 `writing`，所以"配了写作模型就能用助手"看起来是通的。
7. **做不到**让模型直接落库：所有写操作不是"待确认动作"（AI 助手）就是"待确认提议"（档案梳理）；**代价是每一步都要人点**。
8. **做不到**核销影像清单这件事交给模型自动完成：视觉结论只是 `ok/issue/unclear` 的意见，核销永远是人（或经人确认的动作）。
9. **做不到**在没有向量化模型时使用语义检索/提问；换 embedding 模型后**必须手工重新向量化**，否则明确报"配置不一致"。
10. **做不到**校验模型算出来的金额与日期：制度只作为提示词依据，系统里没有公式引擎，**算错了不会被发现**。
11. **做不到**阻止模型在工作台重名/目标模糊时"猜"——只能阻止它**执行**：`findWorkbench` 命中多条时直接抛"工作名称不唯一，请指定编号或 ID"（`agent.ts:107`），动作提交阶段还会校验目标是否变化。

**数据与运维**
12. **做不到**多人协作：没有登录、没有账号、没有并发编辑保护（只有 agent 动作的乐观锁）。
13. **做不到**恢复删除：工作台删除、文件删除（带 `withFile`）、模板彻底删除都不可撤销；唯一的"软"操作是归档。
14. **做不到**在运行中安全复制数据库文件当备份（WAL 未合并），**必须**停服务后 `npm run pack -- --with-runtime-state`（它会用 `backup()` 出一致性快照并自检）。
15. **做不到**并行跑两个服务指向同一个库（单实例锁会拒绝）；也**做不到**阻止两个服务指向不同库但共享同一个安装根目录（锁只认 `DB_FILE` 目录）。
16. **做不到**对 133 个接口给出有意义的测试覆盖：约 45% 有测试，档案模块 20 个接口零覆盖，AI 助手的 3 条"改配置"工具路径没有被验证过确认门。
17. **做不到**自动修复那 6 个损坏的 docx，也**做不到**从系统内找回 12 个已归档模板的缺失文件（归档记录保留，文件需从旧备份恢复）。
18. **做不到**在界面上看到"文件与检索"这个名字的菜单（它叫**文件库**），也**做不到**看到独立的"模板库"菜单项（它在**知识库**里）。
