# 工作台 · 系统设计说明

> 本文是这套系统的"宪法"。所有代码、目录、命名都以此为准。
> 需要改规则时，先改本文，再改代码。

---

## 1. 系统定位

一套**跑在本机**的工作台，解决三件事：

| 编号 | 目标 | 对应功能 |
|---|---|---|
| A | 把**重复性文书工作**自动化 | 模板引擎 + 大模型生成 → 直接产出 Word/Excel 成品 |
| B | 把**项目执行流程**规范化 | 流程阶段 + 材料清单 + 影像/证据清单，逐项可勾选、可追溯 |
| C | 把**资料沉淀成资产** | 文件库 + 全文检索（+后期语义检索） |

设计原则：

1. **数据在你手里** — 所有文件是磁盘上普通文件夹里的普通 Office 文件，用资源管理器就能看，程序坏了也不丢数据。
2. **AI 可选** — 不配 API Key 也能用（手工填写 + 清单管理）；配了 Key 才是"大模型帮你写"。
3. **先固化，再智能** — 流程、模板、命名先标准化，AI 才有稳定的发挥空间。
4. **可随时改** — 工作类型、流程阶段、模板变量、材料清单全部在界面上可增删改，不写死在代码里。

## 2. 技术架构

```
┌─────────────────────────────────────────────────────────┐
│  浏览器  http://127.0.0.1:8787                          │
│  React + Vite 单页应用（构建产物由后端直接托管）           │
└───────────────────────┬─────────────────────────────────┘
                        │ JSON API / 文件上传下载
┌───────────────────────▼─────────────────────────────────┐
│  后端  Fastify + TypeScript                             │
│  ├─ 配置中心   provider / 模型档案 / 路径 / 应用参数      │
│  ├─ 模板引擎   docx 占位符扫描 + 填充，xlsx 模板          │
│  ├─ AI 网关    多 provider 统一转发、流式、用量与错误日志 │
│  ├─ 领域逻辑   工作台 / 阶段 / 材料清单 / 影像清单        │
│  └─ 文件库     归档、命名单一来源、扫描入库、OCR          │
└───────────────────────┬─────────────────────────────────┘
                        │
        ┌───────────────┴────────────────┐
        ▼                                ▼
┌──────────────────┐          ┌──────────────────────────┐
│ SQLite (WAL)     │          │ 数据目录（普通文件夹）    │
│ node:sqlite 内置 │          │ 模板库 / 文件库 / 规范库  │
│ + FTS5 全文索引  │          │ 可直接用资源管理器操作   │
└──────────────────┘          └──────────────────────────┘
```

关键选型理由：

| 选择 | 理由 |
|---|---|
| **Node 24 内置 `node:sqlite`** | 零原生编译、零安装风险；自带 FTS5 全文索引；单文件数据库，复制即备份 |
| **Fastify + React** | 单一进程、单一端口，一条命令启动；前端构建产物由后端托管，不需要额外服务 |
| **docx 自己渲染** | 用 PizZip 直接改 `word/document.xml`，把段落内的 `<w:t>` 拼起来再按 `{变量名}` 替换。不引第三方渲染器，是因为模板里的表格、页眉页脚、编号样式必须 尽量保留（变量之外的样式保持，长文本需检查分页） —— 这是这类公文模板的底线要求 |
| **数据与程序分离** | 程序升级不影响数据；数据目录可以放到 OneDrive/坚果云做同步备份 |

端口固定 **8787**，仅监听 `127.0.0.1`（只有本机能访问，不暴露到局域网）。

## 4. 数据模型

```
work_type           工作类型（行政管理 / 项目实施 …）
  └─ position_template   阶段模板（该类型下每一步该做什么）
       ├─ material_check     材料清单（这一步要准备/留存什么材料）
       └─ evidence_rule      影像清单（这一步要拍什么照片、拍几张、拍什么细节）
  └─ template            模板文件（Word/Excel），绑定到类型或阶段
  └─ workbench           工作台实例（一个项目 / 一项行政事务）
       ├─ position_instance  阶段实例（进度、状态、起止时间、负责人、备注）
       ├─ checklist_item     勾选项（材料是否齐、照片是否拍），记录完成时间与经办人
       ├─ artifact           文件（生成的成品 / 上传的证据 / 扫描件）
       └─ generation_log     生成记录（用了哪个模板、哪个模型、花了多少 token）

ai_provider         模型服务商（base_url、key、是否启用）
ai_profile          模型档案（用途 → 用哪个 provider 的哪个模型）
app_setting         键值配置（数据目录、命名规则、默认模型档案等）
```

所有表都带 `created_at` / `updated_at`；用 `sort_order` 控制显示顺序；软删除用 `archived_at`。

详细 DDL 见 `packages/server/src/db/migrations/`。

## 5. 模板规范（最重要的一节）

### 5.1 支持的文件类型

| 类型 | 处理方式 | 说明 |
|---|---|---|
| `.docx` | 占位符替换 | 排版 尽量保留（变量之外的样式保持，长文本需检查分页），推荐主用 |
| `.xlsx` | 单元格占位符替换 | 表头、公式、格式保留 |
| `.doc` `.xls` | 需先另存为 `.docx` `.xlsx` | 老格式二进制无法处理 |
| `.pdf` `.jpg` 扫描件 | 不填充，作为参考/证据归档 | 后期接 OCR 提取文字 |

### 5.2 占位符语法

| 写法 | 含义 | 状态 |
|---|---|---|
| `{变量名}` | 普通文本替换 | ✅ 已实现 |
| `{变量\|默认值}` | 变量为空时用默认值 | ✅ 已实现 |
| `{#列表}...{/列表}` | 循环（用于表格行 | ⬜ 只扫描不渲染，见 §10 |
| `{@图片}` | 嵌入图片 | ⬜ 只扫描不渲染，见 §10 |

**变量命名的三条铁律**：

1. **中文变量名**，和模板里的人话一致：`{项目名称}`、`{合同编号}`、`{到货日期}`。
2. **同名同义**：同一个概念在所有模板里用同一个变量名，不准出现 `{项目名}` 和 `{工程名称}` 混用。
3. **系统变量统一前缀**：`_今天`、`_本月`、`_工作台编号` 由系统自动填，不用手工输入。

### 5.3 变量清单从哪里来

每个模板旁边有一个同名 `.vars.json`，描述它需要哪些变量：

```json
{
  "template": "月度安全检查表.docx",
  "workType": "行政管理",
  "variables": [
    { "name": "检查月份", "label": "检查月份", "type": "text", "required": true, "example": "2026年3月" },
    { "name": "检查区域", "label": "检查区域", "type": "text", "required": true },
    { "name": "检查人",   "label": "检查人",   "type": "text", "required": true },
    { "name": "隐患清单", "label": "隐患清单", "type": "table", "required": false }
  ]
}
```

**两种建立方式**（界面都提供）：

- **自动扫描**：上传 docx 后点"扫描变量"，系统从文件里把所有 `{xxx}` 抠出来。
- **手工补充**：说明每个变量的中文标签、是否必填、填什么。

### 5.4 大模型生成流程

```
1. 选模板            → 系统读取 .vars.json，生成填写表单
2. 填已知信息        → 手工填 / 从工作台档案带出 / 上传参考资料让它自己读
3. 点"AI 生成"       → 组装提示词（模板要求 + 已知变量 + 参考资料 + 写作规范）
4. 预览并逐项修改    → 变量值以 JSON 返回，可单条重生成
5. 保存成文件        → 填充模板 → 落到 工作台/_生成文书/ → 登记 artifact → 可下载打开
```

写作规范（提示词里固定注入）：公文语体、不编造数字与事实、缺信息留 `【待补：XXX】`、时间地点人物必须来自资料。

## 6. 影像与证据清单规范

"开箱、到货该拍什么照片"这类要求，做成**可执行的清单**，不是一个模糊的提醒。

每条 `evidence_rule` 定义：

| 字段 | 说明 | 例子 |
|---|---|---|
| 阶段 | 属于哪一步 | 02_到货与开箱 |
| 标题 | 拍什么 | 设备开箱前外包装 |
| 必拍张数 | 最少几张 | 2 |
| 拍摄要点 | 必须看清什么 | 完整包装箱、运单号、外观无破损 |
| 拍摄角度 | 建议角度 | 正面全景 + 运单特写 |
| 是否必需 | 缺了会不会卡验收 | 是 |
| 示例图 | 参考样张 | 可上传一张 |

界面上每个规则是一张卡片：**要求 + 上传/拍照按钮 + 已拍张数 + 缩略图**，没拍够标红。所有影像自动按命名规范改名归档，并记录拍摄时间与 EXIF 信息（拍摄时间、设备、GPS）作为佐证。

## 7. AI 接入设计

### 7.1 服务商（`ai_provider`）

预置模板、可增删：

| 名称 | Base URL | 说明 |
|---|---|---|
| DeepSeek | `https://api.deepseek.com/v1` | 中文写作性价比高 |
| OpenAI 兼容 | 自定义 | 中转站、自建服务都走这个 |
| 通义千问 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | 兼容模式 |
| 智谱 GLM | `https://open.bigmodel.cn/api/paas/v4` | 兼容模式 |
| 月之暗面 Kimi | `https://api.moonshot.cn/v1` | 兼容模式 |
| 本地 Ollama | `http://127.0.0.1:11434/v1` | 数据不出本机 |

全部走 **OpenAI 兼容协议**（`/chat/completions`、`/embeddings`），一套代码适配所有。

### 7.2 模型档案（`ai_profile`）

按**用途**而不是按服务商配置，业务代码只说"我要写作模型"：

| 用途 key | 界面名称 | 用在哪儿 | 代码位置 |
|---|---|---|---|
| `writing` | 文书写作 | 生成公文、报告、方案；知识库问答总结 | `domain/generate.ts`、`api/routes-kb.ts` |
| `extract` | 信息抽取 | AI 梳理档案字段/别名；从上传资料抽字段值 | `api/routes-archive.ts`、`domain/extract-info.ts` |
| `reasoning` | 复杂推理 | 验收前缺项分析 | `domain/generate.ts` 的 `analyzeGaps` |
| `agent` | AI 助手 | 对话式办事（查数据、改字段、记备忘） | `domain/agent.ts` |
| `vision` | 图像识别 | 看照片：是否符合拍摄要求、要不要补拍 | `core/vision.ts` |
| `embedding` | 向量化 | 知识库切块建索引、语义检索、问答召回 | `core/kb.ts` |

每个档案可单独指定 provider、模型名、温度、最大 token、超时。

**哪些用途可以回退到「文书写作」**：只有纯文本生成类（`extract` / `reasoning` / `agent`）。
视觉和向量化**不回退** —— 它们有硬性能力要求：看图必须多模态模型，向量化必须走 `/embeddings`。
回退的后果实测过：拿 DeepSeek 去看图，它回一句 content 类型的报错；拿它去向量化，是 404。
两种情况用户都猜不到"其实是没配这个用途"，所以现在宁可明确说「还没指定服务商」。

`agent` 是给 AI 助手单开的一条，换助手模型不会连带影响缺项分析。它比别的用途多一个硬要求：
**必须支持工具调用（function calling）**，否则助手只会聊天、不会真去查数据和改字段。
所以「试调用」对这条用途是特制的 —— 发一个必须调用工具的请求，
直接告诉你模型会不会调，不会调就给明确警告（普通对话测试是抓不出这个问题的）。
这条档案首次创建时**继承「复杂推理」的设置**：不同账号能用的模型名不一样，
写死一个名字反而会造出一个用不了的档案。

`vision` 是**预留但没接线**的用途：档案能配、能试调用，但影像证据那条流程目前没有调用模型的地方。
`PURPOSES` 里的 `wired: false` 就是这件事的单一事实来源，界面据此标「暂未接入」——
不标的话，配好了却一直不生效，人会往 Key 和模型名上找原因。

### 7.2.1 推理模型的 token 预算（踩过的坑）

现在主流的 DeepSeek 模型是**推理模型**：回答之前先"想"，思考内容以 `reasoning_content` 返回，
而且**思考的 token 也计入 `completion_tokens`，也就是同样吃 `max_tokens` 额度**。实测（`deepseek-flash`）：

| 用途 | 探针问题 | 输出 token | 其中思考 |
|---|---|---|---|
| writing | 用一句话说明你是谁 | 256 | 228 |
| extract | 同上 | 444 | 403 |
| reasoning | 同上 | 814 | 786 |

也就是说 4096 的额度里，能留给正文的往往只有三千上下；长模板 + 多字段 JSON 很容易半路被截断。
所以：

- 三个对话用途的 `max_tokens` 设成 **8192**（额度是上限，用不到不花钱）；
- 网关解析 `completion_tokens_details.reasoning_tokens`，截断时报错里直接写明「其中 N 个 token 花在思考上」，
  否则看到的就是一句没有线索的「被截断」；
- 「试调用」的探针用 1024 而不是 200 —— 200 会被思考吃光，接口明明是通的、测试却报失败（这个假故障曾把排查方向带偏）；
- 大批量任务（如 AI 梳理）自己指定更大的上限并分批，别指望档案默认值够用。

### 7.2.2 「配了」不等于「能用」

界面上的绿灯不能只看档案里填没填 —— 服务商被停用、Key 没填、模型名为空，调用一样会失败。
所以状态一律走 `aiReadiness(purpose)`（`ai/gateway.ts`），它复用真正调用时的解析逻辑，返回
`{ready, reason, code, provider, model}`。用在三处：

- 仪表盘 `/api/ai/status` —— 说的是「现在能不能写文书」；
- 知识库 `/api/kb/status` —— 不能向量化时直接给出原因（例如「服务商已被停用」），并说明关键词检索不受影响；
- 语义检索 / 「问它」失败时 —— 区分「库里没内容」和「向量化没配好」，这两件事要改的地方完全不同。

删除服务商时会把指向它的档案的**模型名一起清掉**：外键只置空 `provider_id`，
留着模型名会让解析回退到写作服务商、拿一个那边没有的模型去撞墙，报的错和真实原因差着十万八千里。

### 7.2.3 每个用途到底该选哪个模型
实测数据与淘汰过程见 **[04-模型选型实测](04-模型选型实测.md)**（用真实 Key 跑真实任务，判据按
稳定不出错 → 成本 → 速度排序）。结论：

| 用途 | 选择 | 关键依据 |
|---|---|---|
| writing / extract / reasoning | DeepSeek `deepseek-flash` | 唯一会写 `【待补：…】` 而不编数字的；同题最快 |
| vision | 阿里 `qwen3-vl-flash` | 真多模态（流程尚未接入，见 7.2 的 `wired`） |
| embedding | 阿里 `qwen3.7-text-embedding-flash` | 召回与同类并列满分，单次批量上限最宽 |

两条实测教训都写进了代码，换模型时不用重新踩：

1. **推理模型的"思考"也占 `max_tokens`**（见 7.2.1）；
2. **每个服务商的单次批量上限不同**：阿里 `text-embedding-v3` 只收 10 条，而知识库按 16 条一批提交 ——
   撞上限不能整篇作废，`embedDocument()` 现在会自适应劈半重试（16→8→4→1），
   成功过的尺寸记住复用。自检里有对应用例（假接口故意只收 10 条）。

### 7.3 Key 的存放

存在本地数据库里（`data/runtime/workbench.db`），只在本机、只在 `127.0.0.1` 上使用；接口返回时**只回传掩码**（`sk-****abcd`），永不明文返回。也支持用环境变量覆盖。

### 7.4 用量与错误

每次调用写 `ai_call_log`：用途、provider、模型、耗时、输入/输出 token、是否成功、错误摘要。界面可看，用于控成本和排查。

## 7A. AI 助手（对话式）

界面在「配置 → AI 助手」，原来是「AI 梳理」，现在升级成能对话的助手 ——
AI 梳理变成它的一个页签（和能力）。

**目标**（用户原话）：「我可能有一个事情没空仔细操作，直接交代给大模型，他帮我记住或者直接修改了」，
以及「能改就直接改，改不了就记住，以后涉及到就给我正确答案」。

### 7A.1 三条设计原则

1. **写入一律两步走：提议 → 人确认。**
   模型调用写类工具时**不落盘**，只生成一条 `agent_action`（待确认）；界面上是醒目的橙色卡片，点「执行」才真正生效。
   读类工具（查工作、查模板、查制度、查备忘）直接执行 —— 否则问一句"我有哪些工作"都要点确认，没法用。
   破坏性动作（删除工作台）单独标红，并且**「全部执行」会跳过它们**，必须逐条确认（之前误删过数据，这条不妥协）。

2. **记忆必须参与推理。**
   「以后涉及到就给我正确答案」靠的不是把话存起来，而是**每次都用上**：
   - 对话时：把与当前话题相关的记忆注入系统提示（`relevantMemories`：该工作的优先，再按字面命中加权）；
   - 出文书时：把该工作的记忆注入生成提示词，标为「用户交代过的补充信息」，并声明与它冲突时以它为准。
   只写不读等于没记 —— 自检里专门断言了这两条注入真的发生。

3. **能落到字段就别记成备忘。**
   模型先判断这条信息属于哪个结构化字段（"甲方换成了 XX 公司" → `party_a_name`）；
   没有合适字段、或者只是临时情况，才 `remember`。字段可靠、可校验、能被所有模板复用；备忘是兜底。

### 7A.2 工具清单（`domain/agent.ts`）

| 类别 | 工具 | 说明 |
|---|---|---|
| 读 | `list_workbenches` / `get_workbench` / `list_templates` / `get_due_work` / `search_knowledge` / `get_settings` / `list_memories` | 立即执行，结果回给模型继续推理 |
| 写 | `set_archive_value` / `set_workbench_field` / `add_archive_alias` / `add_archive_field` / `update_setting` / `update_ai_profile` / `remember` | 生成待确认动作 |
| 危险 | `delete_workbench` | 生成 `risk=destructive` 的待确认动作，逐条确认 |

工具调用走 OpenAI 风格的 function calling（DeepSeek 与 Qwen 实测都支持）。
一轮对话最多 6 个工具回合，防止模型钻牛角尖烧钱。

### 7A.3 数据与留痕

| 表 | 装什么 |
|---|---|
| `agent_session` / `agent_message` | 会话与消息（可在界面上回看） |
| `agent_action` | 每条提议：工具、参数、人话摘要、风险级别、状态（pending/applied/discarded/failed）、执行结果、确认时间 |
| `agent_memory` | 备忘：内容、归属工作、期限 |

`agent_action` 是审计线索：谁提的、改前改后是什么、有没有执行，都查得到。

### 7A.4 自检

`npm run test:agent`（28 项）用假模型返回确定的 tool_calls，验证：
写入不落盘 → 确认后才生效 → 忽略的不生效 → 破坏性动作不被批量执行带走 →
记忆被注入到后续对话 → 记忆被注入到出文书提示词 → 局部更新不会误清其它字段。
全部通过后自己清理产生的数据（工作台还原、备忘删除、测试服务商移除）。

### 7A.4 照片：助手能看图，看完接着办事

链路是「**视觉模型看懂 → 写作/助手模型照着办**」，中间用文字衔接：

```
照片 ──▶ 视觉模型（用途 vision，如 qwen3-vl-flash）
           · 看到什么（主体、文字、标识、角度、清晰度）
           · 是否满足这条影像的拍摄要点（要点从 evidence_rule 取）
           · 要不要补拍
        ──▶ 文字结论 ──▶ ① 存进 evidence_review（供人核对）
                        ② 交给 AI 助手，由它决定做什么（核销清单/写字段/记备忘）
                        ③ 出文书时作为【现场照片】段落进提示词
```

**为什么不让写作模型直接看照片**：写作模型是 DeepSeek，收不了图片；
硬塞就是一句看不懂的接口报错。所以照片永远先被"翻译"成文字，再交给写作模型 ——
提示词里同时注明「这是模型对照片的描述，可能看错；照片里没明说的数字不要写具体值」。

三处入口：

| 入口 | 做什么 |
|---|---|
| 工作台 → 影像证据 → 某条 → 「让模型看看」 | 审这条清单下的全部照片，连同"要拍什么"一起判断，结论贴在照片下面 |
| AI 助手 → 「📷 附照片」 | 照片登记成文件后交给助手，它自己判断并**提议**后续动作（都要你确认） |
| 出文书（勾了某张照片作参考） | 照片先被识别，识别结果进提示词，文书内容才算真的"看过现场" |

初检结论是 `ok / issue / unclear` 三档，**只是意见不是结论**：核销清单仍然由人点
（或经人确认的助手动作）。模型看不清时提示词要求它判 unclear，不许猜 ——
实测拿两张无意义的测试图给它，它老老实实说"无法辨识"，没有编出现场内容。

### 7A.5 自检

`npm run test:vision`（17 项，假视觉模型，不花 token）：请求里确实带了图片数据、
结论落库可回查、数量不够判 issue、出文书提示词里出现照片识别结果并注明"可能看错"、
未配视觉模型时给的是人话、跑完把档案/服务商/照片/清单项全部还原。

## 8. 知识库设计

知识库分**两个模块**，分开摆是给人找东西方便，不是给模型分两次问：

| 模块 | 里面是什么 | 检索方式 | 代码位置 |
|---|---|---|---|
| **模板库** | Word/Excel 模板，套上去出成品文件 | 名称 / 说明 / 可填项的关键词匹配 | `core/knowledge.ts` 的 `searchTemplates` |
| **公司制度** | 制度、规范、标准、上级通知，办事照的口径 | 语义检索（向量）+ FTS 全文 | `searchPolicies` → `core/kb.ts` |

### 8.1 模型怎么用这两边（`core/knowledge.ts`）

**一次检索，两边都查**：`searchKnowledge()` 同时打两个模块，每条结果标清 `sourceLabel`（模板库 / 公司制度），
拼成提示词里的 `【可依据的制度与模板】` 段落 —— 制度定口径，模板定格式。

**不是每次都查**：`shouldSearchKnowledge()` 先看这一轮有没有具体线索
（本次特别要求 ≥ 8 字 / 参考资料 ≥ 30 字 / 模板里有成段填写项），
没线索就跳过，省一次 embedding 调用。界面上「参考知识库」勾上则强制每次都查。

**模板不做向量**：模板正文几乎全是固定套话（「甲方：」「签订日期：」），
向量化既贵又没用 —— 真正区分模板的是它叫什么、给谁用、要填哪几项。
所以模板走关键词命中，命中不了就退化成「本类工作可用的表」候选列表（`optional: true`），
而不是硬凑一个分数把不相干的表推荐出来。

检索结果会**回流到界面**：生成结果里的 `knowledge` 数组就是这一轮实际用到的依据，
在「出文书」弹窗的「写内容时参考了」里可见；「知识库 → 公司制度 → ⚖ 查依据」可以单独试这条链路。

### 8.2 文件怎么进知识库

```
界面上传（文件 / 整个文件夹，可以拖）
   └─ POST /api/kb/upload   落到 data/files/_规范库/，保留上传时的目录结构
   └─ 当场登记为 artifact + 抽文字 + 建全文索引
   └─ POST /api/kb/import-all { artifactIds }  只处理刚上传的这批 → 切块 → 向量化
```

- **一个文件一个请求**：进度能看到第几个，单个坏文件也不会拖垮整批。
- **保留目录结构**：`制度/财务/报销办法.docx` 就存成 `_规范库/制度/财务/报销办法.docx`，
  文档标题也带这层目录 —— 否则一批「办法、规定、细则」在库里根本分不清谁是谁。
- **路径穿越挡在门外**：`..` 一律丢弃，逐段安全化，最多 5 层，永远出不了 `_规范库`。
- **重复上传不是错**：按 sha256 复用已有记录，后面导入时自然跳过。
- **也可以照旧手工拷文件**进 `_规范库` 再点「导入全部文件」（它按「还没入库的已登记文件」找），
  两条路落到同一个地方，不会出现「拷进来了但库里没有」。
- 图片和扫描件 PDF 会自动进 OCR 队列；识别结果同样计入全文检索。

### 8.3 检索的实现（`core/kb.ts`）

- **第一层**：SQLite **FTS5** 全文索引。入库时把 docx/xlsx/pdf 抽出纯文本（含模板变量、OCR 结果）写进索引表。支持中文按字切分 + 关键词布尔查询。
- **第二层**：语义检索。用 `embedding` 档案把文本切块向量化，存本地 SQLite（向量以 BLOB 存，余弦相似度在内存算）。规模到几万条以内完全够用。
- **混合排序**：全文命中 + 语义相似度加权，返回时带**出处**（哪个文件、哪一段）。
- 换 embedding 模型后向量不能混用，要重新向量化；未配置向量化模型时语义检索会给出可读提示，关键词检索不受影响。

## 10. 已经定下来的约定（改之前先看这里）

1. **端口 8787，只监听本机。** 不暴露到局域网 —— 数据在本地是这套系统的前提。
2. **数据目录 `D:\project\工作台\data\files`**，与程序分离。此目录仅包含文件；完整备份还需一致的数据库快照与配置；里面都是普通 Office 文件，资源管理器直接能看。
3. **占位符用 `{中文变量名}`。** 扫描器认这一种；要在模板里写别的写法（`【项目名称】`、`{{项目名称}}`），得先改 `core/template.ts` 的扫描规则。
4. **工作类型分两种模式**（`work_type.mode`），这决定新建工作后发生什么：
   - `process` **项目类**：按阶段实例化 `position_instance`，带材料清单和影像清单，编号 `YYYY-P-NNN`
   - `document` **行政管理**：不建阶段，按频率（一次 / 每月 / 每季 / 每年）重复做，完成后回到进行中并给出下期，编号 `YYYY-A-NNN`
5. **档案字段的底线**：AI 可以新增字段、写值、提别名，但**不能改已有 `field_key` 的名字和含义** —— 那会让历史文书对应不上。系统变量（`field_key` 以 `_` 开头）连 AI 也不能覆盖。
6. **模板 code 全表唯一**（含已归档行）：同一个模板删掉再传一次，会自动加序号，不会撞唯一约束。
7. **完成一期 ≠ 结束**：周期性工作点「完成本期」只记 `last_done_at` 并回到进行中；一次性工作才置为 `done` 并写 `actual_end_date`。
8. **删工作台是真删**（库记录 + 磁盘文件夹 + 影像 + 生成的文件），不可恢复；只想收起来用「归档」。界面上删除要求手打「删除」二字，并且会先告诉你将失去什么。

## 11. 怎么改，怎么验

```
改后端（packages/server/**）  →  重启服务即可生效（node 直接跑 TS，没有编译步骤）
改前端（packages/web/**）     →  npm run build → 重启服务
                                 前端产物由后端托管，静态资源清单在启动时读一次，
                                 只 build 不重启会 404（浏览器还要 Ctrl+F5）
```

改完先跑这几条，比在界面上点一遍快：

| 命令 | 覆盖什么 | 注意 |
|---|---|---|
| `npm run typecheck` | 前后端一起查类型 | 前端以前不在范围内的，现已合并 |
| `npm test` | 67 项单元测试：排期计算、JSON 容错、文档渲染等 | 不碰数据库 |
| `npm run test:e2e` | 47 项端到端：建模板 → 填 → 出文件 → 检索 → 建工作台 → 勾清单 → 清理 | **会连真实服务**，所以自建数据一律带 `【自检】` 前缀，开跑前先清残留、跑完自动删干净 |
| `npm run test:kb` | 55 项知识库：上传（文件夹保结构 / 重复 / 路径穿越 / 坏类型 / 批量超限自动降批量）、切块、向量化、维度、检索、删除同步、清理 | 需要一个可用的 embedding 模型 |
| `npm run test:agent` | 31 项 AI 助手：提议不落盘、确认才生效、忽略不生效、破坏性动作不被批量执行、记忆注入对话与出文书、**跑完还原被它动过的档案** | 用假模型，不花 token |
| `npm run test:vision` | 17 项影像初检：请求里带图片、结论落库、数量不够判 issue、出文书提示词带上照片识别结果、未配视觉模型给人话、跑完全还原 | 用假视觉模型，不花 token |
| `npm run test:ocr` | 扫描件 OCR 链路 | 需要 OCR 依赖 |

端到端自检中途失败时会在库里留下带 `【自检】` 的东西 —— 直接删掉，或再跑一次（开头的「清理上次自检残留」会处理）。
